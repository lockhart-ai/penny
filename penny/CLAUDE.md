# CLAUDE.md — Penny Chat Agent

## Architecture Overview

```mermaid
flowchart TD
    User((User)) -->|message| Channel[Signal / Discord]

    subgraph Foreground["Foreground (ChatAgent)"]
        Channel -->|extract| CA[ChatAgent]
        CA -->|"prompt + tools"| FG_Ollama["LLM<br>(OpenAI SDK)"]
        FG_Ollama -->|tool call| Browse[BrowseTool]
        Browse -->|"read page"| Browser[Browser Extension]
        Browse -->|"web search"| Browser
        Browser -.->|results| FG_Ollama
        FG_Ollama -->|response| CA
    end

    CA -->|reply| Channel -->|send| User
    CA -->|log| DB[(SQLite)]

    subgraph Scheduler["Background Scheduler (when idle)"]
        direction TB

        Coll[Collector dispatcher] -->|"per-collection prompt<br>+ scoped tools"| FG_Ollama3["LLM<br>(OpenAI SDK)"]
        Coll -.->|"reads memory rows<br>(extraction_prompt, interval,<br>last_collected_at)"| DB
        Coll -.->|"writes entries<br>scoped to one collection"| DB
        Coll -->|"notify micro-context<br>(after a done-closed cycle)"| Channel
    end

    User -.->|"resets idle<br>cancels background"| Scheduler
```

- **Channels**: Signal (WebSocket + REST) or Discord (discord.py bot)
- **Ollama**: Local LLM inference (default model: gpt-oss:20b)
- **Vision**: Optional vision model (e.g., qwen3-vl) for processing image attachments from Signal
- **Image Generation**: Optional image model (e.g., x/z-image-turbo) for generating images via the `generate_image` chat tool (config-gated on `LLM_IMAGE_MODEL`)
- **Embedding Model**: Required dedicated embedding model (e.g., embeddinggemma) for memory dedup and similarity recall — a hard prerequisite (startup fails fast if `LLM_EMBEDDING_MODEL` is unset), so memory never runs in a degraded, embedding-less mode
- **Browser Extension**: Web search and page reading — all web access goes through the connected browser
- **SQLite**: Logs all prompts and messages; stores the memory framework (collections, logs, skills) and conversation history

  datetime_utils.py   — Timezone derivation from location (geopy + timezonefinder)
  conversation_machine.py — The conversation state machine (#1706): the model fills states, it never walks them. `ConversationState` (idle · elicit · learn · request · apply) + the `OUT_EDGES` edge table, the CANONICAL `STATE_DEFINITIONS` (one stable definition per state, rendered identically everywhere — a state means one thing regardless of where the machine stands) and the `TRANSITIONS` function (the condition selecting each (current, target) move — the half that legitimately varies by current state; IDLE is the DECLARED DEFAULT, rendered last as `DEFAULT_TRANSITION` = "in all other cases", so a message meeting no positive condition has an unambiguous home; IDLE's own DEFINITION carries the TASK-LIFETIME boundary as well (#1919 — every request handled right now stays idle, including a command about something that already exists, and a message with no standing or scheduling component stays here whatever it resembles), so the boundary renders on every from-idle draw before any edge is considered rather than only on the doors that state it). Data, not prose — every classifying state carries the break-out edge → idle; learn never returns to elicit (once instructions have been given there is nothing left to elicit) but DOES reach apply, because the demonstrated round ends by OFFERING to set the routine running, so the machine is parked in learn at the moment the user accepts and the acceptance has to be answerable from there — and what the skill needs comes from the round that just ran, so accepting never restates it (before the run-end auto-attach was removed in #1768, learning instantiated implicitly and this edge had no work to do); apply has NO out-edges, its reset is structural. `MachineSnapshot` (the scoped classifier input: assistant's last turn, parked task anchor, ranked skill candidates, and — for a round parked in request — its partial binding, #1894: `render_classifier_content` gives it its own `## The details this task is waiting on` section beside the anchor, naming the skill and listing what is already given against what is still needed, so the move out of request is judged against a NAMED gap instead of a fresh completeness audit of the conversation), `StateClassifier` (one tagged draw per incoming message over the CURRENT state's out-edges via `MicroContext.classify_state`, customer #3), `presented_edges` (every SKILL-GATED state withheld when there are no skill candidates — the structural false-apply guard), `next_state` (fail → stay: only a DECIDED draw moves the machine), and `build_snapshot` (the PRODUCTION snapshot builder: EVERY skill offered as name + description + parameters, from `db.skills.list_all()` — **no ranking, no cap, no embedding** (code-owner ruling on #1706): a relevance gate here would contradict #1471, which renders the whole registry to chat wholesale precisely because gates HID skills, and this list is strictly smaller than the full recipes chat already carries every turn. Offering everything also means classifier and chat reason over the SAME set. An empty registry still withholds the gated states — reached by there being nothing to offer, not by anything failing). **`SKILL_GATED_STATES` = apply + request**: each one's transition condition directs a second `SKILL: <name>` line (membership-validated against the candidates) so the decision always binds an actionable skill (`StateDecision.skill`) — **both idle doors are keyed to STARTING a task** (#1927, code-owner ruling: "request is only about starting a new task; changes to existing collections don't count") — each condition asks whether the message asks to SET A KNOWN SKILL RUNNING, and both carry the same boundary word for word (changing how something already set up behaves — its notifications, when it runs, what it covers — is not asking to start it), since a reader who rules apply out for missing information reads request next and would otherwise take the identical fall. **This is the BEST MEASURED wording, not a fix, and the residual gap is EVIDENTIAL rather than verbal**: an ask to turn one running job's notifications on holds 3 of 5 (its off-direction 5 of 5 — only the ON direction can be phrased as starting anything), and the leaking draws never reach the boundary at all, stopping at whether the job the message names EXISTS ("there's no known skill currently running") — which this snapshot cannot answer, since `build_snapshot` renders the skill registry and no standing jobs. Three rounds tried to close it in text and each cost a neighbour: a fourth boundary clause keyed to the start-VERB took the target 0.60 → 0.40 and idle → elicit cross-domain 1.00 → 0.60 (two draws ruled out the two longer doors and jumped to the default without ever reaching the elicit bullet — these render first, so a clause added here is paid for further down the list); a schema statement ("jobs already running are not listed here") left the target at 0.40 and broke the inverse guard, idle → elicit uncovered 1.00 → 0.60, an uncovered setup ask reading as a reference to a running job. Both are recorded as watched deletions above `TRANSITIONS` with their numbers. **So the fix is STRUCTURAL, not verbal (#1927, code-owner ruling): `MachineSnapshot` gained `standing_jobs` and the render gained a `## Jobs already running` section** — the light cycle-free `StandingJob` projection (`name` · `skill_name` · `notify` · `schedule`, `SkillCandidate`'s sibling and a leaf for the same reason), filled by `build_snapshot` from the CONFIGURED collections (`extraction_prompt IS NOT NULL` — the dispatcher's own readiness condition, so what this calls running and what actually runs are one definition; an inert container and an archived tombstone are neither). Every job is offered, the skills section's no-ranking-no-cap rule applied to the other registry, and the section **ALWAYS renders** (`(none)` when empty) for the reason the skills section does: absence must be a READ, never an inference from a missing section — reading nothing there was measured as reading "nothing is running", which was true of the section that did not exist and not of the world. Each row states every clause in BOTH directions (`- "<name>" — runs "<skill>" · notifications on|off · <schedule verbatim>`; `no routine attached` / `no schedule` where the row carries none), since a clause that vanishes when false is one the reader has to infer from again. It renders BELOW `## Known skills` (a job is what a skill becomes once set up) and ABOVE the newest message. apply ENACTS a skill (asked for and fully bound), request NEGOTIATES one (asked for but something it needs is missing, so the assistant names the skill and asks; parked, with three exits — apply when the details arrive or the skill is confirmed, elicit when it was the wrong skill and the task is still wanted, idle on a bail). **`ConversationMachine`** is the machine itself (#1706 persistence): `advance(message)` settles any STRUCTURAL move first (a state with no out-edges — apply — resets to idle, recorded as its own `cause=structural` row; completion is never a self-report the model is asked for), builds the snapshot with the ANCHOR resolved from the machine's own row, classifies, then records the draw and applies `next_state`. It owns the **anchor lifecycle** — set entering a parked state FROM idle, KEPT for the duration of the round (a reply three messages later is still classified against the ask it answers), cleared on the break-out to idle — and records **every** draw including the held ones (`outcome` carries the `StateDrawOutcome`, so fail → stay is distinguishable from a decided idle → idle; a ledger of only successful moves would report a perfect classifier by construction). Appending the move IS moving the machine (`db.machine`), so a failed write leaves it where it was rather than moving it silently off-ledger. `link_message(run_id, message_id)` back-fills the provoking message once it HAS an id — the channel logs the incoming message only after the turn (so it never doubles into that turn's own recall), the same deferred-link shape `link_source_message` uses (#1566) — and stamps it as the round's anchor when that turn's move opened a round. **Wired into the turn** (`MessageChannel._classify_state`): it runs BEFORE the chat agent, so the turn is entered with its state already decided; a classifier failure is logged and swallowed rather than costing the user a reply (fail → stay already leaves the machine put). **Entering learn FRAMES the round (#1868)**: `ConversationMachine` takes an optional `RoundFramer` collaborator (injected, since framing a round means database + embedding work this leaf module must not import at import time), and `advance` runs it on a DECIDED move into learn; a fail → stay draw that merely LEAVES the machine in learn frames nothing, since the machine's rule that a contract failure moves nothing has to hold for the store as well as for the state. The result is the typed `RoundFraming` (the framer's `SkillSignature` + the `container` built from it), recorded on the move in ONE write as `state_transition.skill_frame` and read back by `framing()`. It rides the ANCHOR's own lifecycle (`_next_framing`): a fresh entry draw replaces it, every other move CARRIES it (so the turn that accepts what was demonstrated reads the same container the turn that demonstrated it wrote into), idle clears it — and a move that settled nothing carries rather than clears, so a held draw keeps the container the round already has. **A round's identity is settled ONCE, at its FIRST entry (#1902)**: `_frame_learn_entry` takes the machine's CURRENT state, and a learn→learn move on a round already carrying a framing makes no draw at all — it calls `RoundFramer.carry_entry`, which re-settles only the container (find-or-create, because a failed learn turn may have archived it, #1839) and hands the same framing straight back. A correction refines the PROGRAM of the round's one job, never the identity: same routine, same container, the corrected write landing in place. Re-drawing on every entry is what FORKED a round in two — a corrected ask read as a different subject, the fresh draw derived a fresh name, find-or-create minted a sibling container, and run-end extraction registered a second routine beside the first (~21/25 measured samples). The boundary case is a round still UNFRAMED (its entry draw failed): it has no identity to keep, so it is drawn again. **A round that MINTS a routine also records its PROVENANCE (#1902)**: on the move that opens the round's teaching (`_opens_the_teaching` — a decided landing in learn from anywhere but learn), `_next_provenance` records the typed `RoundProvenance` carrying whatever the registry already holds under the framing's pinned name (`snapshot_replaced_skill` → `ReplacedSkill`, the whole row with its embedding base64'd so the round state stays compact JSON). Stored as `state_transition.round_provenance`, read back by `provenance()`, with the framing's own lifecycle (set on entry, carried, cleared at idle). **Both halves of WHEN are load-bearing.** Only a learn turn registers a routine, so a move arriving from outside learn is the last moment the read is truthful — from inside, the round's own extraction has already written that name and the same read would take the round's own work for what it replaced (an unframed round framed on a LATER entry therefore records nothing, and the declared cost is that a bail then leaves that routine standing rather than risk deleting the user's). And only the FRAMER mints: a skill-gated entry binds a routine the registry already holds, so such a round records no provenance at all. **The three shapes are three answers to what a bail owes the registry**: absent = the round minted nothing, leave it alone; present-and-empty = the round minted over nothing, DELETE; present-carrying-a-row = the round was re-teaching, RESTORE. **An idle landing also ENDS the round in the store (#1896/#1902)**: `_end_round` runs before the move is written and takes BOTH things the round left behind — the container that framing pointed at is archived (`round_framing.abandon_round_container`) and what the round wrote to the registry is taken back (`round_framing.abandon_round_skill`), resolved by that provenance. Restoring rather than merely skipping the delete is the point — by bail time the round's own extraction has already replaced what the canonical routine DOES, so leaving it standing would leave an abandoned, half-corrected program live under a name existing jobs still run. The post-apply structural reset is not this path (it drops the framing on its own row before anything is classified, so a job just set running is never retired by a later bail) — which is also what makes promotion IMPLICIT: there is no draft flag, a routine simply survives its round. A failed entry draw records no framing at all and the round runs unframed, which is the pre-#1868 behaviour exactly. **A move into APPLY settles a framing too, once, when the round arrived WITHOUT one (#1875/#1870)**: apply configures the round's own container, so a framing is the one thing that turn cannot do without, while a round already carrying one draws nothing (a re-draw is not a re-read: a fresh draw could point the acceptance at a container the demonstration never used). WHICH draw settles it is `_frame_round`'s two named branches — `_frame_learn_entry` runs the FRAMER (a round being taught has no routine yet, so one is minted), `_bind_apply_entry` runs the BINDER (#1870 — a cold apply asks for a routine the registry already holds, so the classifier's `SKILL:` names it and the only open question is which part of the user's words fills each thing it declares). A decided apply always names a skill by the draw contract, so a missing one is logged as a broken contract and the round stays unframed rather than bound to a guess. A draw that fails either way records no framing, and the turn fails honestly rather than falling back. **A cold apply the words fall SHORT of lands in REQUEST (#1885)**: the binder's `MissingParameters` is an enumerated outcome rather than a failure — the routine really does cover the ask — so it ROUTES the move instead of failing the turn. `bind_entry` returns the typed `RoundEntry` union (`RoundFraming | RoundShortfall`), and `_landing(current, decision, entry)` redirects the recorded `to_state` to `request` whenever the entry came back a `RoundShortfall` (the routine's registry name + description, the values the words DID settle, and each missing parameter with the registry's own what-to-supply, both lists in declared order). **No classifier condition is added or changed** — the idle → request edge already existed and still fires on its own; this is a SECOND door no edge declares, because only the binder reads the words against what the routine declares. The draw still says apply: the raw `STATE: apply` stays readable on its own promptlog row and the move is still `cause=classifier` (a model was in the loop). It is also the only way a machine already sitting in request lands back in request, which `OUT_EDGES[REQUEST]` has no self-edge for. Nothing is built for it (the container's derived name needs every value). **The binder runs at REQUEST entry too, and the partial binding is ROUND STATE (#1894)**: `_frame_round` binds on either skill-gated landing (`_BINDING_STATES` = apply + request, `_bind_round_entry`), so a request the classifier drew DIRECTLY — the door every measured request turn came through — runs the same binder and, when the words are short of something, produces the same `RoundShortfall` instead of a generic "ask for the part that is missing"; both doors present one shape. That shortfall is recorded on the move (`state_transition.round_shortfall`, serialized like `skill_frame`) and read back by `ConversationMachine.shortfall()`, with the lifecycle of the state that reads it (`_next_shortfall`: only a move LANDING in request carries one — a freshly drawn binding replaces, a failed draw carries, a round that binds carries a `skill_frame` instead, elicit/idle clear it). Three consumers read it: `TurnEntry.shortfall` (now a READ of the log, threaded channel → `ChatAgent.handle(shortfall=…)` → `conversation_prompt`, so a turn arriving on a parked round asks for exactly what the turn that parked it asked for), the classifier's `MachineSnapshot.round_binding` (its own rendered section, below), and the next binder draw — `bind_entry(settled=…)` fills only the parameters still OPEN and merges what the round already settled, so the apply draw COMPLETES the binding from persisted values plus the arriving message rather than re-deriving it, and a value given two turns ago cannot come back different. A message the binder still cannot complete lands in request again with its binding intact (the learn→learn re-demonstration shape). **Per-state chat instructions (#1706/#1868/#1869/#1875/#1885)**: `STATE_INSTRUCTIONS` maps EVERY state to its one instruction and `conversation_prompt(state, framing=None, shortfall=None)` composes `Prompt.CONVERSATION_HEAD` + that instruction + the round's own closing line when one was settled + `Prompt.CONVERSATION_TAIL`. WHICH closing line is `_round_line`, keyed by state, reading whichever half of the round's entry that state has: LEARN renders `Prompt.ROUND_FRAMING_LINE` from the FRAMING (the container is already there, so a step that remembers something writes into it); REQUEST renders `Prompt.ROUND_SHORTFALL_LINE` from the SHORTFALL (the routine, what it is for, what they have already given — rendered even when empty, as a stated "nothing yet" line — and what is still missing, asked for by its description and never by its binding key), so the ask is n=0 and nothing on it is invented. APPLY is NOT in that map — its instruction NAMES the round inside itself (`Prompt.APPLY_INSTRUCTION` is a template over `{container}`/`{skill}`), because by then the round is not one more thing to know about the turn but the subject of every sentence in it, and there is **no unframed apply form at all**: `conversation_prompt(APPLY, None)` RAISES, and the chat agent fails the turn before composing a prompt. Both states render the routine and the container VERBATIM, so a name the model would otherwise invent is a name it copies. Elicit renders nothing (it is still asking what the task IS, so it has nothing to say about a container that may not exist yet) and idle never carries a framing at all. With no framing — and, for request, with no shortfall — every state's composition is byte-identical to what it always was, so the rendered round state is additive on every path. The map is TOTAL by construction (pinned by a test) and indexes directly — **there is no default and no fallback**: the machine always has a state, so a missing instruction is a programming error, not a case to absorb (a fallback would mean the state failed to determine the prompt, the one thing the machine exists to fix). No instruction names a state, mentions another state, or hints a classifier ran. `Prompt.CONVERSATION_PROMPT` — what the chat agent uses when no machine decided the turn — is *defined as* idle's composition, so it can never drift from it. The #1687 four-case union (`SKILL_PATH_DEFAULT`) is DELETED: it existed only to help the model work out which case applied, and that question is answered in Python before the turn begins. The pure pieces (`presented_edges` / `render_classifier_content` / `next_state`) stay callable with no database, which is what the classifier eval drives
  round_framing.py    — `RoundFramer`: framing a round at its ENTRY and the container it runs into (#1868/#1870). The framer used to run at the END of a learn turn, so a routine's identity was settled only after the round had already happened — the round had nowhere to put what it found, and the model named a collection by judgment (measured 18/25 task-rooted, the misses concentrated on same-kind-different-place asks). The draw moves to the moment the machine LANDS in learn (the ask and the demonstration both exist there, which is the framer's whole input contract) and Python does the rest deterministically: `frame_entry(ask, message, run_id)` renders the round's user turns through the SHIPPED `build_framing_content`, draws `MicroContext.frame_skill`, derives the container's name from the framed skill plus its demonstrated values (`derive_collection_name`), and FIND-OR-CREATEs it INERT through `db.memories.create_collection` — storage only, no program/schedule/notify, so the dispatcher never runs anything against a container whose routine does not exist yet (#1629), with the framer's own one line as its description (the same meaning anchor the routine states) and the creating run stamped. Returns the typed `RoundFraming` the machine records on the move. **Certified-by-execution is untouched**: nothing here writes a skill row — the registry still only gains a skill at run end, from the ledger. **The container's lifecycle is find-or-create, never mint-per-round**: re-asking for the same job derives the same name and finds the container that exists (tier-1 dedup by construction, #1775), and the same job taught again after a discarded round UNARCHIVES the container already carrying its name. **A round's identity is settled ONCE, at its first entry (#1902)**: `carry_entry(framing, run_id)` is the third entry and the one that DRAWS NOTHING — a correction re-entering learn hands its existing framing back unchanged and only re-settles the container, so the identity-shift branch that used to archive one container and mint another is GONE with the `previous` argument it read (a correction can no longer shift what the round is about). **Two entries, two draws, one outcome (#1870)**: `bind_entry(skill, ask, message, run_id, settled=…)` is the SKILL-GATED entry's sibling of `frame_entry` — a round asking for a routine the registry ALREADY holds mints nothing, so the classifier's bound `SKILL:` is looked up, `build_binding_content` + `MicroContext.bind_skill` fill its declared parameters from the round's user turns, and the registry's own name and description carry into the signature unchanged (a second draw's preferred wording would derive a container name for a job filed under a different one). Since #1894 it is the ONE door for apply AND request entries, and `settled` (what a parked round already bound, narrowed to what the routine still declares) means only the OPEN parameters are rendered and drawn — a question Python already holds the answer to is not asked, so a round with nothing left open settles with no draw at all. Find-or-create on the derived name IS tier-1 dedup by construction: the same job re-asked runs into the container it already had, a different place mints its own. Its three no-container outcomes are logged apart for what each is — a routine the registry does not hold, a `MissingParameters` SHORTFALL naming what the words fell short of, and a draw that produced nothing usable. Since #1885 they no longer end alike: the two failures leave the apply turn with nothing to configure (#1875's honest failure), while the shortfall comes back as a typed `RoundShortfall` (`_shortfall`) that routes the turn into `request`, logged at INFO because a covered ask waiting on one detail is an ordinary turn rather than a degradation. `discard_round_container` is the #1839 failure path's half — an honest learn-failure takes its minutes-old container with it — and `abandon_round_container` is the #1896 BAIL's half: a round that ends in idle takes its container with it too, because a bail preserves nothing and clearing the framing off the move alone would leave an inert collection named for a job nobody is doing. The LITTER retirements are guarded on EMPTINESS, read not judged: litter is a container with nothing in it; one holding entries is something the user can still read, whatever the round did next. The bail's is the deliberate exception — what a demonstration wrote is the round's own intermediate state rather than something to be preserved past the user calling it off. Archive (SYSTEM actor + a cause note on the mutation ledger), never delete — a retired mechanism stays a visible tombstone, and the same job taught again UNARCHIVES it. **`abandon_round_skill` is the bail's OTHER durable half (#1902)**: what the round wrote to the registry (under the name its framing pinned) is taken back too, since a routine standing for a job the user called off is AMBIENT — every later turn reads the registry. WHICH way is READ from the round's provenance (`snapshot_replaced_skill`, recorded when the round's routine was minted), in its three shapes: a round that minted NOTHING (a skill-gated round binding a routine the user already had) leaves the registry alone — the case a name-keyed discard would get catastrophically wrong, since that routine is the user's; a name the round MINTED over nothing is DELETED — the one place this parts company with the container, since the `skill` table is versionless and carries no archived flag, so a name is either in the registry or it is not; and a routine the round was RE-TEACHING is RESTORED to the pre-round row verbatim, timestamps and embedding included (`db.skills.restore`), because the round's own extraction has already replaced what that routine DOES and un-deleting is not the same as putting it back. Either way the change records a `mutation_event` under the SYSTEM actor (`MutationEntityType.SKILL` + `MutationAction.DELETED`/`UPDATED`, the enum's second customer), so a routine vanishing or reverting between turns shows in the recent-changes render like any other configuration change. A framing whose routine never reached the registry is a plain no-op
  notification.py     — telling the user about a finished collector cycle (#1911): `CollectorNotifier` (assemble → draw → queue), the pure `render_notification` document, the typed `NotificationOutcome` the run record is stamped from, and the send gate the retired `SendMessageTool` used to hold (refusal / no recipient / mute, then `db.send_queue`). **The document is BOUNDED and ORDERED (#1934)**: the first live post-reset cycle assembled 50,805 characters for an ordinary three-page news round — a browse result inlined whole (31,725), a `collection_write` restating its whole payload in its own arguments (14,923 on ONE line), and the entries holding that text a third time (14,989) — on a model whose degeneration onset is ~4K prompt tokens, and the message it composed led with a headline that was not the fetched page's top story but WAS the lead of the PREVIOUS notification, sitting in the closest-prior-messages section. So the ORDER is what the message is written FROM: the entries the cycle WROTE lead, the calls follow them (`## How it got there`), and the earlier conversation is LAST under `## Background: earlier messages` with a lead line saying these predate the cycle and where the cycle's own findings are — the only lines in the document the reported run did not produce. Every section is bounded in the pure RENDER (so the bound holds whatever assembled the facts, and a whole-render test pins it with no database): per-item character budgets (`NOTIFY_CALL_CHARS` / `NOTIFY_CALL_RESULT_CHARS` / `NOTIFY_WRITTEN_CONTENT_CHARS` / `NOTIFY_RELATED_LINE_CHARS`) and per-section item caps (`NOTIFY_WRITTEN_ENTRIES` / `NOTIFY_CYCLE_CALLS` / `NOTIFY_RELATED_MESSAGES`, which is now the render's cap as well as the query's `k`). **Never a silent cut** — a condensed value ends in `… [<n> characters omitted]` and a capped section ends in `<n> more <entries|calls|messages> not shown.` (the #1914 holdings precedent), because a draw reading part of a result knowingly is a different thing from one reading it as the whole. This REVERSES #1911's carried-whole rule for `CycleCall`, whose reasoning was that a truncated result is where an invented detail comes from; the measurement is that a document the model cannot read is not a safer document, so the cut stands and states itself
  program.py          — a stored program's own calls (#1911), read to SCOPE the cycle's tool surface: `program_calls` reads each numbered step's first call against the surface this cycle runs with (no tool is named here, so a plugin's verb participates for free). **`covered_calls`/`is_covered` are RETIRED (#1916, watched deletion)** — deriving the cycle's exit from coverage fixed the route in advance, so a cycle that departed from it for a good reason (taking the store's own advice to `update_entry` where the program said `collection_write`) could never close, and died trying to say so in prose; the terminator came back instead. Pure
  skill_extraction.py — SkillExtractor: distils a skill from a LEARN chat turn's ledger at run end (#1658/#1665/#1770/#1850). **Extraction fires only in the `learn` state, and has NO shape requisites (#1850, code-owner ruling)**: `SkillExtractor.extract(run_id, state=…)` yields a skill if and only if the turn's landed machine state is `learn` — any sequence of tool calls during a learn turn becomes a skill, and no other state produces one. The state is a PARAMETER, threaded channel → `ChatAgent.handle(state=…)` → the turn-scoped `_turn_state` → `extract` (this module never reads `db.machine`, so what a run yields cannot disagree with the state the turn ran under); absence of machine history is idle, so a cold machine never learns by accident. A non-learn refusal is the named `ExtractionGate.NOT_LEARN`, logged with the state that produced it — never a silent skip. This closed the measured escape (PR #1849): an APPLY turn's extra enactment (a browse + a write) qualified on shape alone and minted a brand-new skill framed from a round that taught nothing, landing beside the skill it had just applied; an idle one-off that browses and writes reached the same place. ## Agent Architecture

### Agent Base Class (`agents/base.py`)
The base `Agent` class implements the core agentic loop:
- Calls the LLM (via `LlmClient`) with available tools
- Executes tool calls via `ToolExecutor` with parameter validation
- Handles duplicate tool call prevention
- Appends source URLs to responses when model omits them

**System prompt building (template method pattern):**
Each agent overrides `_build_system_prompt(user)` to compose its prompt from reusable building blocks on the base class: `_identity_section()`, `_profile_section()`, `_instructions_section()`, `_context_block()`. No flags or conditionals — each agent explicitly declares what goes in its prompt. Tests assert on the exact full system prompt string to catch structural drift.

**The ambient inversion (#1555)**: the chat system prompt **no longer injects speculative user-content recall**. Instead it opens (in the dynamic tail) with a deterministic **`SelfStateHeader`** (`agents/self_state.py`) — Penny's own operational situation rendered from the registry (`memory` rows) + ledger (`promptlog` runs + `mutation_event`), never a relevance guess: active mechanisms (status · cadence · expiry · last-run outcome), recent activity (runs + config mutations, interleaved, at rollup altitude), the store map (the read index), the **skills and rules** section (#1471, below), the durable user-fact core (name · timezone · location), and a pointers line naming the fetch tools. User content is fetched **on demand** via those tools, anchored by the user's message. **The taught-skill registry is AMBIENT (#1471/#1804)**: the `### Skills and rules` section renders — deterministically, wholesale (no relevance gate, no cap) — the taught-skill registry (`db.skills`, #1590), the **sole skills store** (#1624), each skill as ONE ROW (`render_skill_brief`: `- <name> — <what it's for> (needs: <parameter> — <what to supply>; …)`) in the same `- <name> — <clauses>` shape the mechanisms and store-map sections use, so several skills are a list to skim rather than one undifferentiated block. A taught skill is *in the prompt* WITH its parameters visible, so it **instantiates at 0 calls** (the parameter names are the binding keys). What the row does NOT carry is the numbered recipe (#1804, reversing #1665's wholesale-full-render): nothing on the chat path carries out a skill's steps any more — under the state machine `apply` sets it up in one `collection_set` call, `learn` follows the *user's* instructions, and the recipe is run later by the **collector** from the `extraction_prompt` rendered at instantiation — so on a section read every turn the recipe was context cost against a decision it does not inform. It stays one guess-free `skill_read(name=<name>)` away, which the section's label names. Model-facing vocabulary is **parameters**, never the internal "hole" jargon. (The legacy `skills` collection's standing-rules feed retired with the collection — migration 0092: its seeded rules were never demonstrated, so they could not enter the certified-by-execution table; needed behaviors are re-taught live.)

**The dead recall substrate is gone (#1583)**: the two-stage recall machinery that the ambient inversion (#1555) unwired from the chat prompt — the `memory.inclusion` + `memory.recall` columns, the `Inclusion`/`RecallMode` enums, `read_similar_hybrid` + hybrid ranking, `expand_with_temporal_neighbors`, and the `RECALL_*`/`MEMORY_INCLUSION_THRESHOLD`/`MEMORY_NEIGHBOR_*` config+constants — was **deleted** once #1471 re-homed skill/standing-rule firing onto the self-state header (it had no remaining consumer). What replaced it: the deterministic `SelfStateHeader` for ambient facts, and **on-demand fetch** for user content — the model reads what it needs via the general verbs the header's pointers name (`read_similar` = plain cosine nearest-neighbour; `find` = resolve-by-meaning over the `description_embedding` anchors (and, since #1640, over stored entries' content/key anchors), which **stay** for exactly this, #1558). `memory.notify` (emission, #1557) is untouched. (The `published` pub/sub column was retired separately by #1557/migration 0086.)

The chat turns array (alternating user/assistant messages passed via `history=`) is reconstructed from the last N messages in `db.messages` — independent of any memory metadata.

### Shared LLM Client Instances

All `LlmClient` instances are created centrally in `Penny.__init__()` and shared across agents and commands. `LlmClient` uses the OpenAI Python SDK and targets any OpenAI-compatible endpoint (Ollama's OpenAI-compat layer by default, or omlx/OpenAI cloud with a different `base_url`):

- `model_client`: Text model for all agents and commands
- `vision_model_client`: Optional vision model for image understanding
- `embedding_model_client`: Required embedding model for preference deduplication and similarity recall (always present — the model is a hard prerequisite)
- `image_client`: `OllamaImageClient` for the `generate_image` chat tool (image generation uses Ollama's native REST API, not OpenAI-compatible); wired into the ChatAgent, which registers `generate_image` only when it is present

### Specialized Agents

**ChatAgent** (`agents/chat.py`)
- Handles incoming user messages with the full tool surface (memory + browse)
- Chat-surface tools include `notifications_mute` / `notifications_unmute` (`tools/notifications.py`) — thin toggles over the `MuteState` row (`db.users`) that the model dispatches from natural language ("stop messaging me for a while" / "you can message me again"), replacing the retired `/mute` + `/unmute` commands. NL-dispatch contract: `tests/eval/test_notifications.py`
- Email tools (`search_emails` / `read_emails`, plus `list_emails` / `list_folders` / `draft_email` on Zoho) are config-gated — present only when a mailbox is configured (Fastmail via `FASTMAIL_API_TOKEN`, Zoho via its OAuth triple; both behind the `EmailClient` protocol), retiring the `/email` + `/zoho` commands (epic #1445). Both configured → Fastmail wins (single user, one mailbox). The mailbox client is long-lived (built in `Penny._init_email`, closed in `shutdown`); `ChatAgent._email_tools_builder(user_query, today)` wraps it fresh each turn so `read_emails` summarises against the current question. - **The `last_collected_at` stamp CONSUMES the occurrence, so a cycle that did not spend one keeps it (#1935)**: readiness reads the occurrence strictly after `last_collected_at`, so stamping a cycle that ran no job SKIPS that fire outright — observed live, a chat message cancelled a daily job's cycle seconds in (before any model call had come back) and the day's occurrence was burned. `Collector._settle_occurrence` replaces the `finally`'s unconditional `mark_collected`: it asks `_retry_reason` whether this exit spent its occurrence, and where it did not, leaves the collection DUE so the next tick picks it up again (it is still the most overdue). **Since #1936 it is keyed on the cycle's END** (`CycleEnd`, the bullet below), so the writes and the fire settle on ONE verdict — two reads, ordered so each is decisive: **the cycle ENDED** (a member of `HEALTHY_CYCLE_ENDS` — a write-gate STOP, or a `done()` close that notified, deliberately declined to, or had nothing to notify about) → spent, it did the job the fire was for; **a configuration defect** (`_configuration_defect`, the DETERMINISTIC arm — read off the collection's stored program rather than off what the run did, so a retry re-fails identically; today, a prompt no program can be read out of, the other config defects being refused by readiness before dispatch) → spent immediately, and it OUTRANKS every unhealthy end because a cancelled cycle of an unrunnable collection is still unrunnable. The over-correction guard moved with it: what spends a fire is reaching an END, and the `_produced_work` read this replaced (an entry written or a notification queued) now splits only the run's `worked` / `no_work` outcome. **The bound is the stamp's original job, kept whole**: `PennyConstants.COLLECTOR_RETRY_ATTEMPTS` (3) attempts per occurrence, counted in an in-memory `dict` on the dispatcher (the exit it counts leaves nothing durable to count FROM — a cycle cancelled seconds in writes no `promptlog` row — and the count exists only to bound one burst, so a restart is legitimately a fresh start), cleared the moment a cycle settles. **The count is keyed `(collection, CycleTrigger)` — one budget per ASKER (#1939)**: the scheduler's cadence and the user's "run this now" are two different things attempting the same fire, and one shared count let three failed clicks leave the day's own scheduled attempt with nothing (the next preemption consumed the occurrence on its first try and the job silently skipped its day — this deferral's own failure mode, reached through the door the user was pressing). After the budget the occurrence is consumed whatever happened, so a collection that fails this way every time still drops out of the running instead of re-attempting on every tick. **Two things follow the occurrence rather than the cycle.** The post-cycle retirement (`_retire_if_ended` — the `max_runs` quota + the mid-life `expires_at` retire) is SKIPPED on a kept occurrence for the same reason a cancelled cycle never reaches it: the fire and the run of a bounded schedule are one thing counted twice, and an abort is not a cancellation, so its `failed` run DOES count — a `COUNT=1` one-shot that died on a transport wobble would otherwise archive itself while its occurrence sat due, and an archived collection is never dispatched again. Code-owner ruling: a partial run must not persist state later cycles have to reason about; if a cycle never reaches its healthy conclusion it is retried until it does, **from the pre-run state**. It is keyed to the MUTATION, not to a tool — a `collection_write`, an `update_entry`, a `collection_delete_entry` and **the change-gate's own `KEY_EXISTS_CHANGED` baseline refresh (#1633)** are all recorded identically, that last one being the write nobody makes explicitly and precisely the one an aborted cycle used to leave behind. **The healthy-end enumeration is DATA** (`CycleEnd` + `HEALTHY_CYCLE_ENDS` + `CYCLE_END_RETRY_REASONS` in `constants.py`, the `WRITE_GATE_STOP_REASONS` pattern; the notification arm is `NOTIFIED_CYCLE_ENDS` beside `NOTIFICATION_NOTES`), and **one set drives both this and #1935's occurrence settlement** — a write-gate STOP (an early clean no-news exit IS an end point), a `done()` close that did not notify, one whose notification was QUEUED, and one whose delivery was DELIBERATELY declined (muted, or no registered recipient — a retry reaches the same answer). Everything else REVERTS in one short transaction (prior absent → delete the row; else restore the fields) and leaves the occurrence due for the bounded retry: an abort, a cancellation, a failed notification draw, and the unenumerated `UNFINISHED` default (the step cap, a model that trailed off), which the ruling covers in as many words. The cycle's **read cursors follow the same verdict** — `_run_cycle` hands its `CursorReadTool`s back on `CycleResult.reads` and the caller settles them (`Agent.settle_reads`), because how far a run consumed its input and whether its writes survive are one claim; a cursor that advanced over a reverted write would make the readiness gate read the log as caught up and skip the retry outright. **Chat is untouched**: its turn IS its conclusion, no journal is bound outside a cycle, and a chat write to any other collection is outside the journal's scope. **The LEDGER is not part of the deal** — the aborted run's `promptlog` rows, the mutation events, the `browse-results` fetch cache — because the forensic record of a dead cycle is exactly what an operator needs; the send queue only gains a row at QUEUED, a healthy end, so it never reverts. One consequence for the run record: `RunOutcome.INCOMPLETE` is no longer reachable for a collector cycle — a run whose writes were undone changed nothing durable, so it is the `failed` bail it honestly is. **Three things are WAIVED by the code owner** (documented at the journal, not defended against): a concurrent read mid-cycle sees the live in-progress writes; a process crash mid-cycle persists the partial state (the journal is in memory); and a chat turn writing the SAME collection mid-cycle can be clobbered by a revert. The overflow deliberately names NO fetch tool: a cycle's surface is scoped to its program's calls, so a read tool named here might not be on it. **Presentation only** — nothing constrains what a routine may be or which keys it may use. Why it exists: on PR #1906's round-3 measurement 15 of 25 quiet cycles completed-and-notified because the model invented a fresh key each cycle (nothing it could read said what key the value was already stored under), so the write gate saw `NEW_KEY` where the value was in fact unchanged. The code owner's rule — "the model can only act on the information it is presented; if it needs to know the key, then that's what we need to present" — makes that a presentation defect, not a case for baking a key in.
- **Scoped tool surface (#1556)**: a cadence-fired collector run cannot reshape the registry — the lifecycle tier (`collection_create` / `collection_update` / `collection_merge` / `collection_archive` / `collection_unarchive` / `log_create`) is ABSENT from its surface (a background poll has no business re-architecting the system). The run type declares this via `Collector._include_lifecycle_tools()` (template method → `build_memory_tools(..., include_lifecycle=False)`); the chat agent keeps the lifecycle tools (the user evolves collections through them). `_collector_tool_surface` mirrors the mask, so an `extraction_prompt` naming a lifecycle tool is rejected at authoring time.
- **End conditions (#1556, #1857)**: two nullable `memory` columns — `expires_at` (the collection archives itself once it passes) and `max_runs` (it archives after that many completed cycles, via the system-actor archive path so the row stays a visible tombstone in the archived-inclusive catalog). Both are settable directly AND **lifted out of the schedule's own `UNTIL=` / `COUNT=` parts at parse time**, so a bounded rule and a bounded collection are one thing — a one-shot is `DTSTART:<time>` + `COUNT=1`, which fires once and then archives itself. Stating an end twice (a rule with `UNTIL=` plus an `expires_at` argument) is refused rather than silently resolved one way. `_archive_if_run_limit_reached` reads the completed-run count from the ledger (`db.messages.count_completed_runs`, cancelled runs excluded) after each cycle; `_archive_if_expired` + the pre-dispatch `_retire_expired` sweep own the expiry. The `run_at` column this replaced folded into the rule's `DTSTART` line.
- **Minimal collection surface — six concepts, ONE schedule grammar (#1631/#1857)**: `collection_set` reasons about **six concepts** — `name` · `description` · `skill`(+`params`) · `schedule` · `notify` · `expires_at`. **`intent` is GONE** (migration 0095): it duplicated `description` byte-for-byte at birth, so `description` is the single descriptor everywhere — the routing/dedup meaning anchor (#1558), rendered in the catalog/metadata/echoes. **The schedule is ONE `schedule` string in ONE grammar: an RRULE** (`parse_schedule`), optionally preceded by a `DTSTART:` line — `FREQ=HOURLY` · `FREQ=MINUTELY;INTERVAL=90` · `FREQ=DAILY;BYHOUR=8` · `FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR;BYHOUR=9`. `python-dateutil`'s `rrulestr` is the sole authority on the grammar (no bespoke parsing, no NL parsing in Python) and `Collector._is_ready` gates on the rule's own next occurrence after `last_collected_at or created_at` — the rule IS the cadence, so there is nothing to widen. **The hour a rule states is the hour on the USER'S clock (#1932)**, not UTC: `next_occurrence` anchors the recurrence at `created_at` converted into the profile timezone (seconds zeroed), so `BYHOUR=9` means nine in the morning where they are, and the model writes the hour the user said rather than converting it (the four tool-description places that told it to convert now say so). This **replaced the four-form trigger union** (`every <seconds>` | `once at <ISO> [xN]` | `on advance of <log>` | `cron <5-field expression>`, #1631/#1684) and its six columns with one, because the union's real cost was the routing decision it forced: measured on ten natural-language schedule phrases, gpt-oss:20b wrote 10/10 clean RRULEs (including `FREQ=MINUTELY;INTERVAL=90`, inexpressible as one cron line) against 9 + a two-line workaround for cron, and "every morning" mapped to interval-daily rather than cron 10/10 times at enactment. `COUNT=` and `UNTIL=` are **lifted at parse** into `max_runs` / `expires_at` while staying in the stored rule, so a rendered schedule round-trips. **`expires_at` takes ISO or the user's own words** — tried as ISO first, then `dateparser` **in the user's timezone** (`parse_expires_at`, the zone passed in as a parameter): "in two weeks" and "tomorrow at 9am" land, and reading them as UTC is what put a bounded watch's end on the wrong evening. **A far-future `expires_at` is NORMALISED to no end condition, never stored (#1944)**: an apply turn asked to set a job running indefinitely wrote `expires_at = 2099-12-31`, which then rendered in the self-state header as the mechanism's end condition and was copied back on every later `collection_set` — invented config made sticky by ambient state. Any time past `PennyConstants.SENTINEL_EXPIRY_HORIZON_DAYS` (20 years, a HORIZON measured from now rather than a fixed calendar date, which would itself rot; a wholesale bound erring high, both directions pinned) is a stand-in for "forever", so `parse_expires_at` returns `None` and every render says `expires: never`. Normalised rather than REFUSED, because the job the user asked for is exactly the unbounded one — and never silently: `expiry_was_normalised` is the ONE structural read of that outcome and both things that follow from it hang off it, so they cannot disagree — `sentinel_expiry_note` appends an actionable note to the create / update / re-render result naming what became of the value and what to pass instead, and `update_collection_metadata(clear_expiry=True)` takes a stored expiry OFF the row. **The clear path is load-bearing, not tidiness**: `expires_at=None` means "not stated" on `_MetadataUpdate` like every other optional, so without its own signal an invented expiry could never come off a collection that already carried one — which is exactly how the sentinel became sticky, and the result would have claimed an unbounded job over a row still holding 2099. A sentinel in the schedule's own `UNTIL=` is a separate door and is NOT covered. A schedule `rrulestr` won't read, or an `expires_at` neither reading answers, is a **reject-and-teach** naming the grammar — and where a purely mechanical repair of the text parses (wrapping quotes, a trailing separator, a `DTSTART` joined to the rule with a semicolon) the error **echoes the corrected string verbatim** so the retry is a COPY, never a re-derivation (the measured `every 7200s` rejection whose retry came back as 14400). **On update**: a `schedule` present replaces the stored one atomically, run quota and all; absent leaves it untouched. The stored rule renders back VERBATIM (`render_schedule_clause`) on the self-state mechanisms line (`SelfStateHeader._cadence`), in `memory_metadata`, and in the creation/re-render echo — **display form == invocation form**, with nothing to re-derive at the render since there is only one grammar. A two-line rule renders on one line with its newline written `\n`, which the parser accepts back.

## Scheduler System

The `scheduler/` module manages background tasks:

### BackgroundScheduler (`scheduler/base.py`)
- Runs tasks in priority order (send-queue drainer → collector dispatcher)
- **Skips agents with no work**: when an agent returns False, continues to the next eligible schedule in the same tick. Only breaks when an agent does real work.
- Tracks global idle threshold (default: 60s)
- Notifies schedules when messages arrive (resets timers)
- Passes `is_idle` boolean to schedules (whether system is past global idle threshold)
- **Cancels active background task** when a foreground message arrives (`notify_foreground_start()` calls `task.cancel()`), freeing Ollama immediately for the user's message. Cancelled tasks are idempotent — unprocessed items stay in their queues and are re-picked up on the next cycle
- Commands do NOT interrupt background tasks — they run cooperatively

### Schedule Types (`scheduler/schedules.py`)

**PeriodicSchedule**
- Runs periodically while system is idle at a configurable interval
- Used for the **SendQueueDrainer** (idle-gated, `SEND_QUEUE_DRAIN_INTERVAL` 60s — scheduled before the collector so queued messages deliver promptly) and the Collector dispatcher (idle-gated, COLLECTOR_TICK_INTERVAL default 30s); each collection's own cadence lives on `memory.schedule`, an RRULE
- Tracks last run time and fires again after interval elapses
- Resets when a message arrives

Schedules run a `ScheduledTask` (`scheduler/base.py`) — a structural Protocol (`name` + `async execute() -> bool`). The `Collector` satisfies it, and so does the non-LLM `SendQueueDrainer`.

## Channel System

### MessageChannel ABC (`channels/base.py`)
- Defines interface: `listen()`, `wait_until_ready()`, `_send_raw()`, `send_typing()`, `extract_message()`
- Implements shared logic: `handle_message()`, `send_message()`, `send_response()`, `_log_and_send()`, `_typing_loop()`
- Holds references to chat agent, database, and scheduler
- **Startup readiness before proactive sends**: `Penny.run()` starts `channel.listen()` and the scheduler before startup notifications. Startup announcement/profile prompts run in a separate task that awaits `channel.wait_until_ready()` first. Channels whose send path depends on listener startup override readiness (`DiscordChannel` waits for its `_ready` event); channels that can send immediately inherit the no-op default. This prevents proactive startup sends from deadlocking before listeners such as the browser WebSocket server bind.
- **Outgoing chokepoint — every send is logged**: `_send_raw()` is the single abstract per-channel delivery primitive (the raw Signal REST / Discord / browser-WS send) and does NO logging. Both concrete base methods funnel through `_log_and_send()`, which logs an `OUTGOING` row to `messagelog` (so it surfaces in the `penny-messages` facade) immediately before calling `_send_raw()` — so nothing Penny sends can bypass the conversation record. `send_message(recipient, content, ...)` is the plain path (command results, error notices, onboarding/profile prompts, threading rejections, permission prompts, startup announcements) — it logs the text but computes no embedding and attaches no media (the embedding is filled by the startup backfill) and returns the platform external id. `send_response(recipient, content, parent_id, author, ...)` is the conversational path (chat replies, queued collector sends via the drainer, scheduled tasks) — it additionally embeds the text (stored on the row + reused for nearest-image matching) and returns the DB message id. `ChannelManager` overrides only `_send_raw()` to route to the resolved concrete channel, so the inherited base methods log exactly once (using the shared db) and the routed concrete channel never double-logs.
- **Progress tracker hook**: `_begin_progress(message)` is an optional override that returns a `ProgressTracker` (defined in `channels/base.py`). The tracker has two methods: `update(tools)` (called when a tool batch starts) and `clear()` (idempotent, called once on success and once again from the dispatch loop's `finally`). The default `_make_handle_kwargs` wires `progress.update` as `on_tool_start` for free, and the final response is always delivered via `send_response` so attachments and quote-replies work normally. Channels without a progress UI return `None`

### SignalChannel (`channels/signal/channel.py`)
- WebSocket connection for receiving messages
- REST API for sending messages, typing indicators, and reactions
- Handles quote-reply thread reconstruction
- **Startup connectivity validation**: `validate_connectivity()` retries DNS + a `GET /v1/about` probe up to `PennyConstants.SIGNAL_VALIDATE_MAX_ATTEMPTS` times with `SIGNAL_VALIDATE_RETRY_DELAY` between attempts (~60 s budget) so cold-boot startup can wait out signal-cli-rest-api's 30-60 s warmup. Each failed attempt is logged at WARNING; the final exhaustion is logged at ERROR and the `ConnectionError` is caught in `main()` and written to `penny.log` before exiting. `docker-compose.yml` also gates `penny` on a `curl /v1/about` healthcheck against `signal-api` via `depends_on: service_healthy`, so compose-managed Signal startups never even hit the retry loop. That dependency is **`required: false`** and `signal-api` lives behind the **`signal` compose profile**, which the Makefile (`SIGNAL_PROFILE`) enables only when `SIGNAL_NUMBER` is set — so Discord/iOS deployments never start `signal-api` and penny doesn't wait on it (the health gate applies only when Signal is actually configured). Tests pass `max_attempts=1, retry_delay=0` to stay fast
- **In-flight progress as emoji reactions**: when a user message arrives, the channel reacts to it with 💭 (thinking) via `POST /v1/reactions`. As the agent's tool calls fire, `SignalProgressTracker.update()` swaps the reaction to a tool-specific emoji from `Tool.format_progress_emoji()` (BrowseTool returns 🔍 for searches, 📖 for URL reads). Signal limits each user to one reaction per message, so each new emoji cleanly replaces the previous — no clutter. When the agent finishes, `tracker.clear()` issues `DELETE /v1/reactions` to remove the reaction entirely, and the response is sent as a normal new message via `send_response` (with text + attachments + quote-reply, the same shape as before progress was added). The typing indicator runs alongside throughout. Why reactions instead of editing a "thinking..." text bubble: Signal mobile/desktop clients silently drop attachments added via message edit — even though the wire format technically allows them — so any final response with an image would lose its image. Reactions sidestep editing entirely
- **A resolved permission prompt is MARKED, never deleted (#1938)**: a domain-permission prompt is broadcast to every channel and answered on whichever one the user reaches first (or not at all), so `PermissionManager._prompt` tells every channel the prompt is over — and, since #1938, **how it ended**: the typed `PermissionResolution` (`allowed` · `blocked` · `timed_out`, `penny/constants.py`) rides the `broadcast_permission_dismiss` seam down to each channel's `handle_permission_dismiss`. Signal's prompt is a MESSAGE, so it reacts to **its own** prompt message with that resolution's mark (✅ / ❌ / ⏳ from `PERMISSION_RESOLUTION_EMOJIS`, `target_author` = Penny's own number). It used to REMOTE-DELETE the prompt instead, which Signal has no silent form of — every client rendered a "This message was deleted" tombstone (three in a row when three prompts were answered in the addon), louder litter than the answered prompt and reading as the assistant hiding something. It also put the record and the channel at ODDS: the delete logged nothing and marked no `messagelog` row, so the conversation record still held a prompt the clients no longer showed. A reaction changes neither — the prompt message stands in both — so they agree again (the resolution itself is not persisted; it is a mark on the channel, like the progress reactions above). `SignalChannel.delete_message` went with it — the dismiss path was its only caller, so nothing in Penny issues a remote delete now. The browser and iOS handlers take the resolution and ignore it deliberately: their prompt is a UI popup/sheet, so resolving it is a plain close with no message to mark. Regression net: `tests/channels/test_signal_reactions.py` drives the real manager → channel-manager → Signal-channel path against the mock Signal server, which serves `/v1/remote-delete` **so that an empty delete log is an assertion about a request that would have been answered**, not one indistinguishable from a 404

### DiscordChannel (`channels/discord/channel.py`)
- Uses discord.py for bot integration
- Listens to a single configured channel
- Handles 2000-character message limit by chunking
- Typing indicators auto-expire (no stop needed)
- **Privileged-intents startup guard**: the bot needs the **Message Content Intent** enabled in the Discord developer portal (Bot → Privileged Gateway Intents). Without it `client.start()` raises `discord.errors.PrivilegedIntentsRequired`. `listen()` catches exactly that, logs the actionable `DISCORD_PRIVILEGED_INTENTS_ERROR` one-liner (which intent + the portal link), and re-raises as `ConnectionError` so `main()`'s existing startup-connectivity handler surfaces it in `penny.log` and exits cleanly instead of dumping a raw traceback

### BrowserChannel (`channels/browser/channel.py`)
- WebSocket server for the Firefox addon; also the transport every browse/tool request rides (`send_tool_request`)
- **A connection is a `ConnectionInfo` per device label**, carrying `tool_use_enabled` (the addon's Tool-use toggle), `registered` (the addon's BACKGROUND script — the half that services tool requests — announced itself on this socket; an entry minted by the sidebar's own chat message has made no such claim, and a new socket taking over a known label loses the flag until it registers) and `last_heartbeat` (the addon pings every ~15s)
- **Routing RANKS rather than filters** (`_routing_rank`): among tool-use-enabled connections, registered first, then still heartbeating, then most recently seen. Ranking is what keeps a lone quiet socket routable — it is deprioritized whenever a better one exists and never declared offline on its own. Registration outranks the heartbeat because they answer different questions: a quiet REGISTERED socket has said its background script is there and may just be suspended, while an unregistered one has never claimed it can service a tool request at all, so freshness on it is evidence of nothing. That ordering is only safe because a corpse no longer lingers (below) — before the sweep, nothing removed one and recency was the only available proxy for "still there"
- **Liveness is swept, not discovered by writing (#1940)**: `_watch_liveness` probes every connection past `BROWSER_HEARTBEAT_TIMEOUT_SECONDS` each `BROWSER_LIVENESS_SWEEP_SECONDS`, and a socket that cannot take the probe is closed and evicted. Detection used to be write-driven — nothing noticed a socket was gone until something happened to write to it, so browse requests went into a corpse for ~2.4 minutes (four retry rounds, twelve unanswered requests) until a write finally failed with code 1006. The probe is deliberately the **connect-time status frame**, which the addon already answers by re-registering, so a live-but-quiet socket REPAIRS its entry (label, capabilities, heartbeat) instead of merely surviving. Probes run CONCURRENTLY, each under `BROWSER_LIVENESS_PROBE_TIMEOUT_SECONDS`: a send awaits flow-control drain, so a half-open peer that stopped reading never raises — it just never returns, and serially-unbounded that one probe would wedge the sweep that exists to find it. A healthy addon heartbeats and so is never quiet enough to probe — the sweep costs no traffic
- **A stranded tool request fails fast, scoped to its own socket**: `_pending_requests` holds a `PendingToolRequest` (future + the socket it went out on), so `_fail_pending_on` rejects only what THAT connection owes, logging the count — the flush it replaces rejected every pending future and took live work down with one window closing. The `ConnectionError` is what re-routes the work: `BrowseTool._read_page` catches it and retries onto whatever connection is live, instead of burning the caller's tool timeout for the same news. Its text (`BROWSER_STRANDED_REQUEST_ERROR`) names the connection and the remedy for whoever reads the log — the model sees the browse tool's own error, not this string. A send that fails outright raises immediately rather than waiting at all
- **A handler must return the device label** (`_process_raw_message`): the collection-trigger arm returned bare, so the socket that ran an on-demand cycle was DE-LABELLED for the rest of its receive loop — heartbeats stopped refreshing it and cleanup could not evict it, leaving a zombie routing candidate (this is what ate the incident's four browse retry rounds, closing logged as `device=unregistered`)

### Channel Factory (`channels/__init__.py`)
- `create_channel()` creates appropriate channel based on config
- Auto-detects channel type from credentials if not explicit
- **Primary channel seeds a default device at startup** (Signal with `signal_number`, Discord with `discord_channel_id`; iOS registers its own on pairing). The browser addon stays `is_default=0`. This makes proactive routing structural — `ChannelManager._resolve_channel` prefers the default device's channel over a device-identifier match on the recipient, so proactive/autonomous sends land on the configured primary channel and can never be captured by a browser addon whose label the profile's sender was pinned to during onboarding (#1298). Conversational replies are unaffected — each concrete channel handles its own receive→reply loop and never goes through the manager.

## Command System

Penny supports slash commands sent as messages (e.g., `/config`, `/profile`). Commands are handled before the message reaches the agent loop.

### Architecture (`commands/`)
- **Command ABC** (`base.py`): Each command implements `name`, `description`, `aliases`, and `async execute(context) → CommandResult`
- **CommandRegistry** (`base.py`): Maps command names/aliases to handlers, dispatches messages starting with `/`
- **Factory** (`__init__.py`): `create_command_registry()` registers all built-in commands

### Built-in Commands (always registered)
- **/commands** (`index.py`): Lists all available commands with descriptions
- **/config** (`config.py`): View and modify runtime settings (e.g., `/config idle_seconds 600`). Reads/writes RuntimeConfig table in SQLite; changes take effect immediately
- **/profile** (`profile.py`): View or update user profile (name, location, DOB). Derives IANA timezone from location. Required before Penny will chat

Preferences are no longer slash commands — like/dislike add, remove-by-meaning, and list are dispatched from natural language onto the `likes` / `dislikes` memory collections (see the ChatAgent section). The retired `/like` + `/unlike` + `/dislike` + `/undislike` commands wrote the legacy `preference` table (dropped by migration 0097); the collections are what recall + the ambient extractor share.

There are no conditional (config-gated) commands — email retired onto the chat tool surface (see the ChatAgent email-tools bullet above); `/bug`, `/feature`, `/draw`, `/mute`, `/unmute`, `/schedule`, `/unschedule` all retired earlier in epic #1445.

### Runtime Configuration
- `/config` reads and writes to a `RuntimeConfig` table in SQLite
- `ConfigParam` definitions in `config_params.py` declare runtime-configurable settings with types and validation
- `RuntimeParams` class provides attribute access: `config.runtime.IDLE_SECONDS`
- Three-tier lookup chain: DB override → env override → ConfigParam.default
- Config values are read on each use (not cached), so changes take effect immediately
- Groups: Chat (max steps, search URL, context limits, domain permission mode), Background (idle threshold, COLLECTOR_TICK_INTERVAL, COLLECTOR_RUN_HISTORY, BACKGROUND_MAX_STEPS, dedup thresholds), Email (body max length, search/list limits, request timeout)

## Data Model

All tables defined in `database/models.py` as SQLModel classes:

- **PromptLog**: Every LLM call — `model`, `messages` (JSON), `response` (JSON), `thinking`, `duration_ms`, `agent_name`, `run_id`, `run_outcome`/`run_reason`/`run_target`, `tool_failures` (count of failed tool calls in the run, stamped on the last prompt alongside the outcome — the structural signal the run-health classifier reads), `trailing_messages` (**the run tail**, migration 0102, #1778: the turns the agent loop appended AFTER this call — the terminal assistant tool-call turn plus its tool-result turns — which no later call carried. A tool RESULT is otherwise durable only as a side effect of being fed back, riding into the NEXT call's `messages`; a run that ends the instant a tool returns — a write-gate STOP, `max_steps` on a tool step, a reroll abort, an exception — has no next call, so its terminal outcome was recorded nowhere, and those are exactly the runs worth reading afterwards. Same wire shape as `messages` (it is literally what the next call's `messages` would have ended with), so the readers concatenate rather than merge and one decode path serves both. Stamped by `MessageStore.set_run_trailing_messages` from `Agent._run_agentic_loop`'s `finally` — the universal per-run chokepoint, chat and collector alike, and the one place that still holds the tail when the loop dies (`set_run_outcome` is collector-only, and the motivating case was a chat turn). Empty tail → no write at all, so an ordinary run is untouched and renders byte-identically. Read via `_run_tool_turns` (`database/memory/objects.py`), the single COMPLETE tool-turn accessor behind `render_run_calls` / `project_run` / the I/O tally / the egress-media trace, and via `_row_turns` in the eval harness's transcript extractor — so neither can be missing an entry)
- **MessageLog**: Every user/agent message — `direction`, `sender`, `content`, `parent_id` (thread chain), `external_id` (platform ID), `is_reaction`. (The `thought_id` FK into the legacy `thought` table was dropped by migration 0097 — historical rows lose only that link.) **Emission provenance** (migration 0088, #1568): `mechanism` — the bound collection whose autonomous cycle produced an outgoing send; a by-name reference to `memory.name`, a plain column like `mutation_event.entity_name` (a DB-level FK would close a circular foreign-key cycle with `memory.source_message_id`), served by the partial `ix_messagelog_emission_time` index. NULL for a direct reply (a chat turn with a live triggering user message names no mechanism); the drainer stamps it at delivery time from the queued row's `collection`. Provenance renders where the message renders: the `penny-messages` facade shows `(sent by <mechanism>)` inline on every read, so "which mechanism sent this?" is the same call that read the message
- **UserInfo**: User profile — `name`, `location`, `timezone` (IANA), `date_of_birth`
- **CommandLog**: Command invocations — `command_name`, `command_args`, `response`, `error`
- **RuntimeConfig**: User-configurable settings — `key`, `value` (string, parsed on read)
- **MuteState**: Per-user mute state — row exists = muted, delete = unmuted
- **Device**: Registered devices (Signal, Discord, browser addons) — used for multi-device routing and domain permission prompts
- **DomainPermission**: Per-domain allow/deny state for browser extension web access, synced across addons
- **Thought**: **REMOVED** (migration 0097, #1676) — the legacy inner-monologue table (`content`, `title`, `image`, `valence`, `preference_id` FK, `notified_at`). The thoughts pipeline it backed was nuked in the same migration (the `thoughts` collection and its retired pair), which killed its last consumer; the table, its model, and `ThoughtStore` (`db.thoughts`) are deleted
- **Preference**: **REMOVED** (migration 0097, #1676) — the legacy user-sentiment table (`content`, `valence`, `source`, `mention_count`, `embedding`, `last_thought_at`). Its last real consumers — the thoughts pipeline's seed-preference pick (nuked in the same migration), the startup preference-embedding backfill, and the `/profile` onboarding check — died with it; the table, its model, `PreferenceStore` (`db.preferences`), and the `PreferenceValence`/`PreferenceSource` enums are deleted. This resolves the #1301 legacy question for the table itself; preference-shaped data lives in the `dislikes` collection (and topic-specific collections)
- **Knowledge**: Summarized web page content — `url` (unique), `title`, `summary` (prose paragraph), `embedding`, `source_prompt_id` FK (extraction watermark). One entry per URL, upserted on revisit
- **Memory**: Unified container for the task/memory framework — `name` (PK), `type` (`collection` or `log`), `description` (content-reflective; doubles as the resolve-by-meaning anchor, #1558), `description_embedding` (the anchor vector, backfilled at startup), `notify` (emission-as-property, migration 0085, #1591/#1557: the **sole** emission flag — when true the collection tells the user about new/changed entries via the run-time notify steps appended to its collector prompt before the injected terminal `done()`; set at creation from `collection_create(notify=…)`, flipped by `collection_update(notify=…)`. The `published` pub/sub column + the `notifier` consumer + `read_published_latest` were retired by migration 0086/#1557), `archived`. **Operational-registry provenance + lifecycle** (migration 0081, #1566): `source_message_id` (FK → `messagelog.id`, the spawning user message — linked post-run by `link_source_message`, matched on `created_by_run_id`), `created_by_run_id` (the `promptlog.run_id` of the creating chat run, stamped by `collection_create`). All nullable — seeded/system rows carry none. `collection_catalog` (archived-inclusive) and `memory_metadata` render these as a shared status/expires/created-from-message block. **Schedule** (migration 0104, #1857): `schedule` (nullable) — ONE RRULE string, the whole schedule grammar; `Collector._is_ready` gates on the rule's next occurrence after `last_collected_at or created_at` (the rule's own `DTSTART:` line wins when it has one, else the recurrence anchors at `created_at`). **That anchor is the user's WALL CLOCK (#1932)**: an RRULE states an hour (`BYHOUR=9`) and never a zone, so the zone comes from the profile (`UserInfo.timezone`, `None` → UTC) — `created_at` is converted into it and its seconds zeroed, and `next_occurrence` (`tools/collection_instantiation.py`, DB-free, the zone passed in as a parameter) is the one seam that reads a stored rule. Reading it in UTC is what fired a briefing asked for at a local morning hour four hours early on a UTC-4 profile while the reply promised the local time; zeroing the seconds is what stopped a collection created at `:51` past from being a job that fires at `:51` past for ever. Because `ZoneInfo` resolves the offset per occurrence, a stated hour holds across a DST boundary. The rule text is **never rewritten** — normalising the hour to UTC at store time would make the render a translation of the ask and re-passing it would convert a second time — so `render_schedule_clause` still round-trips. An explicit `DTSTART:…Z` states its own zone and stays an exact instant; a FLOATING `DTSTART` (no `Z`) states none, which RFC 5545 calls local time, so it is read on the same user clock (which also stops it coming back naive and raising in the shared readiness comparison). It **replaced six columns** — `collector_interval_seconds`, `run_at` (folded into `DTSTART`), `source_log` (the dropped `on advance of` form), `cron_expression`, and the auto-throttle pair `base_interval_seconds` / `consecutive_idle_runs` — with no conversion of existing trigger data (code-owner ruling: deployments reset after this arc), logged loudly per collection at migration time. **End conditions**: `expires_at` + `max_runs` (both nullable) archive the collection when the time passes / the quota is reached; both are settable directly and are what the rule's `UNTIL=` / `COUNT=` are lifted into at parse. **Skill provenance** (migration 0090, #1603): `skill_name` (a by-name reference to `skill.name` — a plain column, not a DB FK, since a skill is re-teachable/REPLACE-able) + `skill_params` (the params bound into the skill's render, as JSON) — stamped by `collection_create` at instantiation; both nullable, NULL for a hand-authored/seeded collection. `collection_catalog` and `memory_metadata` render them as a `from skill: <name> (<param>=<value>, …)` line (params omitted when the skill had no holes; the whole line absent — byte-identical render — when `skill_name` is NULL), so "which skill made this, and with what?" is a read off the collection's own row and the rebind/re-render (#1620) reads those bindings as its input. **Re-render from a skill** (#1620): `collection_update(skill=…, params=…)` re-renders a collection's `extraction_prompt` from a skill's CURRENT steps and re-stamps this pair — four cases: **refresh** (the same skill re-taught → re-render from its current definition), **rebind** (new `params`, same skill), **swap** (a different `skill`, full #1591 resolution + hole validation), **adopt** (a legacy `skill=NULL` collection given a skill for the first time, its hand-authored text replaced by the render). The re-render is the SAME `render_skill` fn `collection_create` stamps at birth (so the steps-1..A / no-stored-`done()` invariant holds by construction), records a `mutation_event` with the run id, and echoes the newly rendered program (`render_reinstantiation_echo`, mirroring the creation echo). A plain `collection_update(notify=…)` etc. leaves the prompt + provenance untouched; a raw `extraction_prompt` alongside `skill`/`params` is a conflict. The resolve + render machinery is shared with `collection_create` (`resolve_skill` / `render_skill_prompt` in `tools/memory_tools.py`), not duplicated. **Inert + apply-time job (#1629)**: a skill-less `collection_create` creates an inert storage collection (no prompt/cadence/notify — never dispatches); the second half of the teach bootstrap is `collection_update`'s **adopt** case giving it a skill. Two apply-time rules ride both paths: (1) **retarget-at-apply** — every ATTACHMENT-MARKED leaf is bound to the target collection's own name at the render seam (`retarget_writes` in `database/skills.py`), since "apply this routine HERE" is what decides a leaf that named a collection and nobody supplied — so a skill demoed against collection A, applied to B, acts on B (the rendered program never lies about the collection it acts on). Since #1777 that leaf is a PLACEHOLDER in the stored skill (`{the collection this is set up on}`) rather than a baked constant, so retarget *binds* it rather than overwriting it — and an UNinstantiated skill (the ambient recipe, `skill_read`, the stored row) names no collection at all. Since #1783 the binding is keyed to the per-leaf MARK, not to a tool whitelist (which `retarget_writes` used to recompute independently — one policy, two copies): a `log_append` target, a plugin tool's target, or a read of the routine's own collection all participate without being enumerated, and since #1828 nothing clears a mark — a destination is never a parameter (#1827 principle 4) — so every marked leaf lands on the attached collection, and a user-named destination becomes a bindable parameter only if the framer decides so from the ask; (2) **schedule + notify are apply-time job properties** — `collection_update` accepts the same one-arg `schedule` (plus `expires_at` and `notify`), REPLACING the stored schedule atomically along with the run quota lifted out of it, and recording `schedule`/`expires_at` in the mutation's changed fields. `collection_catalog` renders an inert collection with an honest `extraction_prompt: (none — inert storage, no skill attached yet)` line. Collections are keyed sets with dedup on write; logs are append-only keyless streams
- **MemoryEntry**: One entry in a memory — `memory_name` FK, `key` (nullable for logs), `content`, `author`, `key_embedding`, `content_embedding`. Entries are immutable once written — `update` replaces content for a given key. **Entry-level provenance** (migration 0083, #1560): `created_by_run_id` + `last_written_by_run_id` — the run that first wrote the entry and the run that last rewrote it (a collection entry is overwritten each cycle, so the current-value writer differs from the creator). Stamped at write time by the writing run, threaded as a parameter (no ambient state); both nullable (pre-#1560 / migration-seeded rows carry neither). The run id is the join key into the ledger (the `promptlog` write events); these two stamps are the read-path anchors that keep `read_run_calls` one guess-free hop from wherever an entry renders
- **MutationEvent** (`mutation_event` table, migration 0083, #1560): One durable create / update / archive / unarchive of a registry entity (a collection) — `entity_type`, `entity_name`, `action`, `actor` (`user-run` | `system`), `run_id` (the causing run — the ledger join key), `detail` (JSON `MutationDetail`: changed-field names, a cause note, and the options-presented `EnumeratedDecision` accommodation), `created_at`. The event half of the operational spine (the entity half is #1566's `memory` columns): the `memory` row stays the materialized truth (its `archived` flag), and this table is the audit/provenance trail of how it got there — so "when was this archived, and by what?" is a read. The one ledger table with no other home: an entry write is a `promptlog` tool call and a run is a `promptlog` group, but a *system* archive (the scheduler's `max_runs` / `expires_at` retire) runs no model and logs no prompt. Written at the `MemoryStore` chokepoint (`create` / `_set_archived` / `update_collection_metadata`); read via `db.mutations.history(name)`, rendered into `memory_metadata`'s "Recent changes" block, each line naming its run id (the anchor invariant). Audit, not event sourcing
- **StateTransition** (`state_transition` table, migration 0100, #1706): One move of the conversation state machine — and, as the newest row, the machine's WHOLE state. `from_state`/`to_state` · `cause` (`TransitionCause`: `classifier` — a model draw, carrying the `run_id` join key into the promptlog | `structural` — no model in the loop, the post-apply reset; the mutation ledger's user-run/system split's twin) · `outcome` (the `StateDrawOutcome` of a classifier draw, NULL for a structural move) · `anchor_message_id` (FK → `messagelog.id` — the instigating ask the machine is anchored to AFTER this move: set on entry to a parked state, carried unchanged through the round, NULL once idle; a fact about the transition like `to_state`, not a copy, so the anchor's whole history is readable) · `message_id` (FK) · `run_id` · `skill_name` (what a SKILL-GATED decision bound, by name — a plain column like `messagelog.mechanism`, since a skill is REPLACE-able) · `skill_frame` (the round's FRAMING as serialized `RoundFraming` JSON — the signature the framer drew when the machine entered learn and the container Python built from it, #1868. Beside `skill_name` because it answers the same kind of question about the move — what routine this is about — for the case where the routine does not exist YET: the skill row still enters the registry only at run end, so a framed name is not a `skill.name` to reference. A draw varies and a re-draw is not a re-read, so the entry decision is RECORDED and later read; it rides the anchor's lifecycle — set on entry, carried while parked, NULL once idle) · `round_shortfall` (the round's PARTIAL binding as serialized `RoundShortfall` JSON, #1894 — `skill_frame`'s sibling for a round the words fall SHORT of, which has no signature and no container yet: the routine the ask is covered by, the values already settled, and the parameters that got none. Recorded for the same reason a framing is — a draw varies, so what a round is waiting on is READ on every later turn rather than re-derived from raw conversation — and carried by the state that reads it: only a move LANDING in request keeps one) · `round_provenance` (the round's PROVENANCE as serialized `RoundProvenance` JSON, #1902 — the whole `skill` row that stood under this round's pinned name BEFORE the round opened. Three states, because calling a round off owes the registry three different things: NULL when the round minted nothing (a skill-gated round binds a routine the user already had, so a bail leaves it alone), present-and-empty when the round minted its name over nothing (a bail deletes it), and present-carrying-a-row when the round was re-teaching — that row being what a bail puts back, since by then the round's own run-end extraction has already replaced what that routine does, so merely skipping the delete would leave an abandoned, half-corrected program live under a name existing jobs still run. Settled on the move that MINTS the round's routine — the last point at which "what was here before" is still readable — and carried the framing's way) · `created_at` (indexed, with `cause`/`run_id`). **An append-only log with NO materialized twin**: the newest row's `to_state` is where the machine stands, its `anchor_message_id` the parked round's ask, its `created_at` when it last moved — a current-state row alongside would carry nothing that isn't derivable and would mean two writes per move that can disagree, so there is one write and a failed write moves nothing. (The `memory`/`mutation_event` twin earns itself only because a `memory` row carries name/description/prompt/cadence — facts no event derives; the shape does not transfer.) `from_state` beside `to_state` is deliberate denormalization — derivable from the previous row by join, but on an append-only log a self-describing row is cheaper to read. Nothing is seeded: the cold start is the ABSENCE of history (no rows = idle), never a row asserting it. **Every draw appends a row, including one that moved nothing** — `outcome` distinguishes fail → stay from a decided idle → idle, and scoring per-edge accuracy over production history needs the held draws (a log of only successful transitions reports a perfect classifier by construction)
- **Skill** (`skill` table, migration 0084, #1590): A named, immutable, **versionless** certified-by-execution script distilled from ONE demonstrated run — `name` (PK, unique key; re-teaching REPLACES the row — no version history, since collections carry the rendered TEXT snapshotted at creation), `steps` (JSON `list[SkillStep]` — the `LoggedToolCall` shape copied verbatim from the ledger + per-leaf substitutions), `parameters` (JSON `list[SkillParameter]` — declared SKILL-level parameters, semantic name + required + optional one-line description, #1668; was `holes` before the rename migration 0096), `intent` / `description` (+ `description_embedding` for future resolution, populated at write), `source_run_id` (the demonstrated run — the triggering message reachable *through* it), `author` (the teaching agent), `created_at`/`updated_at`. Authored ONLY by the framework — **there is no `skill_create` tool** (#1658). At the end of every LEARN chat turn the run-end extractor (`penny/skill_extraction.py`) snapshots THAT run's own ledger. **The gate is the STATE, not the run's shape (#1850)**: extraction runs if and only if the turn's landed machine state is `learn` (threaded in as a parameter; no machine history = idle = no extraction), so teaching is the one thing that mints a routine and an apply/idle turn that happens to browse-and-write mints nothing. What remains is mechanics — chat run · ≥1 tool call · ≥1 certified step (the `BAILED` health gate is retired, #1839 — the call-shaped-text bails it keyed on are re-rolled by the loop and can no longer appear in a completed run) — and the read+write taxonomy that once refused a pure read ('answering') and a pure write ('the storage atom') is DELETED: a taught round is learned whatever shape it had. It then captures the run's non-`done` tool calls, keeps the ones that SUCCEEDED and DROPS the rest (filter-not-refuse, #1659), so certified-by-execution holds by construction. Registry-navigation ORIENTATION verbs (`find`/`skill_read`/`memory_metadata`/`collection_catalog`, #1665) are excluded before distill — dropped from the recipe, since a re-run re-orients itself and a `find` result echoing its query can otherwise manufacture a false binding. Only COLLECTOR-runnable steps are captured (#1668): a skill renders into a collector prompt, so a lifecycle call a demo made mid-run (e.g. `collection_create` to set up the container) is dropped from the recipe like an orientation call — filtered against the real `collector_tool_surface` (the same masked surface the authoring-time guard validates extraction_prompts against), so a captured step is never one a collector could never run. Each argument is factored by STRUCTURAL provenance (#1659, `distill_steps`, never by matching the user's prose): a value that equals / occurs as a whole span of / wraps a prior step's result → a binding (`the value from step N`) — comparison is against the result's PAYLOAD, not the framed text (#1665/#1661: the tool-result frame — narration+tag header, browse fetch-handle tail — is stripped first, so a wrapping arg like `Price: $499` over a returned `$499` binds without any fuzzy threshold). **The two directions are asymmetric (#1809)**: *wraps* is plain containment (the whole result sits inside the argument — no coincidence to guard against, and the prose around it ends in ordinary punctuation a span test would reject), while *contained-in* demands the value be a WHOLE whitespace-delimited span of the payload, because that payload may be an entire fetched PAGE and a page contains most short strings by accident. The motivating false binding: a browsed listing's own URL (`…/aurora-deck-2`) carries the product slug, so a write KEY the assistant slugged the same way bound to "the value from step 1" — the price — and the learned routine stored each cycle's price under a key that was also the price, never overwriting. A copy is a whole span of the result; a slice out of the middle of a token is a character coincidence. **Neither direction is asked at all for a value that is already a parameter (#1933)**: identical values collapse to one candidate, so a leaf repeating a value an earlier leaf minted joins that parameter first — a page fetched twice in one demonstration is one input given twice, and reading the repeat as the first fetch's OUTPUT produced `browse(queries=[the value from step 1])`, a routine that no longer says which page it reads. And what a step PRODUCED excludes what it was CALLED with: a result quoting its own arguments back (`## browse: <url>`, an extract result opening with its instruction) is frame in the same sense the narration line is, so those spans are removed from the contained-in comparison — nothing keyed to a tool, so an unheard-of tool that echoes is covered too, and the redirect lands on the step that actually produced the value. Every other string leaf → a **required** parameter (shared values collapse to one; no silent default — an unbound parameter is a loud refusal at instantiation). **That last rule is a DEFAULT, not a determination (#1770)**: it assumes an unexplained value came from the user, which is false for one the model derived-and-transformed from a result or invented outright — and produced skills with required parameters nobody could supply. Those two origins share no literal span with what produced them, so no substring test can reach them (and #1659 ruled prose matching out), so the question is not asked at all any more (#1824/#1828): EVERY leaf is a placeholder, and the run-end draw NAMES each one — a semantic name + one line of what belongs there each run, written by a single-shot leaf-labelling micro-context (one `LABEL <current>: <semantic_name> — <description>` line per spot, poison-screened + re-rolled). A labelled leaf's sites become `SkillSubKind.PLACEHOLDER` substitutions carrying that description, which `render_skill` emits as `{<what belongs there>}` — the same placeholder syntax an unbound parameter uses, and **never the frozen demonstrated value** (freezing is the specific harm: a collector re-running the skill would write that stale phrase into the collection every cycle, forever). The draw must COVER every offered spot with exactly one well-formed line (#1828) — a missing, malformed, repeated, or invented line fails the WHOLE draw after the reroll budget, and every spot then keeps its arg-derived REQUIRED parameter — extraction never blocks. **The interface is the FRAMER's (#1824/#1830)**: a SEPARATE run-end draw, over the user's own turns and nothing else, writes the routine's `name`, `description` and `parameters` — minted from the ask rather than sorted out of what the demonstration used, so a routine never names itself for something it then asks for; a failed framing falls back to the deterministic slug of the triggering message + that message, with no parameters. **The RUNTIME JOIN (#1907)**: each declared parameter also carries `value`, the value the round that taught the routine demonstrated it with — the one observable the framer and the labeller share, since neither sees the other's evidence — and `bind_parameters` uses it at the instantiation seam to write a collection's bound values into the leaves the demonstration put its own values in. So `parameters` live at SKILL level — rendered in the registry, enforced at `collection_set`, decisive for `is_same_job` tier 1 — over a STORED recipe that still reads in the labeller's placeholder descriptions (a routine at rest is pointed at nothing), while the program a CONFIGURED collection runs names the page it fetches and the thing it looks for. A parameter with no demonstrated value (a legacy row, a failed framing) joins nothing and the program renders as it always did; one with no bound value leaves its leaf naming the gap rather than keeping a description that reads like an instruction. description_embedding anchors on the framer's GENERIC description (dedup converges cross-instance); dedup REPLACES an existing skill by name, or by same tool-sequence shape + description-embedding match keeping the existing name. **A round carrying a FRAMING is keyed by it, and the ladder does not run at all (#1902)**: the write lands on the name the round PINNED at entry, so the round's second run (the correction) replaces its own routine in place — one round, one routine — and no same-shaped, same-meaning sibling can capture the write and file this round's routine under another job's name (which would leave the container the round has been writing into pointing at a routine no longer called that). Promotion is implicit SURVIVAL: there is no draft flag, the routine simply outlives its round, and a BAIL takes it back by the round's PROVENANCE (`round_framing.abandon_round_skill` — `db.skills.delete` for a name the round minted over nothing, `db.skills.restore` of the recorded pre-round row for one it was re-teaching, and nothing at all for a round that minted no routine). Internal identifiers are `parameters`, not "hole" (the PL jargon renamed in #1668; the `skill.holes` column → `parameters` via migration 0096). **The collection name is a spot like every other one (#1783/#1828)**: it is named by the same draw, and it additionally carries the **attachment mark** when its demonstrated value names one of Penny's collections (registry-derived — nothing in this path knows which tools a skill contains). Nothing clears the mark: where a routine writes is decided by what it is applied to, so the attachment fills every marked leaf at instantiation and it renders the labeller's own wording; a marked leaf the draw never named falls back to the fixed `WRITE_TARGET_DESCRIPTION` rather than to a required parameter nobody could bind, and migrations 0101/0103 back-fill the placeholder + mark onto skills taught before either change. (This supersedes #1783's other direction — two destinations the USER named stayed two bindable parameters because a verdict cleared the mark; with no verdict, a user-named destination comes back as a parameter only if the framer decides so from the ask, which is where that decision belongs.) **No seed library** (code-owner decision on the #1599 revision): the table ships empty, every skill enters through a learn turn's own run, so the invariant holds universally with no hand-authored exception. #1591's `collection_create` renders a skill + bound params into a collection's `extraction_prompt`
- **AgentCursor**: Per-reader read progress through a log-shaped memory — `(agent_name, memory_name)` PK, `last_read_at` high-water mark. Advanced two-phase by the orchestrator (pending during a run, committed on success). For collectors the cursor owner is the **bound collection name**, not the constant `"collector"` identity — otherwise every collection reading the same log (e.g. the many that read `user-messages`) would collapse onto one shared cursor and starve each other
- **Media**: Images captured while browsing or drawn on request, delivered side-channel — `mime_type`, `data` (raw bytes), `source_url`, `title`, `embedding` (of title+URL for browsed rows, of the description for generated rows). The browse tool stores every page image here; at channel egress `MediaStore.select_image` attaches the most relevant image, most-relevant-first: (1) **exact URL** — if the outgoing message links a page we captured, that page's own image (newest capture); (2) **same domain** — else the embedding-nearest image from a domain the message links; (3) **fallback** — else a uniform-random pick among the top-K embedding-nearest (jitter, so a centroid "magnet" image can't repeat on consecutive messages — applied *only* to this tier; URL/domain matches are deterministic). No floor, so a reply still carries an image whenever one matches. A `generate_image` row is delivered **by id to its own reply** (`send_response(media_ids=...)`, from `ToolResult.media_id`) with precedence over this ladder — never fuzzy-matched for that reply, but in the pool for future ones (#1564). Zero model involvement — no `<media:ID>` tokens, no prompt changes
- **SendQueueItem** (`send_queue` table): Durable outbound message queue — `content`, `collection` (the collector that queued it), `origin`, `created_at`, `sent_at` (nullable; `NULL` = still pending, single source of truth — no separate flag). A finished cycle's notification is enqueued here instead of being dropped when the autonomous-send cooldown hasn't elapsed (#1911: `CollectorNotifier.queue`, which holds the refusal / no-recipient / mute gate the retired `send_message` tool used to); the `SendQueueDrainer` delivers the oldest pending row its lane allows out — stamping the row's `collection` onto the delivered `messagelog` row's `mechanism` (#1568). Kept after delivery (stamped `sent_at`) as an audit trail. **`origin` (migration 0109, #1939) is WHICH LANE**: the `CycleTrigger` that set the queuing cycle running — `cadence` (the schedule's own dispatch; ride the full cooldown) or `on_demand` (the user's "run this now"; deliver on the next tick, because they are sitting in front of it waiting). NOT NULL, defaulting to `cadence` on the column and in `enqueue`, so an unstamped row is in the conservative lane and skipping the cooldown is something a caller has to claim. Observed live: an on-demand run's notification waited ~10.5 minutes because an unrelated chat reply seconds earlier had started the cooldown

## Message Flow

1. Channel receives message → `extract_message()` → `IncomingMessage`
2. Channel calls `handle_message()`:
   - Checks for slash commands first (dispatches via `CommandRegistry`)
   - Notifies scheduler (resets idle timers, suspends background tasks)
   - Starts typing indicator loop
   - Calls `ChatAgent.handle()` which:
     - Finds parent message if quote-reply (via `external_id` lookup)
     - Walks thread history for context
     - Runs agentic loop with tools
   - Logs incoming message to DB
   - Sends response via `send_response()` (logs + sends); every other outgoing message (commands, status, prompts) goes through `send_message()`, which logs too — all sends funnel through `_log_and_send()` → `_send_raw()`
   - Stops typing indicator, resumes background tasks

## Thread/Context System

- Quote-replying continues a conversation thread
- `MessageLog.parent_id` creates a chain of messages
- `db.messages.get_thread_context()` walks the chain (up to 20 messages)

## Key Design Decisions

- **Browser-based search**: All web access (search, page reading) goes through the browser extension via BrowseTool. Text queries are converted to search URLs (configurable via `SEARCH_URL`). No third-party search APIs
- **Browse micro-contexts (#1588 — bulk content never enters the main run context)**: `browse` takes an optional `extract` micro-instruction (`browse(queries, extract="pull out X")`). When set (the collector/script path; chat never sets it, so chat's browse is unchanged), the fetched page content goes into a FRESH single-shot `MicroContext` (`tools/micro_context.py`) — content + instruction, one model call, no tools — and only the small typed result returns to the main loop: the extracted value (byte-identical to the micro-context's return, never re-transcribed by the parent) plus a typed fetch handle (`browse-results#<id>`) to the full content, which is still stored whole in the browse-results log and retrievable by handle (`Memory.entry_by_id`). The micro-context's output contract is enumerated on BOTH sides of the interface (the enumerated-cases doctrine): the prompt names the two tagged forms (`EXTRACTED: <value>` / `NOT_PRESENT: <reason>`) and classification is a deterministic tag parse — a not-present apology can never be promoted to an extracted value; untagged output is re-drawn on the unchanged context for the whole budget, then an honest failure. Output is also screened by the same degeneracy / leaked-Harmony-envelope detectors as the agent-loop reroll guard (poison discarded + re-drawn on the unchanged context up to `DEGENERATE_REROLL_ATTEMPTS`). The outcome set is closed (`MicroExtractOutcome`: extracted / not-present / extraction-failed / poison-reroll-failed — not-present is a *successful read of an absent fact*, distinct from the extraction-failed escape), never a silent empty. A micro-context is structurally incapable of confabulating a stored value it has never seen. It is a ledger-visible model call — its own `agent_name="browse-extract"` / `prompt_type="browse_micro_context"` (`PennyConstants`) so run traces attribute it (run_target = the browse's author) — but it never inflates the parent run's context. **Per-page extraction in batches (#1682/#1941)**: a multi-query `extract` browse runs ONE micro-context PER successfully-fetched page (never one call over the concatenated pages), each result rendered UNDER that page's own `## browse …:` section header — so a multi-source digest keeps items attributed to their source, and a NOT_PRESENT page renders honestly in its own section without masking another page's extracted value. Each stored page-read carries its OWN `browse-results#<id>` fetch handle (a search section carries none). Read-failure signals (`## browse error:` sections) stay visible in place; a total-failure browse returns its error sections directly (no micro-context). N batched pages → N attributed ledger rows. The run trace renders the step as `browse(queries=[…], extract='…')`. **The batch is drawn CONCURRENTLY (#1941)** — one `asyncio.gather` over the page batch, because the per-page contexts are independent by construction (a fresh single-shot context, its own document, its own ledger row, its own poison/reroll budget), so no draw reads anything the draw before it produced and running them one after another spent the whole batch's latency serially (~45-60s for three pages; a measured on-demand cycle spent ~2 minutes across six extracts). **Attribution is unaffected because the batch is PLANNED before it runs**: `_extract_batch` binds each page's render slot AND its own fetch handle in section order up front — the handle iterator is consumed sequentially there, so a search section (readable, never stored) and a read failure (no content section at all) cannot slide a page's handle onto its neighbour — and `_merge_extracted` writes each result back into its own slot, so sections render in page order whatever order the draws finish in. Purely a concurrency change: same calls, same renders, same per-draw reroll machinery (a poison draw re-rolls only ITS context). A draw that RAISES (a transport failure the client surfaces once its retries are spent) still ends the whole call with that error exactly as the sequential loop did — the batch is collected with `return_exceptions=True` and the EARLIEST failing page re-raised (`_drawn_pages`), because `asyncio.gather` does not cancel a raising child's siblings and they would otherwise keep spending the backend, and writing their own ledger rows, against a call that had already failed. The wall-clock win depends on the backend's parallelism (`OLLAMA_NUM_PARALLEL`) — a single-slot backend serializes the draws itself and the batch costs what it always did
- **URL fallback**: If the model's final response doesn't contain any URL, the agent appends the first source URL
- **Duplicate tool blocking**: Agent tracks called tools per run (a seen-calls cache) to prevent LLM tool-call loops. A byte-identical repeat of a still-cached call is blocked — but any successful MUTATING call (`ToolResult.mutated=True`) **clears the cache** (`_process_tool_calls`), because an identical call is only pointless against an UNCHANGED world and a mutation means the world changed (#1673). So a legitimate repeat RUNS in BOTH directions once a mutation intervenes: retry-after-remediation (a failed write retried after its collection was created — the failed write's own error told the model to create it first) and re-read-after-write (verifying the entry just written). Loop-safe by construction: a repeat with no mutation since its prior occurrence never clears the cache, so it stays blocked (a failing retry adds no mutation). When a repeat IS blocked, the rejection frame states the prior call's OUTCOME (`_duplicate_rejection_frame`) — succeeded → reuse its result; FAILED → the failure quoted + fix the precondition (never "use its result", which read as success and made the model narrate a write that never happened)
- **Tool-result framing (tagged first-person narration)**: every tool result is wrapped by `Tool.format_result(name, arguments, result)` (applied once in `Agent._collect_tool_results`) into a **tagged first-person** header — a narration line + a retained `(<tool> result)` machine tag — then the body: `You used \`<tool>\` and here's the result: (<tool> result)\n<body>` on success, `You tried to use \`<tool>\` but it didn't work: (<tool> result)\n<body>` on failure. The narration is resolved by `Tool._resolve_narration` in priority order: an explicit `ToolResult.narration` frame wins, else the registry-dispatched `Tool.to_result_narration(cls, arguments, result)` — the *result* twin of `to_action_str` (the pre-call status string), branching on `result.success` — else the generic default for an unregistered tool. **`BrowseTool` overrides `to_result_narration` (#1480)**: one first-person line for the whole call summarising search-vs-read from the `queries` arg and the outcome (`You searched for "…"` / `You opened <url>` / on a total failure `… but couldn't read anything — no page was read, so there's nothing current to quote`, which states the CONSEQUENCE of the failure and not only the failure, since a run that says only what happened to the call leaves what follows from it to be worked out — measured, 3 of 5 replies to an all-sources-failed lookup volunteered an invented figure) — the per-page `## browse ...:` section headers stay in the body, so the batch is narrated once, not per section. The call `arguments` + the whole `ToolResult` are threaded from `_execute_single_tool` (which returns the `ToolResult`) → `_collect_tool_results`. **Framework-synthesised failures narrate their own frame (#1482).** The failures a tool can't report itself — tool-not-found (which has NO registered class to dispatch from), timeout, uncaught exception, and arg-validation — set `ToolResult.narration` to a specific first-person frame (`FRAMEWORK_NARRATION_NOT_FOUND` "…but there's no such tool.", `_TIMEOUT` "…but it timed out.", `_EXCEPTION` "…but it errored: `<e>`.", `_INVALID_ARGS` "…but the arguments were wrong:") so `format_result` leads with it instead of the generic line and doesn't double-frame the no-class case; the actionable **remedy** (the #1414 house template's diagnosis + how-to-fix tail — did-you-mean + available list, timeout guidance, "try a different approach", the per-field reasons) stays verbatim in `ToolResult.message`. Remaining per-tool narration overrides land in #1481 (memory/lifecycle). **The tag is load-bearing, not decorative.** The OpenAI `role: "tool"` + `tool_call_id` envelope is the standard "this is a tool result" signal, but gpt-oss:20b doesn't reliably honour it when the body reads like prose — it can mistake fetched data (e.g. a returned user message that itself reads like an instruction) for a fresh directive (#1332's #1 failure class). The terse `Result of your \`<tool>\` call:` header used to carry that disambiguation; a live-model probe showed pure-prose narration with no tag RAISED the call-as-text bail rate (5/6 vs. 3/6 tagged), so the `(<tool> result)` tag stays even as the header reads naturally (see `docs/tool-narration-plan.md`). Read tools additionally lead their body with a `N entries from \`<source>\` (ordering):` header via `format_entries` (public since #1914 — the collector's composed prompt renders the bound collection's current entries through the same function, so an ambiently-read key and a tool-result key are one form). Framing happens after `record.failed` is computed (on the raw result) so failure detection is unaffected. The three tool-*shaped* injections that don't flow through `_collect_tool_results` carry the same tagged envelope at their own sites — but with **bespoke, context-specific narration** (#1485), supplied at the call site (they aren't real registered tool calls, so nothing to registry-dispatch) and composed by the shared `Agent._frame_injected_result(tool_name, narration, body)` helper (`{narration} (<tool> result)\n{body}`, single-sourcing the `RESULT_TAG` so the machine-tag invariant holds uniformly). The narrations live on `Prompt` beside the bodies they frame: the synthetic page-context browse pair (`ChatAgent._inject_page_context`, standard `tool_call_id` envelope via `ChatAgent.PAGE_CONTEXT_TOOL_CALL_ID`) → `PAGE_CONTEXT_NARRATION` ("You looked at the page the user is currently viewing…") — deliberately NOT BrowseTool's `You opened <url>` (#1480): a page-context injection is the page the user is viewing, not a browse Penny ran; the duplicate-tool-call rejection (`Agent._dedup_tool_calls`) → an OUTCOME-FIRST narration + body pair selected from the prior matching `ToolCallRecord.failed` (#1673): `DUPLICATE_CALL_NARRATION_FAILED` + `DUPLICATE_CALL_REJECTION_FAILED` (leads with the failure, quotes its first line, prescribes fixing the precondition — never "use its result") vs `DUPLICATE_CALL_NARRATION_SUCCEEDED` + `DUPLICATE_CALL_REJECTION_SUCCEEDED` (the reuse-the-result guidance); a successful mutating call clears the seen-calls cache (`_process_tool_calls`) so a legitimate retry-after-remediation or re-read-after-write runs, loop-safe; the rejected-tool-calls path (`Agent._append_rejected_tool_calls`, e.g. a premature first-move `done()`) → `REJECTED_CALL_NARRATION` + the preserved rejection body. Each frames — never replaces — the actionable rejection/page body the model must still read. Since bespoke narration is now supplied per site, these sites no longer construct a throwaway `ToolResult` (its only consumer was `format_result`'s generic success/failure branch)
- **Tool argument validation (Django-form pattern)**: every `Tool` declares an `args_model` — the Pydantic model that validates its call arguments — and a base `Tool.run(**kwargs)` constructs/validates it *before* `execute` is ever called (the `ToolExecutor` drives `run`, not `execute`). A `ValidationError` becomes an **actionable error tool response** (`success=False`, naming each bad field with the type+description hint from `parameters` plus any custom-validator message), so `execute` only ever sees valid args and concerns itself with the work + runtime/availability decisions. Validity criteria — required fields, types, and content rules (e.g. `SendMessageArgs`' half-formed-body check, which the notify path now validates through) — live as field/model validators **on the model**, never ad-hoc inside `execute`. Argless tools default to `NoArgs`. Non-existent tools still return a clear tool-not-found error from the executor. This is the single, uniform pre-execute gate; the premature-`done` guard is the one exception that can't be arg-validation (it depends on run state, so it lives in the loop — see *A coherent but WRONG tool call still gets an error tool response*)
- **Model-I/O validation (one behaviour taxonomy)**: where tool-arg validation gates a tool call's *static* arguments, this gates the model's *dynamic* I/O — the response (text + tool calls). The keystone is `penny/validation/conditions.py`: **one catalog** (`BehaviorCondition` in `CATALOG`, keyed by `ConditionKey`) of every condition we classify Penny's behaviour through, so the user, Penny (her ambient view of her own runs in the self-state header), and a maintainer share a single coherent view rather than a check that means one thing in the loop and another in the run log. Each condition declares *where it applies* as data — `live` (caught during the run, by one of three mechanisms: the loop's **discard-and-reroll guard**, where the draw never enters the run at all; a `ResponseValidator` disposition, where the draw stands and the model is given a chance to correct it; or the outbound-message content gate), `run_flag` (surfaces post-hoc as a `⚠` line on the run record), `collector_only`. A condition can be both: `no_work_done` is refused live as a premature `done()` **and** flagged post-hoc as a bail; `half_formed_send` is gated live at the notify draw's acceptance rule + the `SendMessageArgs` validator **and** flagged post-hoc. This catalog supersedes the old split between `ValidationReason` (live) and `RunHealthFlag` (post-hoc); `RunOutcome` (the run's terminal state) stays a separate concern. The live machinery is in `penny/validation/outcomes.py`: a `ResponseValidator` is `check(response, ctx: LoopContext) -> ValidationOutcome`, pure (reads, returns a disposition, mutates nothing); the disposition union is `Proceed` / `Retry(condition)` / `Repair(response)` / `RejectToolCall(message)` / `NudgeContinue(message)` / `Stop(response)` (a typed return, not an exception — the loop reshapes into control flow immediately). **`Retry` says nothing back to the model (#1937)**: it re-appends the model's own bad draw and re-calls, which for the three conditions left — markup, a refusal, an ungrounded URL — IS the correction. The teaching user-turn it used to carry retired with its last two customers, the call-shaped-text family (#1839) and the empty draw (#1937), both of which are discarded and re-rolled before the chain runs. `run_validators` runs an agent's chain in order (repairs thread through; first non-proceed short-circuits). Validators are composed per-agent as class attributes (`Agent.response_validators` — chat's and the base's; `BackgroundAgent.run_shape_validators` — the premature-`done` guard; `ChatAgent.run_shape_validators` — the run-end skill narration) that read like a table of contents — **a new guard is a new validator in the list, not a new branch in the loop.** Beside them each shape declares its `invalid_draw_conditions` (#1839), the family the loop rejects outright rather than dispositions over; a collector composes no response-shape chain at all, since every call-less draw of its shape is discarded upstream. This replaced base.py's inline `_check_response` if-ladder + the `handle_text_step`/`handle_premature_terminator` guards. The post-hoc `classify_run`/`render_run_record` (`database/memory/objects.py`) source their `⚠` marker/detail strings from the same catalog, so what we enforce live and what we flag after a run are one definition — the strings are **frozen** (the addon TS type mirrors them). **Import-cycle gotcha**: `validation/__init__.py` re-exports only the database-free leaves (`conditions`, `outcomes`); it must NOT import `response_validators` (which pulls `tools.memory_tools` → `penny.database`), because the database layer imports the `conditions` leaf and importing any `penny.validation` submodule runs `__init__` first — eagerly importing `response_validators` there closes a cycle through `penny.database`. Import validators directly from `penny.validation.response_validators`. Design: `docs/model-io-validation.md`
- **Actionable tool failures**: Every tool failure (validation error, rejected/degenerate input, refused operation, missing key, external error) MUST return a `ToolResult` whose message tells the model two things: (1) *what went wrong* — the specific reason, naming the offending field/value — and (2) *how to correct it* — the concrete next action (provide a non-empty value, supply the full replacement text, call the right alternative tool, etc.). The tool result is the model's only feedback channel: a bare "rejected" or a silent no-op gives it nothing to recover from, so it retries the same mistake or gives up. A diagnosis without a remedy is a half-failure. Examples: `check_extraction_prompt` quotes the length and the minimum and points at the prompt shape; `update_entry`'s degenerate-content refusal names the reason *and* suggests `collection_delete_entry` if removal was intended. This is a hard rule, enforced in review — see the error-handling section of `docs/pr-review-guide.md`
  - **Every miss suggests its nearest match — did-you-mean on lookup/write (#1674)**: wherever a nearest match is *computable* on a failed name or key lookup, the error LEADS with it (`Memory 'aurora-deone' not found — did you mean 'aurora-deck-2'? …` / `Key 'x' not found in 'notes' — did you mean key 'y'? …`) before the existing find/create/list guidance — the render carries the anchor so the fix is a copy, not another lookup (n≤1). Composed at the **tool layer**, not the store (the store stays pure — it can't embed): `MemoryTool.execute` catches `MemoryNotFoundError` and re-renders via `render_memory_not_found(name, suggestion)`, with `MemoryStore.nearest_memory_name(name, embedding=None)` computing the candidate — the **string (typo) leg** (stdlib `difflib` over active names, gated on `PennyConstants.DID_YOU_MEAN_STRING_CUTOFF`, universal since it needs no embedding — this alone catches the motivating typo) plus, for the embedding-capable name-dispatch tools that override `_suggestion_embedding` (`read_similar` / `collection_write` / `log_append` / `collection_update`), the **meaning leg** (description-anchor cosine, gated on the reused `MEMORY_DEDUP_CONTENT_SIM_RELAXED`). Entry-key misses (`update_entry` / `collection_delete_entry`) suggest the nearest key in that collection via the same `difflib` string leg (those tools carry no embedding client). No close candidate → the message is **byte-identical to before** (no empty "did you mean" artifact). No new thresholds invented — the one named constant is the string cutoff (no house string-distance number existed); the meaning/key gates reuse the dedup thresholds.
- **One job, one collection — identity dispatch on `collection_set` (#1567/#1775)**: `collection_set` dispatches on the collection's **identity**, not on its name: the row the call names, else the row it DUPLICATES, else a new one. Duplicate detection is the two-tier `is_same_job` rule in the shared `similarity` package — **(1)** the same `skill` bound to the same `params` (both populated) is the same job whatever it is called; **(2)** otherwise strict token containment of the normalised names. **No threshold on either tier** — tier 2 is a set relation, so there is nothing to tune or drift. Normalisation (`tokenize_job_name`) folds separators (`_`/`-`/whitespace), case, and unicode dash variants, singularises (`singularize`, deliberately naive + conservative), and strips the closed `JOB_ROLE_WORDS` vocabulary — the words that name the *mechanism* watching a subject (`monitor`/`watcher`/`tracker`/`alerts`/`feed`/`latest`…) rather than the subject, so `aurora-deck-2-monitor` reduces to `aurora-deck-2`. Measured against the labelled corpus each layer earns its place (raw containment 4/7 → + role strip 5/7 → + stem 6/7, all at **zero** false merges). **Embeddings deliberately do NOT participate**: they are *anti*-correlated on the hard cases (the highest description cosine in the labelled set, 0.90, belongs to a pair that must not merge; the lowest, 0.24, to a real duplicate) because an embedding says "same kind of thing" and every trap is two collections of the same kind about different *specifics* — real duplicates are **extensions** (one name's tokens inside the other's), the traps are **substitutions** (`2`|`3`, `times`|`fares`, `bbc`|`cbc`), which containment separates by construction. `description_embedding` stays what `find` resolves on and says nothing about duplication. **On a match: an ACTIVE duplicate is UPDATED, not refused** — the refusal it replaced cost an entire observed turn (the model retried, got a byte-identical refusal, and the all-failed abort ended the turn with no reply); the result LEADS with a redirect note naming the collection the call actually landed on, since everything downstream has to use that name. An ARCHIVED match stays the #1567 tombstone refusal (reviving a retired mechanism is the user's call). **Not implemented**: tier 3 (near-containment + same-day + overlapping params → *ask*, never auto-merge), which is what would reach the substitution-shaped duplicates tiers 1-2 miss — the labelled misses are pinned in `tests/test_similarity.py` as a recorded gap.
- **Write-gate STOP semantics (control flow lives in the tool)**: `collection_write` classifies every entry at the write chokepoint into a closed `WriteGateOutcome` StrEnum (`penny/constants.py`, beside `RunOutcome` — a cycle-free leaf so `tools/models.py` / `agents/models.py` / `database/memory/types.py` import it without a cycle through `penny.database`) — the **change-gate**, computed deterministically in Python, never a model judgment (#1587, epic #1554 via #1562). The union is derived from what `_write_one` actually does: `NEW_KEY` (key didn't exist → written) · `KEY_EXISTS_CHANGED` (exact key, *different* value → news; the gate **auto-refreshes the stored baseline in place** through the shared update path — same validation/degeneracy-screen/`last_written_by_run_id` stamp — so the model runs no `update_entry`, its only remaining job is to notify, #1633) · `KEY_EXISTS_UNCHANGED` (exact key, *identical* value → the watch's "no change" signal) · `DUPLICATE_UNCHANGED` (the dedup disjunction matched a *different* key AND the strict CONTENT signal fired → the stored entry already says what this write says, however either is worded: the SAME no-news, reached by the reworded-key door, #1919) · `DUPLICATE` (a key/near-key collision WITHOUT that strict content hit → the write carries a *different* value for something already stored, which is news) · `DEGENERATE` (rejected content) · `UNEXPECTED` (honest escape label — never emitted today, the write path is total, but wired end-to-end so an unclassified state surfaces for review rather than silently). The exact-key comparison (`_content_unchanged`, whitespace-trimmed equality) replaces an embedding threshold for the same-vs-different decision — *same value → never news, different value → always news* — and demands **single-field discipline** (one value per key; a volatile sibling in the same body trips a false `CHANGED`). The DUPLICATE split is that same question asked where no exact key exists to compare by text, so it is answered by the one signal that can: `sim.is_duplicate` returns a `DuplicateMatch` carrying `same_value` = the strict content signal's own verdict (`penny/database/memory/_similarity.py`). **The divergent-value rejection states the SITUATION, not an option (#1919)**: since the split, every `DUPLICATE` is a collision whose content differs, so `_format_duplicate` says three things flatly — this collection already holds an entry about that under the key `'<matched>'`, any other key collides with that same entry again, and `update_entry(key='<matched>', content=<the new value>)` lands it. The wording it replaced offered a refresh "if you have richer info", which reads as advice to weigh: measured, 4 of 5 samples filed the new value under a fresh key instead. The lead-in is gone too — calling them duplicates is the framing that sent the value somewhere else. **Why the split exists (#1919)**: before it, a cycle that re-observed what it already held under a reworded key got the recoverable rejection — an invitation to refresh or write something else — and every measured sample "recovered" by generating a DIFFERENT entry, which is correct behaviour on that surface. A cycle that found nothing new had no way to say so; the split gives it one, structurally, instead of instructing the model not to invent. **STOP**: outcomes in the declared `WRITE_GATE_STOP_REASONS` table (data — `KEY_EXISTS_UNCHANGED` + `DUPLICATE_UNCHANGED`, the two doors onto "the value was already recorded"; later stages extend the table not the code) end a **must-act (collector) run at the chokepoint**. `DUPLICATE` deliberately stays OUT of it: a divergent-value collision is news about a stored entry, so stopping on it would silence the change it carries — "the release moved to June" arriving under a reworded key must never read as nothing having happened. `collection_write` carries the STOP on `ToolResult.stop` (only for a collector-scoped write — chat gets the same enumerated text but *never* a loop-stop, chat isn't must-act); `_execute_single_tool` threads it onto `ToolCallRecord.stop_reason`; `Collector.should_stop_loop` exits on it (no trailing `done()` required — a `done()` after STOP is an unreached no-op); `_run_cycle` counts it a clean close (cursor commits); and `Collector._cycle_result` stamps `run_reason` = the declared stop reason with `RunOutcome` = `no_work`/`worked` by whether any state changed. **Renders** detect a STOP structurally (`_ended_via_write_gate_stop` — a clean `no_work`/`worked` outcome with no `done()` call, so no new column): `render_run_record` shows `[target] <stop reason>` + the stop-point trace (no ⚠ flag — a clean stop is healthy), and `render_run_calls`'s conclusion reads `stopped: <reason>` instead of `done:`.
- **An aborted run names its terminal cause (#1909)**: a model call that comes back with nothing usable — a timeout, a connection or server error, or a reroll budget every draw was discarded on — RAISES `ModelCallAbortedError` out of the invoke layer (`agents/models.py`; an error carrying a message is an exception, never a sentinel returned in the success channel). `_run_agentic_loop_body` catches it at the one call site and closes the run with the same `AGENT_MODEL_ERROR` response it always did, now carrying `ControllerResponse.abort` — a `RunAbort` of the step index, the tool the last SUCCESSFUL step executed, and the error's class + message — and `Collector._no_done_reason` renders that as the run's stamped `run_reason` (`[target] model call failed at step 5 after read_similar: LlmTimeoutError: …`) in place of the generic `cycle ended without a done() call`. Why it needs its own carrier: a call that raises never reaches the client's persist step, so it writes **no `promptlog` row** — the outcome the collector stamps was the only surviving trace, and it said nothing, leaving the whole class diagnosable only by exclusion (31 of 75 measured collector cycles). Observability only — no retry, cycle-shape, notify or outcome-classification change; the aborted response still carries no tool calls, so its `RunOutcome` is the `failed` bail it always was. The one gap this cannot reach is a run whose FIRST call fails (no row exists to stamp); the eval harness's per-sample penny log covers that side.
- **Emission provenance (#1568)**: every autonomous send names its mechanism end-to-end — the reverse index (emission → mechanism), so "which mechanism sent this?" is a read, not a diagnosis. `send_message` enqueues with the bound collection (`send_queue.collection`); the `SendQueueDrainer` carries it onto the delivered `messagelog` row's `mechanism` at delivery (`send_response(mechanism=…)` → `_log_and_send` → `log_message`). A **direct reply** (a chat turn with a live triggering user message) stamps `mechanism = NULL`. **No spam-prevention mechanism lives at the send layer** (code-owner decision on the #1568 revision): the structural no-news class is already suppressed by the write-gate STOP (`KEY_EXISTS_UNCHANGED`) before the notify steps run, and the observed duplicate-message class is model-composed prose a content fingerprint cannot catch. **Read side — provenance renders where the message renders, no resolver tool** (second code-owner revision: a bespoke resolver for a join the row carries is a rendering bug wearing a tool costume, and its `message_id` argument was rendered on no surface the model reads): recent autonomous sends are ambient in the **self-state header's activity block** (`sent · <when> · <mechanism> — "<snippet>"`, interleaved with runs + mutations; direct replies excluded — zero calls); older sends render their mechanism **inline on every `penny-messages` read** (`MessageLogMemory._render_content`: `N. [<stamp>] (sent by <mechanism>) <content>`; a NULL-mechanism row renders byte-identical to the unmarked pre-provenance shape), so pulling a message by relevance or recency IS resolving its source — one call; the second hop ("what created that watch?") is `memory_metadata("<mechanism>")`, whose existing #1566 block renders created-when / by-run / from-message with the quoted ask.
- **Queued sends, not dropped**: nothing that writes an autonomous message owns *when* it goes out — `CollectorNotifier.queue` enqueues into `db.send_queue` (after the refusal/no-recipient/mute delivery gates) and the deterministic `SendQueueDrainer` (an idle-gated `PeriodicSchedule`, no LLM) delivers the oldest pending row once the flat-interval cooldown clears: `now - last_penny_message ≥ SEND_COOLDOWN_SECONDS` (bypassed when the user has spoken since Penny's last message — the send is then conversational). So a cooldown *delays* a message instead of losing it, and timing lives in Python, not model-space. **The second bypass is the row's own `origin` (#1939)**: a message from a cycle the USER triggered (`run_for` → `CycleTrigger.ON_DEMAND`) is conversational in exactly the sense the user-spoke-since bypass already means — they are waiting on it — so it goes out on the next drain tick, while a cadence cycle's message rides the full cooldown. The lane is a READ of what set the cycle running, threaded as a parameter (`_execute_cycle(trigger=…)` → `_notify_if_due` → `notify` → `queue` → `enqueue(origin=…)`), never re-decided from the content; a muted user, a refusal or a missing recipient still decline either way, since the lane says WHEN a message goes out and not WHETHER. Since #1911 there is no `send_message` TOOL at all: the collector was its only customer, and a cycle no longer messages anybody — the gate and the enqueue moved whole into `penny/notification.py`. **Message validity vs. delivery decisions are still split by where each runs**: a half-formed body (blank / punctuation-only, bare URL, bail-out phrase, an unfinished ellipsis+?/! **tail** like `"Hi there! ......???"`, or an ellipsis-truncated tail) is refused by the notify draw's own acceptance rule — so it is RE-DRAWN on the unchanged context rather than queued and rejected later — and re-validated at the queue through the same `SendMessageArgs` model, while refusal / no-recipient / mute are no-op delivery declines that need runtime state. Both read the shared `half_formed_send_reason` (in **`penny/text_validity.py`** — a dependency-light leaf, so `tools/models.py` can import it without closing an import cycle through `penny.database`), the same rule the run-health classifier flags `⚠ HALF-FORMED SEND` on, so what Penny refuses to send and what she flags as a regression are one definition. **The send gate judges the message AS A WHOLE, not on a substring hit** (#1386): a substantive, deliberate message that merely EMBEDS a degenerate fragment mid-text (a message quoting the bad send it observed) is a complete message and is delivered — catching an in-flight collapse in the model's *own* output stays the **agent-loop reroll guard's** job (`is_degenerate_run` on raw output). The strict SUBSTRING poison check stays on `degenerate_reason` (the corpus write gate — a collapse run anywhere corrupts a stored entry). `degenerate_reason`/`is_blank`/`is_unfinished_fragment` and the corpus content filter live in `text_validity` too; the `database.memory` package re-exports them so its public import surface is unchanged (`objects.py` imports them directly from `text_validity`).
- **Invalid draws are rejected, not recovered (#1839)**: the conversation state machine makes a turn's valid terminal states decidable, so a draw that was meant to be a tool call and is not one is an **invalid draw** — discarded and re-rolled on the unchanged context, exactly like a punctuation collapse or a leaked Harmony envelope (the shared `Agent._invoke_nondegenerate` machinery and its one `DEGENERATE_REROLL_ATTEMPTS` budget). It never enters the conversation: no stray output, no nudge user-turn, no marker on the run's prompt rows, so **a recovered run is indistinguishable from a clean one because recovery no longer writes into the run**. In the LEDGER it stays visible — the discarded draw is persisted whole (its context AND its own response) before it is inspected, so a re-rolled step is two `promptlog` rows carrying the same context; that repeat is what the eval harness's loop-health advisory reads (#1841), and the discarded draw's response is what the failure-cause pathology scan reads. After the budget the turn fails via the existing aborted-run path. What each shape counts as invalid is declared per agent as data (`Agent.invalid_draw_conditions`, one `(ConditionKey, predicate)` entry each, tried in order, consulted only when the draw carries no tool calls) — a new one is one more entry, never a branch in the loop. **The collector's invalid case is ANY non-tool-call draw**: prose, an empty body, or the argless `done()` composed as a JSON envelope that never reached the tool channel (gpt-oss's Harmony fallback, #1569; recognised by `is_done_json_bail` so the discarded draw is logged as `DONE_JSON_BAIL` rather than the terminal `TEXT_INSTEAD_OF_TOOL`, which is keyed to the STATE — no call was made — and never to anything the prose says). That subsumes what the collector's own response-shape chain used to say, so `BackgroundAgent` composes none and the collector-flavoured empty-content nudge retired with it. **Chat's invalid case is a draw that is not a REPLY** — a plain conversational reply IS chat's valid terminal state — so `CALL_AS_TEXT` (the full serialized call, or real args carrying the framework's `reasoning` field), then `CALL_FRAGMENT_REPLY` (the mangled remainder, incl. the bare `{}` tail of a forced call attempt, #1570/#1732), then `EMPTY` (**#1937** — a draw carrying fewer than `MIN_RESPONSE_LETTERS` letters once `<think>` blocks are stripped: blank, separators-only, a lone emoji). EMPTY is tried LAST because the `{}` tail has no letters either and `CALL_FRAGMENT_REPLY` is its truer name. It was the last invalid-output class still handled on the VISIBLE path: `EmptyResponseValidator` appended the empty assistant turn plus a nudge user-turn into the conversation, so a draw that came back empty after a discarded one lost the model's in-flight intent and left residue in the context — **the accepted trade-off is that an unchanged-context reroll cannot unstick a deterministically-empty draw; three burns then abort via the #1909 path, which is the honest end.** The nudge constants that used to teach these families (`TOOL_FORMAT_NUDGE` / `COLLECTOR_TOOL_CALL_NUDGE` / `COLLECTOR_DONE_JSON_NUDGE` / `CHAT_CALL_AS_TEXT_NUDGE`, then `CONTINUE_NUDGE` / `FINAL_STEP_NUDGE` + `build_strong_nudge`) and the validators that appended them are **deleted** — and with the empty draw went the LAST producer of a `Retry` nudge, so `Retry` carries none at all now. So is the run-end extractor's `BAILED` gate (`_has_text_bail_nudge`), which keyed on markers that can no longer occur. What still answers an empty FINAL answer is the loop's own honest close (`_empty_content_fallback`): a tools-stripped step whose hallucinated call is repaired away leaves nothing to say, and the run reports that rather than asking again.
- **A coherent but WRONG tool call still gets an error tool response**: the model acted, so the correction goes back as that call's failed result (`success=False`), and the model sees the failure narration (`You tried to use \`<tool>\` but it didn't work: (<tool> result)\nError…`) and retries — never a user-turn nudge. This is what survives the invalid-draw rejection above, because it is not a draw with no call. The **premature-`done` guard** (`PrematureDoneValidator`, the collector's one run-shape validator) is this case: a first-move `done()` — before any read/write/browse — is the `⚠ NO WORK DONE` bail (the model declaring "no new matches" without checking), so it's refused with a `COLLECTOR_PREMATURE_DONE_REJECTION` tool-result and the loop continues (a failed `done` doesn't stop it; see `should_stop_loop`); the model must make a real tool call first. Premature only when this step's calls are all `done` AND no non-`done` call has run yet (the same "no real work" test as run-health `bailed`); a batched `[log_read, done]` or a `done` after any read is honoured. Bounded by `max_steps` — on the final step the `done` closes the cycle. The send-tool's half-formed/truncation gates are this case on `send_message`.
- **A learn turn that produced no skill FAILED (#1839)**: the `learn` state has exactly ONE valid terminal state — a skill in the registry — and the machine decided the turn was a learn turn *before* it ran, so at run end this is a deterministic read of two recorded facts, not a judgment. When a learn-state chat run's run-end extraction returns `NoExtraction` (ANY gate), `ChatAgent._enforce_learn_terminal` **throws the model's reply away** and returns `PennyResponse.LEARN_NOTHING_LEARNED` instead — the observed harm being a reply that offers to set running a routine that was never learned. The tool calls travel with the failure so the run record stays complete, and the machine is left exactly where it stands: **parked in `learn` with its anchor**, so the user's retry is the existing learn→learn re-demonstration edge and a bail is still the break-out to idle. Extraction SUCCESS — and any turn where extraction never ran at all (a vision turn, a run that never reached its text branch and already carries its own honest failure) — takes today's path byte-identically.
- **Degeneracy guard (discard-and-reroll)**: gpt-oss:20b occasionally collapses mid-generation into a run of `.`/`…`/`?` ("...??…?..") when its context grows large — measured with a sharp onset around ~4K prompt tokens (a short abortive output, ~59 tokens), most often landing inside a tool-call argument.  The collapse is *poison*: it corrupts the entry/message it lands in, and once fed back into the conversation the next step is ~4× more likely to collapse too.  `Agent._invoke_nondegenerate` (in `agents/base.py`) checks every raw model output — text content, serialised tool-call arguments (the validation chain never sees tool-call responses; they short-circuit), **and** tool-call names — via `is_degenerate_run` / `is_degenerate_tool_name`, and on a hit **discards** the output (never appending it — appending is the contagion path) and re-rolls the *unchanged* context up to `DEGENERATE_REROLL_ATTEMPTS` (3); if it still can't get a clean draw it returns `None`, throwing out the run rather than acting on poison.  The name check applies only to a name that is **unregistered AND collapse-shaped** (`Functions?????`, `funcs.done?` — before the guard, those flowed to a tool-not-found error that kept the poison in context); an unregistered but plausible identifier (a near-miss like `collection_metadata`, or a Harmony-token-wrapped valid name — a repair case for the future Harmony strip, not poison) keeps the executor's tool-not-found path with its "Did you mean X?" hint.  The detector is also folded into `degenerate_reason`, so `collection_write`/`update_entry`/`send_message` refuse poison content — nothing degenerate reaches `memory_entry`/`messagelog` even if the loop guard is bypassed.  The regex is tuned against the prompt-log corpus for zero false positives on legitimate punctuation ("Wait... what?!", code `...`).  Historical `promptlog` rows keep their poison (audit trail; never re-fed to the model).  Named `DEGENERATE_OUTPUT` in the condition catalog.  Since #1839 this machinery is shared with the whole **call-shaped-text family** (see the invalid-draw bullet above): a transport artifact and a shape violation are both draws that must not enter the run, one budget, one warning that names which condition tripped
- **Leaked Harmony-envelope guard (discard-and-reroll)**: the sibling of the degeneracy guard, sharing its exact discard-and-reroll machinery.  Some remote OpenAI-compatible backends serving gpt-oss (non-Ollama runners) fail to parse the Harmony tool-call envelope, so the *whole call* leaks into `message.content` as literal control-token text (`<|start|>assistant<|channel|>analysis to=functions.browse code<|message|><|call|>`) with `tool_calls` empty — nothing downstream catches it and a chat text turn would deliver the raw envelope to the user verbatim.  `Agent._invoke_nondegenerate` (helper `_unusable_output_condition`) checks every raw output for the transport artifacts and — when the draw carries no tool calls — for the agent shape's declared `invalid_draw_conditions` (#1839), returning WHICH condition tripped so the shared reroll's warning names it honestly.  On a leak it **discards** the output and re-rolls the *unchanged* context (the leak is intermittent — a fresh draw usually comes back clean), aborting the run after `DEGENERATE_REROLL_ATTEMPTS` rather than shipping raw tokens.  **Reject + reroll, never reconstruct** — parsing the envelope grammar ourselves would be brittle and redundant against the runner's own parser.  Sibling of `strip_harmony_control_tokens` (`llm/models.py`), which repairs a leak in the tool-call NAME field; this catches the whole call leaking into content, which the name path never sees.  Detector `has_leaked_harmony_envelope` in `text_validity.py` (keyed on Harmony sentinels, zero-false-positive discipline); named `TOOL_CALL_LEAK` in the condition catalog.  Live-model contract: `tests/eval/test_harmony_leak_recovery.py`; mechanism pinned in `tests/agents/test_agentic_loop.py`
- **Two agent shapes**: ChatAgent (turn-driven, user-facing, full lifecycle + read tools) and Collector (single dispatcher across all collections, scoped read + entry-mutation surface — no lifecycle tools, #1556).  These are the only two run entry points: a chat turn and a collector cycle
- **Priority scheduling**: SendQueueDrainer → Collector dispatcher (Collector returns False when no collection is ready, so the scheduler skips it)
- **Global idle threshold**: Single configurable idle time (default: 60s) controls when idle-dependent tasks become eligible
- **Background cancellation**: Foreground message processing cancels active background tasks (`task.cancel()`) to free the LLM immediately; cancelled work is idempotent and retried next cycle
- **Commands don't interrupt background**: Slash commands run cooperatively without cancelling the active background task
- **Vision captioning**: When images are present and `LLM_VISION_MODEL` is configured, the vision model captions the image first with a vision-specific system prompt, then a combined prompt is forwarded to the text LLM. Search tools are disabled for image messages
- **Image side-channel**: Images never travel through the model. The browse tool decodes each page's image (base64 data URI from the extension), stores the bytes in the `media` table with an embedding of the page title+URL, and the agent loop carries no attachments. At egress (`send_response`), the outgoing text is embedded once (reused for the `penny-messages` log) and `MediaStore.select_image` attaches the most relevant image: the cited page's own capture when the message links a source (exact URL → same domain, both deterministic), else a jittered pick among the top-K embedding-nearest (jitter only on this embedding fallback, so a magnet image can't repeat). No floor, so a reply carries an image whenever one matches (a tangential or funny mismatch beats no image — confirmed product behavior: every message gets an image). **Generated images take a deterministic path with precedence over that ladder** (#1564): the `generate_image` chat tool stores the drawn image with an embedding of the description and stamps the row's id onto `ToolResult.media_id`; the loop threads it onto `ControllerResponse.generated_media_ids` and `send_response(media_ids=...)` fetches **exactly that row** by id and attaches it to the mirror-back reply — the fuzzy ladder doesn't run for that reply (previously the drawn image was fuzzy-matched like everything else, giving it only ~1-in-K odds of landing on its own reply). The embedding keeps the drawn image in the nearest-image pool for future replies. This whole scheme replaced a model-carried `<media:ID>`/inline-URL token scheme that couldn't reliably thread image references through multi-page replies
- **Channel abstraction**: Signal and Discord share the same interface; easy to add more platforms
- **Async throughout**: asyncio, httpx.AsyncClient, openai.AsyncOpenAI, discord.py
- **Host networking**: Docker container uses --network host for simplicity (all services on localhost)
- **Pydantic everywhere**: All external data validated with Pydantic models
- **Table-to-bullets**: Markdown tables converted to bullet points in Python (saves model tokens vs. prompting "no tables")
- **Normal casing**: All user-facing strings (status messages, error messages, acknowledgments) use standard sentence casing — not all lowercase
- **Memory framework (Stages 1–5, 9, 10)**: A unified data primitive — *memory* — with two shapes (collection and log) and one access class `MemoryStore`. Collections dedup on write via a three-signal disjunction (key TCR, key cosine, content cosine — each with strict and relaxed thresholds in `PennyConstants`). Any strict hit, or any two relaxed hits, rejects the write. Logs append without dedup. Stage 2a added 21 model-facing memory tools (`memory_tools.py`). Stage 3 added `build_recall_block` (`recall.py`) — assembles ambient recall context for the chat agent's system prompt by dispatching each active memory by recall mode (`recent`/`relevant`/`all`); paired logs (`user-messages` + `penny-messages`) merge chronologically into a single Conversation section. **Polymorphic `Memory` objects + system-log facades**: the memory layer is a class per shape/backing (`penny/database/memory/`). `db.memory(name)` is the single dispatch — it returns a `Collection` or `Log` (both `memory_entry`-backed, the native store on the base) or a read-only facade, and every tool/recall/addon caller operates on that object polymorphically (wrong-shape ops refuse via base no-ops; nothing branches on a name or shape). `user-messages`/`penny-messages` are `MessageLogMemory` facades over `messagelog` (the object overrides the row primitives to read by direction, synthesizing `MemoryEntry`; a message has two authors — the user/incoming or Penny/outgoing; `append` refuses) and `collector-runs` is a `RunLog` facade over `promptlog` (renders each completed run as a record; `append` refuses) — no duplicated `memory_entry` rows, and the facade marker rows are seeded by migration so dispatch finds them. The cursor *read* logic lives on the `Log` base, uniform across backings; the reader's pending/commit cursor lifecycle stays in `LogReadTool`. `browse-results` is the one remaining real memory log (the browse tool writes it; it has no canonical table behind it). `messagelog.embedding` (for `read_similar` over messages) is filled by the startup backfill, which vectorizes any embedding-bearing table — nothing is copied between tables. Author is passed explicitly as a constructor argument or method parameter — write-capable tools take `author: str` at construction (`build_memory_tools(db, embedding_client, author)`), `BrowseTool(..., author=...)` is built per-agent with `author=self.name`, and `channel.send_response(..., author=...)` requires callers to pass it. No ambient/contextvar state. Embeddings are computed at write time (not lazily) so similarity reads work the moment a memory is reconfigured. `db.memories` replaces the per-domain stores that agents will be ported onto in subsequent stages. See `docs/task-framework-plan.md` (design) and `docs/memory-implementation-plan.md` (staged rollout)

## Database Migrations

File-based migration system in `database/migrations/` (currently 0001–0025):
- Each migration is a numbered Python file (e.g., `0001_initial_schema.py`) with a `def up(conn)` function
- Two types: **schema** (DDL — ALTER TABLE, CREATE INDEX) and **data** (DML — UPDATE, backfills), both use `up()`
- Runner in `database/migrate.py` discovers files, tracks applied migrations in `_migrations` table
- Runs on startup before `create_tables()` in `penny.py`
- `make migrate-test`: copies production DB, applies migrations to copy, reports success/failure
- `make migrate-validate`: checks for duplicate migration number prefixes (also runs in `make check`)
- Rebase-only policy: if two PRs create the same migration number, the second must rebase and renumber
- Run standalone: `python -m penny.database.migrate [--test] [--validate] [db_path]`

## Plugin System

`penny/penny/plugins/` holds opt-in, third-party integrations that contribute LLM-callable tools to the chat surface. A plugin is a subclass of `Plugin` (`plugins/__init__.py`) exposing `is_configured(config)`, `get_tools()`, and `close()`, with a module-level `PLUGIN_CLASS` pointing at it. `load_plugins(config)` imports each name in the `PLUGINS` env list, skips any that aren't configured (missing credentials → logged, non-fatal), instantiates the rest, and `Penny._init_plugins` collects their tools into `ChatAgent(plugin_tools=…)`. Plugins are long-lived (built at startup, `close()`d in `Penny.shutdown`).

- **zoho** (`plugins/zoho/`): Mail organisation (move/label/folder + `create_email_rule`/`list_email_rules`), Calendar (`calendar_client.py` + `calendar_tools.py`), and Projects (`projects_client.py` + `project_tools.py`) tools over the Zoho REST APIs. Reuses the `ZOHO_API_ID`/`ZOHO_API_SECRET`/`ZOHO_REFRESH_TOKEN` triple. Datetime tools convert to UTC before formatting (`astimezone(UTC)`).
- **invoiceninja** (`plugins/invoiceninja/`): invoice + expense tools over the InvoiceNinja v5 API (`INVOICENINJA_API_TOKEN` + `INVOICENINJA_URL`).

**Email-rule data layer** (#1737): email rules are persisted to the `email_rule` table via the `db.email_rules` domain store (`EmailRuleStore` — create / list-active / mark-applied), not raw `session.exec(select(...))`. Condition/action are **typed** (`EmailRuleCondition` / `EmailRuleAction` in `plugins/zoho/rule_models.py` — optional `from`/`subject_contains`/`body_contains` and `move_to`/`label`, each `extra="forbid"` + at-least-one-field), so `create_email_rule` rejects an unknown or empty shape at the tool boundary with an actionable, field-naming message rather than absorbing an arbitrary dict; the row stores their serialized JSON. `EmailRule.user_id` was dropped (single-user Penny — migration 0099); the `provider` column stays (`PennyConstants.PROVIDER_ZOHO`, a future non-Zoho backend gets its own tag). **Known gaps** (tracked as follow-ups): the rules are persisted but **not yet applied automatically** — `plugins/zoho/rules.py` (`RuleMatcher`/`RuleExecutor`/`apply_email_rules`) is the intended application engine but isn't wired into any scheduler, and the model-facing tool surface has no `tests/eval/` contract yet.

## Extending

- **New tool**: Subclass `Tool` in tools/, implement `name`, `description`, `parameters`, `async execute()`, add to agent's tool list in penny.py
- **New channel**: Implement `MessageChannel` ABC, create models, add to `create_channel()` factory
- **New agent type**: Subclass `Agent`, implement `execute()` for background tasks or custom `handle()` for message processing
- **New command**: Subclass `Command` in commands/, implement `name`, `description`, `execute()`, register in `create_command_registry()`
- **New schedule type**: Subclass `Schedule`, implement `should_run()`, `reset()`, `mark_complete()`
- **New LLM backend**: Any OpenAI-compatible endpoint works via `LlmClient` — just set `base_url` / `api_key`. Non-OpenAI-compatible backends can implement the `LlmClient` interface directly (`async chat()`, `async embed()`)

## Test Infrastructure

Strongly prefer end-to-end integration tests over unit tests. Test through public entry points with mocks for external services. Prefer folding new assertions into existing tests over adding new test functions — only add a new test when no existing test covers the relevant code path.

**Mocks** (in `tests/mocks/`):
- `MockSignalServer`: WebSocket + REST server using aiohttp, captures outgoing messages and typing events
- `MockLlmClient` (`llm_patches.py`): Monkeypatches `openai.AsyncOpenAI` so `LlmClient` returns canned `LlmResponse` objects; configurable via `set_default_flow()` or `set_response_handler()`; tracks `requests` and `embed_requests` for assertions. Which micro-context flavours a custom handler CLAIMS (rather than letting the built-in intercept answer) are keyword arguments on `set_response_handler` — `answers_micro_contexts` (default `True`) and `answers_state_classifier` (default `False`) — plain parameters, not attributes smuggled onto the handler function, so a misspelt flag is a signature error instead of a silently-ignored one

The fixture and both schemas live in one place (conftest), not duplicated per file.
- `test_db`: a per-test SQLite **path** (string) pre-seeded with the full post-migration schema — used by fixtures/tests that construct their own `Penny`/`Config` and need a db_path, not a `Database`
- `require_memory(db, name)` (a plain function, not a fixture): `db.memory(name)` narrowed to a non-`None` `Memory`. `db.memory` returns `Memory | None`, which a test seeding or reading a memory it just created never wants — this asserts presence, so a typo'd or since-renamed name fails naming the name instead of raising `AttributeError` on `None` frames later. It is also what keeps `unresolved-attribute` an **error** in `pyproject.toml`: with the Optional noise narrowed and SQLModel column expressions on `col()`, the rule's remaining hits are calls to methods that don't exist

**Why they're fast — schema templates** (`tests/schema_template.py`): building a test DB's schema is expensive (`create_tables()` issues the DDL for every table, `migrate()` replays the whole ~100-file migration stack — ~110ms together), and the suite builds hundreds of fresh databases, which was the single largest chunk of `make check`. The schema is deterministic, so the module builds each template **once per process** and the `db` fixture hands out ~1ms file copies (byte-identical to building from scratch, so tests see no behavioural difference). **Don't hand-roll `Database(path)` + `create_tables()` + `migrate()` — take the `db` fixture instead** (with `@pytest.mark.bare_db` if you need the bare schema), so a test writer gets the fast path by default rather than by remembering a rule. The building-block functions `schema_only_db(path)` / `migrated_db(path)` back the fixture and are there for the few helpers that genuinely can't use it — a custom filename, a `runtime=` override, or more than one database in a test. This is what cut `make check`'s test phase from ~52s to ~18s.

**Test Timing** — never use `asyncio.sleep(N)` in tests:
- Use `wait_until(lambda: <condition>)` to poll for expected side effects (DB state, message count, etc.)
- `scheduler_tick_interval` is set to 0.05s in test config (vs 1.0s production) so scheduler-dependent tests complete quickly
- `running_penny` detects WebSocket connection via `signal_server._websockets` instead of sleeping
- For negative assertions (nothing should happen), verify immediately — don't sleep to "make sure"

**Test Flow**:
1. Start mock Signal server (random port)
2. Monkeypatch the OpenAI SDK (via `mock_llm`)
3. Create Penny with test config pointing to Signal mock
4. Push message through mock Signal WebSocket
5. `wait_until` the expected side effect (outgoing message, DB change, etc.)
6. Assert on captured messages, LLM requests, DB state

**Performance**: The non-eval suite runs in ~18s. Two levers: `scheduler_tick_interval` is 0.05s in tests (vs 1.0s prod), and the schema templates (above) build the DB schema once per process and copy it per test instead of re-running `create_tables()` + all migrations each time (which was the single largest chunk of the runtime — ~34s).

**Scoring is graded, not binary.** A chat scorer returns either failure strings (binary:
empty = pass) or a list of `Check`s (partial credit: the sample scores passed / applicable;
the case metric is the mean). Prefer graded `Check`s for a multi-step contract — each
expected tool call and outcome is its own named check, so the report shows exactly which
expectation missed (e.g. a discuss turn answered from ambient recall dings the
"memory_metadata called" check instead of hiding behind a green PASS). A `Check` carries
three axes beyond its `ok`: `scored=False` (advisory flavour — renders but out of the score),
an optional `rationale` (the observed-vs-expected note rendered beside the outcome —
"expected 3 reads, saw 1" instead of a bare ❌), and the not-applicable third state
`Check.na(...)` (`ignored`, rendered as ➖) — excluded from the graded denominator when a
sample's branch never exercised it, neither pass nor fail. `tool_not_called(db, name)` is the
negative-constraint counterpart to `tool_was_called` for avoided-action checks.

**The RESULT line reports both metrics; a green-via-recovery sample renders "fragile."** Each
case prints `mean … · all-pass K/N` — the partial-credit mean (what the case gates on) beside
the strict all-pass count (samples that passed EVERY applicable check). In the per-sample
report a sample that passed but only after the loop refused/recovered a tool call (derived from
the promptlog via `sample_is_fragile` / `tool_call_rejected`, no new model judgment) is marked
`✅ PASS · fragile`, so real-but-shaky reads distinctly from clean green.

**A re-rolled draw is read from the REPEATED CONTEXT, not from a marker (#1841).** The uniform
loop-health advisory every case reports (`routing_clean` in `tests/eval/conftest.py` — the
`Check(..., scored=False)` one) used to match the literal text of the two bail nudges #1839
deleted, so after that change its bail half could never fire again. What a discarded draw still
leaves is the **second draw itself**: `Agent._invoke_nondegenerate` re-calls the model on the
*unchanged* message list and `LlmClient.chat` persists every completed draw before returning, so
a re-rolled step is two `promptlog` rows carrying byte-identical `messages` — while an ordinary
step's context has grown by the turns the previous step appended and can never repeat.
`MicroContext._draw_clean` re-draws the same way (and its outer shape-violation re-draw mints a
fresh run id each attempt, so the read keys on the repeated CONTEXT alone, never on the run), so
the ONE read — `draw_rerolled` → `_same_context_drawn_twice` — covers the main loop and every
micro-context. Keying on the repeat rather than on which conditions the loop rejects is what
keeps it honest for an `invalid_draw_conditions` entry nobody has added yet; the retired nudge
markers stay as a **legacy leg** so a promptlog written before #1840 still reads. **Declared
limit**: a draw the backend refused to parse (`LlmToolParseError`) raises before the client
persists anything, so that one re-roll leaves no row and no promptlog read can see it.

**Presenting eval runs on a PR (the report-as-comment process).** The harness emits a
verbatim per-case markdown report when `EVAL_REPORT_DIR` is set (`make eval` passes it
through). The **PR body stays a stable description**; **every tweak + re-run pushes the
commit and ADDS A NEW COMMENT** with that run's report — never rewrite the body, never
overwrite a prior comment — so the iteration history (each review round's before/after)
survives. See `docs/agent-task-workflow.md` §4.

**Per-run artifacts + the required lever (#1692).** When `EVAL_REPORT_DIR` is set, the run
also writes three durable artifacts into that directory (beside the `<case_id>.md`
transcripts), emitted by `penny/tests/eval/artifacts.py`: a `manifest.json` (the run's
input identity — commit SHA, dirty-diff filename, model + embedding model + `EVAL_SAMPLES`,
and the run's one-line **lever**), a `dirty.diff` (the working-tree diff saved verbatim,
only when dirty), and a `results.jsonl` (one mechanically-diffable record per case: run id,
case id, family tag, mean, all-pass rate, per-check outcomes, N, timings). The manifest also
renders as a markdown header (`commit · model · N · lever`) atop each `<case_id>.md` report.
**The lever is required**: `make eval` forwards `EVAL_LEVER` (the run's hypothesis, e.g.
`EVAL_LEVER='moved instruction X from skill to prompt'`) alongside `EVAL_REPORT_DIR`, and a
report run with no lever **fails fast** with an actionable message before any sample runs —
the lever is what makes a score shift attributable to the change that caused it. The commit
SHA + dirty diff are computed **host-side** in the Makefile (`EVAL_COMMIT`/`EVAL_DIRTY_DIFF`)
because `.git` is not mounted in the eval container. The `family` tag defaults from the test
module name (`test_<x>` → `<x>`) or is set explicitly via a `family=` arg on a runner call.

**Per-sample penny logs (#1909).** Beside each sample's DB (`<case_id>-<n>.db`) the harness
writes that sample's own logger output as `<case_id>-<n>.log` — the fourth durable per-sample
artifact, alongside the DB and the `<case_id>.md` transcript. A model call that FAILS raises
before the client's persist step, so it writes no promptlog row: everything the run said about
the failure ("LLM chat failed", a timeout attempt, each discarded draw's reroll condition)
existed only as logger output, which pytest captures and then discards for every sample that
passes — the same failure class #1909's `RunAbort` covers from the DB side, and the only carrier
for a run that died on its FIRST call (no row exists to stamp). `sample_logging(db_path)`
attaches a DEBUG `FileHandler` to the `penny` logger for the span of ONE sample (so every line
is attributable, and the handler + raised level are both gone afterwards), and every runner
stands its sample up through the `eval_penny(config, server)` wrapper rather than
`run_penny_with_server` directly — one seam that covers the runners that exist and the ones
added later, **held by a structural pin** rather than by convention (`make check` parses the
harness's own AST and refuses any caller of `run_penny_with_server` but `eval_penny`; a runner
that bypasses the seam is byte-identical in every other respect and its only symptom is a log
file silently never written — measured on the multi-cycle collector runner, which was written
before the seam existed and survived a rebase still bypassing it). Mechanical and unfiltered: no
content filter, and the path is derived from the sample's own `db_path`, so off-report runs write
it into the throwaway tmp dir.

**Failure-cause partition (#1695).** Every FAILED sample is tagged with its cause, derived
STRUCTURALLY (never a model judgment): **harness** (a `TimeoutError`), **pathology** (a known
model pathology fired), or **behavioral** (the model simply got it wrong — the real signal the
loop chases). Pathology is read post-hoc off the persisted promptlog by `run_exhibited_pathology`
(in `tests/eval/conftest.py`), which scans each row's RESPONSE with the SAME `text_validity`
detectors the agent-loop reroll guard runs live (`Agent._unusable_output_condition`): a punctuation
collapse (`DEGENERATE_OUTPUT`), a leaked Harmony envelope (`TOOL_CALL_LEAK`), a collapse-shaped
tool NAME, or a bare call-fragment reply. **The distinguishing rule** — an eval `_Inject*` recovery
trigger is NOT a pathology failure: an injected bail is returned as a synthetic `LlmResponse` that
bypasses the persisting client, so it never lands in a persisted `response`; reading only the output
(never the input `messages`) makes the scan structurally immune to it, so a `bail_injected` sample is
tagged pathology only if the LIVE model additionally produced its own poison. Cause ordering:
pathology outranks a timeout (the poison is the root cause, the timeout its symptom), then harness,
then behavioral. `classify_cause` (pure, in `artifacts.py`) encodes the partition. The runner stamps
each sample's `cause`, and the `CaseArtifact` (`results.jsonl`) carries `sample_causes` (per-sample,
aligned with `sample_scores`; `null` = passed), `cause_counts`, and `pathology_excluded_mean` — the
honest read of model behaviour, the mean over every sample that is NOT a pathology failure, so a
degeneracy spike can't sink a case's score while its raw mean + pathology count stay visible. The
console RESULT line carries a second line with the same tally (`render_cause_summary`, single-sourced
so the PR-comment renderer renders one shape). Deterministic contracts (no live model): the pathology
scan + stamping + render in `tests/test_eval_harness.py`, the artifact fields + pure classifier in
`tests/eval/test_artifacts.py`.

**The nudge-loop / bare-`{}` boundary (#1732).** A #1731 spiral — a chat browse-extract run that
looped on parse-failure recovery nudges (re-browsing the same page each cycle) and died at the turn
timeout with a bare `{}` reply — was tagged **harness** (a `TimeoutError` ended it) but the *loop*,
not the clock, was the event. Two boundary questions, resolved to the narrowest honest rule:
- **The terminal `{}` IS pathology.** `is_call_fragment_reply` (in `text_validity.py`, the *shared*
  detector the live reroll guard and the scan both use) was widened to catch a reply that is nothing
  but an empty JSON object (`{}` / `{ }` / `{}\n`, `_EMPTY_OBJECT_REPLY_RE`) — the degenerate tail of
  a forced tool-call attempt leaked into the text channel. The old `{"`-prefix gate missed it (an
  empty object has no string key). Anchored to the whole stripped reply → zero-false-positive (a reply
  *about* `{}` carries prose; Penny never SENDS a bare `{}`), and the full call envelope
  `{"name":…,"arguments":…}` stays excluded (its teaching validators own it). Widening the *shared*
  detector — not just the scan — keeps #1695's "same detectors live and post-hoc" invariant: the live
  chat guard now discards+rerolls a `{}` reply too (a strict improvement — it was being delivered).
- **Nudge frames are NOT counted.** Repeated recovery nudges are *input* messages; counting them would
  forfeit the output-only injection-immunity (an `_Inject*` case produces exactly one live nudge by
  design, so naive counting would false-tag its fail path pathology) and would need an arbitrary
  threshold. The nudge loop is a *symptom* whose *cause* is the model's own fragment OUTPUT — the
  terminal `{}` the widened detector now catches — so classifying on that output tags the spiral at the
  root while the output-only immunity holds. A count threshold and threading the runner's
  `bail_injected` into classification were both considered and rejected (arbitrary cap / classifier↔runner
  coupling for a case the output scan already handles). Cause ordering is unchanged: pathology still
  outranks the timeout, so the spiral reads pathology, not harness.

**Regression-aware reports + thinking at failed turns (#1693).** When `EVAL_BASELINE` names a
prior run's report directory (or its `results.jsonl`), the per-sample report diffs each graded
check against that prior run and marks a NOW-FAILING check **REGRESSED** (`❌ 🔻 REGRESSED`) when
it was FULLY GREEN there (`passed == total`) — a flip, distinct from a check that was already red.
The flip is per-check, per-`(case_id, label)`, reading the prior `CaseArtifact` records unchanged
(`penny/tests/eval/baseline.py`); the regressed check names its baseline run inline in the checks
legend. `EVAL_BASELINE` is forwarded into the container like `EVAL_REPORT_DIR`/`EVAL_LEVER`; unset
(or a missing file — a first run) → no REGRESSED marks, no error. The report also lifts each LLM
call's **thinking** (already persisted on `promptlog.thinking`) into a collapsed `<details>` at
the failed/regressed **tool-call** turns only — passing turns are omitted so the comment never
bloats. On a first run with no baseline, thinking still renders at failed turns.

**Run-comment assembler (#1717).** The per-run artifacts and per-case transcripts all exist after
a run, but no step composes them into THE ONE markdown comment the protocol
(`docs/eval-report-format.md`) specifies. `penny/tests/eval/assemble.py` is that step: given a
completed run's report directory it emits one document in the spec's section order — the manifest
header (`render_manifest_header`: commit · model · N · lever), the **run totals** (the run-level
aggregate across every case — mean · all-pass · the cause tally, from flattening every case's
`sample_scores`/`sample_causes`), then one block per case: its **dual RESULT line** (mean + all-pass)
and **cause summary** (`render_cause_summary` — this is where the per-case aggregates finally render;
the incremental per-sample flow in `conftest.py` cannot, a whole-case tally not existing yet at
sample-write time), above the case's `<case_id>.md` transcript folded into a collapsed `<details>`
(its own manifest-header prefix stripped, since the assembler renders that header once atop the
comment). Pure artifact consumption — no model, no git, no network — so it's exercised by plain
(non-eval) whole-render tests (`tests/eval/test_assemble.py`), not a GPU run. Run it via
`python -m penny.tests.eval.assemble <report_dir>` (prints the comment to stdout) or
`EVAL_REPORT_DIR=… make assemble` (the same dir `make eval` wrote to). **One and only rendering
(#1753/#1759):** EVERY sample block folds whole under its banner — collapsed by default, its full
body always one click away ("default collapsed" never means the body is dropped) — identical in the
on-disk `.md` and the assembled comment. There is **no compact / banner-only form and no `--full` /
`EVAL_FULL` flag** (removed in #1759 — banner-only rendering dropped entirely). The assembler
re-normalizes each block via `report.split_sample_blocks`/`parse_sample_block`/`fold_sample`, so a
re-assembled pre-#1753 run (unfolded `#### ` failures) folds uniformly too. A passed sample carries no
cause (`_sample_cause` in `artifacts.py`), so the all-pass count is the count of `None` causes —
run totals and each per-case line are computed identically. (The header carries no `embedding`/
`prior` line — `render_manifest_header` omits them, the `prior:` line deferred per `baseline.py` —
and no gate verdict, since a `CaseArtifact` carries no `min_pass_rate`; the RESULT line reports the
two metrics the artifacts hold.)

USER turn explicitly labelled, #1759/#1773) with the check verdict on its anchor row. Whole-run /

header** carries the identity line, a one-line RESULT (mean · all-pass ·
pathology-excluded · cause tally · `families:` rollup · timings), a **gate** line per gated case
(`⚖ threshold on mean|pathology-excluded → PASS/FAIL`, from the new `CaseArtifact.min_pass_rate` /
`gate_metric`), and — in diff mode — a **flips** index (`flips: <label> ✅→❌ (s…)`, one entry per
check fully green in the baseline that failed a sample here). The flips index resolves its baseline
from the run's **durable manifest reference** (`RunManifest.baseline`, recorded from `EVAL_BASELINE`
at eval time, #1752) — NOT from a re-read of the volatile env at assemble time — so `make assemble`
renders the same flips the per-row REGRESSED badges were baked from, even when it carries no
`EVAL_BASELINE` (an explicit `EVAL_BASELINE` at assemble time still overrides, for an ad-hoc re-diff).
Additive artifact fields carry it:
`CheckOutcome` gained `scored`/`cells[]`/`rationales[]`, `Check` gained `kind`, `CaseArtifact` gained
`sample_fragile[]` + `min_pass_rate`/`gate_metric`; `RunManifest` gained `baseline` (#1752). **No artifact is committed** — the PR comment is
the durable record; all raw artifacts (manifest/results.jsonl/`.md`/`.db`/dirty.diff) stay local and
`EVAL_BASELINE` diffs those local paths (#1725 policy). Spec + worked example: `docs/eval-report-format.md`;
whole-render tests in `test_report.py` / `test_assemble.py` (+ extraction in `test_eval_harness.py`).

**Every micro-context renders as its own actor (#1773).** The v3 transcript admitted only
`browse-extract` rows, so the state classifier's draw (#1706) and the run-end skill labeller's
adjudication (#1770) were invisible — their system prompts rendered, the calls made against them did
not — and, being main-agent rows to the turn walk, their scoped slices surfaced as PHANTOM
`👤 user` steps ahead of the real one. Now the extractor (`conftest.py`) admits every micro-context
by its ledger identity and each 🧩 row is labelled with it (`🧩 state-classifier → STATE: apply`),
matching that context's system-prompt row. Where a batch splices is a declared **`MicroPlacement`** —
the causal relationship, not the agent: `DURING_CALL` (browse-extract → after the `extract=` browse
call that spawned it, the unchanged FIFO pairing) · `TURN_HEAD` (state-classifier → right after the
user turn it decided, since the classifier runs before the chat agent) · `RUN_CLOSE` (skill-namer + skill-framer →
closing the turn, after the final reply). One generic walk drains the ledger-ordered batch queue at
those anchors, so a fourth customer is a row in `MICRO_CONTEXT_PLACEMENTS`, not new code; a batch
left unmatched renders at the end rather than vanishing (collapsed never means dropped, #1753).
Deterministic — proven by whole-render tests over fixture promptlog rows, no GPU.

**A case's shared system prompt hoists under its heading (#1763).** A run's samples each carry a
system prompt, and restating every one inline made a chat beat's assembled comment 525K against
GitHub's 64K comment cap — 11 comments for one 4-case run. `report.hoist_shared_prompt_blocks`
(pure, applied by the assembler over the FINISHED document) lifts, per CASE and per CONTEXT, every
line shared by ALL that group's prompts into one collapsed `#### Shared system prompt` block under
the case heading; each sample keeps only the lines genuinely its own, with a
`_[shared block — see **Shared system prompt** above]_` marker standing where the shared text sits.
**Every shared LINE, not just the longest contiguous run** — a case's prompts differ at both ends (a
timestamp opens them, the live self-state closes them) and often mid-prompt too (a sample that
created a collection gained a line), and taking only the longest run left half the prompt inline on
exactly the cases that needed it most. Hoisting is gated on a DERIVED condition (`_worth_hoisting`:
the block stored once plus a marker per use must beat N copies), never a tuned threshold. Per case,
not per run, so a case section stays self-contained once the document is split to fit the cap; a
single-case run (no `### case` heading) treats the whole document as one section. **Nothing is
dropped and nothing is summarised** — every prompt is reconstructable, verbatim, one click from
where it applies (collapsed-never-means-removed, #1753/#1759; the failure this replaced was
*selecting which samples to post*, which is that rule broken in a new costume). Measured on the
beat-0 run: 525K → 266K, 11 comments → 6, and per-sample unique prompt text a **median of 125
bytes** (max 1,329) against a 6.4K wall — so the sample's row now shows the DIFFERENCE, which is
what a reader is actually checking. The floor is the rest: ~172K of thinking blocks and transcript
tables, one per sample and all distinct, so ~3 comments is the minimum for a 32-sample run no matter
what happens to prompts. Whole-render tests in `test_report.py`.

**Durable local artifact home (#1734).** "Stays local" means the **primary checkout's
`data/eval-artifacts/`**, not the running worktree's `data/`. The `./data` bind mount is relative
to the compose-file dir, so an eval run from a worktree would write artifacts under that worktree —
where they die when it's swept post-merge. So `make eval` / `make assemble` resolve the primary
checkout host-side (from the shared git *common* dir — identical from every worktree) and
bind-mount its `data/eval-artifacts` at `/penny/eval-artifacts`. A report run (one declaring
`EVAL_LEVER`) with no explicit `EVAL_REPORT_DIR` defaults to a run-stamped
`/penny/eval-artifacts/run-<stamp>` (= `<primary>/data/eval-artifacts/run-<stamp>` on the host), so
artifacts **survive the worktree being removed** and `EVAL_BASELINE` can point a later run at a
prior run's durable path. An explicit `EVAL_REPORT_DIR` is always honored; a lever-less iteration
run stays ephemeral (no artifacts, no lever requirement). The Makefile derives the mount at parse
time, so `make -n eval` shows the concrete `-v <primary>/data/eval-artifacts:/penny/eval-artifacts`
from any worktree.

**Posting a run: `make eval-report` one-shot + the unreviewed-run banner (#1757).** Posting a run's
report is a **one-shot**, and the debt of *not* posting is made **structural** (structural-state-over-
model-judgment, applied to the eval loop). The joint-checkpoint rule (run → post the report to the PR →
STOP for joint review before the next run) was prose-only — posting was a manual step separate from
running, so skipping it left no visible debt and nothing interrupted the next run (a real violation ran
4+ sequential report-runs without posting any). Two mechanisms:
`make eval-report PR=<n> [RUN=<run-dir-name>] [FORCE=1]` assembles the named run — default: the
**most-recent completed run** (newest dir holding a `manifest.json`) in the durable home — captures the
containerized `python -m penny.tests.eval.assemble` stdout **cleanly** (never `make assemble` piped
through stripping), posts it **verbatim** to PR `<n>` via `GH_TOKEN=$(make token) gh pr comment`, then
stamps a **`.posted` marker** (holding the comment URL) into the run dir. It **fails loudly** when `PR`
is unset, the run dir is missing, the token is empty, or the assemble output is empty; it is
**idempotent by the marker** — a run already carrying `.posted` re-posts only with `FORCE=1`, else prints
the existing URL and exits 0. And `make eval`, **before taking a GPU queue ticket**, scans the durable
home for run dirs with a `manifest.json` but **no** `.posted` and prints a **loud, multi-line banner**
naming each (`⚠ N unreviewed eval run(s) … → post each: make eval-report PR=<n> …`) — **warn, never
block** (a multi-run sweep stays possible; the debt is just undeniable). **Marker semantics**: a
`manifest.json` = a completed run; a `.posted` marker = a posted (reviewed) run; a **lever-less
ephemeral run writes no `manifest.json`** so it never appears in the banner (by design — nothing to
review). The scan/latest/banner logic is pure, plain-tested `penny/tests/eval/checkpoint.py`
(`run_dirs` / `latest_run_dir` / `unreviewed_runs` / `render_banner` + a `latest`/`banner` CLI), invoked
in-container by the recipes so it reads the mounted home; the Makefile checks the marker host-side. Both
recipes reuse the #1734 `EVAL_ARTIFACTS_HOST`/`_MOUNT` derivation, so `make -n eval-report` shows the
same `-v <primary>/data/eval-artifacts:/penny/eval-artifacts` mount from any worktree.

**Past the 64K comment cap, a run posts as MANY comments (#1808).** GitHub refuses a comment body over
65,536 characters, and `eval-report` had no split path — so an over-cap run could not be posted at all by
the supported route (`GraphQL: Body is too long … (addComment)`), and one 8-sample chat beat assembles to
~290K *after* #1763's hoisting. The recipe now stages the assembled body into `<run-dir>/comment/body.md`
and cuts it with the pure, plain-tested `penny/tests/eval/comment_split.py` (`sample_fold_segments` /
`partition_on_sample_folds` / `render_parts` / `split_run_comment` + the two guards + a CLI): **the only
legal seam is a sample-fold boundary** (`report.SAMPLE_BLOCK_START`, single-sourced with the assembler's
re-normalizer — a cut inside a `<details>` renders as broken markup), so **concatenating the parts
reproduces the document byte for byte** — nothing dropped, summarised, or re-wrapped
(collapsed-never-means-removed, applied to posting). Each part is headed `(report N of M — split for
GitHub's 64K comment cap; content verbatim)`; a run that FITS is ONE part with no header (posting is
byte-identical to before); the run header opens the document so it lands on part 1; `.posted` holds the
**first** part's URL so idempotency + the unreviewed-run banner stay honest; the budget is **~58K**, not
64K (the header, and GitHub counting differently from `wc -c`). Two loud refusals guard what is posted:
a body **opening with build noise** (`docker compose`, `GIT_COMMIT=`, `#1 [internal]` — what a hand-piped
`make assemble` publishes; it happened, and eight comments had to be deleted), and a **single sample fold
over the hard cap**, which no legal cut can shrink.

#### Every model-facing change ships a durable eval contract — validated per change, not batched

Any change that alters how the model behaves — a prompt/`extraction_prompt` edit,
a tool description, a loop/nudge/retry/validation mechanism, a tool-surface
change, **or a change to what the model READS** (how a run record, tool result,
or self-state section is rendered) — **must land with a `tests/eval/` case that encodes
the behaviour it establishes or fixes.** The eval suite is both the regression net
(a future prompt tweak can't silently undo it) and the *written contract* for what
we expect the model to do. A model-facing change without an eval contract is
incomplete — the next change will regress it and nothing will catch it.

**Validate each change as you build it, not in one batch at the end.** A multi-part
change (e.g. honest-`done()` guidance, then a structural counts line, then a flag the
self-review reads) is several independent asks of the model — each needs its own
`make eval` gate *as it lands*, because a single eval at the end can't tell you *which*
lever the model did or didn't understand. Shipping the code first and "evaluating later"
has shipped levers here that the model ignored (a phase-1 `done()` guidance scored 0/3
until its wording was sharpened — measurable only because it was eval'd on its own, with
a no-change baseline to beat). Run a **baseline first** when you can (the change vs. its
absence) so the eval shows the lever is load-bearing, not just that the case passes.

**Changes to what the model reads get a NON-REGRESSION eval against the EXISTING cases.**
A rendering change (a new line/flag in a run record, a collector prompt edit) is an input
shift to every consumer of that surface, even though it may edit no prompt. It ships green
only after the existing cases that read that surface (e.g. `test_collector_honesty.py`,
`test_collector_enactment.py`) are re-run on the branch and shown to still hold. The shared
`render_run_record` is read by the self-state header and the addon, so one rendering
edit moves both; the existing suite is the proof it didn't regress them.

**Authoring a case is not running it.** Every prompt change must be *dry-run through
the harness against the live model* (`make eval` / a focused case) and the result read
**before you commit the prompt** — a case you wrote but didn't run tells you nothing
about whether the model actually complies, and "coverage" without execution has shipped
broken prompts here before. When it fails, read the model's thinking (auto-dumped on
failed samples), not just the scorer line — that's where the reason lives.

**The eval runs the SHIPPED prompts, and a failure is often stale data — not model
incapacity.** A fresh eval DB is built exactly like prod (`create_tables()` then
`migrate()`), so the seeded skills / `extraction_prompt`s the model follows are the ones
migrations ship — the eval tests them as deployed, not a hand-built copy. Two consequences:

- *Make a migration the single source of truth for a seeded prompt.* Have the eval drive
  the **migration-seeded** version (seed only the case's inputs, not a second copy of the
  prompt) so what's validated is byte-for-byte what ships — no fixture copy to drift.
- *Suspect stale seeded data before model incapacity.* Real example from this codebase: the
  chat agent set a new `published` flag **correctly** but *also* bolted on a `send_message`
  step and created duplicate collections — not because it couldn't reason about the flag,
  but because the seeded **skills** still taught the old pattern. We nearly renamed a schema
  field chasing a "comprehension" problem that was actually stale data. The thinking trace
  tells you which; fix at the highest rung (data/skill > prompt > code — see the root
  Design Principles). Corollary: adding a seeded collection in a migration changes the chat
  agent's Memory Inventory, so the verbatim system-prompt test will fail until you update
  its expected string — that's the test working, not a regression.

The workflow:

1. **While iterating**, drive the fix with `replay.py` / focused low-N runs (below) — fast, throwaway, may read the local prod DB.
2. **Before opening the PR**, lift the validated behaviour into a committable, privacy-safe `tests/eval/` case: genericize any real data into synthetic topics (per the log→test→fix loop), and assert on persisted DB state / sends / run outcome, never on wording.
3. **If the failure is stochastic** and can't be reproduced by seeding alone, *force the trigger deterministically and let the real model drive the rest* — e.g. `nudge_eval`'s `_InjectTextBail` forces one plain-text bail, then the live model must recover through the production nudge — so the contract is exercised on every run, not ~25% of them.
4. **Pair it with a deterministic mock test in `tests/`** when there's a mechanism to pin (loop control, branching, bounds): `make check` owns the fast mechanism proof, `make eval` owns the live model-behaviour contract.

#### The log → test → fix loop (durable process for correcting model behaviour)

This is the canonical way to identify and fix *any* undesired model behaviour — never
guess at a fix from the code, drive it from a real failing example:

1. **Find candidates in the DB.** The `promptlog` records every model call (messages,
   tools, response, outcome). Query it for real instances of the failure (e.g. collector
   runs whose only tool call is `done()`). There are almost always plenty.
2. **Pull the full verbatim input.** Extract the *entire* JSON the model saw — system
   prompt, every chat/tool turn, the tool definitions — the exact one, not a paraphrase.
   `penny/tests/eval/replay.py` does this: it reads a `promptlog` row **by id** and
   replays it against the live model (so the harness itself carries no prompt content —
   privacy-safe to commit while the real prompt stays in the local, gitignored DB).
3. **Run it to confirm the failure reproduces** verbatim. If it doesn't, you haven't
   captured the real trigger yet — keep looking.
4. **Genericize for privacy.** Swap out any PII / real-topic mentions for synthetic
   equivalents (the repo is public — see the privacy rule). This is what turns a
   verbatim replay into a committable `fixtures.py` case.
5. **Run it again to confirm the genericized version still reproduces** the failure. If
   genericizing killed the repro, the trigger was in the specifics — narrow it back.
6. **Now tweak the prompt to correct it**, re-running the (now report-only or gated)
   eval case until it passes — and watch the *other* cases to catch over-correction.

Caveat: the loop only applies when the failure is a *model decision on a visible input*.
If the model is making the right call on what it's shown but the input itself is wrong
(e.g. a bailout run rendered header-only, so a reader can't see it), that's a
data/rendering bug — fix it in Python first (so the signal is visible), *then* the loop
applies. Distinguish "model ignored the signal" from "model was never shown the signal"
before reaching for a prompt change.

Second caveat — **check the scorer before you blame the model.** A surprising `0/N`
(especially on a report-only case) is as often a mis-specified scorer as a real
failure: read the model's actual tool calls (the auto-dumped thinking) and confirm it
did the wrong thing before tuning the prompt. This session, two `0/3`s were both scorer
bugs — one counted a *distinct* seeded skill as a "duplicate", another penalised a bare
`example.com` that appeared only in an example phrasing. The model was correct; the
contract was wrong. Verify the scorer encodes the intended contract first.

#### Iterating fast: focused low-N first, full suite last

Live-model cases are slow — a collector cycle is ~120-180s **per sample**, so a careless
`4 cases × N=5` loop is ~60 min. Don't iterate that way. While converging a fix:

- Run ONLY the case(s) you're actively changing, at low N — `EVAL_SAMPLES=3 pytest
  "…::test_repairs_done_only_bailout" -m eval -s`. That's ~9 min, not ~60.
- Add a guard case (e.g. `test_healthy` for over-correction) only when a change could
  plausibly affect it, not every loop.
- To inspect *why* a single run failed, run one cycle against the seeded fixture and
  dump its promptlog rows (input messages, thinking, tool calls) — one cycle, ~3 min,
  shows exactly what the model saw and did at each step.
- Run the FULL suite at the default N **once, at the end**, to confirm nothing
  regressed — not as the iteration loop.

#### Always read the model's thinking on a failure — that's where the "why" lives

When a prompt change doesn't move the pass rate, the reason is almost never visible
from the scorer's one-line failure — it's in the model's **thinking trace**. (Real
example: the publish-flag cases failed not because the model misunderstood `published`
— it set it correctly — but because a *stale seeded skill* still told it to add a
`send_message` step. Only the thinking + tool trace made that obvious.) So **reviewing
the thinking is a required step of every prompt-iteration loop, not a last resort.**

The harness does this for you: `_dump_thinking` (in `tests/eval/conftest.py`) prints
each LLM call's thinking + tool calls for **every failed sample automatically** —
pytest surfaces captured stdout for failed tests, so the traces land in the failure
report with no flag needed. Set `EVAL_DUMP_THINKING=1` to also dump passing samples
when you want the full picture. The eval DB is an ephemeral `--rm` container, so this
read-before-discard is the only place the reasoning survives — don't skip it.
