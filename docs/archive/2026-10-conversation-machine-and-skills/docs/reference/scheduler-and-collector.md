# The scheduler and collector — reference

Covers the scheduler, the Collector dispatcher, and the collector-cycle mechanics (notify, cadence, retries, journaling). Read this in full before changing scheduling, collector cadence, or a cycle's end conditions.

- **Write-gate STOP semantics** — lives in `docs/reference/tools.md` (the `collection_write` chokepoint); a STOP is what ends a collector cycle cleanly.
- **`Clock`** — lives in `docs/reference/database.md`; the collector's readiness/expiry checks and the eval harness's pinned clock both read it.

### penny/notification.py

  notification.py     — telling the user about a finished collector cycle (#1911): `CollectorNotifier` (assemble → draw → queue), the pure `render_notification` document, the typed `NotificationOutcome` the run record is stamped from, and the send gate the retired `SendMessageTool` used to hold (refusal / no recipient / mute, then `db.send_queue`). **The document is BOUNDED and ORDERED (#1934)**: the first live post-reset cycle assembled 50,805 characters for an ordinary three-page news round — a browse result inlined whole (31,725), a `collection_write` restating its whole payload in its own arguments (14,923 on ONE line), and the entries holding that text a third time (14,989) — on a model whose degeneration onset is ~4K prompt tokens, and the message it composed led with a headline that was not the fetched page's top story but WAS the lead of the PREVIOUS notification, sitting in the closest-prior-messages section. So the ORDER is what the message is written FROM: the entries the cycle WROTE lead, the calls follow them (`## How it got there`), and the earlier conversation is LAST under `## Background: earlier messages` with a lead line saying these predate the cycle and where the cycle's own findings are — the only lines in the document the reported run did not produce. Every section is bounded in the pure RENDER (so the bound holds whatever assembled the facts, and a whole-render test pins it with no database): per-item character budgets (`NOTIFY_CALL_CHARS` / `NOTIFY_CALL_RESULT_CHARS` / `NOTIFY_WRITTEN_CONTENT_CHARS` / `NOTIFY_RELATED_LINE_CHARS`) and per-section item caps (`NOTIFY_WRITTEN_ENTRIES` / `NOTIFY_CYCLE_CALLS` / `NOTIFY_RELATED_MESSAGES`, which is now the render's cap as well as the query's `k`). **Never a silent cut** — a condensed value ends in `… [<n> characters omitted]` and a capped section ends in `<n> more <entries|calls|messages> not shown.` (the #1914 holdings precedent), because a draw reading part of a result knowingly is a different thing from one reading it as the whole. This REVERSES #1911's carried-whole rule for `CycleCall`, whose reasoning was that a truncated result is where an invented detail comes from; the measurement is that a document the model cannot read is not a safer document, so the cut stands and states itself

### penny/program.py

  program.py          — a stored program's own calls (#1911), read to SCOPE the cycle's tool surface: `program_calls` reads each numbered step's first call against the surface this cycle runs with (no tool is named here, so a plugin's verb participates for free). **`covered_calls`/`is_covered` are RETIRED (#1916, watched deletion)** — deriving the cycle's exit from coverage fixed the route in advance, so a cycle that departed from its program for a good reason could never close, and died trying to say so in prose; the terminator came back instead. Pure

### penny/scheduler/send_queue_drainer.py

    send_queue_drainer.py — SendQueueDrainer: delivers queued autonomous messages on the send cooldown. **Two LANES, read off the queued row's `origin` (#1939)**: the cooldown is anti-spam for messages nobody asked for, so a message from a cycle the USER pressed "run this now" on (`CycleTrigger.ON_DEMAND`) goes out on the next tick, while a cadence cycle's waits the window out. `_next_deliverable` asks the store BY LANE while the cooldown is running (`next_pending(origin=…)`, filtered in the WHERE) rather than reading the head and discarding it — an older cadence message would otherwise hold the user's own result behind it for the whole window, which is the case this exists for

### Emission provenance (#1568)

- **Emission provenance (#1568)**: every autonomous send names its mechanism end-to-end — the reverse index (emission → mechanism), so "which mechanism sent this?" is a read, not a diagnosis. `send_message` enqueues with the bound collection (`send_queue.collection`); the `SendQueueDrainer` carries it onto the delivered `messagelog` row's `mechanism` at delivery (`send_response(mechanism=…)` → `_log_and_send` → `log_message`). A **direct reply** (a chat turn with a live triggering user message) stamps `mechanism = NULL`. **No spam-prevention mechanism lives at the send layer** (code-owner decision on the #1568 revision): the structural no-news class is already suppressed by the write-gate STOP (`KEY_EXISTS_UNCHANGED`) before the notify steps run, and the observed duplicate-message class is model-composed prose a content fingerprint cannot catch. **Read side — provenance renders where the message renders, no resolver tool** (second code-owner revision: a bespoke resolver for a join the row carries is a rendering bug wearing a tool costume, and its `message_id` argument was rendered on no surface the model reads): recent autonomous sends are ambient in the **self-state header's activity block** (`sent · <when> · <mechanism> — "<snippet>"`, interleaved with runs + mutations; direct replies excluded — zero calls); older sends render their mechanism **inline on every `penny-messages` read** (`MessageLogMemory._render_content`: `N. [<stamp>] (sent by <mechanism>) <content>`; a NULL-mechanism row renders byte-identical to the unmarked pre-provenance shape), so pulling a message by relevance or recency IS resolving its source — one call; the second hop ("what created that watch?") is `memory_get("<mechanism>")`, whose existing #1566 block renders created-when / by-run / from-message with the quoted ask.

### Queued sends, not dropped

- **Queued sends, not dropped**: nothing that writes an autonomous message owns *when* it goes out — `CollectorNotifier.queue` enqueues into `db.send_queue` (after the refusal/no-recipient/mute delivery gates) and the deterministic `SendQueueDrainer` (an idle-gated `PeriodicSchedule`, no LLM) delivers the oldest pending row once the flat-interval cooldown clears: `now - last_penny_message ≥ SEND_COOLDOWN_SECONDS` (bypassed when the user has spoken since Penny's last message — the send is then conversational). So a cooldown *delays* a message instead of losing it, and timing lives in Python, not model-space. **The second bypass is the row's own `origin` (#1939)**: a message from a cycle the USER triggered (`run_for` → `CycleTrigger.ON_DEMAND`) is conversational in exactly the sense the user-spoke-since bypass already means — they are waiting on it — so it goes out on the next drain tick, while a cadence cycle's message rides the full cooldown. The lane is a READ of what set the cycle running, threaded as a parameter (`_execute_cycle(trigger=…)` → `_notify_if_due` → `notify` → `queue` → `enqueue(origin=…)`), never re-decided from the content; a muted user, a refusal or a missing recipient still decline either way, since the lane says WHEN a message goes out and not WHETHER. Since #1911 there is no `send_message` TOOL at all: the collector was its only customer, and a cycle no longer messages anybody — the gate and the enqueue moved whole into `penny/notification.py`. **Message validity vs. delivery decisions are still split by where each runs**: a half-formed body (blank / punctuation-only, bare URL, bail-out phrase, an unfinished ellipsis+?/! **tail** like `"Hi there! ......???"`, or an ellipsis-truncated tail) is refused by the notify draw's own acceptance rule — so it is RE-DRAWN on the unchanged context rather than queued and rejected later — and re-validated at the queue through the same `SendMessageArgs` model, while refusal / no-recipient / mute are no-op delivery declines that need runtime state. Both read the shared `half_formed_send_reason` (in **`penny/text_validity.py`** — a dependency-light leaf, so `tools/models.py` can import it without closing an import cycle through `penny.database`), the same rule the run-health classifier flags `⚠ HALF-FORMED SEND` on, so what Penny refuses to send and what she flags as a regression are one definition. **The send gate judges the message AS A WHOLE, not on a substring hit** (#1386): a substantive, deliberate message that merely EMBEDS a degenerate fragment mid-text (a message quoting the bad send it observed) is a complete message and is delivered — catching an in-flight collapse in the model's *own* output stays the **agent-loop reroll guard's** job (`is_degenerate_run` on raw output). The strict SUBSTRING poison check stays on `degenerate_reason` (the corpus write gate — a collapse run anywhere corrupts a stored entry). `degenerate_reason`/`is_blank`/`is_unfinished_fragment` and the corpus content filter live in `text_validity` too; the `database.memory` package re-exports them so its public import surface is unchanged (`objects.py` imports them directly from `text_validity`).

### Collector (`penny/agents/collector.py`)

**Collector** (`agents/collector.py`)
- One dispatcher agent for every kind of background extraction.  Each tick it picks the most-overdue ready collection from the `memory` table (where `extraction_prompt IS NOT NULL` and the row's RRULE `schedule` has an occurrence at or before now that the last run didn't already cover), binds itself to that target via `self._current_target`, runs the agent loop with the target's extraction prompt as instructions and a tool surface scoped to writes against that single collection, then stamps `last_collected_at = now`.
- **Cursor gate (skip-when-no-new-input)** (`_input_pending`/`_live_cursors`, in `_is_ready` after the schedule gate): a *log-driven* collection — one that reads a log via `log_read`, leaving a read cursor — is skipped **without entering the model** whenever every one of its live input logs is caught up (`head <= last_read_at`, probed with the same bounded `read_batch` the collector itself uses, uniform across the `messagelog`/`promptlog` facades and real logs). The cursors a collection already holds *are* its declared inputs (no separate spec); the gate ORs across them (any input behind → run). A cursor whose log the current `extraction_prompt` no longer names — left by a since-dropped `log_read` — is pruned (exact identifier substring match) so it can't lie about what the collection consumes. A collection with no live cursor (generative/browse-driven, or one that picks from another *collection*) returns `None` from `_input_pending` — not gate-eligible, so its schedule alone decides. This is what lets a quiet log stop a collector cold yet have it resume the instant the log moves. This INFERRED gate is untouched by the #1857 schedule collapse; the *declared*-input `on advance of <log>` form that rode beside it (`source_log`, #1604) is **dropped**, and returns later as its own field once it has eval coverage.
- Replaces what used to be four bespoke agents: preference-extractor, knowledge-extractor, thinking, notify.  Each is now just a row in the `memory` table with its own `extraction_prompt` and `schedule`.
- **Emission is a collection PROPERTY** (`notify` flag, #1557), and telling the user is a FRAMEWORK-ENTERED MICRO-CONTEXT after the cycle (#1911): the composed collector prompt carries **only the skill** — the stored `extraction_prompt`, the routine it runs and the values it is pointed at (#1907). Assembly appends exactly ONE step, the terminal `done()` (`Prompt.COLLECTOR_DONE_STEP` via `_injected_steps`/`_max_step_number`, restored #1916); `Prompt.COLLECTOR_NOTIFY_STEPS` (read_similar ×2, compose, `send_message`) stays DELETED, as does `send_message` from every tool surface. What that removed is the tail the cycles were dying in: on PR #1906's instrumented run, 49 of 75 cycles died on reroll exhaustion and 42 of them in the notify tail immediately after a `read_similar` — the model's tool-call envelope decaying on a long chat-flavoured context, 86% of the deaths and near-zero of the value. The tail is taken apart along the line of what needs a model: the two lookups are STORE QUERIES done in Python, the compose is a MODEL job on a fresh short document with **no tool channel at all**, and the send is the deterministic queue. **The cycle's exit is a CALL the model makes again (#1916)**: assembly appends exactly one step, the terminal `done()`, numbered after the skill's own — the coverage read this replaced fixed the route in advance and left a departing cycle with no close at all (11 aborts in one measured run), whereas a model that has finished can always make one more call. `Prompt.COLLECTOR_NOTIFY_STEPS` stays DELETED and `send_message` stays off every surface; only the close came back. What the notify redesign removed is unaffected: on PR #1906's instrumented run, 49 of 75 cycles died on reroll exhaustion and 42 of them in the notify tail immediately after a `read_similar`, and that tail is still gone. The rest of the redesign is unchanged. **The surface is SCOPED to the program too** (code-owner ruling: "we know the tools beforehand so we can dynamically restrict the tool calling surface to only the tools in the actual skill"): a cycle whose program the framework can read runs with EXACTLY that program's calls, closed over `Tool.advises` — so the interjected `read_similar` that re-admits chat-flavoured content mid-program is structurally unavailable rather than discouraged. **`done` is RESTORED (#1916)** — the tool and its injected terminal step; the premature-`done` guard stays deleted. `done()` and a write-gate STOP are a cycle's only closes, and a genuinely stuck one still ends on the max-steps/abort path carrying its own honest #1909 cause. The NOTIFY TRIGGER reads that close: `notify` flag + no STOP + a successful `done()` (#1916, where #1911 read coverage), so a clean close carries no reason of its own and the record's header falls back to the outcome enum — unless the collection notified, in which case the reason is the notification note alone (`NOTIFICATION_NOTES`); `COLLECTOR_COVERED_REASON` retires with the read that named it. The parser is STRICT with it — a step's call must OPEN the step (`N. tool(args)`, the one dialect `render_skill` writes), because the seeded prose rows the lenient scan existed for are gone; a stored prompt that is not a rendered program yields a surface of the TERMINATOR ALONE and a run record naming the CONFIG DEFECT, never a second way of running. **Nothing rendered on a surface may name a tool it lacks** (the n≤1 corollary): each tool DECLARES the siblings its own text points at (`Tool.advises` — `collection_write` → `collection_remove`), the scoped surface is the transitive closure over that relation, each runtime-rule line declares the tools it names and renders only when the surface carries them (a read-only program gets no rules block at all), and the all-duplicates close names no call of its own (the actionable one is per entry, where the matched key is). Enforced, not swept once: `tests/tools/test_tool_advice_coherence.py` ast-scans every tool's model-facing strings (class body, module constants, and the helpers it composes results from — followed TRANSITIVELY since #1919, because the house style is constants over inline literals and a one-hop scan reads a helper that names a constant as having nothing to say; that blind spot was hiding `find`'s whole addressing render, which names seven verbs it now declares) for references to any registered tool name and fails on an undeclared one. A **write-gate STOP** (`KEY_EXISTS_UNCHANGED`, or since #1919 `DUPLICATE_UNCHANGED` when the same value was already recorded under a differently-worded key) still aborts early and is read by the trigger itself — it lands on the very call that would otherwise complete the program, so no-news never notifies, structurally, through either door. **The trigger** is three structural facts: `notify`, no STOP, and coverage — nothing keys on a tool's identity, so a skill with no write step AT ALL notifies exactly like a watch. A fourth fact closes the gap between those two shapes (#2417): a skill whose program DOES declare a write step (read off the tool's own `stores_entries` mark, never a name) but whose cycle mutated nothing this run (`ToolCallRecord.mutated`, tool-agnostic) is read the same as a STOP — the model skipped the write decision rather than the gate catching it, which a bare `notify` + no-STOP + `done()` read could not tell apart from a routine that never writes at all. **The notify micro-context** (`penny/notification.py` + `MicroContext.compose_notification`, customer #6) is handed a document assembled entirely framework-side — the entries the run wrote (read off `last_written_by_run_id`, so it is tool-agnostic), then the run's calls with their results, then the nearest `user-messages` / `penny-messages` entries fetched IN PYTHON by embedding what the run found (its description when it wrote nothing), or a plain nothing-matched line — and draws ONE `MESSAGE:` line, poison-screened and re-rolled, accepted only if it is a message worth delivering (the shared `half_formed_send_reason` rule + a refusal check). **That document is BOUNDED and ORDERED (#1934)** — writes lead, calls follow, prior messages come LAST under an explicit background heading, and every section is capped in the pure render with an honest `… [<n> characters omitted]` / `<n> more … not shown.` marker; see the `notification.py` entry in the directory listing above for the measurement that forced it. A failed draw records honestly on the run and sends nothing. The emitted text goes to the existing send-queue/cooldown logic unchanged (the refusal / no-recipient / mute gate, then `db.send_queue`, drained by the `SendQueueDrainer`). **Run records stay honest across all four terminal shapes** — aborted, stopped, completed-quiet, completed-notified: `PennyConstants.COLLECTOR_COVERED_REASON` opens a completed cycle's reason and carries what the notification came to (`NOTIFICATION_NOTES`), which is also how `render_run_record` tells a completed run from a write-gate stop (it reads the declared reason, not the absence of a `done()` call — that inference is dead now that a clean close has none). The chat agent maps a user's "tell me / keep me posted" request onto the `notify` flag (a `collection_create(notify=…)` param, or `collection_update(notify=…)`); it cannot add a `send_message` step to a stored prompt, because `collector_tool_surface` no longer contains one and the authoring-time guard refuses it. This retired the pub/sub layer (#1557, migration 0086): the `notifier` consumer, the `published` column, `read_published_latest`, and the collector's consumer gates are gone. (History: migration 0068 folded the thoughts pipeline onto the old pub/sub model, removing `collection_move`; 0086 then moved thoughts onto the `notify` flag.)

- User-defined collections created via chat (`collection_create`, which INSTANTIATES a skill — the skill's steps render into the collection's `extraction_prompt`, #1591) are picked up automatically on the next tick — no restart required. **A collection is storage plus an OPTIONAL job (#1629)**: `collection_create` with NO `skill` yields an **inert** collection — storage only, `extraction_prompt`/`schedule`/`notify` all NULL — so it **never dispatches** (`_is_ready` selects on `extraction_prompt IS NOT NULL`), yet is store-map visible and idempotency-checked at birth. It gets a job later via the **two-step teach bootstrap**: create inert → demonstrate the routine once in chat (browse → extract → `collection_write` into the real collection) → the run-end extractor learns it as a skill automatically, because the demonstration is a `learn` turn (#1658/#1850) → `collection_update(skill=…, params=…, schedule=…, notify=…)` **adopts** the skill and re-renders. A job-shaped arg (schedule/notify/expiry) on a skill-less create is refused (an inert container has no job to run).
- Tool surface: a cycle gets ONLY its program's own calls, closed over `Tool.advises` (#1911). The unscoped set it narrows from is reads (unrestricted — there being no framework collections left to hide) + entry mutations (`collection_write`, `collection_remove`) pinned to the bound target via the `_memory_scope()` hook + `log_append` + browse + choose. There is no `send_message` anywhere — a cycle cannot message the user — but `done` joins every scoped surface unconditionally (#1916), since assembly injects a terminal step into every composed prompt and a cycle that departs from its program still needs a way to say it has finished; an unreadable program therefore leaves a surface of the terminator ALONE. **The registry-shape lifecycle tier is absent** (`collection_create` / `collection_update` / archive / `log_create`, #1556): a cadence run reads, writes entries, browses, and notifies — it cannot create, reconfigure, or archive a mechanism (`_include_lifecycle_tools()` → False). A cycle's end is a successful `done()` or a write-gate STOP (#1916 restoring #1569's terminator over #1911's coverage read).
- Cadence: `COLLECTOR_TICK_INTERVAL` (default 30s, idle-gated) drives the dispatcher; each collection's own RRULE `schedule` decides when it is due within that.
- **The `last_collected_at` stamp CONSUMES the occurrence, so a cycle that did not spend one keeps it (#1935)**: readiness reads the occurrence strictly after `last_collected_at`, so stamping a cycle that ran no job SKIPS that fire outright — observed live, a chat message cancelled a daily job's cycle seconds in (before any model call had come back) and the day's occurrence was burned. `Collector._settle_occurrence` replaces the `finally`'s unconditional `mark_collected`: it asks `_retry_reason` whether this exit spent its occurrence, and where it did not, leaves the collection DUE so the next tick picks it up again (it is still the most overdue). **Since #1936 it is keyed on the cycle's END** (`CycleEnd`, the bullet below), so the writes and the fire settle on ONE verdict — two reads, ordered so each is decisive: **the cycle ENDED** (a member of `HEALTHY_CYCLE_ENDS` — a write-gate STOP, or a `done()` close that notified, deliberately declined to, or had nothing to notify about) → spent, it did the job the fire was for; **a configuration defect** (`_configuration_defect`, the DETERMINISTIC arm — read off the collection's stored program rather than off what the run did, so a retry re-fails identically; today, a prompt no program can be read out of, the other config defects being refused by readiness before dispatch) → spent immediately, and it OUTRANKS every unhealthy end because a cancelled cycle of an unrunnable collection is still unrunnable. Everything else — a preemption, #1909's `RunAbort`, a failed notification draw, the step cap, a model that trailed off — is a cycle that never reached its conclusion: its writes are reverted, so there is nothing left of it to protect, and its fire is KEPT for the bounded retry. The over-correction guard moved with it: what spends a fire is reaching an END, and the `_produced_work` read this replaced (an entry written or a notification queued) now splits only the run's `worked` / `no_work` outcome. **The bound is the stamp's original job, kept whole**: `PennyConstants.COLLECTOR_RETRY_ATTEMPTS` (3) attempts per occurrence, counted in an in-memory `dict` on the dispatcher (the exit it counts leaves nothing durable to count FROM — a cycle cancelled seconds in writes no `promptlog` row — and the count exists only to bound one burst, so a restart is legitimately a fresh start), cleared the moment a cycle settles. **The count is keyed `(collection, CycleTrigger)` — one budget per ASKER (#1939)**: the scheduler's cadence and the user's "run this now" are two different things attempting the same fire, and one shared count let three failed clicks leave the day's own scheduled attempt with nothing (the next preemption consumed the occurrence on its first try and the job silently skipped its day — this deferral's own failure mode, reached through the door the user was pressing). A settled cycle releases EVERY trigger's count for that collection (`_release_retries`), because what a count bounds is attempts at ONE occurrence: once any cycle spends it there is no longer an occurrence for the other asker's count to be about. After the budget the occurrence is consumed whatever happened, so a collection that fails this way every time still drops out of the running instead of re-attempting on every tick. **Two things follow the occurrence rather than the cycle.** The post-cycle retirement (`_retire_if_ended` — the `max_runs` quota + the mid-life `expires_at` retire) is SKIPPED on a kept occurrence for the same reason a cancelled cycle never reaches it: the fire and the run of a bounded schedule are one thing counted twice, and an abort is not a cancellation, so its `failed` run DOES count — a `COUNT=1` one-shot that died on a transport wobble would otherwise archive itself while its occurrence sat due, and an archived collection is never dispatched again. And the `memory_changed` refresh signal (what wakes the addon surfaces' detail view) was sourced on this path from `mark_collected` alone, so a cycle that withholds the stamp raises it itself (`MemoryStore.notify_changed`) — otherwise an on-demand "run this now" whose cycle died would leave the panel showing nothing.
- **A cycle's entry writes survive only its HEALTHY CONCLUSION (#1936)**: a collector cycle that browsed, WROTE the changed value and then died before its close consumed the change and delivered nothing — the retry re-observed the same page, re-wrote the identical value, the change-gate read `KEY_EXISTS_UNCHANGED` → write-gate STOP → the user was never told about a change that really happened. Code-owner ruling: a partial run must not persist state later cycles have to reason about; if a cycle never reaches its healthy conclusion it is retried until it does, **from the pre-run state**. The mechanism is an **in-memory UNDO JOURNAL**, not a staging layer: writes stay exactly as they are — live, through the existing chokepoint — and `Collector._bind` opens a `CycleJournal` on the bound collection (`db.memories.begin_cycle`) that records, before each mutating op, the key's PRIOR row state (content, author, both embeddings, both run-id stamps, `created_at`). **FIRST TOUCH PER KEY WINS**, so N touches revert to the true pre-run state. It is keyed to the MUTATION, not to a tool — a `collection_write`, a `collection_remove` and **the change-gate's own `KEY_EXISTS_CHANGED` baseline refresh (#1633)** are all recorded identically, that last one being the write nobody makes explicitly and precisely the one an aborted cycle used to leave behind. **The healthy-end enumeration is DATA** (`CycleEnd` + `HEALTHY_CYCLE_ENDS` + `CYCLE_END_RETRY_REASONS` in `constants.py`, the `WRITE_GATE_STOP_REASONS` pattern; the notification arm is `NOTIFIED_CYCLE_ENDS` beside `NOTIFICATION_NOTES`), and **one set drives both this and #1935's occurrence settlement** — a write-gate STOP (an early clean no-news exit IS an end point), a `done()` close that did not notify, one whose notification was QUEUED, and one whose delivery was DELIBERATELY declined (muted, or no registered recipient — a retry reaches the same answer). Everything else REVERTS in one short transaction (prior absent → delete the row; else restore the fields) and leaves the occurrence due for the bounded retry: an abort, a cancellation, a failed notification draw, and the unenumerated `UNFINISHED` default (the step cap, a model that trailed off), which the ruling covers in as many words. The cycle's **read cursors follow the same verdict** — `_run_cycle` hands its `CursorReadTool`s back on `CycleResult.reads` and the caller settles them (`Agent.settle_reads`), because how far a run consumed its input and whether its writes survive are one claim; a cursor that advanced over a reverted write would make the readiness gate read the log as caught up and skip the retry outright. **Chat is untouched**: its turn IS its conclusion, no journal is bound outside a cycle, and a chat write to any other collection is outside the journal's scope. **The LEDGER is not part of the deal** — the aborted run's `promptlog` rows, the mutation events, the `browse-results` fetch cache — because the forensic record of a dead cycle is exactly what an operator needs; the send queue only gains a row at QUEUED, a healthy end, so it never reverts. One consequence for the run record: `RunOutcome.INCOMPLETE` is no longer reachable for a collector cycle — a run whose writes were undone changed nothing durable, so it is the `failed` bail it honestly is. **Three things are WAIVED by the code owner** (documented at the journal, not defended against): a concurrent read mid-cycle sees the live in-progress writes; a process crash mid-cycle persists the partial state (the journal is in memory); and a chat turn writing the SAME collection mid-cycle can be clobbered by a revert. No staging store, no read-through, no facade, no schema change, no migration.
- **The auto-throttle is DELETED (#1857)** — `_apply_throttle`, the `consecutive_idle_runs` / `base_interval_seconds` columns, and the `COLLECTOR_THROTTLE_AFTER` / `COLLECTOR_MAX_INTERVAL` config params are gone (migration 0104). Code-owner ruling: "we'll drop the collector throttling logic altogether and just adhere to schedules; separately we have throttling inside the send_message logic which is the right place for it now." A schedule runs exactly as stated — nothing widens it from idleness — and rate protection lives in the send cooldown (the `SendQueueDrainer`), where it applies to what actually reaches the user rather than to how often a collector looks. `_produced_work` survives the deletion: it still reads the per-call `ToolCallRecord.mutated` flag, now solely to split a cycle's `worked` / `no_work` outcome. **Since #1914 it reads TWO sources**, because a cycle has two ways of doing something and only one is a tool call: the `mutated` flags (what the MODEL did) and the notification outcome (`_produced_work(response, notified)` — a `NotificationOutcome.QUEUED` is work, the two failure outcomes are not, exactly like a muted send's `mutated=False`). Telling the user is a framework-entered micro-context since #1911, so a read-only routine that ran and told the user recorded `no_work` — the outcome contradicting the reason line beside it, which already named the notification.
- **A configured collection's cycle reads THREE things (#1907)**: `Collector._compose_prompt(target, skill)` frames the program with (a) the INSTRUCTIONS — the stored `extraction_prompt`, whose leaves already carry the collection's bound values because the runtime join baked them in at the render seam — (b) the ROUTINE it runs (`The routine you run: <name> — <what it is for>`, read off the `skill` row `skill_name` names) and (c) the VALUES it is pointed at, one `- <name>: <value>` line each from `skill_params`. The values are in the program already; listing them beside it is what makes each one readable as a TERM of the job, and it is the one place a term the program has no leaf for can still be read. A collection with no `skill_name` (hand-authored, seeded) renders byte-identically to before — the block is absent entirely. **Visible degradation**: a parameter the routine declares and the collection was never given renders as a named gap (`- <name>: nothing was supplied for this — it needs <what to supply>`), which is the reachable shape after a re-teach adds a parameter to a running job; a `skill_name` the registry no longer holds says that rather than nothing.
- **The cycle also reads WHAT THE COLLECTION HOLDS (#1914)**: `Collector._holdings_section` is the second trailing block of the composed prompt (`_build_system_prompt` = the composed program + holdings + `_run_history_section`, in that order — the entries sit next to the program that acts on them, the run outcomes close it as they always have). It renders the bound collection's own entries, newest first, through the SAME `format_entries` (`tools/memory_tools.py`, made public for this) the read tools return — so a key read AMBIENTLY is in the invocation form a `key=` argument takes and is COPIED, never derived (n≤1). An empty collection says `It holds nothing yet.`; a collection deeper than `PennyConstants.COLLECTOR_HOLDINGS_LIMIT` (20 — a self-state-header-style prompt-budget bound, tunable) renders its newest entries plus `<n> older entries not shown.`, an honest count rather than a silent cut. The window is bounded in the QUERY (`Collection.read_latest(k)`) and the remainder is a COUNT (`Collection.entry_count()`, new — a keyed read like the others, so a log gets the house wrong-shape refusal rather than a plausible zero), never a whole-partition read sliced in Python. The overflow deliberately names NO fetch tool: a cycle's surface is scoped to its program's calls, so a read tool named here might not be on it. **Presentation only** — nothing constrains what a routine may be or which keys it may use. Why it exists: on PR #1906's round-3 measurement 15 of 25 quiet cycles completed-and-notified because the model invented a fresh key each cycle (nothing it could read said what key the value was already stored under), so the write gate saw `NEW_KEY` where the value was in fact unchanged. The code owner's rule — "the model can only act on the information it is presented; if it needs to know the key, then that's what we need to present" — makes that a presentation defect, not a case for baking a key in.
- **Scoped tool surface (#1556)**: a cadence-fired collector run cannot reshape the registry — the lifecycle tier (`collection_create` / `collection_update` / `collection_archive` / `collection_unarchive` / `log_create`) is ABSENT from its surface (a background poll has no business re-architecting the system). The run type declares this via `Collector._include_lifecycle_tools()` (template method → `build_memory_tools(..., include_lifecycle=False)`); the chat agent keeps the lifecycle tools (the user evolves collections through them). `_collector_tool_surface` mirrors the mask, so an `extraction_prompt` naming a lifecycle tool is rejected at authoring time.
- **End conditions (#1556, #1857)**: two nullable `memory` columns — `expires_at` (the collection archives itself once it passes) and `max_runs` (it archives after that many completed cycles, via the system-actor archive path so the row stays a visible, archived-inclusive tombstone — enumerable by the self-state header's mechanisms section and, by name, its archived line (#2288)). Both are settable directly AND **lifted out of the schedule's own `UNTIL=` / `COUNT=` parts at parse time**, so a bounded rule and a bounded collection are one thing — a one-shot is `DTSTART:<time>` + `COUNT=1`, which fires once and then archives itself. Stating an end twice (a rule with `UNTIL=` plus an `expires_at` argument) is refused rather than silently resolved one way. `_archive_if_run_limit_reached` reads the completed-run count from the ledger (`db.messages.count_completed_runs`, cancelled runs excluded) after each cycle; `_archive_if_expired` + the pre-dispatch `_retire_expired` sweep own the expiry. The `run_at` column this replaced folded into the rule's `DTSTART` line.
- **Minimal collection surface — six concepts, ONE schedule grammar (#1631/#1857)**: `collection_configure` reasons about **six concepts** — `collection` · `description` · `skill`(+`parameters`) · `schedule` · `notify` · `expires_at`. **`intent` is GONE** (migration 0095): it duplicated `description` byte-for-byte at birth, so `description` is the single descriptor everywhere — the routing/dedup meaning anchor (#1558), rendered in the self-state header/metadata/echoes. **The schedule is ONE `schedule` string in ONE grammar: an RRULE** (`parse_schedule`), optionally preceded by a `DTSTART:` line — `FREQ=HOURLY` · `FREQ=MINUTELY;INTERVAL=90` · `FREQ=DAILY;BYHOUR=8` · `FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR;BYHOUR=9`. `python-dateutil`'s `rrulestr` is the sole authority on the grammar (no bespoke parsing, no NL parsing in Python) and `Collector._is_ready` gates on the rule's own next occurrence after `last_collected_at or created_at` — the rule IS the cadence, so there is nothing to widen. **The hour a rule states is the hour on the USER'S clock (#1932)**, not UTC: `next_occurrence` anchors the recurrence at `created_at` converted into the profile timezone (seconds zeroed), so `BYHOUR=9` means nine in the morning where they are, and the model writes the hour the user said rather than converting it (the four tool-description places that told it to convert now say so). This **replaced the four-form trigger union** (`every <seconds>` | `once at <ISO> [xN]` | `on advance of <log>` | `cron <5-field expression>`, #1631/#1684) and its six columns with one, because the union's real cost was the routing decision it forced: measured on ten natural-language schedule phrases, gpt-oss:20b wrote 10/10 clean RRULEs (including `FREQ=MINUTELY;INTERVAL=90`, inexpressible as one cron line) against 9 + a two-line workaround for cron, and "every morning" mapped to interval-daily rather than cron 10/10 times at enactment. `COUNT=` and `UNTIL=` are **lifted at parse** into `max_runs` / `expires_at` while staying in the stored rule, so a rendered schedule round-trips. **`expires_at` takes ISO or the user's own words** — tried as ISO first, then `dateparser` **in the user's timezone** (`parse_expires_at`, the zone passed in as a parameter): "in two weeks" and "tomorrow at 9am" land, and reading them as UTC is what put a bounded watch's end on the wrong evening. **A far-future `expires_at` is NORMALISED to no end condition, never stored (#1944)**: an apply turn asked to set a job running indefinitely wrote `expires_at = 2099-12-31`, which then rendered in the self-state header as the mechanism's end condition and was copied back on every later `collection_configure` — invented config made sticky by ambient state. Any time past `PennyConstants.SENTINEL_EXPIRY_HORIZON_DAYS` (20 years, a HORIZON measured from now rather than a fixed calendar date, which would itself rot; a wholesale bound erring high, both directions pinned) is a stand-in for "forever", so `parse_expires_at` returns `None` and every render says `expires: never`. Normalised rather than REFUSED, because the job the user asked for is exactly the unbounded one — and never silently: `expiry_was_normalised` is the ONE structural read of that outcome and both things that follow from it hang off it, so they cannot disagree — `sentinel_expiry_note` appends an actionable note to the create / update / re-render result naming what became of the value and what to pass instead, and `update_collection_metadata(clear_expiry=True)` takes a stored expiry OFF the row. **The clear path is load-bearing, not tidiness**: `expires_at=None` means "not stated" on `_MetadataUpdate` like every other optional, so without its own signal an invented expiry could never come off a collection that already carried one — which is exactly how the sentinel became sticky, and the result would have claimed an unbounded job over a row still holding 2099. A sentinel in the schedule's own `UNTIL=` is a separate door and is NOT covered. A schedule `rrulestr` won't read, or an `expires_at` neither reading answers, is a **reject-and-teach** naming the grammar — and where a purely mechanical repair of the text parses (wrapping quotes, a trailing separator, a `DTSTART` joined to the rule with a semicolon) the error **echoes the corrected string verbatim** so the retry is a COPY, never a re-derivation (the measured `every 7200s` rejection whose retry came back as 14400). **On update**: a `schedule` present replaces the stored one atomically, run quota and all; absent leaves it untouched. The stored rule renders back VERBATIM (`render_schedule_clause`) on the self-state mechanisms line (`SelfStateHeader._cadence`), in `memory_get`, and in the creation/re-render echo — **display form == invocation form**, with nothing to re-derive at the render since there is only one grammar. A two-line rule renders on one line with its newline written `\n`, which the parser accepts back.

The `scheduler/` module manages background tasks:

### BackgroundScheduler (`penny/scheduler/base.py`)

### BackgroundScheduler (`scheduler/base.py`)
- Runs tasks in priority order (send-queue drainer → collector dispatcher)
- **Skips agents with no work**: when an agent returns False, continues to the next eligible schedule in the same tick. Only breaks when an agent does real work.
- Tracks global idle threshold (default: 60s)
- Notifies schedules when messages arrive (resets timers)
- Passes `is_idle` boolean to schedules (whether system is past global idle threshold)
- **Cancels active background task** when a foreground message arrives (`notify_foreground_start()` calls `task.cancel()`), freeing Ollama immediately for the user's message. Cancelled tasks are idempotent — unprocessed items stay in their queues and are re-picked up on the next cycle
- Commands do NOT interrupt background tasks — they run cooperatively


### Schedule Types (`penny/scheduler/schedules.py`)

### Schedule Types (`scheduler/schedules.py`)

**PeriodicSchedule**
- Runs periodically while system is idle at a configurable interval
- Used for the **SendQueueDrainer** (idle-gated, `SEND_QUEUE_DRAIN_INTERVAL` 60s — scheduled before the collector so queued messages deliver promptly) and the Collector dispatcher (idle-gated, COLLECTOR_TICK_INTERVAL default 30s); each collection's own cadence lives on `memory.schedule`, an RRULE
- Tracks last run time and fires again after interval elapses
- Resets when a message arrives

Schedules run a `ScheduledTask` (`scheduler/base.py`) — a structural Protocol (`name` + `async execute() -> bool`). The `Collector` satisfies it, and so does the non-LLM `SendQueueDrainer`.
