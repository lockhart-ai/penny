# Validation and text validity — reference

Covers the model-I/O validation taxonomy and the content-validity predicates it is built from. Read this in full before changing a response validator or a degeneracy/half-formed-send rule.

### penny/validation/response_validators.py

    response_validators.py — Concrete validators (xml/refusal/hallucinated-url/repairs), composed per-agent. The hallucinated-URL validator and the malformed-URL cleaner read a URL through ONE extractor, as the ADDRESS alone (#2159): the run of characters a URL may contain (RFC 3986 plus non-ASCII letters/digits/marks), split at a markdown link's `](` seam so each side is its own URL, trimmed of trailing sentence marks, `*`/`_` emphasis and unpaired closers — so a citation bracket (`【…】`), bold, or a link whose text is its own URL is never read into the URL. **There is no narrate-from-the-RECORD validator left at all** (#2455 naive baseline, #2473): `AppliedConfigurationValidator` (what the run SET RUNNING) and `WritesLandedValidator` (what the run WROTE) used to fire at the text branch and redraw the reply with their record in view, discarding whatever had just been drafted — both records exist the moment their tool call lands, so `ChatAgent.after_tool_step` appends each straight onto that step's own tool-result message, before any draft exists to discard, and there is nothing left for a text-branch validator to say. `SkillNarrationValidator` is gone with the skill system it narrated — there is no routine for a learn turn to have learned any more. `ChatAgent.run_shape_validators` / `Agent.run_shape_validators` / `BackgroundAgent.run_shape_validators` are all empty. The call-shaped-text validators (text-instead-of-tool/done-json-bail/call-as-text) are GONE (#1839 — that family is rejected by the loop's reroll guard, not recovered by conversation), and so is `EmptyResponseValidator` (#1937 — the same rejection, for the draw that says nothing); their detectors moved to `text_validity`, which is also where `strip_think_tags` now lives, since the empty-draw guard and this chain must normalise a draw's substance the same way. A `Retry` writes nothing into the conversation: it discards the draft and re-draws on the unchanged messages, so a retry re-samples the state the draft was drawn from (#2160), once per condition. The one exception is the hallucinated-URL retry (#2698): it carries `Retry.note`, and the loop appends the draft (assistant turn) plus the note naming the URL(s) with no source (user turn) before re-drawing, so the redraw can rewrite without them or read a page that has them. When a flagged URL is a close miscopy of a same-host URL the source text holds (a dropped path word, or the same last path segment), the note hands her the exact source URL to use verbatim instead. NOT re-exported from __init__ (imports tools.memory_tools → database; would cycle)

### penny/text_validity.py

  text_validity.py    — Content-validity predicates (degenerate/blank/half-formed-send/description/extraction-prompt/**degeneration-collapse run**/**leaked-Harmony-envelope**/**call-shaped text**/**empty draw**), dependency-light leaf (stdlib + `constants`) shared by the memory write path, the tool arg-validators (memory_args) and the notify draw's own acceptance rule, the collector readiness gate, the run-health classifier, and the agent-loop reroll guard — which since #1839 reads its WHOLE invalid-draw predicate set from here (`is_degenerate_run` · `has_leaked_harmony_envelope` · `is_degenerate_tool_name` · `is_call_fragment_reply` · `is_call_as_text_bail` · `is_done_json_bail` · `is_empty_draw`, #1937), one leaf rather than a split between here and the validator chain. `strip_think_tags` lives here too (moved with the empty-draw guard, #1937): it is the shared NORMALISATION every reader of a draw's substance applies first — the empty guard, the refusal and hallucinated-URL validators, the loop's final-answer build — so a draw that is nothing but reasoning reads the same at all four. **`suggest_tool_name` + `LEGACY_TOOL_RENAMES` live here too (#1944)** — the one answer to "what tool did this miss mean?", read by the executor's live tool-not-found result AND by `check_extraction_prompt_tools` (whose docstring already claimed to mirror it): the rename table's MEANING leg first, then `difflib` on `PennyConstants.DID_YOU_MEAN_STRING_CUTOFF`. The table is the migrations' own rename history resolved TRANSITIVELY (`collection_metadata`→`memory_get` · `collection_update`→`collection_configure` · `update_entry`→`collection_write` · `read_last`/`read_latest`→`collection_list` · `collection_read_latest`→`collection_list` · `collection_delete_entry`→`collection_remove` · `log_read_log`/`log_read_next`/`log_read_recent`→`log_read`), and is authoritative about renames only — never about what exists, so a replacement absent from the caller's surface falls through to the string leg

### Model-I/O validation (one behaviour taxonomy)

- **Model-I/O validation (one behaviour taxonomy)**: where tool-arg validation gates a tool call's *static* arguments, this gates the model's *dynamic* I/O — the response (text + tool calls). The keystone is `penny/validation/conditions.py`: **one catalog** (`BehaviorCondition` in `CATALOG`, keyed by `ConditionKey`) of every condition we classify Penny's behaviour through, so the user, Penny (her ambient view of her own runs in the self-state header), and a maintainer share a single coherent view rather than a check that means one thing in the loop and another in the run log. Each condition declares *where it applies* as data — `live` (caught during the run, by one of three mechanisms: the loop's **discard-and-reroll guard**, where the draw never enters the run at all; a `ResponseValidator` disposition, which repairs a usable draw, re-draws it once, or answers it; or the outbound-message content gate), `run_flag` (surfaces post-hoc as a `⚠` line on the run record), `collector_only`. A condition can be both: `half_formed_send` is gated live at the notify draw's acceptance rule + the `SendMessageArgs` validator **and** flagged post-hoc. `no_work_done` is post-hoc only — there is no live premature-`done()` check (below), so a first-move `done()` closes the cycle and is caught, if at all, only as the run-health `⚠ NO WORK DONE` flag after the fact. This catalog supersedes the old split between `ValidationReason` (live) and `RunHealthFlag` (post-hoc); `RunOutcome` (the run's terminal state) stays a separate concern. The live machinery is in `penny/validation/outcomes.py`: a `ResponseValidator` is `check(response, ctx: LoopContext) -> ValidationOutcome`, pure (reads, returns a disposition, mutates nothing); the disposition union is `Proceed` / `Retry(condition)` / `Repair(response)` / `RejectToolCall(message)` / `NudgeContinue(message)` / `Stop(response)` (a typed return, not an exception — the loop reshapes into control flow immediately). (`RedrawWithRecord` retired with #2473 — see `response_validators.py` above: both records it served now reach the model with the tool result, before any draft.) **`Retry` re-draws from the unchanged conversation (#2160)**: it records its condition, discards the draft and re-calls on the same messages, so a retry re-samples the state the draft was drawn from — the same re-roll `_invoke_nondegenerate` does for unusable draws, one layer up. Nothing is written into the conversation, neither the draft nor a note about it — except when the retry carries a `note` (#2698): the ungrounded-URL retry does, because the model cannot usually see the defect in its own draft (the URL reads as real to it), and the loop then appends the draft (assistant turn) plus the note naming the URL(s) with no source (user turn) before re-drawing — so the redraw can rewrite without them or read a page that has them. When a flagged URL is a close miscopy of a same-host URL the source text holds (a dropped path word, or the same last path segment), the note hands her the exact source URL to use verbatim instead. The note also names the URL inside the conversation, so the run's later draws read it as sourced (accepted; the note is the true record of what was flagged). For the three conditions the chain retries — markup, a refusal, an ungrounded URL — a fresh draw usually does not repeat them; when it does, the second draw proceeds because its condition is spent. On exhaustion the call returns the last draw, tool calls stripped when none were offered. `run_validators` runs an agent's chain in order (repairs thread through; first non-proceed short-circuits). Validators are composed per-agent as class attributes (`Agent.response_validators` — chat's and the base's) that read like a table of contents — **a new guard is a new validator in the list, not a new branch in the loop.** `Agent.run_shape_validators` / `BackgroundAgent.run_shape_validators` / `ChatAgent.run_shape_validators` are all currently empty — there is no skill narration or premature-`done` guard left to compose. Beside them each shape declares its `invalid_draw_conditions` (#1839), the family the loop rejects outright rather than dispositions over; a collector composes no response-shape chain at all, since every call-less draw of its shape is discarded upstream. This replaced base.py's inline `_check_response` if-ladder + the `handle_text_step`/`handle_premature_terminator` guards. The post-hoc `classify_run`/`render_run_record` (`database/memory/objects.py`) source their `⚠` marker/detail strings from the same catalog, so what we enforce live and what we flag after a run are one definition — the strings are **frozen** (the addon TS type mirrors them). **Import-cycle gotcha**: `validation/__init__.py` re-exports only the database-free leaves (`conditions`, `outcomes`); it must NOT import `response_validators` (which pulls `tools.memory_tools` → `penny.database`), because the database layer imports the `conditions` leaf and importing any `penny.validation` submodule runs `__init__` first — eagerly importing `response_validators` there closes a cycle through `penny.database`. Import validators directly from `penny.validation.response_validators`. Design: `docs/model-io-validation.md`

### Invalid draws are rejected, not recovered (#1839)

- **Invalid draws are rejected, not recovered (#1839)**: each agent shape has a decidable valid terminal state — a reply for chat, a tool call for the collector — so a draw that was meant to be one and is not is an **invalid draw** — discarded and re-rolled on the unchanged context, exactly like a punctuation collapse or a leaked Harmony envelope (the shared `Agent._invoke_nondegenerate` machinery and its one `DEGENERATE_REROLL_ATTEMPTS` budget). It never enters the conversation: no stray output, no nudge user-turn, no marker on the run's prompt rows, so **a recovered run is indistinguishable from a clean one because recovery no longer writes into the run**. In the LEDGER it stays visible — the discarded draw is persisted whole (its context AND its own response) before it is inspected, so a re-rolled step is two `promptlog` rows carrying the same context; that repeat is what the eval harness's loop-health advisory reads (#1841), and the discarded draw's response is what the failure-cause pathology scan reads. After the budget the turn fails via the existing aborted-run path. What each shape counts as invalid is declared per agent as data (`Agent.invalid_draw_conditions`, one `(ConditionKey, predicate)` entry each, tried in order, consulted only when the draw carries no tool calls) — a new one is one more entry, never a branch in the loop. **The collector's invalid case is ANY non-tool-call draw**: prose, an empty body, or the argless `done()` composed as a JSON envelope that never reached the tool channel (gpt-oss's Harmony fallback, #1569; recognised by `is_done_json_bail` so the discarded draw is logged as `DONE_JSON_BAIL` rather than the terminal `TEXT_INSTEAD_OF_TOOL`, which is keyed to the STATE — no call was made — and never to anything the prose says). That subsumes what the collector's own response-shape chain used to say, so `BackgroundAgent` composes none and the collector-flavoured empty-content nudge retired with it. **Chat's invalid case is a draw that is not a REPLY** — a plain conversational reply IS chat's valid terminal state — so `CALL_AS_TEXT` (the full serialized call, or real args carrying the framework's `reasoning` field), then `CALL_FRAGMENT_REPLY` (the mangled remainder, incl. the bare `{}` tail of a forced call attempt, #1570/#1732), then `EMPTY` (**#1937** — a draw carrying fewer than `MIN_RESPONSE_LETTERS` letters once `<think>` blocks are stripped: blank, separators-only, a lone emoji). EMPTY is tried LAST because the `{}` tail has no letters either and `CALL_FRAGMENT_REPLY` is its truer name. It was the last invalid-output class still handled on the VISIBLE path: `EmptyResponseValidator` appended the empty assistant turn plus a nudge user-turn into the conversation, so a draw that came back empty after a discarded one lost the model's in-flight intent and left residue in the context — **the accepted trade-off is that an unchanged-context reroll cannot unstick a deterministically-empty draw; three burns then abort via the #1909 path, which is the honest end.** The nudge constants that used to teach these families (`TOOL_FORMAT_NUDGE` / `COLLECTOR_TOOL_CALL_NUDGE` / `COLLECTOR_DONE_JSON_NUDGE` / `CHAT_CALL_AS_TEXT_NUDGE`, then `CONTINUE_NUDGE` / `FINAL_STEP_NUDGE` + `build_strong_nudge`) and the validators that appended them are **deleted** — and with the empty draw went the LAST producer of a `Retry` nudge, so `Retry` carries none at all now. So is the run-end extractor's `BAILED` gate (`_has_text_bail_nudge`), which keyed on markers that can no longer occur. What still answers an empty FINAL answer is the loop's own honest close (`_empty_content_fallback`): a tools-stripped step whose hallucinated call is repaired away leaves nothing to say, and the run reports that rather than asking again.

### A coherent but WRONG tool call still gets an error tool response

- **A coherent but WRONG tool call still gets an error tool response**: the model acted, so the correction goes back as that call's failed result (`success=False`), and the model sees the failure narration (`You tried to use \`<tool>\` but it didn't work: (<tool> result)\nError…`) and retries — never a user-turn nudge. This is what survives the invalid-draw rejection above, because it is not a draw with no call. **There is no premature-`done` guard any more** (`run_shape_validators` is empty on every agent shape): a first-move `done()` — before any read/write/browse — closes the cycle like any other `done()`, read by the NOTIFY TRIGGER and the run-health `⚠ NO WORK DONE` flag exactly as a late one would be. Bounded by `max_steps` — on the final step the `done` closes the cycle. The send-tool's half-formed/truncation gates are this case on `send_message`.

### Degeneracy guard (discard-and-reroll)

- **Degeneracy guard (discard-and-reroll)**: gpt-oss:20b occasionally collapses mid-generation into a run of `.`/`…`/`?` ("...??…?..") when its context grows large — measured with a sharp onset around ~4K prompt tokens (a short abortive output, ~59 tokens), most often landing inside a tool-call argument.  The collapse is *poison*: it corrupts the entry/message it lands in, and once fed back into the conversation the next step is ~4× more likely to collapse too.  `Agent._invoke_nondegenerate` (in `agents/base.py`) checks every raw model output — text content, serialised tool-call arguments (the validation chain never sees tool-call responses; they short-circuit), **and** tool-call names — via `is_degenerate_run` / `is_degenerate_tool_name`, and on a hit **discards** the output (never appending it — appending is the contagion path) and re-rolls the *unchanged* context up to `DEGENERATE_REROLL_ATTEMPTS` (3); if it still can't get a clean draw it returns `None`, throwing out the run rather than acting on poison.  The name check applies only to a name that is **unregistered AND collapse-shaped** (`Functions?????`, `funcs.done?` — before the guard, those flowed to a tool-not-found error that kept the poison in context); an unregistered but plausible identifier (a near-miss like `collection_metadata`, or a Harmony-token-wrapped valid name — a repair case for the future Harmony strip, not poison) keeps the executor's tool-not-found path with its "Did you mean X?" hint.  The detector is also folded into `degenerate_reason`, so `collection_write` refuses poison content — nothing degenerate reaches `memory_entry`/`messagelog` even if the loop guard is bypassed.  The regex is tuned against the prompt-log corpus for zero false positives on legitimate punctuation ("Wait... what?!", code `...`).  Historical `promptlog` rows keep their poison (audit trail; never re-fed to the model).  Named `DEGENERATE_OUTPUT` in the condition catalog.  Since #1839 this machinery is shared with the whole **call-shaped-text family** (see the invalid-draw bullet above): a transport artifact and a shape violation are both draws that must not enter the run, one budget, one warning that names which condition tripped

### Leaked Harmony-envelope guard (discard-and-reroll)

- **Leaked Harmony-envelope guard (discard-and-reroll)**: the sibling of the degeneracy guard, sharing its exact discard-and-reroll machinery.  Some remote OpenAI-compatible backends serving gpt-oss (non-Ollama runners) fail to parse the Harmony tool-call envelope, so the *whole call* leaks into `message.content` as literal control-token text (`<|start|>assistant<|channel|>analysis to=functions.browse code<|message|><|call|>`) with `tool_calls` empty — nothing downstream catches it and a chat text turn would deliver the raw envelope to the user verbatim.  `Agent._invoke_nondegenerate` (helper `_unusable_output_condition`) checks every raw output for the transport artifacts and — when the draw carries no tool calls — for the agent shape's declared `invalid_draw_conditions` (#1839), returning WHICH condition tripped so the shared reroll's warning names it honestly.  On a leak it **discards** the output and re-rolls the *unchanged* context (the leak is intermittent — a fresh draw usually comes back clean), aborting the run after `DEGENERATE_REROLL_ATTEMPTS` rather than shipping raw tokens.  **Reject + reroll, never reconstruct** — parsing the envelope grammar ourselves would be brittle and redundant against the runner's own parser.  Sibling of `strip_harmony_control_tokens` (`llm/models.py`), which repairs a leak in the tool-call NAME field; this catches the whole call leaking into content, which the name path never sees.  Detector `has_leaked_harmony_envelope` in `text_validity.py` (keyed on Harmony sentinels, zero-false-positive discipline); named `TOOL_CALL_LEAK` in the condition catalog.  Mechanism pinned in `tests/agents/test_agentic_loop.py` (`TestHarmonyEnvelopeLeakGuard`)
