# The database and memory layer — reference

Covers the Data Model (every SQLModel table) and the store classes beyond the small ones left in the map. Read this in full before changing a table, a store's read/write shape, or the clock.

- **Emission provenance** — lives in `docs/reference/scheduler-and-collector.md`; `messagelog.mechanism` is the column, the collector notify path is what stamps it.
- **The skill substrate (`penny/skills.py`)** — lives in `docs/reference/conversation-machine.md`; this file covers only the registry store (`penny/skill_store.py`).

### penny/clock.py

  clock.py            — `Clock`: the ONE place the runtime asks what time it is (#2207). `Clock.now()` is the real clock, timezone-aware UTC; it sits on `Config.clock`, `Penny` hands it to `Database(clock=…)`, and every store and reader takes it from there (`db.clock`) — passed down, never ambient, never swapped while Penny runs. On it: the `Current date and time` line (`current_datetime_line`), the instant a user's words about time are counted from (`parse_expires_at`, whose `now` is a required argument), the `created_at` a schedule is anchored at and the `last_collected_at` it is paced from, the collector's readiness and expiry checks, the send cooldown, and every timestamp a store writes — each store stamps its rows explicitly from the clock it was given rather than leaving them to the models' `default_factory`, which stays only as the fallback for a row built outside a store. Deliberately NOT on it, because they measure the process or talk to a system with a clock of its own: model-call durations, uptime, OAuth/APNs token expiry, a browser socket's heartbeat age, the scheduler's monotonic intervals, the window a calendar plugin asks a remote calendar for, and the migration runner's bookkeeping. Production never passes one, so it runs on the real clock exactly as before; the eval harness passes a `PinnedClock`. `tests/test_clock.py` holds the seam: a full turn on a clock years away leaves no row stamped off the machine's

### penny/database/send_queue_store.py

    send_queue_store.py — SendQueueStore: durable outbound queue (enqueue, next_pending, mark_sent). `enqueue` stamps the row's `origin` (`CycleTrigger`, defaulting to `CADENCE` — the lane that waits out the cooldown, so bypassing it has to be claimed) and `next_pending(origin=…)` narrows to one lane in the WHERE (#1939)

### penny/database/memory/

    memory/           — the memory layer: `Memory` (base, memory_entry row access + shared similarity/cursor reads + shape-op no-ops) → `Collection` / `Log`, and the read-only facades `MessageLogMemory` (messagelog) / `RunLog` (promptlog); `MemoryStore` registry + the `memory(name)` dispatch factory; `types` (enums, errors, inputs); `_similarity` (pure dedup + retrieval math); `journal` (the bound collector cycle's UNDO journal, #1936 — `EntryPrior`, one entry's restorable state, and `CycleJournal`, the first-touch-per-key record of what each key held before the cycle touched it, replayed by `MemoryStore.end_cycle(revert=True)`); `LoggedToolCall` (the canonical round-trippable logged-call shape, #1560 — `name` is VERBATIM, so **every comparison reads `.tool`** instead, #2013: the dispatchable identifier, `strip_harmony_control_tokens` applied to the logged name. A backend that leaks Harmony control tokens produces `collection_write<|channel|>commentary`, which the LIVE object strips at the read-off boundary — so the call dispatched and the entry landed — while every consumer re-reading the LOG matched nothing, and skill extraction's surface test silently dropped the write step from 3 of 18 measured samples, persisting a routine that browses and keeps nothing with every visible signal green. The record keeps the leak (a real diagnostic signal, and the round-trip invariant `from_function(x.to_wire()) == x` holds unchanged); the projections — `render`, `_run_tool_calls` and everything they feed — read the tool). `db.memory(name)` returns the right object; `db.memories` is the registry, and `begin_cycle`/`end_cycle` are the journal's two calls

### penny/database/machine_store.py

    machine_store.py  — `MachineStore` (`db.machine`): the conversation state machine's durable half (#1706) — ONE append-only table, `state_transition`, and the machine's whole state is a fold over it (`latest_transition`: the newest row's `to_state` IS where the machine stands, its `anchor_message_id` IS the parked round's ask, its `created_at` IS when it last moved). No materialized current-state twin: it would carry nothing that isn't derivable and would mean two writes per move that can disagree — so `record_transition` is the SINGLE write that both advances the machine and audits it, and (unlike `MutationStore.record`) it is deliberately NOT best-effort, since a swallowed failure would lose the move itself. Deals in plain state STRINGS — `conversation_machine.py` imports the database package only function-locally to stay a leaf, so the typing seam lives there and this layer never imports the state enum (the same discipline `micro_context` keeps)

### penny/database/mutation_store.py

    mutation_store.py — `MutationStore` (`db.mutations`): the registry-mutation event ledger (#1560) — records + reads create/update/archive/unarchive/delete events (entity, run, actor, what changed) via `mutation_event`; plus `MutationDetail` / `EnumeratedDecision` (the options-presented record shape), `FieldPrior` and `render_mutation`. **`MutationDetail.priors` is the BEFORE half (#1946)**: `changed_fields` says a field moved, and this says what it moved FROM — the one fact neither the `memory` row (overwritten in place) nor the run's `promptlog` call (which carries only the value asked for) can still answer. Captured at the store chokepoint inside the transaction that applies the change (`_snapshot_fields` / `_priors_from` in `database/memory/store.py`, keyed off `_FIELD_PRIORS`, whose totality against `_MetadataUpdate.apply_to`'s labels is pinned by a test), and on the archive/unarchive flip too — there as a prior alone, with `changed_fields` left empty, since archiving is named by its ACTION. `value=None` is a positive statement (the field held nothing), which is why it is a model per field rather than a bare mapping. ADDITIVE: an event written before it existed decodes with an empty list, `_detail_tail`/`render_mutation` never read it, and every ledger render is byte-identical. Read back by `priors_for_run(entity_name, run_id)` — the fields ONE run changed, folded oldest-first so the first prior per field wins (the value the run found when it started, the only "was" a user asking about their own job means). `MutationEntityType` gained its second member in #1902 (`SKILL`, the case its docstring was declared for) and `MutationAction` gained `DELETED` — the skill registry's retirement, named as its own action rather than reusing `ARCHIVED` because that table is versionless: a reader following an archived collection finds it, a reader following a deleted routine does not. Both renders take the action as a free string, so the additions need no consumer change

### penny/skill_store.py

  skill_store.py    — `SkillStore` (`db.skills`): the versionless skill registry — `upsert` (create or REPLACE by name), `get`, `delete` + `restore` (#1902 — a bail taking back what its round wrote: `delete` for a name the round minted, since no archived flag exists on this table, and `restore` writing a whole `Skill` row back verbatim — timestamps included, nothing stamped — for a routine the round was re-teaching over), `list_all`, `resolve_by_meaning` (description-anchor cosine ranking, the fuzzy leg of #1591's name-or-meaning resolution), and (de)serialization of the structured `steps`/`parameters` JSON

### One job, one collection — identity dispatch on `collection_configure` (#1567/#1775)

- **One job, one collection — identity dispatch on `collection_configure` (#1567/#1775)**: `collection_configure` dispatches on the collection's **identity**, not on its name: the row the call names, else the row it DUPLICATES, else a new one. Duplicate detection is the two-tier `is_same_job` rule in the shared `similarity` package — **(1)** the same `skill` bound to the same `params` (both populated) is the same job whatever it is called; **(2)** otherwise strict token containment of the normalised names. **No threshold on either tier** — tier 2 is a set relation, so there is nothing to tune or drift. Normalisation (`tokenize_job_name`) folds separators (`_`/`-`/whitespace), case, and unicode dash variants, singularises (`singularize`, deliberately naive + conservative), and strips the closed `JOB_ROLE_WORDS` vocabulary — the words that name the *mechanism* watching a subject (`monitor`/`watcher`/`tracker`/`alerts`/`feed`/`latest`…) rather than the subject, so `aurora-deck-2-monitor` reduces to `aurora-deck-2`. Measured against the labelled corpus each layer earns its place (raw containment 4/7 → + role strip 5/7 → + stem 6/7, all at **zero** false merges). **Embeddings deliberately do NOT participate**: they are *anti*-correlated on the hard cases (the highest description cosine in the labelled set, 0.90, belongs to a pair that must not merge; the lowest, 0.24, to a real duplicate) because an embedding says "same kind of thing" and every trap is two collections of the same kind about different *specifics* — real duplicates are **extensions** (one name's tokens inside the other's), the traps are **substitutions** (`2`|`3`, `times`|`fares`, `bbc`|`cbc`), which containment separates by construction. `description_embedding` stays what `find` resolves on and says nothing about duplication. **On a match: an ACTIVE duplicate is UPDATED, not refused** — the refusal it replaced cost an entire observed turn (the model retried, got a byte-identical refusal, and the all-failed abort ended the turn with no reply); the result LEADS with a redirect note naming the collection the call actually landed on, since everything downstream has to use that name. An ARCHIVED match stays the #1567 tombstone refusal (reviving a retired mechanism is the user's call). **Not implemented**: tier 3 (near-containment + same-day + overlapping params → *ask*, never auto-merge), which is what would reach the substitution-shaped duplicates tiers 1-2 miss — the labelled misses are pinned in `tests/test_similarity.py` as a recorded gap.

### Memory framework (Stages 1–5, 9, 10)

- **Memory framework (Stages 1–5, 9, 10)**: A unified data primitive — *memory* — with two shapes (collection and log) and one access class `MemoryStore`. Collections dedup on write via a three-signal disjunction (key TCR, key cosine, content cosine — each with strict and relaxed thresholds in `PennyConstants`). Any strict hit, or any two relaxed hits, rejects the write. Logs append without dedup. Stage 2a added 21 model-facing memory tools (`memory_tools.py`). Stage 3 added `build_recall_block` (`recall.py`) — assembles ambient recall context for the chat agent's system prompt by dispatching each active memory by recall mode (`recent`/`relevant`/`all`); paired logs (`user-messages` + `penny-messages`) merge chronologically into a single Conversation section. **Polymorphic `Memory` objects + system-log facades**: the memory layer is a class per shape/backing (`penny/database/memory/`). `db.memory(name)` is the single dispatch — it returns a `Collection` or `Log` (both `memory_entry`-backed, the native store on the base) or a read-only facade, and every tool/recall/addon caller operates on that object polymorphically (wrong-shape ops refuse via base no-ops; nothing branches on a name or shape). `user-messages`/`penny-messages` are `MessageLogMemory` facades over `messagelog` (the object overrides the row primitives to read by direction, synthesizing `MemoryEntry`; a message has two authors — the user/incoming or Penny/outgoing; `append` refuses) and `collector-runs` is a `RunLog` facade over `promptlog` (renders each completed run as a record; `append` refuses) — no duplicated `memory_entry` rows, and the facade marker rows are seeded by migration so dispatch finds them. The cursor *read* logic lives on the `Log` base, uniform across backings; the reader's pending/commit cursor lifecycle stays in `LogReadTool`. `browse-results` is the one remaining real memory log (the browse tool writes it; it has no canonical table behind it). `messagelog.embedding` (for `read_similar` over messages) is filled by the startup backfill, which vectorizes any embedding-bearing table — nothing is copied between tables. Author is passed explicitly as a constructor argument or method parameter — write-capable tools take `author: str` at construction (`build_memory_tools(db, embedding_client, author)`), `BrowseTool(..., author=...)` is built per-agent with `author=self.name`, and `channel.send_response(..., author=...)` requires callers to pass it. No ambient/contextvar state. Embeddings are computed at write time (not lazily) so similarity reads work the moment a memory is reconfigured. `db.memories` replaces the per-domain stores that agents will be ported onto in subsequent stages. See `docs/archive/task-framework-plan.md` (design) and `docs/archive/memory-implementation-plan.md` (staged rollout)

### Data Model

## Data Model

All tables defined in `database/models.py` as SQLModel classes:

- **PromptLog**: Every LLM call — `model`, `messages` (JSON), `response` (JSON), `thinking`, `duration_ms`, `agent_name`, `run_id`, `run_outcome`/`run_reason`/`run_target`, `tool_failures` (count of failed tool calls in the run, stamped on the last prompt alongside the outcome — the structural signal the run-health classifier reads), `trailing_messages` (**the run tail**, migration 0102, #1778: the turns the agent loop appended AFTER this call — the terminal assistant tool-call turn plus its tool-result turns — which no later call carried. A tool RESULT is otherwise durable only as a side effect of being fed back, riding into the NEXT call's `messages`; a run that ends the instant a tool returns — a write-gate STOP, `max_steps` on a tool step, a reroll abort, an exception — has no next call, so its terminal outcome was recorded nowhere, and those are exactly the runs worth reading afterwards. Same wire shape as `messages` (it is literally what the next call's `messages` would have ended with), so the readers concatenate rather than merge and one decode path serves both. Stamped by `MessageStore.set_run_trailing_messages` from `Agent._run_agentic_loop`'s `finally` — the universal per-run chokepoint, chat and collector alike, and the one place that still holds the tail when the loop dies (`set_run_outcome` is collector-only, and the motivating case was a chat turn). Empty tail → no write at all, so an ordinary run is untouched and renders byte-identically. Read via `_run_tool_turns` (`database/memory/objects.py`), the single COMPLETE tool-turn accessor behind `render_run_calls` / `project_run` / the I/O tally / the egress-media trace, and via `_row_turns` in the eval harness's transcript extractor — so neither can be missing an entry)
- **MessageLog**: Every user/agent message — `direction`, `sender`, `content`, `parent_id` (thread chain), `external_id` (platform ID), `is_reaction`. (The `thought_id` FK into the legacy `thought` table was dropped by migration 0097 — historical rows lose only that link.) **Emission provenance** (migration 0088, #1568): `mechanism` — the bound collection whose autonomous cycle produced an outgoing send; a by-name reference to `memory.name`, a plain column like `mutation_event.entity_name` (a DB-level FK would close a circular foreign-key cycle with `memory.source_message_id`), served by the partial `ix_messagelog_emission_time` index. NULL for a direct reply (a chat turn with a live triggering user message names no mechanism); the drainer stamps it at delivery time from the queued row's `collection`. Provenance renders where the message renders: the `penny-messages` facade shows `(sent by <mechanism>)` inline on every read, so "which mechanism sent this?" is the same call that read the message
- **UserInfo**: User profile — `name`, `location`, `timezone` (IANA), `date_of_birth`
- **CommandLog**: Command invocations — `command_name`, `command_args`, `response`, `error`
- **RuntimeConfig**: User-configurable settings — `key`, `value` (string, parsed on read)
- **MuteState**: Per-user mute state — row exists = muted, delete = unmuted
- **Device**: Registered devices (Signal, Discord, browser addons) — used for multi-device routing and domain permission prompts
- **DomainPermission**: Per-domain allow/deny state for browser extension web access, synced across addons
- **Thought**: **REMOVED** (migration 0097, #1676) — the legacy inner-monologue table (`content`, `title`, `image`, `valence`, `preference_id` FK, `notified_at`). The thoughts pipeline it backed was nuked in the same migration (the `thoughts` collection and its retired pair), which killed its last consumer; the table, its model, and `ThoughtStore` (`db.thoughts`) are deleted
- **Preference**: **REMOVED** (migration 0097, #1676) — the legacy user-sentiment table (`content`, `valence`, `source`, `mention_count`, `embedding`, `last_thought_at`). Its last real consumers — the thoughts pipeline's seed-preference pick (nuked in the same migration), the startup preference-embedding backfill, and the `/profile` onboarding check — died with it; the table, its model, `PreferenceStore` (`db.preferences`), and the `PreferenceValence`/`PreferenceSource` enums are deleted. This resolves the #1301 legacy question for the table itself; preference-shaped data lives in the `dislikes` collection (and topic-specific collections)
- **Knowledge**: Summarized web page content — `url` (unique), `title`, `summary` (prose paragraph), `embedding`, `source_prompt_id` FK (extraction watermark). One entry per URL, upserted on revisit
- **Memory**: Unified container for the task/memory framework — `name` (PK), `type` (`collection` or `log`), `description` (content-reflective; doubles as the resolve-by-meaning anchor, #1558), `description_embedding` (the anchor vector, backfilled at startup), `notify` (emission-as-property, migration 0085, #1591/#1557: the **sole** emission flag — when true the collection tells the user about new/changed entries via the run-time notify steps appended to its collector prompt before the injected terminal `done()`; set at creation from `collection_create(notify=…)`, flipped by `collection_update(notify=…)`. The `published` pub/sub column + the `notifier` consumer + `read_published_latest` were retired by migration 0086/#1557), `archived`. **Operational-registry provenance + lifecycle** (migration 0081, #1566): `source_message_id` (FK → `messagelog.id`, the spawning user message — linked post-run by `link_source_message`, matched on `created_by_run_id`), `created_by_run_id` (the `promptlog.run_id` of the creating chat run, stamped by `collection_create`). All nullable — seeded/system rows carry none. `memory_get` renders these as a status/expires/created-from-message block. **Schedule** (migration 0104, #1857): `schedule` (nullable) — ONE RRULE string, the whole schedule grammar; `Collector._is_ready` gates on the rule's next occurrence after `last_collected_at or created_at` (the rule's own `DTSTART:` line wins when it has one, else the recurrence anchors at `created_at`). **That anchor is the user's WALL CLOCK (#1932)**: an RRULE states an hour (`BYHOUR=9`) and never a zone, so the zone comes from the profile (`UserInfo.timezone`, `None` → UTC) — `created_at` is converted into it and its seconds zeroed, and `next_occurrence` (`tools/collection_instantiation.py`, DB-free, the zone passed in as a parameter) is the one seam that reads a stored rule. Reading it in UTC is what fired a briefing asked for at a local morning hour four hours early on a UTC-4 profile while the reply promised the local time; zeroing the seconds is what stopped a collection created at `:51` past from being a job that fires at `:51` past for ever. Because `ZoneInfo` resolves the offset per occurrence, a stated hour holds across a DST boundary. The rule text is **never rewritten** — normalising the hour to UTC at store time would make the render a translation of the ask and re-passing it would convert a second time — so `render_schedule_clause` still round-trips. An explicit `DTSTART:…Z` states its own zone and stays an exact instant; a FLOATING `DTSTART` (no `Z`) states none, which RFC 5545 calls local time, so it is read on the same user clock (which also stops it coming back naive and raising in the shared readiness comparison). It **replaced six columns** — `collector_interval_seconds`, `run_at` (folded into `DTSTART`), `source_log` (the dropped `on advance of` form), `cron_expression`, and the auto-throttle pair `base_interval_seconds` / `consecutive_idle_runs` — with no conversion of existing trigger data (code-owner ruling: deployments reset after this arc), logged loudly per collection at migration time. **End conditions**: `expires_at` + `max_runs` (both nullable) archive the collection when the time passes / the quota is reached; both are settable directly and are what the rule's `UNTIL=` / `COUNT=` are lifted into at parse. **Skill provenance** (migration 0090, #1603): `skill_name` (a by-name reference to `skill.name` — a plain column, not a DB FK, since a skill is re-teachable/REPLACE-able) + `skill_params` (the params bound into the skill's render, as JSON) — stamped by `collection_create` at instantiation; both nullable, NULL for a hand-authored/seeded collection. `memory_get` renders them as a `from skill: <name> (<param>=<value>, …)` line (params omitted when the skill had no holes; the whole line absent — byte-identical render — when `skill_name` is NULL), so "which skill made this, and with what?" is a read off the collection's own row and the rebind/re-render (#1620) reads those bindings as its input. **Re-render from a skill** (#1620): `collection_update(skill=…, params=…)` re-renders a collection's `extraction_prompt` from a skill's CURRENT steps and re-stamps this pair — four cases: **refresh** (the same skill re-taught → re-render from its current definition), **rebind** (new `params`, same skill), **swap** (a different `skill`, full #1591 resolution + hole validation), **adopt** (a legacy `skill=NULL` collection given a skill for the first time, its hand-authored text replaced by the render). The re-render is the SAME `render_skill` fn `collection_create` stamps at birth (so the steps-1..A / no-stored-`done()` invariant holds by construction), records a `mutation_event` with the run id, and echoes the newly rendered program (`render_reinstantiation_echo`, mirroring the creation echo). A plain `collection_update(notify=…)` etc. leaves the prompt + provenance untouched; a raw `extraction_prompt` alongside `skill`/`params` is a conflict. The resolve + render machinery is shared with `collection_create` (`resolve_skill` / `render_skill_prompt` in `tools/memory_tools.py`), not duplicated. **Inert + apply-time job (#1629)**: a skill-less `collection_create` creates an inert storage collection (no prompt/cadence/notify — never dispatches); the second half of the teach bootstrap is `collection_update`'s **adopt** case giving it a skill. Two apply-time rules ride both paths: (1) **retarget-at-apply** — every ATTACHMENT-MARKED leaf is bound to the target collection's own name at the render seam (`retarget_writes` in `database/skills.py`), since "apply this routine HERE" is what decides a leaf that named a collection and nobody supplied — so a skill demoed against collection A, applied to B, acts on B (the rendered program never lies about the collection it acts on). Since #1777 that leaf is a PLACEHOLDER in the stored skill (`{the collection this is set up on}`) rather than a baked constant, so retarget *binds* it rather than overwriting it — and an UNinstantiated skill (the ambient recipe, the stored row) names no collection at all. Since #1783 the binding is keyed to the per-leaf MARK, not to a tool whitelist (which `retarget_writes` used to recompute independently — one policy, two copies): a `log_append` target, a plugin tool's target, or a read of the routine's own collection all participate without being enumerated, and since #1828 nothing clears a mark — a destination is never a parameter (#1827 principle 4) — so every marked leaf lands on the attached collection, and a user-named destination becomes a bindable parameter only if the framer decides so from the ask; (2) **schedule + notify are apply-time job properties** — `collection_update` accepts the same one-arg `schedule` (plus `expires_at` and `notify`), REPLACING the stored schedule atomically along with the run quota lifted out of it, and recording `schedule`/`expires_at` in the mutation's changed fields. `memory_get` renders an inert collection with an honest `steps: none` line. Collections are keyed sets with dedup on write; logs are append-only keyless streams
- **MemoryEntry**: One entry in a memory — `memory_name` FK, `key` (nullable for logs), `content`, `author`, `key_embedding`, `content_embedding`. Entries are immutable once written — `update` replaces content for a given key. **Entry-level provenance** (migration 0083, #1560): `created_by_run_id` + `last_written_by_run_id` — the run that first wrote the entry and the run that last rewrote it (a collection entry is overwritten each cycle, so the current-value writer differs from the creator). Stamped at write time by the writing run, threaded as a parameter (no ambient state); both nullable (pre-#1560 / migration-seeded rows carry neither). The run id is the join key into the ledger (the `promptlog` write events); these two stamps are the read-path anchors that keep `run_list` one guess-free hop from wherever an entry renders
- **MutationEvent** (`mutation_event` table, migration 0083, #1560): One durable create / update / archive / unarchive of a registry entity (a collection) — `entity_type`, `entity_name`, `action`, `actor` (`user-run` | `system`), `run_id` (the causing run — the ledger join key), `detail` (JSON `MutationDetail`: changed-field names, a cause note, and the options-presented `EnumeratedDecision` accommodation), `created_at`. The event half of the operational spine (the entity half is #1566's `memory` columns): the `memory` row stays the materialized truth (its `archived` flag), and this table is the audit/provenance trail of how it got there — so "when was this archived, and by what?" is a read. The one ledger table with no other home: an entry write is a `promptlog` tool call and a run is a `promptlog` group, but a *system* archive (the scheduler's `max_runs` / `expires_at` retire) runs no model and logs no prompt. Written at the `MemoryStore` chokepoint (`create` / `_set_archived` / `update_collection_metadata`); read via `db.mutations.history(name)`, rendered into `memory_get`'s "Recent changes" block, each line naming its run id (the anchor invariant). Audit, not event sourcing
- **StateTransition** (`state_transition` table, migration 0100, #1706): One move of the conversation state machine — and, as the newest row, the machine's WHOLE state. `from_state`/`to_state` · `cause` (`TransitionCause`: `classifier` — a model draw, carrying the `run_id` join key into the promptlog | `structural` — no model in the loop, the post-apply reset; the mutation ledger's user-run/system split's twin) · `outcome` (the `StateDrawOutcome` of a classifier draw, NULL for a structural move) · `anchor_message_id` (FK → `messagelog.id` — the instigating ask the machine is anchored to AFTER this move: set on entry to a parked state, carried unchanged through the round, NULL once idle; a fact about the transition like `to_state`, not a copy, so the anchor's whole history is readable) · `message_id` (FK) · `run_id` · `skill_name` (what a SKILL-GATED decision bound, by name — a plain column like `messagelog.mechanism`, since a skill is REPLACE-able) · `skill_frame` (the round's FRAMING as serialized `RoundFraming` JSON — the signature the framer drew when the machine entered learn and the container Python built from it, #1868. Beside `skill_name` because it answers the same kind of question about the move — what routine this is about — for the case where the routine does not exist YET: the skill row still enters the registry only at run end, so a framed name is not a `skill.name` to reference. A draw varies and a re-draw is not a re-read, so the entry decision is RECORDED and later read; it rides the anchor's lifecycle — set on entry, carried while parked, NULL once idle) · `round_shortfall` (the round's PARTIAL binding as serialized `RoundShortfall` JSON, #1894 — `skill_frame`'s sibling for a round the words fall SHORT of, which has no signature and no container yet: the routine the ask is covered by, the values already settled, and the parameters that got none. Recorded for the same reason a framing is — a draw varies, so what a round is waiting on is READ on every later turn rather than re-derived from raw conversation — and carried by the state that reads it: only a move LANDING in request keeps one) · `round_provenance` (the round's PROVENANCE as serialized `RoundProvenance` JSON, #1902 — the whole `skill` row that stood under this round's pinned name BEFORE the round opened. Three states, because calling a round off owes the registry three different things: NULL when the round minted nothing (a skill-gated round binds a routine the user already had, so a bail leaves it alone), present-and-empty when the round minted its name over nothing (a bail deletes it), and present-carrying-a-row when the round was re-teaching — that row being what a bail puts back, since by then the round's own run-end extraction has already replaced what that routine does, so merely skipping the delete would leave an abandoned, half-corrected program live under a name existing jobs still run. Settled on the move that MINTS the round's routine — the last point at which "what was here before" is still readable — and carried the framing's way) · `created_at` (indexed, with `cause`/`run_id`). **An append-only log with NO materialized twin**: the newest row's `to_state` is where the machine stands, its `anchor_message_id` the parked round's ask, its `created_at` when it last moved — a current-state row alongside would carry nothing that isn't derivable and would mean two writes per move that can disagree, so there is one write and a failed write moves nothing. (The `memory`/`mutation_event` twin earns itself only because a `memory` row carries name/description/prompt/cadence — facts no event derives; the shape does not transfer.) `from_state` beside `to_state` is deliberate denormalization — derivable from the previous row by join, but on an append-only log a self-describing row is cheaper to read. Nothing is seeded: the cold start is the ABSENCE of history (no rows = idle), never a row asserting it. **Every draw appends a row, including one that moved nothing** — `outcome` distinguishes fail → stay from a decided idle → idle, and scoring per-edge accuracy over production history needs the held draws (a log of only successful transitions reports a perfect classifier by construction)
- **Skill** (`skill` table, migration 0084, #1590): A named, immutable, **versionless** certified-by-execution script distilled from ONE demonstrated run — `name` (PK, unique key; re-teaching REPLACES the row — no version history, since collections carry the rendered TEXT snapshotted at creation), `steps` (JSON `list[SkillStep]` — the `LoggedToolCall` shape copied verbatim from the ledger + per-leaf substitutions), `parameters` (JSON `list[SkillParameter]` — declared SKILL-level parameters, semantic name + required + optional one-line description, #1668; was `holes` before the rename migration 0096), `intent` / `description` (+ `description_embedding` for future resolution, populated at write), `source_run_id` (the demonstrated run — the triggering message reachable *through* it), `author` (the teaching agent), `created_at`/`updated_at`. Authored ONLY by the framework — **there is no `skill_create` tool** (#1658). At the end of every LEARN chat turn the run-end extractor (`penny/skill_extraction.py`) snapshots THAT run's own ledger. **The gate is the STATE, not the run's shape (#1850)**: extraction runs if and only if the turn's landed machine state is `learn` (threaded in as a parameter; no machine history = idle = no extraction), so teaching is the one thing that mints a routine and an apply/idle turn that happens to browse-and-write mints nothing. What remains is mechanics — chat run · ≥1 tool call · ≥1 certified step (the `BAILED` health gate is retired, #1839 — the call-shaped-text bails it keyed on are re-rolled by the loop and can no longer appear in a completed run) — and the read+write taxonomy that once refused a pure read ('answering') and a pure write ('the storage atom') is DELETED: a taught round is learned whatever shape it had. It then captures the run's non-`done` tool calls, keeps the ones that SUCCEEDED and DROPS the rest (filter-not-refuse, #1659), so certified-by-execution holds by construction. Registry-navigation ORIENTATION verbs (`find`/`memory_get`, #1665) are excluded before distill — dropped from the recipe, since a re-run re-orients itself and a `find` result echoing its query can otherwise manufacture a false binding. Only COLLECTOR-runnable steps are captured (#1668): a skill renders into a collector prompt, so a lifecycle call a demo made mid-run (e.g. `collection_create` to set up the container) is dropped from the recipe like an orientation call — filtered against the real `collector_tool_surface` (the same masked surface the authoring-time guard validates extraction_prompts against), so a captured step is never one a collector could never run. Each argument is factored by STRUCTURAL provenance (#1659, `distill_steps`, never by matching the user's prose): a value that equals / occurs as a whole span of / wraps a prior step's result → a binding (`the value from step N`) — comparison is against the result's PAYLOAD, not the framed text (#1665/#1661: the tool-result frame — narration+tag header, browse fetch-handle tail — is stripped first, so a wrapping arg like `Price: $499` over a returned `$499` binds without any fuzzy threshold). **The two directions are asymmetric (#1809)**: *wraps* is plain containment (the whole result sits inside the argument — no coincidence to guard against, and the prose around it ends in ordinary punctuation a span test would reject), while *contained-in* demands the value be a WHOLE whitespace-delimited span of the payload, because that payload may be an entire fetched PAGE and a page contains most short strings by accident. The motivating false binding: a browsed listing's own URL (`…/aurora-deck-2`) carries the product slug, so a write KEY the assistant slugged the same way bound to "the value from step 1" — the price — and the learned routine stored each cycle's price under a key that was also the price, never overwriting. A copy is a whole span of the result; a slice out of the middle of a token is a character coincidence. **Neither direction is asked at all for a value that is already a parameter (#1933)**: identical values collapse to one candidate, so a leaf repeating a value an earlier leaf minted joins that parameter first — a page fetched twice in one demonstration is one input given twice, and reading the repeat as the first fetch's OUTPUT produced `browse(queries=[the value from step 1])`, a routine that no longer says which page it reads. And what a step PRODUCED excludes what it was CALLED with: a result quoting its own arguments back (`## browse: <url>`, an extract result opening with its instruction) is frame in the same sense the narration line is, so those spans are removed from the contained-in comparison — nothing keyed to a tool, so an unheard-of tool that echoes is covered too, and the redirect lands on the step that actually produced the value. Every other string leaf → a **required** parameter (shared values collapse to one; no silent default — an unbound parameter is a loud refusal at instantiation). **That last rule is a DEFAULT, not a determination (#1770)**: it assumes an unexplained value came from the user, which is false for one the model derived-and-transformed from a result or invented outright — and produced skills with required parameters nobody could supply. Those two origins share no literal span with what produced them, so no substring test can reach them (and #1659 ruled prose matching out), so the question is not asked at all any more (#1824/#1828): EVERY leaf is a placeholder, and the run-end draw NAMES each one — a semantic name + one line of what belongs there each run, written by a single-shot leaf-labelling micro-context (one `LABEL <current>: <semantic_name> — <description>` line per spot, poison-screened + re-rolled). A labelled leaf's sites become `SkillSubKind.PLACEHOLDER` substitutions carrying that description, which `render_skill` emits as `{<what belongs there>}` — the same placeholder syntax an unbound parameter uses, and **never the frozen demonstrated value** (freezing is the specific harm: a collector re-running the skill would write that stale phrase into the collection every cycle, forever). The draw must COVER every offered spot with exactly one well-formed line (#1828) — a missing, malformed, repeated, or invented line fails the WHOLE draw after the reroll budget, and every spot then keeps its arg-derived REQUIRED parameter — extraction never blocks. **The interface is the FRAMER's (#1824/#1830)**: a SEPARATE run-end draw, over the user's own turns and nothing else, writes the routine's `name`, `description` and `parameters` — minted from the ask rather than sorted out of what the demonstration used, so a routine never names itself for something it then asks for; a failed framing falls back to the deterministic slug of the triggering message + that message, with no parameters. **The RUNTIME JOIN (#1907)**: each declared parameter also carries `value`, the value the round that taught the routine demonstrated it with — the one observable the framer and the labeller share, since neither sees the other's evidence — and `bind_parameters` uses it at the instantiation seam to write a collection's bound values into the leaves the demonstration put its own values in. So `parameters` live at SKILL level — rendered in the registry, enforced at `collection_configure`, decisive for `is_same_job` tier 1 — over a STORED recipe that still reads in the labeller's placeholder descriptions (a routine at rest is pointed at nothing), while the program a CONFIGURED collection runs names the page it fetches and the thing it looks for. A parameter with no demonstrated value (a legacy row, a failed framing) joins nothing and the program renders as it always did; one with no bound value leaves its leaf naming the gap rather than keeping a description that reads like an instruction. description_embedding anchors on the framer's GENERIC description (dedup converges cross-instance); dedup REPLACES an existing skill by name, or by same tool-sequence shape + description-embedding match keeping the existing name. **A round carrying a FRAMING is keyed by it, and the ladder does not run at all (#1902)**: the write lands on the name the round PINNED at entry, so the round's second run (the correction) replaces its own routine in place — one round, one routine — and no same-shaped, same-meaning sibling can capture the write and file this round's routine under another job's name (which would leave the container the round has been writing into pointing at a routine no longer called that). Promotion is implicit SURVIVAL: there is no draft flag, the routine simply outlives its round, and a BAIL takes it back by the round's PROVENANCE (`round_framing.abandon_round_skill` — `db.skills.delete` for a name the round minted over nothing, `db.skills.restore` of the recorded pre-round row for one it was re-teaching, and nothing at all for a round that minted no routine). Internal identifiers are `parameters`, not "hole" (the PL jargon renamed in #1668; the `skill.holes` column → `parameters` via migration 0096). **The collection name is a spot like every other one (#1783/#1828)**: it is named by the same draw, and it additionally carries the **attachment mark** when its demonstrated value names one of Penny's collections (registry-derived — nothing in this path knows which tools a skill contains). Nothing clears the mark: where a routine writes is decided by what it is applied to, so the attachment fills every marked leaf at instantiation and it renders the labeller's own wording; a marked leaf the draw never named falls back to the fixed `WRITE_TARGET_DESCRIPTION` rather than to a required parameter nobody could bind, and migrations 0101/0103 back-fill the placeholder + mark onto skills taught before either change. (This supersedes #1783's other direction — two destinations the USER named stayed two bindable parameters because a verdict cleared the mark; with no verdict, a user-named destination comes back as a parameter only if the framer decides so from the ask, which is where that decision belongs.) **No seed library** (code-owner decision on the #1599 revision): the table ships empty, every skill enters through a learn turn's own run, so the invariant holds universally with no hand-authored exception. #1591's `collection_create` renders a skill + bound params into a collection's `extraction_prompt`
- **AgentCursor**: Per-reader read progress through a log-shaped memory — `(agent_name, memory_name)` PK, `last_read_at` high-water mark. Advanced two-phase by the orchestrator (pending during a run, committed on success). For collectors the cursor owner is the **bound collection name**, not the constant `"collector"` identity — otherwise every collection reading the same log (e.g. the many that read `user-messages`) would collapse onto one shared cursor and starve each other
- **Media**: Images captured while browsing or drawn on request, delivered side-channel — `mime_type`, `data` (raw bytes), `source_url`, `title`, `embedding` (of title+URL for browsed rows, of the description for generated rows). The browse tool stores every page image here; at channel egress `MediaStore.select_image` attaches the most relevant image, most-relevant-first: (1) **exact URL** — if the outgoing message links a page we captured, that page's own image (newest capture); (2) **same domain** — else the embedding-nearest image from a domain the message links; (3) **fallback** — else a uniform-random pick among the top-K embedding-nearest (jitter, so a centroid "magnet" image can't repeat on consecutive messages — applied *only* to this tier; URL/domain matches are deterministic). No floor, so a reply still carries an image whenever one matches. A `generate_image` row is delivered **by id to its own reply** (`send_response(media_ids=...)`, from `ToolResult.media_id`) with precedence over this ladder — never fuzzy-matched for that reply, but in the pool for future ones (#1564). Zero model involvement — no `<media:ID>` tokens, no prompt changes
- **SendQueueItem** (`send_queue` table): Durable outbound message queue — `content`, `collection` (the collector that queued it), `origin`, `created_at`, `sent_at` (nullable; `NULL` = still pending, single source of truth — no separate flag). A finished cycle's notification is enqueued here instead of being dropped when the autonomous-send cooldown hasn't elapsed (#1911: `CollectorNotifier.queue`, which holds the refusal / no-recipient / mute gate the retired `send_message` tool used to); the `SendQueueDrainer` delivers the oldest pending row its lane allows out — stamping the row's `collection` onto the delivered `messagelog` row's `mechanism` (#1568). Kept after delivery (stamped `sent_at`) as an audit trail. **`origin` (migration 0109, #1939) is WHICH LANE**: the `CycleTrigger` that set the queuing cycle running — `cadence` (the schedule's own dispatch; ride the full cooldown) or `on_demand` (the user's "run this now"; deliver on the next tick, because they are sitting in front of it waiting). NOT NULL, defaulting to `cadence` on the column and in `enqueue`, so an unstamped row is in the conservative lane and skipping the cooldown is something a caller has to claim. Observed live: an on-demand run's notification waited ~10.5 minutes because an unrelated chat reply seconds earlier had started the cooldown
