# The database and memory layer — reference

Covers the Data Model (every SQLModel table) and the store classes beyond the small ones left in the map. Read this in full before changing a table, a store's read/write shape, or the clock.

- **Emission provenance** — lives in `docs/reference/scheduler-and-collector.md`; `messagelog.mechanism` is the column, the collector notify path is what stamps it.

### penny/clock.py

  clock.py            — `Clock`: the ONE place the runtime asks what time it is (#2207). `Clock.now()` is the real clock, timezone-aware UTC; it sits on `Config.clock`, `Penny` hands it to `Database(clock=…)`, and every store and reader takes it from there (`db.clock`) — passed down, never ambient, never swapped while Penny runs. On it: the `Current date and time` line (`current_datetime_line`), the instant a user's words about time are counted from (`parse_expires_at`, whose `now` is a required argument), the `created_at` a schedule is anchored at and the `last_collected_at` it is paced from, the collector's readiness and expiry checks, the send cooldown, and every timestamp a store writes — each store stamps its rows explicitly from the clock it was given rather than leaving them to the models' `default_factory`, which stays only as the fallback for a row built outside a store. Deliberately NOT on it, because they measure the process or talk to a system with a clock of its own: model-call durations, uptime, OAuth/APNs token expiry, a browser socket's heartbeat age, the scheduler's monotonic intervals, the window a calendar plugin asks a remote calendar for, and the migration runner's bookkeeping. Production never passes one, so it runs on the real clock exactly as before; the eval harness passes a `PinnedClock`. `tests/test_clock.py` holds the seam: a full turn on a clock years away leaves no row stamped off the machine's

### penny/database/send_queue_store.py

    send_queue_store.py — SendQueueStore: durable outbound queue (enqueue, next_pending, mark_sent). `enqueue` stamps the row's `origin` (`CycleTrigger`, defaulting to `CADENCE` — the lane that waits out the cooldown, so bypassing it has to be claimed) and `next_pending(origin=…)` narrows to one lane in the WHERE (#1939)

### penny/database/memory/

    memory/           — the memory layer: `Memory` (base, memory_entry row access + shared similarity/cursor reads + shape-op no-ops) → `Collection` / `Log`, and the read-only facades `MessageLogMemory` (messagelog) / `RunLog` (promptlog); `MemoryStore` registry + the `memory(name)` dispatch factory; `types` (enums, errors, inputs); `_similarity` (pure retrieval math — embedding stacking + cosine; entry identity is `identity`), `identity` (the entry-identity ladder: rules, shortlist, decision model, honest question, #2715); `journal` (the bound collector cycle's UNDO journal, #1936 — `EntryPrior`, one entry's restorable state, and `CycleJournal`, the first-touch-per-key record of what each key held before the cycle touched it, replayed by `MemoryStore.end_cycle(revert=True)`); `LoggedToolCall` (the canonical round-trippable logged-call shape, #1560 — `name` is VERBATIM, so **every comparison reads `.tool`** instead, #2013: the dispatchable identifier, `strip_harmony_control_tokens` applied to the logged name. A backend that leaks Harmony control tokens produces `collection_write<|channel|>commentary`, which the LIVE object strips at the read-off boundary — so the call dispatched and the entry landed — while every consumer re-reading the LOG matched nothing, and skill extraction's surface test silently dropped the write step from 3 of 18 measured samples, persisting a routine that browses and keeps nothing with every visible signal green. The record keeps the leak (a real diagnostic signal, and the round-trip invariant `from_function(x.to_wire()) == x` holds unchanged); the projections — `render`, `run_tool_calls` and everything they feed — read the tool). `db.memory(name)` returns the right object; `db.memories` is the registry, and `begin_cycle`/`end_cycle` are the journal's two calls

### penny/database/mutation_store.py

    mutation_store.py — `MutationStore` (`db.mutations`): the registry-mutation event ledger (#1560) — records + reads create/update/archive/unarchive/delete events (entity, run, actor, what changed) via `mutation_event`; plus `MutationDetail` / `EnumeratedDecision` (the options-presented record shape), `FieldPrior` and `render_mutation`. **`MutationDetail.priors` is the BEFORE half (#1946)**: `changed_fields` says a field moved, and this says what it moved FROM — the one fact neither the `memory` row (overwritten in place) nor the run's `promptlog` call (which carries only the value asked for) can still answer. Captured at the store chokepoint inside the transaction that applies the change (`_snapshot_fields` / `_priors_from` in `database/memory/store.py`, keyed off `_FIELD_PRIORS`, whose totality against `_MetadataUpdate.apply_to`'s labels is pinned by a test), and on the archive/unarchive flip too — there as a prior alone, with `changed_fields` left empty, since archiving is named by its ACTION. `value=None` is a positive statement (the field held nothing), which is why it is a model per field rather than a bare mapping. ADDITIVE: an event written before it existed decodes with an empty list, `_detail_tail`/`render_mutation` never read it, and every ledger render is byte-identical. Read back by `priors_for_run(entity_name, run_id)` — the fields ONE run changed, folded oldest-first so the first prior per field wins (the value the run found when it started, the only "was" a user asking about their own job means). `MutationEntityType` gained its second member in #1902 (`SKILL`, the case its docstring was declared for) and `MutationAction` gained `DELETED` — the skill registry's retirement, named as its own action rather than reusing `ARCHIVED` because that table is versionless: a reader following an archived collection finds it, a reader following a deleted routine does not. Both renders take the action as a free string, so the additions need no consumer change

### One job, one collection — identity dispatch on `collection_configure` (#1567/#1775)

- **One job, one collection — identity dispatch on `collection_configure` (#1567/#1775)**: `collection_configure` dispatches on the collection's **identity**, not on its name: the row the call names, else the row it DUPLICATES, else a new one. Duplicate detection is `is_same_job` (`similarity/dedup.py`) — strict token containment of the normalised names. **No threshold** — it is a set relation, so there is nothing to tune or drift. Normalisation (`tokenize_job_name`) folds separators (`_`/`-`/whitespace), case, and unicode dash variants, singularises (`singularize`, deliberately naive + conservative), and strips the closed `JOB_ROLE_WORDS` vocabulary — the words that name the *mechanism* watching a subject (`monitor`/`watcher`/`tracker`/`alerts`/`feed`/`latest`…) rather than the subject, so `aurora-deck-2-monitor` reduces to `aurora-deck-2`. Measured against the labelled corpus each layer earns its place (raw containment 4/7 → + role strip 5/7 → + stem 6/7, all at **zero** false merges). **Embeddings deliberately do NOT participate**: they are *anti*-correlated on the hard cases (the highest description cosine in the labelled set, 0.90, belongs to a pair that must not merge; the lowest, 0.24, to a real duplicate) because an embedding says "same kind of thing" and every trap is two collections of the same kind about different *specifics* — real duplicates are **extensions** (one name's tokens inside the other's), the traps are **substitutions** (`2`|`3`, `times`|`fares`, `bbc`|`cbc`), which containment separates by construction. `description_embedding` stays what `find` resolves on and says nothing about duplication. **On a match: an ACTIVE duplicate is UPDATED, not refused** — the refusal it replaced cost an entire observed turn (the model retried, got a byte-identical refusal, and the all-failed abort ended the turn with no reply); the result LEADS with a redirect note naming the collection the call actually landed on, since everything downstream has to use that name. An ARCHIVED match stays the #1567 tombstone refusal (reviving a retired mechanism is the user's call). **Not implemented**: a near-containment + same-day + overlapping-params *ask* (never auto-merge), which is what would reach the substitution-shaped duplicates containment misses — the labelled misses are pinned in `tests/test_similarity.py` as a recorded gap.

### Memory framework (Stages 1–5, 9, 10)

- **Memory framework (Stages 1–5, 9, 10)**: A unified data primitive — *memory* — with two shapes (collection and log) and one access class `MemoryStore`. Collections decide entry identity on write through the **identity ladder** (`penny/database/memory/identity.py`, #2715): (1) deterministic rules (`similarity/identity.py`) — keys equal after normalising (case, accents, punctuation, separators, a leading `the`, a trailing parenthetical, brackets) are the same entry; identical content is a repeat; keys differing in a number token (digits, Roman numerals) are different entries; (2) an embedding shortlist ranks the top few stored entries (ranking only, no cutoff); (3) one choice question per candidate to the decision model (`LLM_DECISION_MODEL`, `penny/llm/decision_client.py`, Ollama's `/v1/systemone`) — `same_value`/`new_value`/`different`/`unsure`; (4) unsure, or no model configured (the named degraded mode, preflight-warned), writes through as new and the tool reply asks the writing model honestly whether it meant the shortlisted candidate. The write itself takes the ladder's decisions as a REQUIRED parameter (`identity` owns the decision, the store only applies it): a `new_value` verdict MERGES — the stored value replaced in place, the prior reported with the one call that restores it — so a look-alike is never rejected and never silently overwritten. The ladder is split three ways so no blocking HTTP runs on the event loop: sync rules+shortlist, async decision (the same async path that embeds), sync apply. The manual entry writes (browser addon, iOS) run the rules-only path (`write_rule_decided`). Logs append without dedup. Stage 2a added 21 model-facing memory tools (`memory_tools.py`). Stage 3 added `build_recall_block` (`recall.py`) — assembles ambient recall context for the chat agent's system prompt by dispatching each active memory by recall mode (`recent`/`relevant`/`all`); paired logs (`user-messages` + `penny-messages`) merge chronologically into a single Conversation section. **Polymorphic `Memory` objects + system-log facades**: the memory layer is a class per shape/backing (`penny/database/memory/`). `db.memory(name)` is the single dispatch — it returns a `Collection` or `Log` (both `memory_entry`-backed, the native store on the base) or a read-only facade, and every tool/recall/addon caller operates on that object polymorphically (wrong-shape ops refuse via base no-ops; nothing branches on a name or shape). `user-messages`/`penny-messages` are `MessageLogMemory` facades over `messagelog` (the object overrides the row primitives to read by direction, synthesizing `MemoryEntry`; a message has two authors — the user/incoming or Penny/outgoing; `append` refuses) and `collector-runs` is a `RunLog` facade over `promptlog` (renders each completed run as a record; `append` refuses) — no duplicated `memory_entry` rows, and the facade marker rows are seeded by migration so dispatch finds them. The cursor *read* logic lives on the `Log` base, uniform across backings; the reader's pending/commit cursor lifecycle stays in `LogReadTool`. `browse-results` is the one remaining real memory log (the browse tool writes it; it has no canonical table behind it). `messagelog.embedding` (for `read_similar` over messages) is filled by the startup backfill, which vectorizes any embedding-bearing table — nothing is copied between tables. Author is passed explicitly as a constructor argument or method parameter — write-capable tools take `author: str` at construction (`build_memory_tools(db, embedding_client, author, decider)`), `BrowseTool(..., author=...)` is built per-agent with `author=self.name`, and `channel.send_response(..., author=...)` requires callers to pass it. No ambient/contextvar state. Embeddings are computed at write time (not lazily) so similarity reads work the moment a memory is reconfigured. `db.memories` replaces the per-domain stores that agents will be ported onto in subsequent stages. See `docs/archive/task-framework-plan.md` (design) and `docs/archive/memory-implementation-plan.md` (staged rollout)
- **Hybrid resolve-by-meaning — `find`'s keyword leg (#2774)**: `MemoryStore.resolve_objects`/`resolve_messages` (`store.py`) rank TWO legs independently and fuse them by reciprocal rank (`_fuse_rrf`, constant `PennyConstants.FIND_RRF_K`): the existing embedding (cosine) leg, and a keyword leg over two FTS5 virtual tables — `memory_entry_fts` (a stored entry's key + content) and `messagelog_fts` (a conversation message's content) — built by migration 0127 and kept in sync by SQL triggers (the same external-content pattern `0051_promptlog_fts.py` uses for the addon's prompt search; no Python-side sync call). A collection/log's own *description* is never keyword-indexed — only stored entries and messages are, so an object hit stays embedding-only. The query text is tokenised and OR-joined, each token quoted and prefix-matched (`_fts_match_query`), so a literal word (a name an embedding blends away) can rank a hit even when its cosine falls below the embedding leg's own `cosine > 0` gate. Store hits and conversation hits are budgeted and floored EACH IN ITS OWN SECTION (`FIND_STORE_LIMIT`/`FIND_MESSAGE_LIMIT`, `FIND_RELATIVE_FLOOR_RATIO`), so one section can never crowd the other's result. The keyword leg degrades to empty (pure-embedding ranking) on a schema that predates migration 0127 — including the test suite's bare current-models schema (`schema_template.py`) — rather than erroring on a missing table.

### Data Model

## Data Model

All tables defined in `database/models.py` as SQLModel classes:

- **PromptLog**: Every LLM call — `model`, `messages` (JSON), `response` (JSON — the literal `"{}"`, never NULL, for a call that never got one), `thinking`, `duration_ms`, `agent_name`, `run_id`, `run_outcome`/`run_reason`/`run_target`, `tool_failures` (count of failed tool calls in the run, stamped on the last prompt alongside the outcome — the structural signal the run-health classifier reads), `trailing_messages` (**the run tail**, migration 0102, #1778: the turns the agent loop appended AFTER this call — the terminal assistant tool-call turn plus its tool-result turns — which no later call carried. A tool RESULT is otherwise durable only as a side effect of being fed back, riding into the NEXT call's `messages`; a run that ends the instant a tool returns — a write-gate STOP, `max_steps` on a tool step, a reroll abort, an exception — has no next call, so its terminal outcome was recorded nowhere, and those are exactly the runs worth reading afterwards. Same wire shape as `messages` (it is literally what the next call's `messages` would have ended with), so the readers concatenate rather than merge and one decode path serves both. Stamped by `MessageStore.set_run_trailing_messages` from `Agent._run_agentic_loop`'s `finally` — the universal per-run chokepoint, chat and collector alike, and the one place that still holds the tail when the loop dies (`set_run_outcome` is now called by `ChatAgent` too, #2355 part D — a chat turn stamps its own failed run exactly like a collector cycle does its own). Empty tail → no write at all, so an ordinary run is untouched and renders byte-identically. Read via `_run_tool_turns` (`database/memory/objects.py`), the single COMPLETE tool-turn accessor behind `render_run_calls` / `project_run` / the I/O tally / the egress-media trace, and via `_row_turns` in the eval harness's transcript extractor — so neither can be missing an entry). **How a CALL ended** (migration 0114, #2355 part A): `call_outcome` (`CallOutcome`: `completed` | `cancelled` | `timed_out` | `raised`; NULL on every pre-migration row, read as `completed` by convention) + `call_error_class`/`call_error_message` (the failed call's own exception class + message, set only on `timed_out`/`raised`) — written by `LlmClient.chat` ONCE, at the end, however the call ends, rather than only on success; a call cancelled by a tool's own timeout or one that exhausted its retries used to leave no row at all. `parent_run_id`/`parent_tool_call_id` (same migration): the enclosing chat/collector run — and, for a draw made from inside a dispatched tool call (today, only `browse`'s extraction), that call's own id — a MICRO-CONTEXT draw was made on behalf of, since a micro-context mints its own `run_id` for its own ledger attribution. Read back by `MessageStore.get_child_draws(run_id)` and nested under the right step by `render_run_calls`'s `child_draws` parameter (#2355 part D), so `run_get` on a turn shows both the tool call it made and the model call that did not finish on its behalf. **Why a COMPLETED call's output was not used** (migration 0123, #2702): `discard_reason` (a `ConditionKey` machine value — `degenerate_output`, `xml`, `budget_cut`, …) + optional `discard_detail`, stamped post-hoc by `MessageStore.mark_prompt_discarded` from each rejection site (the loop's discard-and-reroll guard, a validator's `Retry`, the empty-final-answer and narration fallbacks, the micro-context poison screen and cut-draw retry, a structured draw's parse failure), by the row id `log_prompt` returns and `LlmResponse.prompt_log_id` carries. A reroll/retry attempt's row reads `call_outcome="completed"` exactly like the call that counted — this is what distinguishes it. Additive, never model-facing: only the addon serializers and the live push read the columns. **The run's numbered link table** (migration 0124, #2717): `link_handles` — the run's `HandleTable` as JSON (`{"1": "https://…"}`, number → URL), stamped on the last prompt row for `run_id` by `MessageStore.set_run_link_handles` from `Agent._run_agentic_loop`'s `finally`, beside `set_run_trailing_messages`. A run-record field the model never sees: the logged turns carry handles, the artefacts built from the run (stored entries, the outgoing reply) carry the real URLs Python expanded at write/send time, and the eval harness's provenance reads expand the given text through this table — the run was given every URL, as its handle. NULL on pre-migration rows and on runs whose surfaces rendered no handles.
- **MessageLog**: Every user/agent message — `direction`, `sender`, `content`, `parent_id` (thread chain), `external_id` (platform ID), `is_reaction`. (The `thought_id` FK into the legacy `thought` table was dropped by migration 0097 — historical rows lose only that link.) **The run whose reply a direct reply delivers** (migration 0120, #2630): `run_id` — the chat run's own `promptlog.run_id`, stamped by the framework on the chat reply path (threaded from the channel's turn driver through `send_response` → `_log_and_send` → `log_message`), so the conversation history's per-turn tool line pairs a run with its reply by identity rather than by the timestamp guess "the first send at or after the run's last logged call". A by-value reference to `promptlog.run_id` (not unique there, so no DB-level FK), indexed; NULL for every pre-0120 row and for autonomous sends (the drainer's or any `send_message`), which have no run behind them and get no tool line. **Emission provenance** (migration 0088, #1568): `mechanism` — the bound collection whose autonomous cycle produced an outgoing send; a by-name reference to `memory.name`, a plain column like `mutation_event.entity_name` (a DB-level FK would close a circular foreign-key cycle with `memory.source_message_id`), served by the partial `ix_messagelog_emission_time` index. NULL for a direct reply (a chat turn with a live triggering user message names no mechanism); the drainer stamps it at delivery time from the queued row's `collection`. Provenance renders where the message renders: the `penny-messages` facade shows `(sent by <mechanism>)` inline on every read, so "which mechanism sent this?" is the same call that read the message
- **UserInfo**: User profile — `name`, `location`, `timezone` (IANA), `date_of_birth`
- **CommandLog**: Command invocations — `command_name`, `command_args`, `response`, `error`
- **RuntimeConfig**: User-configurable settings — `key`, `value` (string, parsed on read)
- **MuteState**: Per-user mute state — row exists = muted, delete = unmuted
- **Device**: Registered devices (Signal, Discord, browser addons) — used for multi-device routing and domain permission prompts
- **DomainPermission**: Per-domain allow/deny state for browser extension web access, synced across addons
- **Thought**: **REMOVED** (migration 0097, #1676) — the legacy inner-monologue table (`content`, `title`, `image`, `valence`, `preference_id` FK, `notified_at`). The thoughts pipeline it backed was nuked in the same migration (the `thoughts` collection and its retired pair), which killed its last consumer; the table, its model, and `ThoughtStore` (`db.thoughts`) are deleted
- **Preference**: **REMOVED** (migration 0097, #1676) — the legacy user-sentiment table (`content`, `valence`, `source`, `mention_count`, `embedding`, `last_thought_at`). Its last real consumers — the thoughts pipeline's seed-preference pick (nuked in the same migration), the startup preference-embedding backfill, and the `/profile` onboarding check — died with it; the table, its model, `PreferenceStore` (`db.preferences`), and the `PreferenceValence`/`PreferenceSource` enums are deleted. This resolves the #1301 legacy question for the table itself; preference-shaped data lives in the `dislikes` collection (and topic-specific collections)
- **Knowledge**: Summarized web page content — `url` (unique), `title`, `summary` (prose paragraph), `embedding`, `source_prompt_id` FK (extraction watermark). One entry per URL, upserted on revisit
- **Memory**: Unified container for the task/memory framework — `name` (PK), `type` (`collection` or `log`), `description` (content-reflective; doubles as the resolve-by-meaning anchor, #1558), `description_embedding` (the anchor vector, backfilled at startup), `notify` (emission-as-property, migration 0085, #1591/#1557: the **sole** emission flag — when true the collection tells the user about new/changed entries via the run-time notify steps appended to its collector prompt before the injected terminal `done()`; set at creation from `collection_create(notify=…)`, flipped by `collection_update(notify=…)`. The `published` pub/sub column + the `notifier` consumer + `read_published_latest` were retired by migration 0086/#1557), `archived`. **Operational-registry provenance + lifecycle** (migration 0081, #1566): `source_message_id` (FK → `messagelog.id`, the spawning user message — linked post-run by `link_source_message`, matched on `created_by_run_id`), `created_by_run_id` (the `promptlog.run_id` of the creating chat run, stamped by `collection_create`). All nullable — seeded/system rows carry none. `memory_get` renders these as a status/expires/created-from-message block. **Schedule** (migration 0104, #1857): `schedule` (nullable) — ONE RRULE string, the whole schedule grammar; `Collector._is_ready` gates on the rule's next occurrence after `last_collected_at or created_at` (the rule's own `DTSTART:` line wins when it has one, else the recurrence anchors at `created_at`). **That anchor is the user's WALL CLOCK (#1932)**: an RRULE states an hour (`BYHOUR=9`) and never a zone, so the zone comes from the profile (`UserInfo.timezone`, `None` → UTC) — `created_at` is converted into it and its seconds zeroed, and `next_occurrence` (`tools/collection_instantiation.py`, DB-free, the zone passed in as a parameter) is the one seam that reads a stored rule. Reading it in UTC is what fired a briefing asked for at a local morning hour four hours early on a UTC-4 profile while the reply promised the local time; zeroing the seconds is what stopped a collection created at `:51` past from being a job that fires at `:51` past for ever. Because `ZoneInfo` resolves the offset per occurrence, a stated hour holds across a DST boundary. The rule text is **never rewritten** — normalising the hour to UTC at store time would make the render a translation of the ask and re-passing it would convert a second time — so `render_schedule_clause` still round-trips. An explicit `DTSTART:…Z` states its own zone and stays an exact instant; a FLOATING `DTSTART` (no `Z`) states none, which RFC 5545 calls local time, so it is read on the same user clock (which also stops it coming back naive and raising in the shared readiness comparison). It **replaced six columns** — `collector_interval_seconds`, `run_at` (folded into `DTSTART`), `source_log` (the dropped `on advance of` form), `cron_expression`, and the auto-throttle pair `base_interval_seconds` / `consecutive_idle_runs` — with no conversion of existing trigger data (code-owner ruling: deployments reset after this arc), logged loudly per collection at migration time. **End conditions**: `expires_at` + `max_runs` (both nullable) archive the collection when the time passes / the quota is reached; both are settable directly and are what the rule's `UNTIL=` / `COUNT=` are lifted into at parse (a schedule's own `UNTIL=` is refused — a schedule says how OFTEN a job runs, never when it stops; say that with `expires_at`). **A job is set directly**: `collection_configure(collection=<name>, prompt=<free text>, schedule=…, notify=…, expires_at=…)` writes the model's own free-text instructions straight into `extraction_prompt` — no resolution, no rendering seam, no parameters to bind. `memory_get` renders an inert (prompt-less) collection with an honest `steps: none` line. Collections are keyed sets with dedup on write; logs are append-only keyless streams
- **MemoryEntry**: One entry in a memory — `memory_name` FK, `key` (nullable for logs), `content`, `author`, `key_embedding`, `content_embedding`. Entries are immutable once written — `update` replaces content for a given key. **Entry-level provenance** (migration 0083, #1560): `created_by_run_id` + `last_written_by_run_id` — the run that first wrote the entry and the run that last rewrote it (a collection entry is overwritten each cycle, so the current-value writer differs from the creator). Stamped at write time by the writing run, threaded as a parameter (no ambient state); both nullable (pre-#1560 / migration-seeded rows carry neither). The run id is the join key into the ledger (the `promptlog` write events); these two stamps are the read-path anchors that keep `run_list` one guess-free hop from wherever an entry renders
- **MutationEvent** (`mutation_event` table, migration 0083, #1560): One durable create / update / archive / unarchive of a registry entity (a collection) — `entity_type`, `entity_name`, `action`, `actor` (`user-run` | `system`), `run_id` (the causing run — the ledger join key), `detail` (JSON `MutationDetail`: changed-field names, a cause note, and the options-presented `EnumeratedDecision` accommodation), `created_at`. The event half of the operational spine (the entity half is #1566's `memory` columns): the `memory` row stays the materialized truth (its `archived` flag), and this table is the audit/provenance trail of how it got there — so "when was this archived, and by what?" is a read. The one ledger table with no other home: an entry write is a `promptlog` tool call and a run is a `promptlog` group, but a *system* archive (the scheduler's `max_runs` / `expires_at` retire) runs no model and logs no prompt. Written at the `MemoryStore` chokepoint (`create` / `_set_archived` / `update_collection_metadata`); read via `db.mutations.history(name)`, rendered into `memory_get`'s "Recent changes" block, each line naming its run id (the anchor invariant). Audit, not event sourcing
- **AgentCursor**: Per-reader read progress through a log-shaped memory — `(agent_name, memory_name)` PK, `last_read_at` high-water mark. Advanced two-phase by the orchestrator (pending during a run, committed on success). For collectors the cursor owner is the **bound collection name**, not the constant `"collector"` identity — otherwise every collection reading the same log (e.g. the many that read `user-messages`) would collapse onto one shared cursor and starve each other
- **Media**: Images captured while browsing or drawn on request, delivered side-channel — `mime_type`, `data` (raw bytes), `source_url`, `title`, `embedding` (of title+URL for browsed rows, of the description for generated rows). The browse tool stores every page image here; at channel egress `MediaStore.select_image` attaches the most relevant image, most-relevant-first: (1) **exact URL** — if the outgoing message links a page we captured, that page's own image (newest capture); (2) **same domain** — else the embedding-nearest image from a domain the message links; (3) **fallback** — else a uniform-random pick among the top-K embedding-nearest (jitter, so a centroid "magnet" image can't repeat on consecutive messages — applied *only* to this tier; URL/domain matches are deterministic). No floor, so a reply still carries an image whenever one matches. A `generate_image` row is delivered **by id to its own reply** (`send_response(media_ids=...)`, from `ToolResult.media_id`) with precedence over this ladder — never fuzzy-matched for that reply, but in the pool for future ones (#1564). Zero model involvement — no `<media:ID>` tokens, no prompt changes
- **SendQueueItem** (`send_queue` table): Durable outbound message queue — `content`, `collection` (the collector that queued it), `origin`, `created_at`, `sent_at` (nullable; `NULL` = still pending, single source of truth — no separate flag). A finished cycle's notification is enqueued here instead of being dropped when the autonomous-send cooldown hasn't elapsed (#1911; since #2656 the enqueue holds the hand-off: `enqueue_report(collection, origin, report_run_id)` puts no content on the row — the drainer composes the message from the named run's written entries and stores it before delivering, holding the refusal / no-recipient / mute gate the retired `send_message` tool used to); the `SendQueueDrainer` delivers the oldest pending row its lane allows out — stamping the row's `collection` onto the delivered `messagelog` row's `mechanism` (#1568). Kept after delivery (stamped `sent_at`) as an audit trail. **`origin` (migration 0109, #1939) is WHICH LANE**: the `CycleTrigger` that set the queuing cycle running — `cadence` (the schedule's own dispatch; ride the full cooldown) or `on_demand` (the user's "run this now"; deliver on the next tick, because they are sitting in front of it waiting). NOT NULL, defaulting to `cadence` on the column and in `enqueue`, so an unstamped row is in the conservative lane and skipping the cooldown is something a caller has to claim. Observed live: an on-demand run's notification waited ~10.5 minutes because an unrelated chat reply seconds earlier had started the cooldown. **The report columns (migration 0122, #2656)**: `report_run_id` (the collector cycle's run id whose written entries the report is built from; a row with it set and empty content is a report awaiting composition), `attempts` (failed composes counted, bounding the retry), `failed_at` (stamped when the budget is spent — kept, never delivered, excluded from the pending queries structurally, and distinct from `cancelled_at`: a failed report is a compose that never produced a message, a cancelled one was withheld on purpose)
