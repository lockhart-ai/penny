# Agents and the agent loop — reference

Covers the base agentic loop, ChatAgent, the shared LLM clients, and the self-state header. Read this in full before changing `penny/agents/` or the agent-loop mechanics in `penny/preflight.py`.

### penny/preflight.py

  preflight.py        — Setup-health / preflight checks: one legible startup summary (Preflight → PreflightReport). Hard-fails (PreflightError, caught in main → exit 1) on an unreachable LLM endpoint or an unresolvable chat/embedding model; soft-warns on a missing vision/image model, a disconnected browser addon, or a mis-routed primary channel (routing-bug guard). Runs in Penny.run() after channel connectivity, before backfills

### penny/agents/models.py

    models.py         — ControllerResponse, MessageRole, ToolCallRecord, GeneratedQuery, plus the run-abort trio (#1909): `ModelCallError` (one failed call's error class + message), the self-rendering `ModelCallAbortedError` exception the invoke layer RAISES with it (an error carrying a message is an exception, never a sentinel in the success channel), and `RunAbort` (`ControllerResponse.abort` — where the run died: step index, the tool the last SUCCESSFUL step ran, and that error). Since #2355 part A, `LlmClient.chat` logs this call's own `promptlog` row however it ends (completed, cancelled, timed out, or raised) rather than only on success — so `RunAbort`'s facts travel on `ControllerResponse` AND the call that produced them now leaves its own trace; `RunAbort.render()` is what the collector stamps as the run's reason, so the run record names the terminal cause instead of the generic no-`done()` line

### penny/agents/chat.py

    chat.py           — ChatAgent: conversation-mode agent (handles user messages with tools). **There is no conversation machine** (#2455 naive baseline): every turn runs the same `Prompt.CONVERSATION_PROMPT` — there is no second state to pick an instruction for, so there is no state to thread, no round to configure, and no learn/apply/request terminal to enforce. Declares chat's `invalid_draw_conditions` (the draws that are not a reply: call-shaped text, then the empty draw); `run_shape_validators` is empty — there is no skill-narration or applied-configuration frame left to narrate at a text branch. **Two records are still delivered straight onto the tool result the moment a configuring or writing call lands** (`ChatAgent.after_tool_step`, called from the loop right after a tool step's results are absorbed): `render_applied_configuration` (what a `collection_configure` call just set the job to — read off the container's own row, carrying what each field this turn MOVED held before, via `db.mutations.priors_for_run`) and the writes-landed record (`render_writes_landed` over `db.memories.entries_written_by_run`; when nothing landed but the run TRIED to keep something, `render_nothing_landed` lists each call whose tool declares `Tool.stores_entries` with that tool's own answer, verbatim) — both appended to the END of that step's own tool-result message, never into the system prompt (editing the prefix mid-run would invalidate a local build's prefix cache) and never as a message after a draft (a message arriving after a reply reads as the user correcting it, which is what made the first reply get thrown away and redrawn every time). A later step's addendum states the record AS OF NOW (the whole picture, not a delta), so a run with two writes never leaves an earlier message understating what has landed.

### penny/agents/conversation_map.py

    conversation_map.py — ConversationMap: renders the `## Conversation map` block (#2752) — the deterministic, append-only map of the exchanges older than the history window, appended to the END of the LEADING static system message (#2757, after identity/rules/instructions and before the tool schemas gemma4's renderer puts right after it), never the per-turn dynamic message. Shares `Agent._history_window_size` with the history's own grow/cut window (anchored on the same `MessageStore.count_user_turns`, #2756) so the two can never disagree about where the window starts — which means the map changes ONLY on a cut turn, the one turn the window's own first exchange moves; every other turn it is byte-identical, so the whole static+tools prefix is reused. One line per exchange, built by the framework from the user's own words and the run records (never the model, §2.4): the user's clipped first line, the exchange's recorded outcome (pages read off the `browse-results` entries stamped with the run, keyed writes off the `last_written_by_run_id` stamp, registry changes off the mutation ledger), and `named:` — the items her stored reply MARKED (bold spans and link texts, deduplicated, capped; never her sentences, §3.6, and never a URL, since stored replies keep real URLs, #2729). Consecutive outcome-less short exchanges collapse into one ranged line; the horizon is `CHAT_MAP_DAYS` local dates (a line leaves at most once a day) and past `CHAT_MAP_MAX_LINES` the OLDEST WHOLE DAY collapses into one line naming its `log_read` read — both boundings remove from the front whole, and the closing anchor is fixed text, so the map before an exchange ages out is a byte-identical prefix of the map after it. Each line's absolute time anchors the full text one `log_read(day=…)` call away

### penny/agents/self_state.py

    self_state.py     — SelfStateHeader: renders Penny's operational self-state deterministically from the registry + ledger (#1555, the ambient inversion), split across BOTH chat system messages (#2814 — see `render_static`/`render_dynamic` below). `render_static()` rides the LEADING static message, ahead of the conversation map: `### Jobs` — a global notifications line (whether proactive notifications are muted or on — always stated, in both directions, read off the same key the notifier gates on, since the notifications tool's own description was otherwise the only carrier of a state nothing rendered, #1919), then EVERY job, no cap (#2288): each line states the job's status (active/archived), cadence, its own `notify: on` / `notify: off` clause (#1919 — the same both-directions-always shape as the line above it, for the neighbouring question: that line says whether proactive messages go out AT ALL, this says whether THIS job is one of the things that would send one), end condition, and last-run outcome+time, with a second, indented line carrying the job's URL (the first `https?://` found in its prompt, when there is one) and the start of its own instructions, capped, with a `memory_get('<name>')` note when cut — so a job's own words, not a derived label, are what names it on this surface (there is no separate "Known skills" section: a job IS its instructions now); and `### Your memory` — every live collection and log, no cap, with every archived one named on one trailing line (#2288), each with an entry count EXCEPT the four system-log facades (`PennyConstants.SYSTEM_LOGS` — `user-messages`/`penny-messages`/`browse-results`/`collector-runs`), which show their name and scope with NO live count: that count is read straight off `messagelog`/`promptlog` and ticks on every ordinary turn (an incoming message, a reply, a browse call), which would otherwise rebuild this prefix every turn and defeat the point of caching it — the facade's NAME still renders (the `log_read` anchor, n≤1 reachability), only its count does not. Both sections are otherwise pure renders of the registry alone (no activity, no clock), so `render_static()`'s output is byte-identical turn to turn unless a job or a USER-OWNED collection/log actually changed (a write, a schedule edit, an archive) — honest and rare next to every turn, same bet the conversation map already makes (prod's hourly collector jobs rebuild it on their own cadence). `render_dynamic()` rides the per-turn DYNAMIC message instead, since this genuinely churns every turn: `### Recent activity` — runs, config mutations, and autonomous sends (#1568) interleaved · durable user facts · a closing pointers line. Standing rules — the seeded `rules` collection in full, oldest first, or the empty-collection line that keeps the anchor on screen (#2633; the ONE shared render the collector cycle's prompt and the notify document also show) — render in neither split: in the chat prompt they render in the instruction part instead (`standing_rules_instruction`). `render()` keeps the historical whole-header shape (unused by `ChatAgent` since #2814) for tests that exercise `SelfStateHeader` as a unit

### Duplicate tool blocking

- **Duplicate tool blocking**: Agent tracks called tools per run (a seen-calls cache) to prevent LLM tool-call loops. A byte-identical repeat of a still-cached call is blocked — but any successful MUTATING call (`ToolResult.mutated=True`) **clears the cache** (`_process_tool_calls`), because an identical call is only pointless against an UNCHANGED world and a mutation means the world changed (#1673). So a legitimate repeat RUNS in BOTH directions once a mutation intervenes: retry-after-remediation (a failed write retried after its collection was created — the failed write's own error told the model to create it first) and re-read-after-write (verifying the entry just written). Loop-safe by construction: a repeat with no mutation since its prior occurrence never clears the cache, so it stays blocked (a failing retry adds no mutation). When a repeat IS blocked, the rejection frame states the prior call's OUTCOME (`_duplicate_rejection_frame`) — succeeded → reuse its result; FAILED → the failure quoted + fix the precondition (never "use its result", which read as success and made the model narrate a write that never happened)

### Tool-result framing (tagged first-person narration)

- **Tool-result framing (tagged first-person narration)**: every tool result is wrapped by `Tool.format_result(name, arguments, result)` (applied once in `Agent._collect_tool_results`) into a **tagged first-person** header — a narration line + a retained `(<tool> result)` machine tag — then the body: `You used \`<tool>\` and here's the result: (<tool> result)\n<body>` on success, `You tried to use \`<tool>\` but it didn't work: (<tool> result)\n<body>` on failure. The narration is resolved by `Tool._resolve_narration` in priority order: an explicit `ToolResult.narration` frame wins, else the registry-dispatched `Tool.to_result_narration(cls, arguments, result)` — the *result* twin of `to_action_str` (the pre-call status string), branching on `result.success` — else the generic default for an unregistered tool. **`BrowseTool` overrides `to_result_narration` (#1480)**: one first-person line for the whole call summarising search-vs-read from the `queries` arg and the outcome (`You searched for "…"` / `You opened <url>` / on a total failure `… but couldn't read anything — no page was read, so there's nothing current to quote`, which states the CONSEQUENCE of the failure and not only the failure, since a run that says only what happened to the call leaves what follows from it to be worked out — measured, 3 of 5 replies to an all-sources-failed lookup volunteered an invented figure) — the per-page `## browse ...:` section headers stay in the body, so the batch is narrated once, not per section. The call `arguments` + the whole `ToolResult` are threaded from `_execute_single_tool` (which returns the `ToolResult`) → `_collect_tool_results`. **Framework-synthesised failures narrate their own frame (#1482).** The failures a tool can't report itself — tool-not-found (which has NO registered class to dispatch from), timeout, uncaught exception, and arg-validation — set `ToolResult.narration` to a specific first-person frame (`FRAMEWORK_NARRATION_NOT_FOUND` "…but there's no such tool.", `_TIMEOUT` "…but it timed out.", `_EXCEPTION` "…but it errored: `<e>`.", `_INVALID_ARGS` "…but the arguments were wrong:") so `format_result` leads with it instead of the generic line and doesn't double-frame the no-class case; the actionable **remedy** (the #1414 house template's diagnosis + how-to-fix tail — did-you-mean + available list, timeout guidance, "try a different approach", the per-field reasons) stays verbatim in `ToolResult.message`. Remaining per-tool narration overrides land in #1481 (memory/lifecycle). **The tag is load-bearing, not decorative.** The OpenAI `role: "tool"` + `tool_call_id` envelope is the standard "this is a tool result" signal, but gpt-oss:20b doesn't reliably honour it when the body reads like prose — it can mistake fetched data (e.g. a returned user message that itself reads like an instruction) for a fresh directive (#1332's #1 failure class). The terse `Result of your \`<tool>\` call:` header used to carry that disambiguation; a live-model probe showed pure-prose narration with no tag RAISED the call-as-text bail rate (5/6 vs. 3/6 tagged), so the `(<tool> result)` tag stays even as the header reads naturally (see `docs/archive/tool-narration-plan.md`). Read tools additionally lead their body with a `N entries from \`<source>\` (ordering):` header via `format_entries` (public since #1914 — the collector's composed prompt renders the bound collection's current entries through the same function, so an ambiently-read key and a tool-result key are one form). Framing happens after `record.failed` is computed (on the raw result) so failure detection is unaffected. The three tool-*shaped* injections that don't flow through `_collect_tool_results` carry the same tagged envelope at their own sites — but with **bespoke, context-specific narration** (#1485), supplied at the call site (they aren't real registered tool calls, so nothing to registry-dispatch) and composed by the shared `Agent._frame_injected_result(tool_name, narration, body)` helper (`{narration} (<tool> result)\n{body}`, single-sourcing the `RESULT_TAG` so the machine-tag invariant holds uniformly). The narrations live on `Prompt` beside the bodies they frame: the synthetic page-context browse pair (`ChatAgent._inject_page_context`, standard `tool_call_id` envelope via `ChatAgent.PAGE_CONTEXT_TOOL_CALL_ID`) → `PAGE_CONTEXT_NARRATION` ("You looked at the page the user is currently viewing…") — deliberately NOT BrowseTool's `You opened <url>` (#1480): a page-context injection is the page the user is viewing, not a browse Penny ran; the duplicate-tool-call rejection (`Agent._dedup_tool_calls`) → an OUTCOME-FIRST narration + body pair selected from the prior matching `ToolCallRecord.failed` (#1673): `DUPLICATE_CALL_NARRATION_FAILED` + `DUPLICATE_CALL_REJECTION_FAILED` (leads with the failure, quotes its first line, prescribes fixing the precondition — never "use its result") vs `DUPLICATE_CALL_NARRATION_SUCCEEDED` + `DUPLICATE_CALL_REJECTION_SUCCEEDED` (the reuse-the-result guidance); a successful mutating call clears the seen-calls cache (`_process_tool_calls`) so a legitimate retry-after-remediation or re-read-after-write runs, loop-safe; the rejected-tool-calls path (`Agent._append_rejected_tool_calls`, e.g. a premature first-move `done()`) → `REJECTED_CALL_NARRATION` + the preserved rejection body. Each frames — never replaces — the actionable rejection/page body the model must still read. Since bespoke narration is now supplied per site, these sites no longer construct a throwaway `ToolResult` (its only consumer was `format_result`'s generic success/failure branch)

### An aborted run names its terminal cause (#1909)

- **An aborted run names its terminal cause (#1909)**: a model call that comes back with nothing usable — a timeout, a connection or server error, or a reroll budget every draw was discarded on — RAISES `ModelCallAbortedError` out of the invoke layer (`agents/models.py`; an error carrying a message is an exception, never a sentinel returned in the success channel). `_run_agentic_loop_body` catches it at the one call site and closes the run with the same `AGENT_MODEL_ERROR` response it always did, now carrying `ControllerResponse.abort` — a `RunAbort` of the step index, the tool the last SUCCESSFUL step executed, and the error's class + message — and `Collector._unfinished_reason` renders that as the run's stamped `run_reason` (`[target] model call failed at step 5 after read_similar: LlmTimeoutError: …`) in place of the generic `cycle ended without a done() call`. Observability only — no retry, cycle-shape, notify or outcome-classification change; the aborted response still carries no tool calls, so its `RunOutcome` is the `failed` bail it always was. (Until #2355 part A, a call that raised never reached the client's persist step, so it wrote no `promptlog` row at all — the stamped outcome was the only surviving trace of the whole class, including a run whose FIRST call failed; `LlmClient.chat` now logs that call's own row however it ends, closing both gaps.)
  **A third abort cause, `BUDGET_EXCEEDED` (#2475)**, fires when a draw comes back with `finish_reason == FINISH_REASON_LENGTH` (its own per-call-kind token cap cut it off mid-thought, #2474) — caught in `Agent._invoke_nondegenerate` BEFORE the discard-and-reroll machinery even looks at the draw's shape, since re-rolling on the same budget and thinking settings would almost certainly cut the next draw too. Unlike an unreachable model, this cause is still handed to `_narrate_or_account`'s last draw — but with `thinking_enabled=False`, so the answer, not the reasoning, gets what budget is left.

### Every draw carries its own call-kind token budget (#2474/#2475)

- `Agent._invoke_model` — the one method that actually calls `self._model_client.chat(...)`, for both an ordinary loop step and the last-draw narration — resolves `token_budget_for(self.config.runtime, self.name)` on every call, so chat and collector calls both ride capped (`TOKEN_BUDGET_CHAT` / `TOKEN_BUDGET_COLLECTOR`, `config_params.py`). `thinking_enabled` defaults True; the one caller that turns it off is the budget-exceeded last draw (above).

### A chat turn that fell back to the honest account is stamped on its run (#2355 part D)

- **A chat turn that fell back to the honest account is stamped on its run (#2355 part D)**: every call site of `Agent._narrate_or_account` — max-steps, an empty final answer, a reroll-exhausted abort, a budget-exceeded abort (#2475), and `ChatAgent`'s own learn-nothing / apply-no-framing narrations — plus `Agent._aborted_response`'s immediate `AGENT_MODEL_ERROR` return (the model-runner-unreachable branch, which never reaches a draw at all) is a turn that needed this fallback machinery, which is itself the signal worth recording: internal recoveries included, even when the eventual reply reads fine. A background cycle's own `_draw_narration` override skips every one of these ORDINARILY (#2370) — except the budget-exceeded one: `live_draw=True` is the explicit flag (set only by `_aborted_response`'s `BUDGET_EXCEEDED` branch, deliberately separate from `thinking_enabled` — which means only whether the draw reasons) that makes `BackgroundAgent` draw live anyway, per the code owner's ruling that every call kind still ends in a model summary when the model can be reached. Each passes its own THIRD-PERSON structural `reason` (distinct from `facts`, the model-facing second-person sentence the draw is handed) to the one template-method hook, `Agent._record_turn_failure(run_id, reason)` — a no-op on the base `Agent` (a collector cycle already stamps its own richer reason itself, in `Collector.run_cycle`'s `finally`, so the hook firing there too would just be overwritten) and `ChatAgent.set_run_outcome(run_id, RunOutcome.FAILED, reason)` wired through it. The self-state header's recent-activity block reads the stamp back (`MessageStore.recent_failed_chat_turns`, `SelfStateHeader._chat_failure_line`) as its one exception to "chat turns are already the conversation" — asked about it later, there is no conversation left to carry it — and `run_get(run='run <id>')` on it (via the new `parent_run_id`/`parent_tool_call_id` link, #2355 part A) shows the tool call and the model call that did not finish, nested under the step it was made for (`render_run_calls`'s new `child_draws` parameter).

### Image side-channel

- **Image side-channel**: Images never travel through the model. The browse tool decodes each page's image (base64 data URI from the extension), stores the bytes in the `media` table with an embedding of the page title+URL, and the agent loop carries no attachments. At egress (`send_response`), the outgoing text is embedded once (reused for the `penny-messages` log) and `MediaStore.select_image` attaches the most relevant image: the cited page's own capture when the message links a source (exact URL → same domain, both deterministic), else a jittered pick among the top-K embedding-nearest (jitter only on this embedding fallback, so a magnet image can't repeat). No floor, so a reply carries an image whenever one matches (a tangential or funny mismatch beats no image — confirmed product behavior: every message gets an image). **Generated images take a deterministic path with precedence over that ladder** (#1564): the `generate_image` chat tool stores the drawn image with an embedding of the description and stamps the row's id onto `ToolResult.media_id`; the loop threads it onto `ControllerResponse.generated_media_ids` and `send_response(media_ids=...)` fetches **exactly that row** by id and attaches it to the mirror-back reply — the fuzzy ladder doesn't run for that reply (previously the drawn image was fuzzy-matched like everything else, giving it only ~1-in-K odds of landing on its own reply). The embedding keeps the drawn image in the nearest-image pool for future replies. This whole scheme replaced a model-carried `<media:ID>`/inline-URL token scheme that couldn't reliably thread image references through multi-page replies

### Agent Base Class (`penny/agents/base.py`)

### Agent Base Class (`agents/base.py`)
The base `Agent` class implements the core agentic loop:
- Calls the LLM (via `LlmClient`) with available tools
- Executes tool calls via `ToolExecutor` with parameter validation
- Handles duplicate tool call prevention
- Appends source URLs to responses when model omits them

**System prompt building (template method pattern):**
Each agent overrides `_build_system_prompt(user)` to compose its prompt from reusable building blocks on the base class: `_identity_section()`, `_profile_section()`, `_instructions_section()`, `_context_block()`. No flags or conditionals — each agent explicitly declares what goes in its prompt. Tests assert on the exact full system prompt string to catch structural drift.

**Static system leading, history append-only, dynamic system right before the user (#2756; previously two leading system messages, #2745) — CHAT's shape**: `Agent._build_messages` renders the request as `[system(static), history…, system(dynamic), user]`. The static message is `_build_system_prompt`'s output — identity, instructions, everything that never changes between turns, PLUS Jobs and the store map (`SelfStateHeader.render_static()`, #2814) — and the dynamic message is `_dynamic_system_section()`: the datetime anchor by default, plus chat's own per-turn state (page hint + the rest of the self-state header, `SelfStateHeader.render_dynamic()` — recent activity + durable user facts + pointers). **Chat's static message also carries the conversation map, appended at its END** (#2752/#2757, `ConversationMap`) — one line per exchange older than the history window; it changes only on a cut turn (the shared `Agent._history_window_size` boundary), never on an ordinary turn, so it rides the reused prefix rather than the dynamic message that changes every turn. **Jobs and the store map ride the same reused prefix for the same reason** (#2814): both are pure renders of the registry alone, with no clock and no activity in them, so they stay byte-identical turn to turn unless a job or a USER-OWNED collection/log actually changes — a rarer event than every turn, even though a write to one or a collector cycle (prod runs one hourly) does trigger a rebuild, same as the map does on a cut turn. The four system-log facades are deliberately excluded from this: their own live counts tick on every ordinary turn, so they render with no count at all (see the `self_state.py` entry above) rather than defeating the whole point of the move. Recent activity does NOT move with them: it churns on every run/mutation/emission, so it stays in the dynamic message where a change can never touch the cached prefix. The dynamic message moved to right BEFORE the user's own turn (#2756): prod's runner (oMLX) only renders a non-leading system message in place when it follows a `user`/`tool` message and precedes nothing or an `assistant` message, and this is that one placement — a MID-CONVERSATION system message, between history's last entry and `user` — which oMLX renders in place once patched to keep it there (unpatched, it downgrades a non-leading system message into the following user turn's own text). OpenRouter (eval) renders this placement natively, no patch needed, so eval and prod read the same prompt. Ollama's gemma4 renderer puts the tool schemas inside the FIRST system turn, after its content, so the static text (Jobs, store map, and map included), the tool schemas, AND the growing history (`CHAT_HISTORY_TURNS` turns, growing to `2*CHAT_HISTORY_TURNS - 1` before cutting back, #2756) are one prefix the server reuses across turns — only the dynamic state and the live user message are re-read every time. The per-turn content stays in a system-role turn, never in or beside the user turn (the #1296/#1304 revert measured that recalled context beside the live message reads as the live ask). Unit tests pin the static message byte-identical across two renders with a shifted clock and ALSO across an activity-only change (a new run with no job/collection mutation), while pinning that it correctly DIFFERS when a job or a collection actually changes (#2814).

**The Collector diverges from this shape entirely (#2778)**: a cycle has no history, so the shape above would put its dynamic section right after the static one — two LEADING system messages, which oMLX merges ahead of the tool schemas, so the collector never cached its prefix (measured in prod: a repeat same-job start reused 0 tokens). `Collector` overrides `_build_messages` to `[system, user]` — no dynamic system message at all — and moves the per-cycle state into the USER turn via its own `_cycle_prompt` override (the job's own instructions, then what the collection holds, then its run history, then the clock last — there's no live ask for state to crowd beside, so the #1296/#1304 concern above doesn't apply to a background cycle). The job's identity (name, description, instructions) also moved out of `_build_system_prompt` into that same user turn, which leaves the leading system message — the cycle framing + the close instruction + the runtime rules + the standing rules — byte-identical across every job and every cycle: one shared prefix, with the tool schemas right after it, that a server-side cache reuses across the whole collector fleet, not just same-job reruns. Detail: `docs/reference/scheduler-and-collector.md`.

**The ambient inversion (#1555)**: the chat system prompt **no longer injects speculative user-content recall**. Instead a deterministic **`SelfStateHeader`** (`agents/self_state.py`) — Penny's own operational situation rendered from the registry (`memory` rows) + ledger (`promptlog` runs + `mutation_event`), never a relevance guess — carries jobs (status · cadence · notify · expiry · last-run outcome, plus each job's own URL and the start of its instructions; EVERY one, no cap, #2288 — see `docs/reference/agents.md`'s `self_state.py` entry above) and the store map (the read index; every live store, no cap, with every archived collection and log named on one trailing line, #2288) in the STATIC leading message (`render_static()`, #2814 — both are pure registry renders, so this part of the prefix is reused unless a job or collection changes), and recent activity (runs + config mutations, interleaved, at rollup altitude), the durable user-fact core (name · timezone · location), and a pointers line naming the fetch tools in the per-turn DYNAMIC message that opens with them (`render_dynamic()`). User content is fetched **on demand** via those tools, anchored by the user's message. **There is no taught-skill registry any more** (#2455 naive baseline): a job's instructions are its own free-text `prompt`, run verbatim by the collector — there is no separate recipe to instantiate, no parameters to bind, and nothing for a "Known skills" section to list beyond the job itself, which the Jobs section already states.

**The dead recall substrate is gone (#1583)**: the two-stage recall machinery that the ambient inversion (#1555) unwired from the chat prompt — the `memory.inclusion` + `memory.recall` columns, the `Inclusion`/`RecallMode` enums, `read_similar_hybrid` + hybrid ranking, `expand_with_temporal_neighbors`, and the `RECALL_*`/`MEMORY_INCLUSION_THRESHOLD`/`MEMORY_NEIGHBOR_*` config+constants — was **deleted** (it had no remaining consumer). What replaced it: the deterministic `SelfStateHeader` for ambient facts, and **on-demand fetch** for user content — the model reads what it needs via the general verb the header's pointers name: `find` = resolve-by-meaning over the `description_embedding` anchors (and, since #1640, over stored entries' content/key anchors, and since #2289, over the two conversation logs too), which **stays** for exactly this, #1558. `memory.notify` (emission, #1557) is untouched. (The `published` pub/sub column was retired separately by #1557/migration 0086.)

The chat turns array (alternating user/assistant messages passed via `history=`) is reconstructed from the last N messages in `db.messages` — independent of any memory metadata.


### Shared LLM Client Instances

### Shared LLM Client Instances

All `LlmClient` instances are created centrally in `Penny.__init__()` and shared across agents and commands. `LlmClient` uses the OpenAI Python SDK and targets any OpenAI-compatible endpoint (Ollama's OpenAI-compat layer by default, or omlx/OpenAI cloud with a different `base_url`):

- `model_client`: Text model for all agents and commands — image attachments ride the chat turn's own user message to this model (#2635), so it must understand images
- `embedding_model_client`: Required embedding model for preference deduplication and similarity recall (always present — the model is a hard prerequisite)
- `image_client`: `MfluxImageClient` for the `generate_image` chat tool — talks to the local mflux FLUX.2 [klein] server (`image_server/`, #2792), which runs on the host outside Docker; wired into the ChatAgent, which registers `generate_image` only when it is present


### Specialized Agents

### ChatAgent (`penny/agents/chat.py`)

**ChatAgent** (`agents/chat.py`)
- Handles incoming user messages with the full tool surface (memory + browse)
- **The delivery turn (`handle_job_report`, #2656)** — the one system-originated turn: the send-queue drainer hands it a framework-rendered `JobReport` (a notifying cycle's job name, description, why it ran, and every written entry FULL), and the turn writes the message the user receives with her whole context — persona, history, standing rules, the user's formatting asks — riding the same `_dispatch_turn` template method `handle` rides. Its input is never logged as an incoming message (nothing the user said); its reply is gated and queued by the drainer, so it is logged and delivered exactly like any other autonomous send, with the mechanism stamped (`promptlog.prompt_type="job_report"` distinguishes the run)
- Chat-surface tools include `notifications_set` (`tools/notifications.py`) — one toggle over the `MuteState` row (`db.users`), taking the direction as an `on` bool rather than a tool name to pick between (folds the retired `notifications_mute` / `notifications_unmute` pair, #2812), that the model dispatches from natural language ("stop messaging me for a while" / "you can message me again"), replacing the retired `/mute` + `/unmute` commands. NL-dispatch contract: `tests/eval/chat/idle/test_notifications.py`
- Email tools (`search_emails` / `read_emails`, plus `list_emails` / `list_folders` / `draft_email` on Zoho) are config-gated — present only when a mailbox is configured (Fastmail via `FASTMAIL_API_TOKEN`, Zoho via its OAuth triple; both behind the `EmailClient` protocol), retiring the `/email` + `/zoho` commands (epic #1445). Both configured → Fastmail wins (single user, one mailbox). The mailbox client is long-lived (built in `Penny._init_email`, closed in `shutdown`); `ChatAgent._email_tools_builder(user_query, today)` wraps it fresh each turn so `read_emails` summarises against the current question. The NL trigger is the tool surface itself — there is no taught skill any more, so dispatch rides the tools' own descriptions and the model's ordinary reasoning over them. NL-dispatch contract: `tests/eval/chat/idle/test_email_dispatch.py`
- Likes/dislikes are dispatched from natural language onto the `likes` / `dislikes` memory collections via the always-present memory tools (`collection_write` / `collection_remove` / `collection_list`), replacing the retired `/like` + `/unlike` + `/dislike` + `/undislike` commands (epic #1445). Add ("I'm really into X"), remove-by-meaning ("forget about X" — matched by meaning, never exact text), and list ("what am I into?") ride the same tool descriptions, with no taught skill behind them. These collections are what the ambient extractor fills and recall reads; the legacy `preference` table was dropped by migration 0097 (#1676, resolving #1301's legacy-table question).
- Prompt: identity + instructions + Jobs + the store map (`SelfStateHeader.render_static()`, the STATIC prefix, #2814) + the conversation map, then (page hint) + recent activity + durable user facts (`SelfStateHeader.render_dynamic()`, the per-turn DYNAMIC tail), all rendered deterministically from the registry + ledger. No speculative user-content recall (the ambient inversion, #1555); user content is fetched on demand via the tools the header's pointers name
- Conversation history flows independently as alternating user/assistant turns passed via `history=`
- Images: an image attachment rides the current turn's own user message (`Agent.run(images=…)` → the user `LlmMessage`'s `images`, translated to `image_url` content parts at the wire) — the chat model reads it directly, under chat's token budget and thinking-off last draw (#2635). There is no separate caption call and no `LLM_VISION_MODEL`; a non-vision chat model fails the turn through the honest model-error path. The conversation record keeps a deterministic marker where the image was (`PennyConstants.IMAGE_HISTORY_MARKER`); history never resends the image
- Image generation: when an image model is configured, the `generate_image` tool is registered (mirroring the retired `/draw` command's conditionality). It generates the image via `MfluxImageClient` (the local mflux server), stores it in the `media` table with an embedding of the description, and returns a text result naming what was drawn plus the stored row's id on `ToolResult.media_id`. The loop threads that id onto `ControllerResponse.generated_media_ids` and the channel attaches **exactly that row** to the mirror-back reply at egress (`send_response(media_ids=...)`) — a deterministic generate→deliver link, not a fuzzy match, so a just-drawn image always lands on the reply that describes it (nothing travels through the model). The embedding keeps the drawn image matchable by the nearest-image ladder for future replies
