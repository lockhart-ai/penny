# The conversation machine and round framing — reference

Covers the conversation state machine, round framing, skill extraction, and the skill substrate. Read this in full before changing a conversation-machine state, transition, or how a taught skill is framed, bound, or distilled.

- **The skill registry store (`penny/skill_store.py`)** — lives in `docs/reference/database.md`; this file covers the pure substrate (`penny/skills.py`).

### penny/conversation_machine.py

  conversation_machine.py — The conversation state machine (#1706): the model fills states, it never walks them. `ConversationState` (idle · elicit · learn · request · apply) + the `OUT_EDGES` edge table, the CANONICAL `STATE_DEFINITIONS` (one stable definition per state, rendered identically everywhere — a state means one thing regardless of where the machine stands) and the `TRANSITIONS` function (the condition selecting each (current, target) move — the half that legitimately varies by current state; IDLE is the DECLARED DEFAULT, rendered last as `DEFAULT_TRANSITION` = "in all other cases", so a message meeting no positive condition has an unambiguous home; IDLE's own DEFINITION carries the TASK-LIFETIME boundary as well (#1919 — every request handled right now stays idle, including a command about something that already exists, and a message with no standing or scheduling component stays here whatever it resembles), so the boundary renders on every from-idle draw before any edge is considered rather than only on the doors that state it). Data, not prose — every classifying state carries the break-out edge → idle; learn never returns to elicit (once instructions have been given there is nothing left to elicit) but DOES reach apply, because the demonstrated round ends by OFFERING to set the routine running, so the machine is parked in learn at the moment the user accepts and the acceptance has to be answerable from there — and what the skill needs comes from the round that just ran, so accepting never restates it (before the run-end auto-attach was removed in #1768, learning instantiated implicitly and this edge had no work to do); apply has NO out-edges, its reset is structural. `MachineSnapshot` (the scoped classifier input: assistant's last turn, parked task anchor, ranked skill candidates, and — for a round parked in request — its partial binding, #1894: `render_classifier_content` gives it its own `## The details this task is waiting on` section beside the anchor, naming the skill and listing what is already given against what is still needed, so the move out of request is judged against a NAMED gap instead of a fresh completeness audit of the conversation), `StateClassifier` (one tagged draw per incoming message over the CURRENT state's out-edges via `MicroContext.classify_state`, customer #3), `presented_edges` (every SKILL-GATED state withheld when there are no skill candidates — the structural false-apply guard), `next_state` (fail → stay: only a DECIDED draw moves the machine), and `build_snapshot` (the PRODUCTION snapshot builder: EVERY skill offered as name + description + parameters, from `db.skills.list_all()` — **no ranking, no cap, no embedding** (code-owner ruling on #1706): a relevance gate here would contradict #1471, which renders the whole registry to chat wholesale precisely because gates HID skills, and this list is strictly smaller than the full recipes chat already carries every turn. Offering everything also means classifier and chat reason over the SAME set. An empty registry still withholds the gated states — reached by there being nothing to offer, not by anything failing). **`SKILL_GATED_STATES` = apply + request**: each one's transition condition directs a second `SKILL: <name>` line (membership-validated against the candidates) so the decision always binds an actionable skill (`StateDecision.skill`) — **both idle doors are keyed to STARTING a task** (#1927, code-owner ruling: "request is only about starting a new task; changes to existing collections don't count") — each condition asks whether the message asks to SET A KNOWN SKILL RUNNING, and both carry the same boundary word for word (changing how something already set up behaves — its notifications, when it runs, what it covers — is not asking to start it), since a reader who rules apply out for missing information reads request next and would otherwise take the identical fall. **This is the BEST MEASURED wording, not a fix, and the residual gap is EVIDENTIAL rather than verbal**: an ask to turn one running job's notifications on holds 3 of 5 (its off-direction 5 of 5 — only the ON direction can be phrased as starting anything), and the leaking draws never reach the boundary at all, stopping at whether the job the message names EXISTS ("there's no known skill currently running") — which this snapshot cannot answer, since `build_snapshot` renders the skill registry and no standing jobs. Three rounds tried to close it in text and each cost a neighbour: a fourth boundary clause keyed to the start-VERB took the target 0.60 → 0.40 and idle → elicit cross-domain 1.00 → 0.60 (two draws ruled out the two longer doors and jumped to the default without ever reaching the elicit bullet — these render first, so a clause added here is paid for further down the list); a schema statement ("jobs already running are not listed here") left the target at 0.40 and broke the inverse guard, idle → elicit uncovered 1.00 → 0.60, an uncovered setup ask reading as a reference to a running job. Both are recorded as watched deletions above `TRANSITIONS` with their numbers. **So the fix is STRUCTURAL, not verbal (#1927, code-owner ruling): `MachineSnapshot` gained `standing_jobs` and the render gained a `## Jobs already running` section** — the light cycle-free `StandingJob` projection (`name` · `skill_name` · `notify` · `schedule`, `SkillCandidate`'s sibling and a leaf for the same reason), filled by `build_snapshot` from the CONFIGURED collections (`extraction_prompt IS NOT NULL` — the dispatcher's own readiness condition, so what this calls running and what actually runs are one definition; an inert container and an archived tombstone are neither). Every job is offered, the skills section's no-ranking-no-cap rule applied to the other registry, and the section **ALWAYS renders** (`(none)` when empty) for the reason the skills section does: absence must be a READ, never an inference from a missing section — reading nothing there was measured as reading "nothing is running", which was true of the section that did not exist and not of the world. Each row states every clause in BOTH directions (`- "<name>" — runs "<skill>" · notify: on|off · <schedule verbatim>`; `no skill attached` / `no schedule` where the row carries none), since a clause that vanishes when false is one the reader has to infer from again. It renders BELOW `## Known skills` (a job is what a skill becomes once set up) and ABOVE the newest message. apply ENACTS a skill (asked for and fully bound), request NEGOTIATES one (asked for but something it needs is missing, so the assistant names the skill and asks; parked, with three exits — apply when the details arrive or the skill is confirmed, elicit when it was the wrong skill and the task is still wanted, idle on a bail). **`ConversationMachine`** is the machine itself (#1706 persistence): `advance(message)` settles any STRUCTURAL move first (a state with no out-edges — apply — resets to idle, recorded as its own `cause=structural` row; completion is never a self-report the model is asked for), builds the snapshot with the ANCHOR resolved from the machine's own row, classifies, then records the draw and applies `next_state`. It owns the **anchor lifecycle** — set entering a parked state FROM idle, KEPT for the duration of the round (a reply three messages later is still classified against the ask it answers), cleared on the break-out to idle — and records **every** draw including the held ones (`outcome` carries the `StateDrawOutcome`, so fail → stay is distinguishable from a decided idle → idle; a ledger of only successful moves would report a perfect classifier by construction). Appending the move IS moving the machine (`db.machine`), so a failed write leaves it where it was rather than moving it silently off-ledger. `link_message(run_id, message_id)` back-fills the provoking message once it HAS an id — the channel logs the incoming message only after the turn (so it never doubles into that turn's own recall), the same deferred-link shape `link_source_message` uses (#1566) — and stamps it as the round's anchor when that turn's move opened a round. **Wired into the turn** (`MessageChannel._classify_state`): it runs BEFORE the chat agent, so the turn is entered with its state already decided; a classifier failure is logged and swallowed rather than costing the user a reply (fail → stay already leaves the machine put). **Entering learn FRAMES the round (#1868)**: `ConversationMachine` takes an optional `RoundFramer` collaborator (injected, since framing a round means database + embedding work this leaf module must not import at import time), and `advance` runs it on a DECIDED move into learn; a fail → stay draw that merely LEAVES the machine in learn frames nothing, since the machine's rule that a contract failure moves nothing has to hold for the store as well as for the state. The result is the typed `RoundFraming` (the framer's `SkillSignature` + the `container` built from it), recorded on the move in ONE write as `state_transition.skill_frame` and read back by `framing()`. It rides the ANCHOR's own lifecycle (`_next_framing`): a fresh entry draw replaces it, every other move CARRIES it (so the turn that accepts what was demonstrated reads the same container the turn that demonstrated it wrote into), idle clears it — and a move that settled nothing carries rather than clears, so a held draw keeps the container the round already has. **A round's identity is settled ONCE, at its FIRST entry (#1902)**: `_frame_learn_entry` takes the machine's CURRENT state, and a learn→learn move on a round already carrying a framing makes no draw at all — it calls `RoundFramer.carry_entry`, which re-settles only the container (find-or-create, because a failed learn turn may have archived it, #1839) and hands the same framing straight back. A correction refines the PROGRAM of the round's one job, never the identity: same routine, same container, the corrected write landing in place. Re-drawing on every entry is what FORKED a round in two — a corrected ask read as a different subject, the fresh draw derived a fresh name, find-or-create minted a sibling container, and run-end extraction registered a second routine beside the first (~21/25 measured samples). The boundary case is a round still UNFRAMED (its entry draw failed): it has no identity to keep, so it is drawn again. **A round that MINTS a routine also records its PROVENANCE (#1902)**: on the move that opens the round's teaching (`_opens_the_teaching` — a decided landing in learn from anywhere but learn), `_next_provenance` records the typed `RoundProvenance` carrying whatever the registry already holds under the framing's pinned name (`snapshot_replaced_skill` → `ReplacedSkill`, the whole row with its embedding base64'd so the round state stays compact JSON). Stored as `state_transition.round_provenance`, read back by `provenance()`, with the framing's own lifecycle (set on entry, carried, cleared at idle). **Both halves of WHEN are load-bearing.** Only a learn turn registers a routine, so a move arriving from outside learn is the last moment the read is truthful — from inside, the round's own extraction has already written that name and the same read would take the round's own work for what it replaced (an unframed round framed on a LATER entry therefore records nothing, and the declared cost is that a bail then leaves that routine standing rather than risk deleting the user's). And only the FRAMER mints: a skill-gated entry binds a routine the registry already holds, so such a round records no provenance at all. **The three shapes are three answers to what a bail owes the registry**: absent = the round minted nothing, leave it alone; present-and-empty = the round minted over nothing, DELETE; present-carrying-a-row = the round was re-teaching, RESTORE. **An idle landing also ENDS the round in the store (#1896/#1902)**: `_end_round` runs before the move is written and takes BOTH things the round left behind — the container that framing pointed at is archived (`round_framing.abandon_round_container`) and what the round wrote to the registry is taken back (`round_framing.abandon_round_skill`), resolved by that provenance. Restoring rather than merely skipping the delete is the point — by bail time the round's own extraction has already replaced what the canonical routine DOES, so leaving it standing would leave an abandoned, half-corrected program live under a name existing jobs still run. The post-apply structural reset is not this path (it drops the framing on its own row before anything is classified, so a job just set running is never retired by a later bail) — which is also what makes promotion IMPLICIT: there is no draft flag, a routine simply survives its round. A failed entry draw records no framing at all and the round runs unframed, which is the pre-#1868 behaviour exactly. **A move into APPLY settles a framing too, once, when the round arrived WITHOUT one (#1875/#1870)**: apply configures the round's own container, so a framing is the one thing that turn cannot do without, while a round already carrying one draws nothing (a re-draw is not a re-read: a fresh draw could point the acceptance at a container the demonstration never used). WHICH draw settles it is `_frame_round`'s two named branches — `_frame_learn_entry` runs the FRAMER (a round being taught has no routine yet, so one is minted), `_bind_apply_entry` runs the BINDER (#1870 — a cold apply asks for a routine the registry already holds, so the classifier's `SKILL:` names it and the only open question is which part of the user's words fills each thing it declares). A decided apply always names a skill by the draw contract, so a missing one is logged as a broken contract and the round stays unframed rather than bound to a guess. A draw that fails either way records no framing, and the turn fails honestly rather than falling back. **A cold apply the words fall SHORT of lands in REQUEST (#1885)**: the binder's `MissingParameters` is an enumerated outcome rather than a failure — the routine really does cover the ask — so it ROUTES the move instead of failing the turn. `bind_entry` returns the typed `RoundEntry` union (`RoundFraming | RoundShortfall`), and `_landing(current, decision, entry)` redirects the recorded `to_state` to `request` whenever the entry came back a `RoundShortfall` (the routine's registry name + description, the values the words DID settle, and each missing parameter with the registry's own what-to-supply, both lists in declared order). **No classifier condition is added or changed** — the idle → request edge already existed and still fires on its own; this is a SECOND door no edge declares, because only the binder reads the words against what the routine declares. The draw still says apply: the raw `STATE: apply` stays readable on its own promptlog row and the move is still `cause=classifier` (a model was in the loop). It is also the only way a machine already sitting in request lands back in request, which `OUT_EDGES[REQUEST]` has no self-edge for. Nothing is built for it (the container's derived name needs every value). **The binder runs at REQUEST entry too, and the partial binding is ROUND STATE (#1894)**: `_frame_round` binds on either skill-gated landing (`_BINDING_STATES` = apply + request, `_bind_round_entry`), so a request the classifier drew DIRECTLY — the door every measured request turn came through — runs the same binder and, when the words are short of something, produces the same `RoundShortfall` instead of a generic "ask for the part that is missing"; both doors present one shape. That shortfall is recorded on the move (`state_transition.round_shortfall`, serialized like `skill_frame`) and read back by `ConversationMachine.shortfall()`, with the lifecycle of the state that reads it (`_next_shortfall`: only a move LANDING in request carries one — a freshly drawn binding replaces, a failed draw carries, a round that binds carries a `skill_frame` instead, elicit/idle clear it). Three consumers read it: `TurnEntry.shortfall` (now a READ of the log, threaded channel → `ChatAgent.handle(shortfall=…)` → `conversation_prompt`, so a turn arriving on a parked round asks for exactly what the turn that parked it asked for), the classifier's `MachineSnapshot.round_binding` (its own rendered section, below), and the next binder draw — `bind_entry(settled=…)` fills only the parameters still OPEN and merges what the round already settled, so the apply draw COMPLETES the binding from persisted values plus the arriving message rather than re-deriving it, and a value given two turns ago cannot come back different. A message the binder still cannot complete lands in request again with its binding intact (the learn→learn re-demonstration shape). **Per-state chat instructions (#1706/#1868/#1869/#1875/#1885)**: `STATE_INSTRUCTIONS` maps EVERY state to its one instruction and `conversation_prompt(state, framing=None, shortfall=None)` composes `Prompt.CONVERSATION_HEAD` + that instruction + the round's own closing line when one was settled + `Prompt.CONVERSATION_TAIL`. WHICH closing line is `_round_line`, keyed by state, reading whichever half of the round's entry that state has: LEARN renders `Prompt.ROUND_FRAMING_LINE` from the FRAMING (the container is already there, so a step that remembers something writes into it); REQUEST renders `Prompt.ROUND_SHORTFALL_LINE` from the SHORTFALL (the routine, what it is for, what they have already given — rendered even when empty, as a stated "nothing yet" line — and what is still missing, asked for by its description and never by its binding key), so the ask is n=0 and nothing on it is invented. APPLY is NOT in that map — its instruction NAMES the round inside itself (`Prompt.APPLY_INSTRUCTION` is a template over `{container}`/`{skill}`), because by then the round is not one more thing to know about the turn but the subject of every sentence in it, and there is **no unframed apply form at all**: `conversation_prompt(APPLY, None)` RAISES, and the chat agent fails the turn before composing a prompt. Both states render the routine and the container VERBATIM, so a name the model would otherwise invent is a name it copies. Elicit renders nothing (it is still asking what the task IS, so it has nothing to say about a container that may not exist yet) and idle never carries a framing at all. With no framing — and, for request, with no shortfall — every state's composition is byte-identical to what it always was, so the rendered round state is additive on every path. The map is TOTAL by construction (pinned by a test) and indexes directly — **there is no default and no fallback**: the machine always has a state, so a missing instruction is a programming error, not a case to absorb (a fallback would mean the state failed to determine the prompt, the one thing the machine exists to fix). No instruction names a state, mentions another state, or hints a classifier ran. `Prompt.CONVERSATION_PROMPT` — what the chat agent uses when no machine decided the turn — is *defined as* idle's composition, so it can never drift from it. The #1687 four-case union (`SKILL_PATH_DEFAULT`) is DELETED: it existed only to help the model work out which case applied, and that question is answered in Python before the turn begins. The pure pieces (`presented_edges` / `render_classifier_content` / `next_state`) stay callable with no database, which is what the classifier eval drives

### penny/round_framing.py

  round_framing.py    — `RoundFramer`: framing a round at its ENTRY and the container it runs into (#1868/#1870). The framer used to run at the END of a learn turn, so a routine's identity was settled only after the round had already happened — the round had nowhere to put what it found, and the model named a collection by judgment (measured 18/25 task-rooted, the misses concentrated on same-kind-different-place asks). The draw moves to the moment the machine LANDS in learn (the ask and the demonstration both exist there, which is the framer's whole input contract) and Python does the rest deterministically: `frame_entry(ask, message, run_id)` renders the round's user turns through the SHIPPED `build_framing_content`, draws `MicroContext.frame_skill`, derives the container's name from the framed skill plus its demonstrated values (`derive_collection_name`), and FIND-OR-CREATEs it INERT through `db.memories.create_collection` — storage only, no program/schedule/notify, so the dispatcher never runs anything against a container whose routine does not exist yet (#1629), with the framer's own one line as its description (the same meaning anchor the routine states) and the creating run stamped. Returns the typed `RoundFraming` the machine records on the move. **Certified-by-execution is untouched**: nothing here writes a skill row — the registry still only gains a skill at run end, from the ledger. **The container's lifecycle is find-or-create, never mint-per-round**: re-asking for the same job derives the same name and finds the container that exists (tier-1 dedup by construction, #1775), and the same job taught again after a discarded round UNARCHIVES the container already carrying its name. **A round's identity is settled ONCE, at its first entry (#1902)**: `carry_entry(framing, run_id)` is the third entry and the one that DRAWS NOTHING — a correction re-entering learn hands its existing framing back unchanged and only re-settles the container, so the identity-shift branch that used to archive one container and mint another is GONE with the `previous` argument it read (a correction can no longer shift what the round is about). **Two entries, two draws, one outcome (#1870)**: `bind_entry(skill, ask, message, run_id, settled=…)` is the SKILL-GATED entry's sibling of `frame_entry` — a round asking for a routine the registry ALREADY holds mints nothing, so the classifier's bound `SKILL:` is looked up, `build_binding_content` + `MicroContext.bind_skill` fill its declared parameters from the round's user turns, and the registry's own name and description carry into the signature unchanged (a second draw's preferred wording would derive a container name for a job filed under a different one). Since #1894 it is the ONE door for apply AND request entries, and `settled` (what a parked round already bound, narrowed to what the routine still declares) means only the OPEN parameters are rendered and drawn — a question Python already holds the answer to is not asked, so a round with nothing left open settles with no draw at all. Find-or-create on the derived name IS tier-1 dedup by construction: the same job re-asked runs into the container it already had, a different place mints its own. Its three no-container outcomes are logged apart for what each is — a routine the registry does not hold, a `MissingParameters` SHORTFALL naming what the words fell short of, and a draw that produced nothing usable. Since #1885 they no longer end alike: the two failures leave the apply turn with nothing to configure (#1875's honest failure), while the shortfall comes back as a typed `RoundShortfall` (`_shortfall`, which tells the two empty-handed directions apart and builds the shortfall through `round_shortfall`) that routes the turn into `request`, logged at INFO because a covered ask waiting on one detail is an ordinary turn rather than a degradation. `round_shortfall` is the only construction of a shortfall on the production path — the registry row supplies the routine's name, description and declared order, the caller supplies only the values — and it is public because the eval harness's isolated classifier draw builds the same binding through it, off the seeded registry row (#2084). The one mirror that remains is the transition world's `parked_binding`, which builds a case's recorded binding from its fixture DRAFT because the seeder runs before the registry holds the routine; a deterministic test asserts the two agree. `discard_round_container` is the #1839 failure path's half — an honest learn-failure takes its minutes-old container with it — and `abandon_round_container` is the #1896 BAIL's half: a round that ends in idle takes its container with it too, because a bail preserves nothing and clearing the framing off the move alone would leave an inert collection named for a job nobody is doing. The LITTER retirements are guarded on EMPTINESS, read not judged: litter is a container with nothing in it; one holding entries is something the user can still read, whatever the round did next. The bail's is the deliberate exception — what a demonstration wrote is the round's own intermediate state rather than something to be preserved past the user calling it off. Archive (SYSTEM actor + a cause note on the mutation ledger), never delete — a retired mechanism stays a visible tombstone, and the same job taught again UNARCHIVES it. **`abandon_round_skill` is the bail's OTHER durable half (#1902)**: what the round wrote to the registry (under the name its framing pinned) is taken back too, since a routine standing for a job the user called off is AMBIENT — every later turn reads the registry. WHICH way is READ from the round's provenance (`snapshot_replaced_skill`, recorded when the round's routine was minted), in its three shapes: a round that minted NOTHING (a skill-gated round binding a routine the user already had) leaves the registry alone — the case a name-keyed discard would get catastrophically wrong, since that routine is the user's; a name the round MINTED over nothing is DELETED — the one place this parts company with the container, since the `skill` table is versionless and carries no archived flag, so a name is either in the registry or it is not; and a routine the round was RE-TEACHING is RESTORED to the pre-round row verbatim, timestamps and embedding included (`db.skills.restore`), because the round's own extraction has already replaced what that routine DOES and un-deleting is not the same as putting it back. Either way the change records a `mutation_event` under the SYSTEM actor (`MutationEntityType.SKILL` + `MutationAction.DELETED`/`UPDATED`, the enum's second customer), so a routine vanishing or reverting between turns shows in the recent-changes render like any other configuration change. A framing whose routine never reached the registry is a plain no-op

### penny/skill_extraction.py

  skill_extraction.py — SkillExtractor: distils a skill from a LEARN chat turn's ledger at run end (#1658/#1665/#1770/#1850). **Extraction fires only in the `learn` state, and has NO shape requisites (#1850, code-owner ruling)**: `SkillExtractor.extract(run_id, state=…)` yields a skill if and only if the turn's landed machine state is `learn` — any sequence of tool calls during a learn turn becomes a skill, and no other state produces one. The state is a PARAMETER, threaded channel → `ChatAgent.handle(state=…)` → the turn-scoped `_turn_state` → `extract` (this module never reads `db.machine`, so what a run yields cannot disagree with the state the turn ran under); absence of machine history is idle, so a cold machine never learns by accident. A non-learn refusal is the named `ExtractionGate.NOT_LEARN`, logged with the state that produced it — never a silent skip. This closed the measured escape (PR #1849): an APPLY turn's extra enactment (a browse + a write) qualified on shape alone and minted a brand-new skill framed from a round that taught nothing, landing beside the skill it had just applied; an idle one-off that browses and writes reached the same place. The **read+write taxonomy qualification is DELETED** with it — a learn run that only read and one that only wrote both extract now, since a routine's shape is not the framework's to judge. **Learning attaches NOTHING (#1706)**: the run-end auto-attach (#1687 split 6 — binding the just-learned skill to a collection the same run created) is REMOVED. The conversation state machine makes teaching and instantiating two clear turns — `learn` runs the round, reports it, and offers; `apply` binds the skill via `collection_configure` when the user asks — so the framework no longer folds them at run end. A demonstrated round leaves a naive `collection_write` behind: a collection holding the value, with no `skill_name`, no rendered `extraction_prompt`, and nothing scheduled. What remains beside the state gate is MECHANICS, not qualification: chat run · ≥1 tool call · ≥1 SUCCEEDED, COLLECTOR-runnable, non-ORIENTATION call (the `BAILED` health gate retired with the nudge markers it keyed on, #1839; registry-navigation verbs — `find`/`memory_get` — are still dropped from the recipe, since a re-run re-orients itself and a `find` result echoing its query manufactured a false binding, #1665). A learn turn that captures nothing stays `NoExtraction` and #1839's honest learn-failure reply fires — learn's one valid terminal state is a skill in the registry → distill (`distill_steps` over the certified, non-`done`, non-orientation steps) → **label** every spot via a single-shot leaf-labelling micro-context (#1828: one `LABEL <current>: <semantic_name> — <what belongs there each run>` line per spot, poison-screened + re-rolled). It JUDGES NOTHING — every leaf is a placeholder unconditionally, so no draw is asked where a value came from (#1824: the per-candidate provenance verdict it replaces pinned at ~0.7-0.8 across three wording interventions and compounded with every extra leaf). A labelled spot becomes a `SkillSubKind.PLACEHOLDER` substitution carrying its description — never the frozen demonstrated value — and stops being a parameter; the draw is accepted only if it covers EVERY offered spot with exactly one well-formed line (#1828 — a decayed tag, a repeat, or a line for a spot nobody offered fails the WHOLE draw, re-drawn for the whole budget), so an unlabelled spot means the whole draw failed and every spot keeps its arg-derived required parameter; an attachment-marked leaf is a placeholder either way, because a destination is never a parameter (#1827 principle 4). → **frame** the routine's INTERFACE beside it, from the user's ask ALONE (#1830, `MicroContext.frame_skill`): the two draws share no inputs and no outputs, and either may fail alone. **Since #1868 the interface is normally READ rather than drawn here**: the framer runs when the machine ENTERS learn, so the routine was named before the round ran, and `extract(run_id, state=…, framing=…)` reuses that signature (threaded channel → `ChatAgent.handle(framing=…)` → `_turn_framing` → `extract`, the same discipline the state takes). A re-draw is not a re-read — the turn was instructed under the entry name and wrote into the container derived from it, so filing the skill under whatever a second draw preferred would leave that container pointing at a routine no longer called that. The run-end draw survives as the path for a round nothing framed. The framer's `NAME:`/`DESCRIPTION:` and one `PARAMETER <name> — <what to supply>` line per minted parameter become the skill's name, description and `parameters`; a failed framing falls back to the deterministic slug of the triggering message with NO parameters (the #1829 interim, now the failure rung). The dedup embedding anchors on the framer's GENERIC description, so two demonstrations of the same routine on different occasions converge. Each framed parameter keeps the VALUE its round demonstrated it with, and that value is the RUNTIME JOIN (#1907): the two draws share no inputs and no outputs, so the value both halves independently point at is the only thing that can say which leaf a parameter fills, and `bind_parameters` reads it at the instantiation seam. The parameters live at SKILL level — rendered by `render_skill_brief`'s `needs:` tail, enforced by `collection_configure`'s unbound-required-parameter validation, decisive for `is_same_job` tier 1 — over a STORED recipe that still reads in the labeller's placeholder descriptions, while the recipe a configured COLLECTION runs reads with its bound values → dedup (REPLACE by name, or by same tool-sequence shape + generic-description-embedding match keeping the existing name). Returns a typed SkillExtracted (carrying the demonstrated-on origin message for the narration frame) / NoExtraction(gate) — never a silent None. There is NO skill_create tool

### penny/skills.py

  skills.py         — the skill substrate (#1590): pure step/parameter models (`SkillStep`/`SkillParameter`/`SkillSubstitution`, the `LoggedToolCall` shape + provenance-tagged leaves), `distill_steps` (STRUCTURAL provenance, #1659: a leaf that equals / occurs as a whole whitespace-delimited span of / wraps a prior step's result → binding; every other string leaf → a required parameter, never a silent default — the utterance-substring test is gone; that last rule is a DEFAULT the run-end labeller's per-spot labels resolve, #1770/#1828). **A REPEAT is an input given twice, never a step's output (#1933)**, and both halves of that are structural: the COLLAPSE rule is asked FIRST (a leaf whose exact demonstrated value an earlier leaf already minted a parameter for joins that parameter, before any provenance test), and a prior step's result is read with the step's OWN argument echoes removed (`_prior_result` — a browse section header naming the page it fetched, an extract result opening with the instruction it was handed; a span that went INTO a call cannot have come OUT of it, the same class as #1665's find-echo exclusion, and keyed to no tool name so an unheard-of tool echoing its arguments is covered for free). The echo exclusion applies to the CONTAINED-IN direction only — *wraps* still compares the whole payload, since an argument containing the entire result is quoting it. Without them the demonstration's second fetch of a page it had already fetched bound to the first fetch's *result*, so the routine read `browse(queries=[the value from step 1])` and no longer said which page it fetches. **EVERY leaf goes through that one process (#1783)** — whatever tool it sits on, whatever argument it fills: no write target, no privileged argument, no tool whitelist anywhere in the path (a skill is a learned sequence of ARBITRARY tool calls, so any rule keyed to a tool name assumes a shape it cannot know). A leaf whose demonstrated VALUE names one of Penny's own COLLECTIONS additionally carries the **attachment mark** (`SkillSubstitution.attachment`, registry-derived, set by comparing values against the names `distill_steps` is handed): applying the routine somewhere is what decides such a leaf. Nothing clears the mark since #1828 — a destination is never a parameter (#1827 principle 4) — so `retarget_writes` binds every marked leaf, and `WRITE_TARGET_DESCRIPTION` ("the collection this is set up on") survives as the description for a marked leaf the labelling draw never named, plus the legacy rows migrations 0101/0103 back-fill, and `render_skill` (steps + bound params → the numbered TEXT `extraction_prompt`; a `SkillSubKind.PLACEHOLDER` leaf renders as `{<what belongs there>}` from the substitution's `description`, never the demonstrated value). Parameters are SKILL-level — semantic name (the binding key) + optional one-line description (#1668) + the `value` the teaching round DEMONSTRATED it with, not tool-arg echoes. **The RUNTIME JOIN (#1907)**: `bind_parameters(steps, parameters, params)` is `retarget_writes`' sibling at the same instantiation seam — a routine's interface and its implementation are drawn by two contexts that share no evidence (#1824), so the demonstrated value is the only thing that can say which leaf a parameter fills, and where a parameter's demonstrated value equals a leaf's (compared on whitespace + case alone — punctuation and spelling exactly, so a short value can never claim a leaf that merely contains it) the bound value is written into that leaf and its substitution dropped. A BINDING leaf and an ATTACHMENT-marked one are out by construction; a value two parameters both claim binds neither; a parameter with nothing bound leaves its leaf saying `{no value was supplied for the parameter '<name>'}` rather than a description that reads like an instruction. Pure, like `retarget_writes` — the stored skill keeps its verbatim ledger arguments. **The apply-time pair (#1867)**: everything above is the round that TAUGHT a routine; `build_binding_content` (+ `render_spoken_turns`) renders the document the BINDER micro-context reads — the signature as it already stands, then the user's own turns, in that order because the words are what is being read — and `derive_collection_name(skill_name, values)` is the pure (skill, values in declared parameter order) → container name that makes a job's identity deterministic instead of a naming judgment. The scheme: slug the skill name, then each value in declared order, joined with hyphens, lowercase throughout — with a url normalised to host + path first (scheme, `www.`, credentials/port, query, fragment and trailing slash dropped), so one page written four ways is one job. `monitor_price` pointed at `https://faux-market.example/keel-lantern` derives `monitor-price-faux-market-example-keel-lantern` — the whole point being that the name is obvious with nothing to resolve. The length policy is a READING budget (`DERIVED_NAME_MAX_LENGTH`, the name renders as one clause among others on a line), spent on WHOLE tokens with **no hash and no ellipsis**, and spent ROUND-ROBIN across the values so every parameter stays represented — a plain tail truncation would drop the last value's tokens first and collapse two jobs differing only in their last parameter onto one name. **Collision posture**: same skill + same values → same name, and that IS the point (re-asking for a job finds the container you already have — tier-1 dedup by construction, #1775); two different jobs collide only if they agree token for token to the budget, which is accepted rather than defended against, since the alternative is a disambiguating suffix nobody can read. ### A learn turn that produced no skill FAILED (#1839)

- **A learn turn that produced no skill FAILED (#1839)**: the `learn` state has exactly ONE valid terminal state — a skill in the registry — and the machine decided the turn was a learn turn *before* it ran, so at run end this is a deterministic read of two recorded facts, not a judgment. When a learn-state chat run's run-end extraction returns `NoExtraction` (ANY gate), `ChatAgent._enforce_learn_terminal` **throws the model's reply away** and returns `PennyResponse.LEARN_NOTHING_LEARNED` instead — the observed harm being a reply that offers to set running a routine that was never learned. The tool calls travel with the failure so the run record stays complete, and the machine is left exactly where it stands: **parked in `learn` with its anchor**, so the user's retry is the existing learn→learn re-demonstration edge and a bail is still the break-out to idle. Extraction SUCCESS — and any turn where extraction never ran at all (a vision turn, a run that never reached its text branch and already carries its own honest failure) — takes today's path byte-identically.
