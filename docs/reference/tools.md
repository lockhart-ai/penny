# Tools and micro-contexts — reference

Covers the Tool ABC, BrowseTool, every micro-context customer, and the memory tool surface. Read this in full before changing a tool's arguments, a micro-context's output contract, or the write-gate.

- **Write-gate STOP semantics** also ends a collector cycle — see `docs/reference/scheduler-and-collector.md` for how a STOP is read as a clean close.

### penny/tools/base.py

    base.py           — Tool ABC (declares `args_model` + `run()`: validate args via the Pydantic model, then `execute`), ToolRegistry, ToolExecutor (drives `tool.run`). Its tool-not-found did-you-mean goes through `text_validity.suggest_tool_name` (#1944): a name this project RENAMED resolves through the rename table FIRST — a historical fact no character comparison can recover — and only when the replacement is on the surface, so the suggestion always names something callable; everything else falls to the string leg. The measured miss it fixes: a guessed `collection_metadata` (retired by migration 0059) was answered with `collection_set`, the character-nearest name and a different tool entirely, while the one it wanted was `memory_get`

### penny/tools/browse.py

    browse.py         — BrowseTool: web search and page reading via browser extension. Optional `extract` micro-instruction (#1588): a fetched PAGE's full content goes to a fresh single-shot micro-context and only the typed value + the stored page's log and id (`log='browse-results' id=<id>`, what `log_get` takes) return to the main loop. A SEARCH is never extracted from (#2141) — it comes back as its trimmed list of links either way — and a failed page extraction carries that page's links beside the failure sentence

### penny/tools/micro_context.py

    micro_context.py  — MicroContext: single-shot extraction over bulk content (content + instruction, no tools) via the shared model client; output contract enumerated on both sides (EXTRACTED:/NOT_PRESENT: tags, deterministic parse; the tag must OPEN the output and the EXTRACTED value is EVERYTHING after it — a multi-line digest/list is served whole, #1682 — while the NOT_PRESENT reason stays a single line; untagged → re-rolled → honest failure); poison screened + re-rolled by the text_validity detectors; returns a small typed MicroContextResult. **Second customer (#1828, the #1824 inversion)**: `label_skill` NAMES every spot in a demonstrated routine and judges nothing — one `LABEL <current>: <semantic_name> — <one-line description of what belongs there each run>` line per spot, keyed by the current arg-derived name so the mapping back needs no guess → typed `SkillLabels` carrying `labels: dict[str, LeafLabel]`. The `PARAM` line, the `NAME:`/`DESCRIPTION:` lines, `ParameterVerdict` and the grouped-by-verdict response (#1807) are DELETED from this customer: provenance is not asked at all now, and the routine's interface (name · description · parameters) is the FRAMER's separate draw from the user's ask alone, so neither sees the other's evidence. Its user turn is the rendered document ALONE (the classifier's bare-content template — the ask lives wholly in the system prompt), and it rides the SAME poison/reroll `_draw_clean` loop with its own system prompt + ledger attribution. **COVERAGE is the runtime constraint (`accepts`), and an accepted draw never contains an invalid line (#1828, code-owner ruling)**: the caller passes the offered spots' current names, and the draw is accepted only when EVERY one has exactly one well-formed line and nothing else does. A missing line (the observed failure — the tag decaying mid-draw, which the parse rightly refuses), a spot named twice, or a line for a spot nobody offered (a spot INVENTED — the shared-spot split) are each a contract violation like the classifier drawing an out-of-set state: discarded and re-drawn on the unchanged context, then an honest WHOLE-draw failure and every spot keeps its arg-derived name. Correctness of accepted results over salvage — no partial rescue. **The wire tag is a short, common, non-compound word (#1842, the #1826 long-literal decay class)**: the eleven-character `PLACEHOLDER` it replaced came back as `PLACEBLODER`, `PLACEHOLER` (three times in one draw), `PLACEHOlder`, and once carrying a zero-width character — and since the parse matches tags EXACTLY (no fuzzy matching, by standing ruling), each decayed line read as no line and failed a whole labelling whose judgments were themselves perfect. The ruling changed the WORD, never the matching: a literal the model has to spell is a literal it can misspell. The #1770 PER_ITEM best-effort tolerance was built for the verdict labeller, where absence had a safe meaning; here the caller KNOWS the offered set, so a hole is a defect the validator can see. The grammar stays permissive (a customer that can't check coverage keeps the best-effort read); the one per-spot path left is a line that stops after its name, which is well-formed, so the draw stands and the CONSUMER reads the blank description as no label rather than rendering an empty slot. Model-facing names are carried VERBATIM; hardening one into a binding key is `slug_parameter_name`'s, applied where a name becomes a key (the framer's mint). **Third customer (#1706)**: `classify_state` picks the conversation machine's next state from the CURRENT state's out-edges (tagged `STATE: <name>`, MEMBERSHIP-validated — a drawn state outside the offered union is a contract violation like an untagged draw: re-rolled, then an honest `INVALID` the machine reads as no-transition) → typed `StateDraw` (+ `skill` when the decided state is the caller-declared skill-gated one: the `SKILL:` second line, membership-validated against the offered skills — missing/out-of-set = the same violation); string-typed on purpose (this module never imports the machine's state enum — `conversation_machine.py` imports this module, not the reverse). **The output shape is DECLARED AS DATA (#1814)**: each customer names a `MicroContextShape` (`micro_context_shape.py`) instead of owning a bespoke `str.partition`/`startswith` parser, the prompt's tagged-lines block is RENDERED from that declaration (`render_line`), and `MicroContext._valid_draw` is the ONE validate step — poison screen → `parse_draw` against the shape → the caller's runtime constraint (`accepts`, where membership sets live, since a static shape can't carry them) → reroll while violated, on ONE budget shared with poison (`DEGENERATE_REROLL_ATTEMPTS`, #1839's ruling carried forward: a violation is DETECTED against the declared shape / offered set / membership union rather than judged, so a detected-invalid draw is cheap to throw away and redraw — the fallback stays the honest end after the budget, not a thing to reach one draw sooner) → a typed `DrawFailure` (`POISON` | `INVALID`) each customer maps onto its own enumerated outcome (`POISON_REROLL_FAILED`/`EXTRACTION_FAILED`, `POISON_REROLL_FAILED`/`INVALID`, `None`+slug fallback). A customer reads named fields off the `ParsedDraw` (`DrawField`) and partitions nothing. **Fourth customer (#1830/#1868)**: `frame_skill` writes a routine's public INTERFACE — a generic name, a one-line description, one MINTED parameter per piece the user would have to say again, and the VALUE this round demonstrated each parameter with (tagged `NAME:`/`DESCRIPTION:` + one PER_ITEM `PARAMETER <name> — <what the user supplies>` line, the two-field carve the labeller's placeholder line has, + one SHARED `VALUE <name>: <value>` line per parameter) → typed `SkillSignature` carrying `parameters: tuple[FramedParameter, ...]`, each with its `value`. The VALUE line is the BINDER's line, declared once above both customers and read by both, so a prompt and a parser cannot drift apart across two customers that deal in the same thing. Its value half exists because the framer moved to learn ENTRY (#1868) and a job's container is NAMED from the skill plus these values — so the coverage rule is #1828's, applied to the draw's OWN minted set (one value line per parameter it named, no more and no fewer), and every value must be a literal span of the user's words: an invented one would mint a container for a job nobody asked for, and nothing downstream could tell. The span check reads the framer's own document, because for this customer the document IS the user's turns (the binder needs its `spoken` separately, since its document renders a signature too). Its content is the round's USER turns and NOTHING else (`build_framing_content`, the bare-content user template): what a routine is FOR is answered by the ask, and every other thing a round leaves behind is evidence of HOW it was carried out — measured, a values list handed over with the ask argued four of five draws into treating every value as something to be supplied. It offers NO set, so it mints rather than sorts, which is what lets it decide a piece the demonstration never separated out. Name and parameters come out of ONE decision, which is what makes them unable to contradict (a routine cannot call itself a price watcher and then ask what to watch). **The system prompt is a WHOLESALE code-owner rewrite (round 6)**: five rounds of measured fixes each landed as another clause on the previous wording and produced an obscure private dialect, so the whole prompt was restated once — read the ask · name the skill · decide the parameters, with the PARAMETER line's own schema inline where that line is described. Everything the rounds measured is kept: the parameter question and the not-a-parameter list (what the framing carries · storage · cadence · notification); **one value** per parameter, never a list (run 1 — all five two-sources samples drew one `sites — list of URLs`); a **generic name + what-to-supply description**, never this occasion's value (run 2); **distinct names** for two things of the same kind (run 3 — which asked in its own thinking whether two lines could share a name); the value's own **KIND**, never a piece decomposed out of it (run 4 — deliberate url-templating, "the site always same base"); and **no examples** in the description (run 5). Two deliberate absences, code-owner ruled: no worked example of a filled line in this version (its return is a measurement, not an assumption), and the type nouns `url`/`topic` ARE the contract being taught rather than fixture leakage. **Round 8 (code-owner ruling) changed the parameter step's ROOT to ENUMERATE-then-FILTER**: every earlier version asked the minimal-information question *hypothetically* ("picture the user coming back — what would they have to give?"), and an imagined occasion admits imagined needs — the measured class was parameters INVENTED whole (a `search_term`/`search_keyword` promoted for an ask that named a page and no search), which nothing forbade because the question never said where a parameter may come FROM. The step now says to LIST, in reasoning, the pieces the user actually provided, then keep only those they would have to provide again — so a parameter can only be one of those pieces and an invention is structurally unavailable rather than discouraged. The filter clauses are unchanged; they now filter a set that exists. **Its runtime constraint (`accepts`) is that the signature is USABLE**, each violation re-rolled then an honest whole-draw failure: no parameter at all (the floor — a routine that needs nothing said can only repeat its demonstration), a MALFORMED `PARAMETER` line, or the same parameter name twice (compared HARDENED — a name is a binding key, and two lines under one key means one silently disappearing). With no offered set there is no coverage gap to notice a dropped line by, so `parse_draw` COUNTS the tag-carrying lines it dropped (`ParsedDraw.malformed`) and the framer refuses any. Parameter names are hardened HERE by `slug_parameter_name` (moved to this module with the framer — the mint IS the key), unlike a leaf label's, which is carried verbatim. **Fifth customer (#1867)**: `bind_skill` fills an EXISTING routine's declared parameters from the user's own words — the framer's apply-time sibling, and the customer that makes task identity deterministic. Where the framer MINTS an interface once from the round that taught it, this one runs every time that routine is asked for again: the parameter set is an INPUT, so nothing here decides what a routine needs, only which part of the user's words fills each thing it already needs. Two PER_ITEM tags, both short common non-compound words (#1842): `VALUE <parameter_name>: <the value, in the user's own words>` and `MISSING <parameter_name>` → the typed union `BoundValues(values)` | `MissingParameters(names, values)`, `None` the honest escape. **The SHORTFALL is part of the contract from the first line, not a failure**: a parameter the words supply nothing for gets its own MISSING line, so "they didn't say" is a POSITIVE statement the draw made rather than an inference from a line that never arrived (the structural `request` signal, which since #1885 ROUTES the turn into that state rather than failing it) — and the values the words DID supply travel with it, so reporting one missing parameter never costs a correct binding, and they are what the request turn renders as "already given, don't ask again". **Its runtime constraints (`accepts`) are all structural**, each violation re-rolled then an honest whole-draw failure: no MALFORMED line (#1830's rule, since every line here is PER_ITEM and a dropped one is a parameter answered by nothing); the drawn names, HARDENED, equal the declared names as a MULTISET — one comparison covering coverage, membership and repeats at once, #1828's rule for a customer that knows its offered set exactly; and **every VALUE a literal span of what the USER said**, which is the check the whole customer exists for (the measured defect being a bound url carrying an underscore that appears nowhere in the message). The span tolerance is declared once (`spoken_form`: whitespace runs collapsed to one space, trimmed, case-folded) and is deliberately small — punctuation, spelling and word order compare exactly, and it is PUBLIC so the eval scores through the same definition production validates with. `bind_skill(content, declared, spoken)` takes the user's turns SEPARATELY from the rendered document on purpose: the document renders the signature too, and a value copied out of a parameter's own description is a confabulation wearing the document's clothes. **Sixth customer (#1911)**: `compose_notification` writes the one message a finished collector cycle sends — the first customer that closes a background cycle rather than a chat turn, and the one whose whole point is having NO tool channel (the four-step notify tail it replaces was where 42 of 49 measured cycle deaths landed, on a decayed tool-call envelope). Its document is assembled framework-side (`penny/notification.py`) and its shape is one `MESSAGE:` line spanning the REMAINDER — the `EXTRACTED:` shape, except anchored ANYWHERE rather than at the head, because the tag's job here is to say where the message the user receives BEGINS, so a chatty preamble is left behind rather than failing the notification. Its runtime constraint (`accepts`) is that the drawn text is worth delivering, read through the SHARED `half_formed_send_reason` rule the send path validates with (plus a refusal check), so what the framework draws and what it is willing to deliver are one definition and a half-formed draw is re-rolled rather than queued-then-refused. `None` after the budget: the caller records that on the run and sends nothing

### penny/tools/micro_context_shape.py

    micro_context_shape.py — the DECLARED output shape of a tagged-line micro-context (#1814): a small line GRAMMAR as frozen Pydantic models (the `validation.conditions` CATALOG pattern — data walked by one dispatcher — not the `Tool.args_model` pattern, because the wire format is tagged lines and a model would need a parser either way). `LineSpec` (tag · `LineRole` · `PayloadSpan` · `LineAnchor` · fields) + `FieldSpec` (name · model-facing `placeholder` · `FieldShape` · required · terminating `Separator`); `render_line` emits the contract-block line so the prompt and the parser are one declaration read twice; `parse_draw` is the single parse → `ParsedDraw` (`singles` by tag + per-item `items`), `None` = contract violation. **`LineRole` is the strict/best-effort axis**: `REQUIRED` (missing or malformed → invalid draw → reroll) · `ALTERNATIVE` (at least one must match — extract's two opening tags) · `OPTIONAL` (singular, malformed reads as absent — the conditionally-required `SKILL:` line) · `PER_ITEM` (repeats; a malformed one is DROPPED), so "absence is never a verdict" (#1770) is a declared property rather than a convention each parser remembered — while what absence MEANS stays the customer's: one that knows the exact set it offered declares COVERAGE as a runtime constraint (`accepts`) and an incomplete draw is a violation like any other (the leaf labeller, #1828), so the grammar stays permissive for the customers that can't check. **Tolerance is declared once**: whitespace-delimited dash variants (the en-dash-for-em-dash draw that made a parameter's semantic name swallow its own description and persisted a 60-character binding key), markdown decoration on the TAG'S OWN LINE (list markers, `**bold**` — never on a multi-line value's later lines, which are the value), and one matched pair of wrapping quotes on a field value. **`FieldShape.NAME` is the plausibility gate**: a name is a token (word characters, spaces, hyphens), not a sentence — the contract block's own "a single lowercase word or snake_case" relaxed to the case+spaces the downstream hardener already fixes, so a "name" carrying its own description is a MALFORMED line rather than a value. Dependency-light leaf (pydantic + `text_validity`).

### penny/tools/skill_tools.py

    skill_tools.py    — The skill substrate's renders beyond the recipe itself (#1804/#1943): `render_skill_brief` (`<name> — <what it's for> (parameters: <parameter> — <what to supply>; …)`, one line, no steps at any step count) is what the surfaces that JUDGE a skill read — the ambient `### Known skills` section and the run-end narration frame; `render_skill_shape` (#1943 — ``` `browse` 3 queries → `collection_write` 4 entries → `browse` → `browse` ```, one skimmable line) is the same steps at SHAPE altitude, read ONLY by the learn-close narration frame beside the brief. Its segment is the step's OWN tool name — in the house's **inline-prose backtick dialect, deliberately with NO parens**, because a call shape here is a call shape the reply reads aloud (#1799) and a parens-less mention reads as "a thing that exists", which is what a step of a RECORD is — plus, per top-level argument holding a LIST of more than one thing, `<n> <argument name>`: the argument's own noun, read as data, so a plugin verb nobody has heard of renders like a built-in one and nothing in the path knows a tool name (a skill is an arbitrary tool sequence). A list of one renders no count (one is what a call ordinarily carries) and a scalar/dict argument is one thing however many fields it has; argument VALUES never render at all; and the counts read the STORED arguments — every later seam (parameter binding, attachment retarget, the render's substitutions) replaces a LEAF and never a list's length, so a routine at rest and the job it becomes have the same shape (pinned). Past `PennyConstants.SKILL_SHAPE_STEPS` (8, a reading budget) it states ` … <n> more steps not shown.` rather than trailing away. Whether the record comes back TRANSLATED rather than recited is the eval contract's own scored check (`memory-learn-close-shape`). Deliberately the same shape as the state classifier's `SkillCandidate.render` (same facts, same words, so the two surfaces can't disagree from different evidence); not single-sourced because `conversation_machine` is a leaf that must not import the database package. The bare `parameters:` line format a job's own render needs too lives in `tools/collection_instantiation.py` (`render_skill_parameters`) — the shared home (#2287), and `render_skill_full` (name · `parameters:` · `steps:`) composes it with `render_skill` for a read of one bare skill. **There is NO `skill_create` tool** — skills are distilled automatically at chat-run end (#1658, `penny/skill_extraction.py`); the model INSTANTIATES one (`collection_configure`), reads one by name with `skill_get` (#2305), and describing a configured job — its steps AND its routine's parameters, required/optional, with the value THAT job bound — is one `memory_get` call on the job (#2287)

### penny/tools/memory_tools.py

    memory_tools.py   — Tool subclasses: each funnels through `db.memory(name)` (the single dispatch) and calls a method on the returned `Memory` object, which refuses wrong-shape ops (collection ops on a log, log_read on a collection) via a base no-op (`WrongShapeError`) and read-only facades via `ReadOnlyMemoryError` — no tool branches on a name or shape. A collection's entries are read by `collection_list` (newest-first), `collection_get` (one entry by its exact key), `collection_keys` (the list of keys) and `collection_sample` (a random pick). A log's entries are read by `log_read` (cursored batch for a collector, recent window for chat — each entry of a real stored log carrying its `id=<n>` beside its timestamp) and `log_get` (one entry in full, by that id; a collection, the two message logs and the run log are each refused with how they are read, naming no tool but `log_read`). `memory_get` is shape-agnostic; `find` (#1558; the `_mine` suffix dropped in #1640 — everything it searches is hers) resolves anything of Penny's own by meaning across the whole registry (collections + logs, archived included) + taught skills (the `skill` table, #1624) + stored entries (`memory_entry` content/key anchors across the non-archived collections + real logs — #1640), plain-cosine, ONE fused best-first list (same embedding space, so entry and object cosines rank directly; each entry scores as the max over its content/key facets), returning each hit's exact identity fused with the deterministic addressing (which tool operates on it) — and for a stored-entry hit the value it holds, so a short fact's find IS the answer. `find` also searches `user-messages`/`penny-messages` (#2289): a message is ranked in the same fused pass, but reported separately from the store hits, under its own heading, and only when it would have ranked in that fused top `FIND_MATCH_LIMIT` — so the conversation can never crowd out a collection, log, skill or entry (`MemoryStore.resolve_messages`). `read_similar` is off the tool surface; `Memory.read_similar` (the store method) stays, read by `notification.py`'s own nearest-message lookup and by `find`'s message candidates alike. A taught-skill hit's addressing leads with `skill_get(skill='<name>')` (#2305) — the one way to read its parameters and steps — then how to set it running and how to change it. The guess-free fallback every not-found error (MemoryNotFoundError) points at. **Ledger read surface (#1580)**: `run_list(source=<'chat' | collector>)` BROWSES a source's recent runs as tool-call sequences (cursored batch); `run_get(run='run <id>')` RESOLVES the single run the self-state header's typed `run <id>` anchor names (a point lookup, same `render_run_calls` projection) — the run-id ↔ target unification that makes the rendered `run <id>` consumable verbatim (n≤1). `run_get` is run-only (send provenance is a render, #1568/#1608; mutations render their detail inline in `memory_get` + name their causing `run <id>` here, so no `mut` arm until a surface renders that anchor). The per-collector-records verb `collector_run_history` retired here — it overlapped `run_list(source)` and its consumer (the quality collector) was retired (#1569); a collector's run history is now reachable via `run_list(source)` + the ambient header + `log_read("collector-runs")`. **Configuring a framed round carries only the TERMS (#1869)**: `CollectionSetTool` takes the round's `RoundFraming` (threaded down like `run_id`, via `build_memory_tools(round_framing=…)` and the `Agent._configuring_round()` template method, which `ChatAgent` overrides to return the framing on an APPLY turn). With one, the call's collection, its `skill` and its `params` are all supplied here — the container the round built, the routine run-end extraction filed it under, and the values that framing carries — so the model's call says only when the job runs, when it stops and whether to tell the user. Reuse becomes structural (the job lands on the round's container every time, and a call naming anything else is retargeted with a note saying so, the `_SAME_JOB_UPDATED` rule) and tier-1 identity holds by construction. With no framing the tool is byte-identical to what it was — the degrade path for a pre-framing world or a failed entry draw. build_memory_tools(db, embedding_client, author) factory

### Browse micro-contexts (#1588 — bulk content never enters the main run context)

- **Browse micro-contexts (#1588 — bulk content never enters the main run context)**: `browse` takes an optional `extract` micro-instruction (`browse(queries, extract="pull out X")`). When set (the collector/script path; chat never sets it, so chat's browse is unchanged), the fetched page content goes into a FRESH single-shot `MicroContext` (`tools/micro_context.py`) — content + instruction, one model call, no tools — and only the small typed result returns to the main loop: the extracted value (byte-identical to the micro-context's return, never re-transcribed by the parent) plus the stored page's log and id (`log='browse-results' id=<id>`, the two arguments `log_get` takes; the clause names no tool, so it is true on a collector's scoped surface too), which is still stored whole in the browse-results log and retrievable by that id (`Memory.entry_by_id`). The micro-context's output contract is enumerated on BOTH sides of the interface (the enumerated-cases doctrine): the prompt names the two tagged forms (`EXTRACTED: <value>` / `NOT_PRESENT: <reason>`) and classification is a deterministic tag parse — a not-present apology can never be promoted to an extracted value; untagged output is re-drawn on the unchanged context for the whole budget, then an honest failure. **Where the boundary between the two tags falls is STATED (#1942)**: an instruction routinely names several things at once and a real page carries some of them, so the prompt says the state the content is in — content carrying SOME of what was asked for is an `EXTRACTED:` read that gives whatever it has for each thing and leaves out the rest, and `NOT_PRESENT:` is for content carrying NONE of it. Unstated, it was decided per draw: one draw over a page holding titles and links but no summaries answered NOT_PRESENT — losing the titles and links with it — while a later draw over the SAME content extracted. The rule is keyed to what the page holds and never to whether the instruction hedged ("summaries when present"), because what a page carries is not a property of how the ask was worded. `browse`'s own `extract` description states the same thing from the caller's side, replacing #1838's warning that an extra detail "makes the read come back empty" — true then, false now. Contract: `tests/eval/extractor/test_browse_extract_fields.py` (all-present control · partly-present on a link index · partly-present on a prose page · none-present honesty guard). Output is also screened by the same degeneracy / leaked-Harmony-envelope detectors as the agent-loop reroll guard (poison discarded + re-drawn on the unchanged context up to `DEGENERATE_REROLL_ATTEMPTS`). The outcome set is closed (`MicroExtractOutcome`: extracted / not-present / extraction-failed / poison-reroll-failed — not-present is a *successful read of an absent fact*, distinct from the extraction-failed escape), never a silent empty. A micro-context is structurally incapable of confabulating a stored value it has never seen. It is a ledger-visible model call — its own `agent_name="browse-extract"` / `prompt_type="browse_micro_context"` (`PennyConstants`) so run traces attribute it (run_target = the browse's author) — but it never inflates the parent run's context. **Per-page extraction in batches (#1682/#1941)**: a multi-query `extract` browse runs ONE micro-context PER successfully-fetched page (never one call over the concatenated pages), each result rendered UNDER that page's own `## browse …:` section header — so a multi-source digest keeps items attributed to their source, and a NOT_PRESENT page renders honestly in its own section without masking another page's extracted value. Each stored page-read carries its OWN `log='browse-results' id=<id>` in the failure/unavailable renders (a search section carries none). Read-failure signals (`## browse error:` sections) stay visible in place; a total-failure browse returns its error sections directly (no micro-context). **A SEARCH section is never extracted from, and a FAILED page extraction hands back the page's links (#2141)**: `_page_section` prepends `Prompt.SEARCH_RESULT_HEADER` to a search's trimmed links — an instruction addressed to the CHAT model telling it to pick a URL — and handing that to the extractor had it obey the instruction meant for the other reader, answering with a bare URL that violates the declared `EXTRACTED:`/`NOT_PRESENT:` shape three times over (one measured sample logged 13 violations; every one of fifteen logged between 1 and 39). So `_extract_batch` plans page reads ALONE and a search comes back verbatim, which is also what the header says it is: titles and links, to be picked from. The other half is the same defect's second door — the page body never enters the conversation, so a failure saying only that it failed left the chat model nothing to open, and it re-searched onto the same page until the pathology gate stopped it. `_links_clause` appends the page's own standalone markdown links (`_LINK_RE`, capped at `MAX_SEARCH_LINKS`) under `Links on the page:` to every failure render — `EXTRACTION_FAILED`, poison, and the no-model degradation — restoring the n≤1 path from a failure to the next call. NOT_PRESENT carries none: the page was read and the fact is absent, which is a finding rather than something to recover from. `success` therefore reads "did anything readable come back" (`_read_anything`), since a search-only extract browse now has no draw to speak for it. N batched pages → N attributed ledger rows. The run trace renders the step as `browse(queries=[…], extract='…')`. **The batch is drawn CONCURRENTLY (#1941)** — one `asyncio.gather` over the page batch, because the per-page contexts are independent by construction (a fresh single-shot context, its own document, its own ledger row, its own poison/reroll budget), so no draw reads anything the draw before it produced and running them one after another spent the whole batch's latency serially (~45-60s for three pages; a measured on-demand cycle spent ~2 minutes across six extracts). **Attribution is unaffected because the batch is PLANNED before it runs**: `_extract_batch` binds each page's render slot AND its own fetch handle in section order up front — the handle iterator is consumed sequentially there, so a search section (readable, never stored) and a read failure (no content section at all) cannot slide a page's handle onto its neighbour — and `_merge_extracted` writes each result back into its own slot, so sections render in page order whatever order the draws finish in. Purely a concurrency change: same calls, same renders, same per-draw reroll machinery (a poison draw re-rolls only ITS context). A draw that RAISES (a transport failure the client surfaces once its retries are spent) still ends the whole call with that error exactly as the sequential loop did — the batch is collected with `return_exceptions=True` and the EARLIEST failing page re-raised (`_drawn_pages`), because `asyncio.gather` does not cancel a raising child's siblings and they would otherwise keep spending the backend, and writing their own ledger rows, against a call that had already failed. The wall-clock win depends on the backend's parallelism (`OLLAMA_NUM_PARALLEL`) — a single-slot backend serializes the draws itself and the batch costs what it always did

### Ambient run/tool-call linkage (#2458 — a one-place change)

- **Every model call links itself to the run and the tool call it happens inside — structurally, not by wiring.** `penny/llm/run_context.py` holds three `contextvars.ContextVar`s (current run id, its parent, and the current tool call id) plus `run_scope(run_id)` / `tool_call_scope(tool_call_id)` context managers; `LlmClient.chat` reads them at log time instead of taking `parent_run_id`/`parent_tool_call_id` as parameters at all. Adding, moving, or removing a `MicroContext` customer is a one-place change: it never has to know, or be told, what encloses it. `run_scope` is opened by the TWO places a run starts — `channels/base.py::_run_message_through_agent` (a chat turn, before the state classifier even draws) and `agents/collector.py::_execute_cycle` (a collector cycle, wrapping the loop AND the notifier that runs after it returns) — plus defensively by `Agent.run`/`Agent.execute`/`ChatAgent.handle` for any direct caller that bypasses those; it collapses to a no-op when the id it is opened with is already ambient, so nesting the SAME id never makes a run its own parent. A micro-context's own draw (`MicroContext._draw_clean`) opens its OWN fresh scope around its one `chat()` call, which is what makes nesting work at any depth: whatever was ambient a moment ago becomes that draw's parent. `tool_call_scope` is opened by the dispatcher (`Agent._execute_single_tool`) around one dispatched call's execution, before the tool's `args_model` even validates — `Tool.run`/`execute` take no id parameter at all any more (`receives_tool_call_id` is gone). `asyncio.gather` wraps each bare coroutine in its own `Task`, which copies the ambient context at creation, so N parallel tool calls (or N parallel page-extraction draws inside one `browse` call) each get an independent snapshot — one call's id never leaks into a sibling's. A call given no explicit `run_id` and no ambient one either (a one-shot with nothing above it — `startup.py`, `commands/profile.py`, `ChatAgent.caption_image`) mints a fresh one at the `chat()` chokepoint rather than logging an unfetchable `run_id=None` row, so a future micro-context that forgets to thread one through stays visible to `run_get`/`get_child_draws` instead of disappearing.

### Tool argument validation (Django-form pattern)

- **Tool argument validation (Django-form pattern)**: every `Tool` declares an `args_model` — the Pydantic model that validates its call arguments — and a base `Tool.run(**kwargs)` constructs/validates it *before* `execute` is ever called (the `ToolExecutor` drives `run`, not `execute`). A `ValidationError` becomes an **actionable error tool response** (`success=False`, naming each bad field with the type+description hint from `parameters` plus any custom-validator message), so `execute` only ever sees valid args and concerns itself with the work + runtime/availability decisions. Validity criteria — required fields, types, and content rules (e.g. `SendMessageArgs`' half-formed-body check, which the notify path now validates through) — live as field/model validators **on the model**, never ad-hoc inside `execute`. Argless tools default to `NoArgs`. Non-existent tools still return a clear tool-not-found error from the executor. This is the single, uniform pre-execute gate; the premature-`done` guard is the one exception that can't be arg-validation (it depends on run state, so it lives in the loop — see *A coherent but WRONG tool call still gets an error tool response*)

### Actionable tool failures

- **Actionable tool failures**: Every tool failure (validation error, rejected/degenerate input, refused operation, missing key, external error) MUST return a `ToolResult` whose message tells the model two things: (1) *what went wrong* — the specific reason, naming the offending field/value — and (2) *how to correct it* — the concrete next action (provide a non-empty value, supply the full replacement text, call the right alternative tool, etc.). The tool result is the model's only feedback channel: a bare "rejected" or a silent no-op gives it nothing to recover from, so it retries the same mistake or gives up. A diagnosis without a remedy is a half-failure. Examples: `check_extraction_prompt` quotes the length and the minimum and points at the prompt shape; `collection_write`'s divergent-value rejection names the reason *and* the exact `collection_write` call that lands the new value. This is a hard rule, enforced in review — see the error-handling section of `docs/pr-review-guide.md`

### Every miss suggests its nearest match — did-you-mean on lookup/write (#1674)

  - **Every miss suggests its nearest match — did-you-mean on lookup/write (#1674)**: wherever a nearest match is *computable* on a failed name or key lookup, the error LEADS with it (`Memory 'aurora-deone' not found — did you mean 'aurora-deck-2'? …` / `Key 'x' not found in 'notes' — did you mean key 'y'? …`) before the existing find/create/list guidance — the render carries the anchor so the fix is a copy, not another lookup (n≤1). Composed at the **tool layer**, not the store (the store stays pure — it can't embed): `MemoryTool.execute` catches `MemoryNotFoundError` and re-renders via `render_memory_not_found(name, suggestion)`, with `MemoryStore.nearest_memory_name(name, embedding=None)` computing the candidate — the **string (typo) leg** (stdlib `difflib` over active names, gated on `PennyConstants.DID_YOU_MEAN_STRING_CUTOFF`, universal since it needs no embedding — this alone catches the motivating typo) plus, for the embedding-capable name-dispatch tools that override `_suggestion_embedding` (`read_similar` / `collection_write` / `log_append` / `collection_update`), the **meaning leg** (description-anchor cosine, gated on the reused `MEMORY_DEDUP_CONTENT_SIM_RELAXED`). Entry-key misses (`collection_remove`) suggest the nearest key in that collection via the same `difflib` string leg (those tools carry no embedding client). No close candidate → the message is **byte-identical to before** (no empty "did you mean" artifact). No new thresholds invented — the one named constant is the string cutoff (no house string-distance number existed); the meaning/key gates reuse the dedup thresholds.

### Write-gate STOP semantics (control flow lives in the tool)

- **Write-gate STOP semantics (control flow lives in the tool)**: `collection_write` classifies every entry at the write chokepoint into a closed `WriteGateOutcome` StrEnum (`penny/constants.py`, beside `RunOutcome` — a cycle-free leaf so `tools/models.py` / `agents/models.py` / `database/memory/types.py` import it without a cycle through `penny.database`) — the **change-gate**, computed deterministically in Python, never a model judgment (#1587, epic #1554 via #1562). The union is derived from what `_write_one` actually does: `NEW_KEY` (key didn't exist → written) · `KEY_EXISTS_CHANGED` (exact key, *different* value → news; the gate **auto-refreshes the stored baseline in place** through the shared update path — same validation/degeneracy-screen/`last_written_by_run_id` stamp — so the model runs no further call, its only remaining job is to notify, #1633) · `KEY_EXISTS_UNCHANGED` (exact key, *identical* value → the watch's "no change" signal) · `DUPLICATE_UNCHANGED` (the dedup disjunction matched a *different* key AND the strict CONTENT signal fired → the stored entry already says what this write says, however either is worded: the SAME no-news, reached by the reworded-key door, #1919) · `DUPLICATE` (a key/near-key collision WITHOUT that strict content hit → the write carries a *different* value for something already stored, which is news) · `DEGENERATE` (rejected content) · `UNEXPECTED` (honest escape label — never emitted today, the write path is total, but wired end-to-end so an unclassified state surfaces for review rather than silently). The exact-key comparison (`_content_unchanged`, whitespace-trimmed equality) replaces an embedding threshold for the same-vs-different decision — *same value → never news, different value → always news* — and demands **single-field discipline** (one value per key; a volatile sibling in the same body trips a false `CHANGED`). The DUPLICATE split is that same question asked where no exact key exists to compare by text, so it is answered by the one signal that can: `sim.is_duplicate` returns a `DuplicateMatch` carrying `same_value` = the strict content signal's own verdict (`penny/database/memory/_similarity.py`). **The divergent-value rejection states the SITUATION, not an option (#1919)**: since the split, every `DUPLICATE` is a collision whose content differs, so `_format_duplicate` says three things flatly — this collection already holds an entry about that under the key `'<matched>'`, any other key collides with that same entry again, and a `collection_write` naming the matched key lands it. The wording it replaced offered a refresh "if you have richer info", which reads as advice to weigh: measured, 4 of 5 samples filed the new value under a fresh key instead. The lead-in is gone too — calling them duplicates is the framing that sent the value somewhere else. **Why the split exists (#1919)**: before it, a cycle that re-observed what it already held under a reworded key got the recoverable rejection — an invitation to refresh or write something else — and every measured sample "recovered" by generating a DIFFERENT entry, which is correct behaviour on that surface. A cycle that found nothing new had no way to say so; the split gives it one, structurally, instead of instructing the model not to invent. **STOP**: outcomes in the declared `WRITE_GATE_STOP_REASONS` table (data — `KEY_EXISTS_UNCHANGED` + `DUPLICATE_UNCHANGED`, the two doors onto "the value was already recorded"; later stages extend the table not the code) end a **must-act (collector) run at the chokepoint**. `DUPLICATE` deliberately stays OUT of it: a divergent-value collision is news about a stored entry, so stopping on it would silence the change it carries — "the release moved to June" arriving under a reworded key must never read as nothing having happened. `collection_write` carries the STOP on `ToolResult.stop` (only for a collector-scoped write — chat gets the same enumerated text but *never* a loop-stop, chat isn't must-act); `_execute_single_tool` threads it onto `ToolCallRecord.stop_reason`; `Collector.should_stop_loop` exits on it (no trailing `done()` required — a `done()` after STOP is an unreached no-op); `_run_cycle` counts it a clean close (cursor commits); and `Collector._cycle_result` stamps `run_reason` = the declared stop reason with `RunOutcome` = `no_work`/`worked` by whether any state changed. **Renders** detect a STOP structurally (`_ended_via_write_gate_stop` — a clean `no_work`/`worked` outcome with no `done()` call, so no new column): `render_run_record` shows `[target] <stop reason>` + the stop-point trace (no ⚠ flag — a clean stop is healthy), and `render_run_calls`'s conclusion reads `stopped: <reason>` instead of `done:`.
