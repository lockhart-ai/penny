# Tools and micro-contexts — reference

Covers the Tool ABC, BrowseTool, every micro-context customer, and the memory tool surface. Read this in full before changing a tool's arguments, a micro-context's output contract, or the write-gate.

- **Write-gate STOP semantics** also ends a collector cycle — see `docs/reference/scheduler-and-collector.md` for how a STOP is read as a clean close.

### penny/tools/base.py

    base.py           — Tool ABC (declares `args_model` + `run()`: validate args via the Pydantic model, then `execute`), ToolRegistry, ToolExecutor (drives `tool.run`). Its tool-not-found did-you-mean goes through `text_validity.suggest_tool_name` (#1944): a name this project RENAMED resolves through the rename table FIRST — a historical fact no character comparison can recover — and only when the replacement is on the surface, so the suggestion always names something callable; everything else falls to the string leg. The measured miss it fixes: a guessed `collection_metadata` (retired by migration 0059) was answered with `collection_set`, the character-nearest name and a different tool entirely, while the one it wanted was `memory_get`

### penny/tools/browse.py

    browse.py         — BrowseTool: web search, result picking, and page reading via browser extension, in ONE call (#2718). `items` — each a search, a link citation, or a URL, each with its OWN `looking_for` (carrying #1570's required-extract rule per item). A URL is read directly; a SEARCH is run, its results ranked by the picker behind the tool boundary (`tools/browse_picker.py`), the top-ranked result read and extracted — falling through while the read finds nothing it was asked for (an honest "the page carries none of it" judged by the picker's yes/no carry question; `EXTRACTION_FAILED` falls through the same way; an unreadable carry answer counts as yes), up to `BROWSE_MAX_PICKED_READS`. The titles-only search result section is gone; the picker's escape (no usable answer) renders the trimmed list. Extract output is capped at `BROWSE_EXTRACT_MAX_CHARS`, the cut naming how much was left out + the fetch handle (§2.9). Every URL the model READS renders as its numbered handle (#2717), queries citing `[n]` resolve through the run's table, and the REAL sections (URLs intact) are what the browse-results log stores and what `source_urls` reads

### Link handles (#2717 — the model never types a URL)

- **Link handles (#2717)**: one `HandleTable` (`tools/link_handles.py`) per run — a chat turn, a collector cycle, or a job-report delivery turn — owned by Python and passed as an explicit parameter (run starter → `get_tools` → tools; run starter → `run` → `LoopContext`), never ambient state. A URL is assigned its number on first sight and keeps it for the whole run, so a handle the model read from one surface is the same number it cites back. Handles are a RENDERING: stored state keeps real URLs (memory entries are expanded back before `collection_write` persists them; the browse-results log stores the un-converted sections), and conversion is applied at each seam where the model READS — browse page sections (header included) and search lists, the page-context injection, past assistant replies in history, memory read renders (`collection_list`, `collection_get`, `log_read`, `find`, the collector's holdings block), and the job-report render. Each seam appends the one plain citation line ("Links are numbered, like [12]…") when it rendered a link that had not been rendered before. At reply finalisation every `[n]` in the answer expands to its URL (the conversation record and the wire carry real links; the browser sidebar and Discord render them as links, Signal as the bare URL), and a citation the table does not hold is rejected before sending — see `docs/reference/validation.md`. A browse query that IS a citation resolves to the page it names; one the table does not hold is refused with the same honest note. Contract: `tests/eval/chat/idle/test_browse_cites_source.py`, `tests/eval/extractor/test_browse_extract_fields.py`


### penny/tools/micro_context.py

    micro_context.py  — MicroContext: single-shot extraction over bulk content (content + instruction, no tools) via the shared model client. **One customer** since #2615 retired the tagged contract and #2656 retired the notify composer: the browse extractor — a fetched page's content plus the `extract` instruction, one draw with thinking off, and the plain text IS the value verbatim (nothing parses it; the page's own address leads the answer, #2648). Every draw is screened by the same poison detectors the agent-loop reroll guard uses (degeneracy / leaked Harmony envelope / empty draw — discarded and re-drawn on the UNCHANGED context up to `DEGENERATE_REROLL_ATTEMPTS`, never appended); a draw cut at its token budget gets ONE more call with thinking forced off. Returns a small typed `MicroContextResult` (`extracted` | `extraction_failed`) — never a silent empty. The tagged-line shape machinery that served the retired customers (`micro_context_shape.py`, `_valid_draw`, `DrawField`) is gone with them (#2615, #2656). It is a ledger-visible model call — its own `agent_name="browse-extract"` / `prompt_type="browse_micro_context"` so run traces attribute it — but it never inflates the parent run's context.

### penny/tools/collection_instantiation.py

    collection_instantiation.py — the pure pieces behind `collection_configure` (#1591): there is no skill to resolve, no parameters to bind, and no rendering seam — a job's `prompt` is the model's own free text, run verbatim. What remains is the **schedule** parse (`parse_schedule` — one `schedule` arg, ONE grammar: an RRULE line with an optional leading `DTSTART:` line, validated by `dateutil`'s `rrulestr`, with `COUNT=` lifted into `max_runs`; a rule's own `UNTIL=` is refused — a schedule says how OFTEN a job runs, never when it stops, so the error names `expires_at` instead) + `render_schedule_clause` (renders the stored rule back VERBATIM — display == invocation) + `parse_expires_at` (ISO first, then `dateparser` in the user's timezone, the zone passed in as a parameter so this module stays DB-free; a far-future sentinel returns `None`) + `expiry_was_normalised` / `sentinel_expiry_note` (the sentinel rule in `docs/reference/scheduler-and-collector.md`'s minimal-collection-surface bullet), the creation echo, the **inert echo** (#1629 — the prompt-less create's honest "storage only, no job yet" confirm-shape), and `render_tombstone_duplicate` (the idempotency-at-birth tombstone confirm-shape, #1567; its active-duplicate REFUSAL sibling is deleted — an active duplicate is updated in place now, #1775). DB-free, whole-render tested; the orchestration (embed, parse, dedup, create) lives on `CollectionCreateTool` in `tools/memory_tools.py`, with duplicate detection one level up on `CollectionSetTool` — the registered front door, and the only place that can answer a duplicate by UPDATING the collection we already have

### penny/tools/memory_tools.py

    memory_tools.py   — Tool subclasses: each funnels through `db.memory(name)` (the single dispatch) and calls a method on the returned `Memory` object, which refuses wrong-shape ops (collection ops on a log, log_read on a collection) via a base no-op (`WrongShapeError`) and read-only facades via `ReadOnlyMemoryError` — no tool branches on a name or shape. A collection's entries are read by `collection_list` (newest-first by default, or `order='random'` for a uniform random sample — folding in the retired `collection_sample` tool, #2812), `collection_get` (one entry by its exact key), and `collection_keys` (the list of keys). A log's entries are read by `log_read` (cursored batch for a collector, recent window for chat — each entry of a real stored log carrying its `id=<n>` beside its timestamp) and `log_get` (one entry in full, by that id; a collection, the two message logs and the run log are each refused with how they are read, naming no tool but `log_read`). `memory_get` is shape-agnostic; for a collection it also shows the entry count and keys (bounded like `collection_list`'s own default cap, content a `collection_list` call away) and gates the "what it does each cycle" prompt framing on whether a schedule runs it — no schedule, and a stored prompt reads labelled unused and clearable instead (#2857). `find` (#1558; the `_mine` suffix dropped in #1640 — everything it searches is hers) resolves anything of Penny's own by meaning across the whole registry (collections + logs, archived included) + stored entries (`memory_entry` content/key anchors across the non-archived collections + real logs — #1640), plain-cosine, ONE fused best-first list (same embedding space, so entry and object cosines rank directly; each entry scores as the max over its content/key facets), returning each hit's exact identity fused with the deterministic addressing (which tool operates on it) — and for a stored-entry hit the value it holds, so a short fact's find IS the answer. `find` also searches `user-messages`/`penny-messages` (#2289): a message is ranked in the same fused pass, but reported separately from the store hits, under its own heading, and only when it would have ranked in that fused top `FIND_MATCH_LIMIT` — so the conversation can never crowd out a collection, log or entry (`MemoryStore.resolve_messages`). `read_similar` is off the tool surface; `Memory.read_similar` (the store method) stays, read by `notification.py`'s own nearest-message lookup and by `find`'s message candidates alike. The guess-free fallback every not-found error (MemoryNotFoundError) points at. **Ledger read surface (#1580)**: `run_list(source=<'chat' | collector>)` BROWSES a source's recent runs as tool-call sequences (cursored batch); `run_get(run='run <id>')` RESOLVES the single run the self-state header's typed `run <id>` anchor names (a point lookup, same `render_run_calls` projection) — the run-id ↔ target unification that makes the rendered `run <id>` consumable verbatim (n≤1). `run_get` is run-only (send provenance is a render, #1568/#1608; mutations render their detail inline in `memory_get` + name their causing `run <id>` here, so no `mut` arm until a surface renders that anchor). The per-collector-records verb `collector_run_history` retired here — it overlapped `run_list(source)` and its consumer (the quality collector) was retired (#1569); a collector's run history is now reachable via `run_list(source)` + the ambient header + `log_read("collector-runs")`. **`CollectionSetTool` is the registered front door for `collection_configure`**: it dispatches by identity — the collection the call names, else the one it duplicates, else a new one — and carries the job's terms straight through: `prompt`, `schedule`, `notify`, `expires_at`. A call naming a collection anything else is retargeted with a note saying so (the `_SAME_JOB_UPDATED` rule). `CollectionUpdateTool` refuses a `prompt` that would land on a collection with no schedule in effect — the row's own or one this same call sets — since nothing would ever run it (#2857); a BLANK `prompt` there instead clears a stored one that was never going to run, while a blank on a collection with a schedule in effect is still refused exactly as the arg gate always refused a blank (`CollectionUpdateTool._clear_prompt` / `_no_schedule_refusal`). `build_memory_tools(db, embedding_client, author)` factory

### Browse micro-contexts (#1588 — bulk content never enters the main run context)

- **Browse micro-contexts (#1588 — bulk content never enters the main run context)**: `browse` takes an optional `extract` micro-instruction (`browse(queries, extract="pull out X")`). When set (the collector/script path; chat never sets it, so chat's browse is unchanged), the fetched page content goes into a FRESH single-shot `MicroContext` (`tools/micro_context.py`) — content + instruction, one model call, no tools — and only the small typed result returns to the main loop: the extracted value (byte-identical to the micro-context's return, never re-transcribed by the parent) plus the stored page's log and id (`log='browse-results' id=<id>`, the two arguments `log_get` takes; the clause names no tool, so it is true on a collector's scoped surface too), which is still stored whole in the browse-results log and retrievable by that id (`Memory.entry_by_id`). The micro-context's output contract is enumerated on BOTH sides of the interface (the enumerated-cases doctrine): the prompt names the two tagged forms (`EXTRACTED: <value>` / `NOT_PRESENT: <reason>`) and classification is a deterministic tag parse — a not-present apology can never be promoted to an extracted value; untagged output is re-drawn on the unchanged context for the whole budget, then an honest failure. **Where the boundary between the two tags falls is STATED (#1942)**: an instruction routinely names several things at once and a real page carries some of them, so the prompt says the state the content is in — content carrying SOME of what was asked for is an `EXTRACTED:` read that gives whatever it has for each thing and leaves out the rest, and `NOT_PRESENT:` is for content carrying NONE of it. Unstated, it was decided per draw: one draw over a page holding titles and links but no summaries answered NOT_PRESENT — losing the titles and links with it — while a later draw over the SAME content extracted. The rule is keyed to what the page holds and never to whether the instruction hedged ("summaries when present"), because what a page carries is not a property of how the ask was worded. `browse`'s own `extract` description states the same thing from the caller's side, replacing #1838's warning that an extra detail "makes the read come back empty" — true then, false now. Contract: `tests/eval/extractor/test_browse_extract_fields.py` (all-present control · partly-present on a link index · partly-present on a prose page · none-present honesty guard). Output is also screened by the same degeneracy / leaked-Harmony-envelope detectors as the agent-loop reroll guard (poison discarded + re-drawn on the unchanged context up to `DEGENERATE_REROLL_ATTEMPTS`). The outcome set is closed (`MicroExtractOutcome`: extracted / not-present / extraction-failed / poison-reroll-failed — not-present is a *successful read of an absent fact*, distinct from the extraction-failed escape), never a silent empty. A micro-context is structurally incapable of confabulating a stored value it has never seen. It is a ledger-visible model call — its own `agent_name="browse-extract"` / `prompt_type="browse_micro_context"` (`PennyConstants`) so run traces attribute it (run_target = the browse's author) — but it never inflates the parent run's context. **Per-page extraction in batches (#1682/#1941)**: a multi-query `extract` browse runs ONE micro-context PER successfully-fetched page (never one call over the concatenated pages), each result rendered UNDER that page's own `## browse …:` section header — so a multi-source digest keeps items attributed to their source, and a NOT_PRESENT page renders honestly in its own section without masking another page's extracted value. Each stored page-read carries its OWN `log='browse-results' id=<id>` in the failure/unavailable renders (a search section carries none). Read-failure signals (`## browse error:` sections) stay visible in place; a total-failure browse returns its error sections directly (no micro-context). **A SEARCH section is never extracted from, and a FAILED page extraction hands back the page's links (#2141)**: `_page_section` prepends `Prompt.SEARCH_RESULT_HEADER` to a search's trimmed links — an instruction addressed to the CHAT model telling it to pick a URL — and handing that to the extractor had it obey the instruction meant for the other reader, answering with a bare URL that violates the declared `EXTRACTED:`/`NOT_PRESENT:` shape three times over (one measured sample logged 13 violations; every one of fifteen logged between 1 and 39). So `_extract_batch` plans page reads ALONE and a search comes back verbatim, which is also what the header says it is: titles and links, to be picked from. The other half is the same defect's second door — the page body never enters the conversation, so a failure saying only that it failed left the chat model nothing to open, and it re-searched onto the same page until the pathology gate stopped it. `_links_clause` appends the page's own standalone markdown links (`_LINK_RE`, capped at `MAX_SEARCH_LINKS`) under `Links on the page:` to every failure render — `EXTRACTION_FAILED`, poison, and the no-model degradation — restoring the n≤1 path from a failure to the next call. NOT_PRESENT carries none: the page was read and the fact is absent, which is a finding rather than something to recover from. `success` therefore reads "did anything readable come back" (`_read_anything`), since a search-only extract browse now has no draw to speak for it. N batched pages → N attributed ledger rows. The run trace renders the step as `browse(queries=[…], extract='…')`. **The batch is drawn CONCURRENTLY (#1941)** — one `asyncio.gather` over the page batch, because the per-page contexts are independent by construction (a fresh single-shot context, its own document, its own ledger row, its own poison/reroll budget), so no draw reads anything the draw before it produced and running them one after another spent the whole batch's latency serially (~45-60s for three pages; a measured on-demand cycle spent ~2 minutes across six extracts). **Attribution is unaffected because the batch is PLANNED before it runs**: `_extract_batch` binds each page's render slot AND its own fetch handle in section order up front — the handle iterator is consumed sequentially there, so a search section (readable, never stored) and a read failure (no content section at all) cannot slide a page's handle onto its neighbour — and `_merge_extracted` writes each result back into its own slot, so sections render in page order whatever order the draws finish in. Purely a concurrency change: same calls, same renders, same per-draw reroll machinery (a poison draw re-rolls only ITS context). A draw that RAISES (a transport failure the client surfaces once its retries are spent) still ends the whole call with that error exactly as the sequential loop did — the batch is collected with `return_exceptions=True` and the EARLIEST failing page re-raised (`_drawn_pages`), because `asyncio.gather` does not cancel a raising child's siblings and they would otherwise keep spending the backend, and writing their own ledger rows, against a call that had already failed. The wall-clock win depends on the backend's parallelism (`OLLAMA_NUM_PARALLEL`) — a single-slot backend serializes the draws itself and the batch costs what it always did

### The collector's close carries the notify choice (#2385)

- **`done(notify=…)` — the close is where the cycle says whether it has news**: `DoneTool` binds `DoneArgs` (`tools/memory_args.py`) with a REQUIRED `notify: bool`, declared in the schema and validated by the uniform pre-execute gate — a close missing it, or carrying a non-boolean, is a failed record the loop rerolls, never a close nobody argued for. The description states the two arms and the honest boundaries: true when the cycle found or stored something the user would want to hear now; false when nothing changed since what they were last told (a quiet cycle is a normal outcome, not a failure); and saying true sends nothing by itself — the close queues a report row and the message is written later by the chat-agent delivery turn the send-queue drainer runs (#2656), and a job with notifications off or a muted user sends nothing either way. The run record is still GENERATED from the ledger, so the close carries nothing else to confabulate. The collector reads the flag off the successful `done` record (`Collector._done_notify`) and the report is queued only on `notify=true` AND the collection's `notify` switch (see `docs/reference/scheduler-and-collector.md`); what the model reads the choice against — what the collection holds and what it last told the user — is rendered on the cycle's own prompt.

### CallLink: every model call takes the run and tool call it belongs to (#2458 — explicit, not ambient)

- **Every model call, and every dispatched tool call, carries its own linkage as an explicit, required value — never ambient state.** The code owner's ruling against the first draft of this (a `contextvars`-backed ambient scope): "I don't want global state that's too timing dependent and indirect. The functions themselves should require the arg and that way when other kittens are modifying things they have to pass it in." `penny/llm/call_link.py`'s `CallLink` is a frozen value with four fields — `run_id` / `parent_run_id` / `parent_tool_call_id` (the LOGGED identity a `promptlog` row stores) and `tool_call_id` (POSITION — which dispatched call this link is presently inside, read only by `child()`, never logged itself). `LlmClient.chat` and `MicroContext.extract` (#2455 naive baseline — the conversation-machine customers `label_skill`/`frame_skill`/`bind_skill`/`classify_state` and the notify composer are gone) all take `call_link: CallLink` as a required keyword argument — no default, so the type checker is the enforcement a kitten adding or moving a `MicroContext` customer can't skip.
  Four constructors: `CallLink.top(run_id)` — a run starter that already minted its own id (the channel, a collector cycle); `CallLink.new_top()` — a one-shot with nothing above it (`commands/profile.py`), minting one itself; `call_link.for_tool_call(tool_call_id)` — built by the tool dispatcher (`Agent._execute_single_tool`) around one dispatched call, same identity, now positioned inside that call; `call_link.child()` — a micro-context's own draw (`MicroContext._draw_clean`), which mints its OWN run id, converts the caller's POSITION into this draw's logged `parent_tool_call_id` (then resets position to `None`), and links back to the caller's run as parent. That position→identity conversion is what keeps nesting correct at any depth: a draw made straight from inside a dispatched tool call links to that call, while a draw made from inside ANOTHER draw (never itself positioned inside a tool call) correctly gets `parent_tool_call_id=None` rather than inheriting the outer draw's own tool call. `Tool.run`/`Tool.execute` take `call_link: CallLink` UNIFORMLY on every tool (not just the ones that draw) — the uniform base signature is what keeps "a new tool that draws can't forget it" true; a declared per-tool opt-in flag (the retired `receives_tool_call_id`) is exactly the forgettable shape this replaces. Concurrency safety is structural, not `Task`-copy-dependent: the dispatcher builds each dispatched call its own `CallLink` object via `for_tool_call`, so N parallel tool calls in one step (`asyncio.gather`) never share anything to leak between them.

### Tool argument validation (Django-form pattern)

- **Tool argument validation (Django-form pattern)**: every `Tool` declares an `args_model` — the Pydantic model that validates its call arguments — and a base `Tool.run(**kwargs)` constructs/validates it *before* `execute` is ever called (the `ToolExecutor` drives `run`, not `execute`). A `ValidationError` becomes an **actionable error tool response** (`success=False`, naming each bad field with the type+description hint from `parameters` plus any custom-validator message), so `execute` only ever sees valid args and concerns itself with the work + runtime/availability decisions. Validity criteria — required fields, types, and content rules (e.g. `SendMessageArgs`' half-formed-body check, which the notify path now validates through) — live as field/model validators **on the model**, never ad-hoc inside `execute`. Argless tools default to `NoArgs`. Non-existent tools still return a clear tool-not-found error from the executor. This is the single, uniform pre-execute gate; the premature-`done` guard is the one exception that can't be arg-validation (it depends on run state, so it lives in the loop — see *A coherent but WRONG tool call still gets an error tool response*)

### Actionable tool failures

- **Actionable tool failures**: Every tool failure (validation error, rejected/degenerate input, refused operation, missing key, external error) MUST return a `ToolResult` whose message tells the model two things: (1) *what went wrong* — the specific reason, naming the offending field/value — and (2) *how to correct it* — the concrete next action (provide a non-empty value, supply the full replacement text, call the right alternative tool, etc.). The tool result is the model's only feedback channel: a bare "rejected" or a silent no-op gives it nothing to recover from, so it retries the same mistake or gives up. A diagnosis without a remedy is a half-failure. Examples: `check_extraction_prompt` quotes the length and the minimum and points at the prompt shape; `collection_write`'s divergent-value rejection names the reason *and* the exact `collection_write` call that lands the new value. This is a hard rule, enforced in review — see the error-handling section of `docs/pr-review-guide.md`

### Every miss suggests its nearest match — did-you-mean on lookup/write (#1674)

  - **Every miss suggests its nearest match — did-you-mean on lookup/write (#1674)**: wherever a nearest match is *computable* on a failed name or key lookup, the error LEADS with it (`Memory 'aurora-deone' not found — did you mean 'aurora-deck-2'? …` / `Key 'x' not found in 'notes' — did you mean key 'y'? …`) before the existing find/create/list guidance — the render carries the anchor so the fix is a copy, not another lookup (n≤1). Composed at the **tool layer**, not the store (the store stays pure — it can't embed): `MemoryTool.execute` catches `MemoryNotFoundError` and re-renders via `render_memory_not_found(name, suggestion)`, with `MemoryStore.nearest_memory_name(name, embedding=None)` computing the candidate — the **string (typo) leg** (stdlib `difflib` over active names, gated on `PennyConstants.DID_YOU_MEAN_STRING_CUTOFF`, universal since it needs no embedding — this alone catches the motivating typo) plus, for the embedding-capable name-dispatch tools that override `_suggestion_embedding` (`read_similar` / `collection_write` / `log_append` / `collection_update`), the **meaning leg** (description-anchor cosine, gated on the reused `MEMORY_DEDUP_CONTENT_SIM_RELAXED`). Entry-key misses (`collection_remove`) suggest the nearest key in that collection via the same `difflib` string leg (those tools carry no embedding client). No close candidate → the message is **byte-identical to before** (no empty "did you mean" artifact). No new thresholds invented — the one named constant is the string cutoff (no house string-distance number existed); the meaning/key gates reuse the dedup thresholds.

### Write-gate STOP semantics (control flow lives in the tool)

- **Write-gate STOP semantics (control flow lives in the tool)**: `collection_write` classifies every entry at the write chokepoint into a closed `WriteGateOutcome` StrEnum (`penny/constants.py`, beside `RunOutcome` — a cycle-free leaf so `tools/models.py` / `agents/models.py` / `database/memory/types.py` import it without a cycle through `penny.database`) — the **change-gate**, computed deterministically in Python, never a model judgment (#1587, epic #1554 via #1562). The union is derived from what `_write_one` actually does: `NEW_KEY` (key didn't exist → written) · `KEY_EXISTS_CHANGED` (the write resolved to an existing entry whose value DIFFERS — the exact key with different content, or a different key the identity ladder matched as the same thing; the gate **auto-refreshes the stored baseline in place** through the shared update path — same validation/degeneracy-screen/`last_written_by_run_id` stamp — so the model runs no further call, its only remaining job is to notify, #1633; the reply shows the PRIOR value verbatim plus the one call that restores it and writes the new value under its own key, so a wrong match is reversible in one call, #2715) · `KEY_EXISTS_UNCHANGED` (exact key, *identical* value → the watch's "no change" signal) · `DUPLICATE_UNCHANGED` (the identity ladder matched a *different* key whose entry already says what this write says — the identical-content rule or a `same_value` decision: the SAME no-news, reached by the reworded-key door, #1919) · `NEW_KEY` covers what `DUPLICATE` used to: the ladder retires the divergent-value rejection — a look-alike pair is merged (`new_value`), written through (`different`), or written through with the honest question (`unsure`/no model), never rejected and never silently overwritten (#2715) · `DEGENERATE` (rejected content) · `UNEXPECTED` (honest escape label — never emitted today, the write path is total, but wired end-to-end so an unclassified state surfaces for review rather than silently). The exact-key comparison (`_content_unchanged`, whitespace-trimmed equality) replaces an embedding threshold for the same-vs-different decision — *same value → never news, different value → always news* — and demands **single-field discipline** (one value per key; a volatile sibling in the same body trips a false `CHANGED`). Where no exact key exists to compare by text, the identity ladder answers instead — rules, shortlist, decision model, honest question (#2715; full description in `docs/reference/database.md`). The #1919 split's motive stands behind the ladder: a cycle that re-observed what it already held under a reworded key used to get a recoverable rejection and every measured sample "recovered" by generating a DIFFERENT entry; the ladder makes the correct outcome structural — the look-alike is MERGED in place, its prior reported reversibly — instead of instructing the model what to do with a rejection. **STOP**: `collection_write` does not stop a cycle on any write-gate outcome any more (#2385's ruling removed the duplicate-write STOP; #2538 then removed the always-empty `WRITE_GATE_STOP_WORTHY_OUTCOMES` membership check it left behind). An unchanged write is a quiet observation: the gate still reports that the value was already held, but the call returns normally so the model reaches its close and records with `done(notify=…)` whether the user should hear about the cycle. A look-alike with a different value is a merge in place, never a rejection, so a change arriving under a reworded key is never silenced either. `WRITE_GATE_STOP_REASONS` (`KEY_EXISTS_UNCHANGED` + `DUPLICATE_UNCHANGED`) stays only to name what a LEGACY row's stop reason means: `_ended_via_write_gate_stop` reads a clean `no_work`/`worked` outcome whose reason is in that table, so a row stamped before #2385 still renders as a stop (`render_run_record` shows `[target] <stop reason>` + the stop-point trace, no ⚠ flag; `render_run_calls`'s conclusion reads `stopped: <reason>` instead of `done:`) — no cycle produces a new one.
