# Agent Task Workflow

The repeatable SOP a **task agent** follows to take **one** GitHub issue from assignment → merged PR → cleanup. One agent owns one ticket, in its own worktree, start to finish. This document is handed to the agent as its operating contract.

The golden rule underneath all of it: **stay in scope, keep the tree isolated, and never publish anything that isn't green and PII-clean.**

---

## 0. Inputs (what you're given)
- **One issue** — its number, scope, and any explicit "out of scope" boundary. Do not expand past it; if you discover adjacent work, note it for a follow-up issue, don't do it here.
- If the issue is `blocked` or `investigation`, **stop** — it needs a design pass, not implementation. Report back instead of coding.
- **Tickets rot — verify against the current code before implementing.** A ticket's file/line references and described structure were true when it was written; `main` may have moved since (a cited function refactored away, a mechanism reverted). Read the referenced code first and target *what exists now*, noting the discrepancy in your PR. If the drift is so large the ticket's premise no longer holds — or you hit a design decision the maintainer hasn't made — stop and report rather than guessing.

## 1. Branch in your own worktree (off clean main)
- Sync the baseline first: `git fetch origin main`. Branch from **`origin/main`**, never a stale local ref or another agent's branch.
- Work only in your **own** worktree. Never touch `main`'s working tree or another agent's worktree.
- Branch name is **descriptive**, not generic: `fix-timezone-local-render`, not `patch-1`.

## 2. Write a task plan file
- Create a short plan file in your worktree scratch area (gitignored / not part of the PR): the ticket link, your intended approach, the exact files you expect to touch, the **test strategy**, the **eval contract** if the change is model-facing, and the scope boundary you're holding.
- This is your working memory — update it as you go. It never lands in the PR.
- **The scratch area is shared across concurrently running agents — take your own subdirectory and name every file uniquely.** Write to `<scratch>/<your-branch>/` and give any helper you author a name carrying your branch or agent id (`plan-<branch>.md`, `poll-<branch>.sh`), never a generic `plan.md` / `poll.sh` a sibling will silently overwrite mid-task. Nothing in scratch is durable storage: it is working memory only, and §9 discards it.

## 3. Implement (to project convention)
- Follow the **Design Principles** in `CLAUDE.md` and the full **`docs/pr-review-guide.md`** rulebook: Pydantic for all structured data, short methods (10–20 lines), no magic strings, the database-stores pattern, FKs over denormalization, datetime columns for ordering, no silent fallbacks, no broad excepts.
- Prefer the **highest rung** that works: change behavior via data/prompt before code where the ticket allows.
- If `main` moves under you, **rebase** on it (`git rebase origin/main`) — resolve conflicts in place; never checkout/reset/branch-switch to escape a rebase.
- Adding a **DB migration**? Pick its number from `origin/main`'s migrations directory **after** your §1 fetch — never from the ticket text or memory (`main` moves; a duplicate prefix collides at merge — this happened: an agent wrote `0080` while a concurrent PR landed `0080` on main). Re-check the number on every rebase; `make migrate-validate` is the tripwire.

## 4. Test — the one and only gate, run ONCE at the end
- **The gate runs ONCE per task, at the end** — after implementation AND the §5 quality-review fixes are all in, immediately before §7. Do NOT gate at intermediate milestones (mid-implementation "checkpoints", pre-quality + post-quality, "just to see") — each run is minutes of Docker, and CI re-verifies every push anyway. If the gate is red, fix and re-run until `EXIT_CODE=0` — the fix loop is the only sanctioned repetition. (Targeted spot-checks while developing — running a single test file via the gate command — are fine; full-gate runs are the thing that happens once.) The sequence for any code change is always *edit → completely done → gate once → fix anything it raises → PR*.
- **A diff with no executable changes (docs/markdown only) runs no local gate at all** — the gate validates Python; there is nothing in a markdown diff for it to check, and CI's required check satisfies branch protection on the PR. Don't run it as ritual.
- Run **exactly**: `make fix check 2>&1 | tee /tmp/check-output-$(git branch --show-current).txt; echo "EXIT_CODE=$pipestatus[1]" >> /tmp/check-output-$(git branch --show-current).txt`
  — the output path is **per-branch** because agents run concurrently: a shared `/tmp/check-output.txt` interleaves `EXIT_CODE` lines from sibling worktrees and makes a green line unattributable.
- **If your isolation guard refuses that command, run the tee alone and re-run plainly for the status.** A worktree-isolated harness reads the `;`-chained `>>` append as a compound redirect it cannot prove stays inside your tree and refuses the whole line. The working split is two plain commands: first `make fix check 2>&1 | tee /tmp/check-output-$(git branch --show-current).txt` (a single pipeline is accepted), then — because a pipeline's exit status is `tee`'s, so no `EXIT_CODE` line gets written — a plain `make fix check` with no pipe and no redirect, whose exit status the harness surfaces directly. Read the tee'd file for `FAILED` / `error[` either way. Never drop the per-branch output file to dodge the guard, and never call a run green on the absence of an error message.
- Then read your branch's output file: check **`EXIT_CODE` first** (must be `0`), then grep for `FAILED` / `error[`.
- **If the run is interrupted** (e.g. `make: *** Error 130` from contention with a concurrent agent's Docker run), the output file is garbage — discard it and re-run the full gate cleanly. Never judge from a partial file.
- Never use `make pytest`, `make check` alone, or `docker compose run` directly.
- **The gate runs in the foreground, in-turn — never background it and end your turn to "wait."** A backgrounded gate is the §8 dead-waiter moved earlier: two agents in one fleet stalled exactly this way — one parked mid-§4 on a gate process that no longer existed, one went silent after committing. Evals are the only sanctioned background run (they have their own detach + record + self-heal rules below); for everything else, if a process you launched is the thing you're waiting on, you stay in-turn until it resolves.
- **Run the gate from *inside your worktree*, never the top-level checkout.** `make`/compose mount `./penny/penny` relative to the compose-file directory, so running `make` from the main repo dir tests *main*, not your branch — a green result there is meaningless. (This is separate from the §7 `make token` gotcha, which is the one thing you run against the main checkout.)
- **Build the image fresh so local tooling matches CI.** A cached local `penny` image can carry stale *pinned* tools (e.g. an old `ty`) and pass while CI's fresh build fails on the pinned version. `make build` before trusting the gate (`--no-cache` if a pin changed recently) so your local `ty`/`ruff` match CI's.
- **All code changes require tests.** Prefer folding assertions into an existing test over a new function; prefer integration tests through public entry points over unit tests.
- **Any textual render that enters the model's context is asserted WHOLE** — one `assert output == """<full literal>"""` per surface (plus whole-render sub-cases), never scattered substring asserts. See the pr-review-guide's *Whole-Render Assertions* section; fixtures deterministic so the literal is exact.
- **Model-facing change?** (prompt / `extraction_prompt` / tool description / what the model reads) → it MUST land with a `tests/eval/` contract, and you must **dry-run it against the live model** (`make eval` / focused case) and read the result *before* committing. Validate each lever as you build it, not batched at the end.
  - **The loop your PR is a round of is `docs/eval-iteration-workflow.md`** — one beat, pairs agreed first, scoped runs, joint reads; read it when your ticket is a round of an eval iteration rather than a standalone change.
  - **Epic-wide eval deferral (the sanctioned exception):** when your dispatch brief explicitly defers eval validation to an end-of-epic sweep, skip the live-model dry-run — but add a **"Model-facing changes"** section to the PR body inventorying exactly what changed in what the model reads, so the sweep has a complete list to validate. The mandate above is the default; the deferral must be explicit in the brief, never inferred.
  - **Two ways to run: `make eval-remote` is yours; `make eval` is the local GPU.** They are not the same machine with different numbers. **`make eval-remote`** drives a hosted provider, does NOT queue, and several agents can run it at once — that is the one to use. **`make eval`** drives the single-tenant local GPU and self-serializes via a first-come-first-served ticket file (`EVAL_QUEUE_DIR`): it runs when its ticket is the oldest live one and the GPU is free, holds the ticket until it finishes, and prints your queue position while waiting. Tickets whose holder died are reaped, so a killed waiter can't wedge the line. Either is safe to run while siblings are active — remote runs are invisible to the queue, and each run gets its own artifact directory and run id — but see the budget below, because "no queue" is not "no limit".
  - **Stay inside your concurrency budget on remote runs.** No queue means nothing stops you taking more than your share. Wall clock depends on the total samples in flight across ALL live agents, not on how they are split, and the machine tops out around **40 in flight** — past that, samples start missing their channel-readiness window and the run gets slower AND dirtier. The default is 8 workers × 5 samples = 40, which is the whole budget for one agent. **When siblings are live, pass `EVAL_WORKERS=2`** (10 in flight), so four agents land at 40 between them. Your supervisor sets the number if it matters; absent an instruction, `EVAL_WORKERS=2` is the safe default. The constraint is CPU for booting Penny instances, not the GPU — local embedding sustains ~65/s against a full suite's ~10/s, so embeddings are not what you are competing for.
  - **A remote run costs real money.** Not much — a scoped run is cents — but it is the user's account, and a full suite is roughly a dollar. That is another reason the scoping rule below is not a formality.
  - **Scope every eval run — NEVER the bare full suite.** This rule SURVIVES the move to remote, with a different reason behind it. It is no longer mainly about wall clock (a remote full suite is ~10 minutes, not ~60): it is that a full suite is the user's money, it is 40 samples in flight for its whole duration — the entire budget, starving every sibling — and it answers a question you were not asked. Your ticket is one beat; the cases that beat touches are the cases you run. Always pass a focused subset: `EVAL_SAMPLES=3 EVAL_PYTEST_ARGS="<your case file> -k <case> -q -m eval -s" make eval-remote` while iterating, and for the final non-regression pass name only the case files your change could plausibly affect. **The full suite is the supervisor's or the user's to run, never yours** — ask, don't take it.
  - **Detach + record: the result log is the source of truth.** Run your eval so it survives you going dormant — a detached/background invocation teeing to a per-branch log (e.g. `/tmp/eval-<branch>.log`). On EVERY wake, **check that log before doing anything else**: the run may have completed while you slept even when no notification arrived. (Measured: three agents once had green eval results sitting in their logs all night while waiting for a wake-up that never came.)
  - **Self-heal on wake.** If your eval process/container no longer exists AND the log has no final summary line, the run died — relaunch it. Never conclude "still waiting" without confirming your waiter process actually exists. Your supervisor heartbeats the fleet (see `CLAUDE.md` → Agent Supervision), but the first line of defense is you checking your own artifacts on every wake.
  - **An eval iteration runs against a LIVE PR from the get-go.** The PR is opened **with (or before) the first run** — you do not iterate locally and publish a finished result; the iteration *happens on the PR*, and every run posts its verbatim report as a **new PR comment**. The comment stream **is** the durable record of the iteration (reports are inspected as GitHub markdown, easier to read than a local file, and the sequence preserves each round's before/after). This extends the "each re-run adds a comment" convention below into the full protocol: PR-first, comment-per-run, never a rewritten body or an overwritten comment.
  - **Capture eval runs as PR content — the harness emits the report.** Set `EVAL_LEVER='<one-line hypothesis>'` on the `make eval` / `make eval-remote` invocation — with a lever declared and no explicit `EVAL_REPORT_DIR`, the target defaults reports to a run-stamped dir under `/penny/eval-artifacts`, the **primary checkout's** `data/eval-artifacts` bind-mounted durably (#1734), so the markdown survives the `--rm` container **and** the worktree being swept post-merge (do NOT point `EVAL_REPORT_DIR` at the worktree's own `./data` — those artifacts die with the tree; an explicit container-absolute path *under `/penny/eval-artifacts`* is still honored). What a case's report contains is `docs/eval-case-design.md` and the renderer it is pinned by; what follows is how it reaches the PR.
  - **Posting is a one-shot, run FROM YOUR OWN WORKTREE: `make eval-report PR=<n> [RUN=<run-dir-name>] [FORCE=1]`** — never a hand-assembled `make assemble` piped into `gh`, which publishes the build log as the comment body (it happened; eight comments had to be deleted, and the recipe now refuses a body opening with build noise). It assembles the run, posts the markdown **verbatim**, and stamps a **`.posted` marker** holding the comment URL into the run dir. `RUN` defaults to the most-recent completed run. It is **idempotent by the marker** — a posted run re-posts only with `FORCE=1` — and it **fails loudly** rather than silently doing nothing when `PR` is unset, the run dir is missing, the token is empty, or the assembled body is empty. **Your worktree is where it must run**: the assembler has to be *your branch's* code, and running it from the primary checkout builds `main`'s assembler against branch-format artifacts and dies on `unrecognized sample block`.
  - **First, make your worktree's `.env` a SYMLINK to the primary checkout's — before the first command in it that mints a token.** A fresh worktree's `.env` is an empty *directory* Docker created as a mount point, so test `[ -L .env ]` (**is it a symlink**), never `[ -e .env ]` — the placeholder passes an existence check and then fails at the point of use. Replacing it links in both halves at once: the `GITHUB_APP_*` config, and `PENNY_PRIMARY_CHECKOUT`, which is what the compose override resolves `data/private:ro` from so the container can read the App key (it lives only in the primary checkout, and a symlink cannot reach it — `./data` is bind-mounted, so an absolute link points at a host path the container has no view of).
  - **Read a `make token` failure as the diagnostic it is.** A missing `GITHUB_APP_*` **key** means the `.env` symlink is absent; a failure on the key **file** means the compose mount is. Its message says to run from the primary checkout — **do not**: that is a symptom of the missing symlink, and following it is how you get `main`'s assembler.
  - **Over GitHub's 64K comment cap the report SPLITS; it is never trimmed.** A real run blows past the cap, so the body is cut on **sample-fold boundaries only**, each part headed `report N of M`, posted in order, with `.posted` holding the first part's URL. Concatenating the parts reproduces the document byte for byte — nothing is dropped or summarised.
  - **The unreviewed-run banner rides `make eval`**: before taking a queue ticket it names every completed run that carries no `.posted`, loudly, in the transcript. It **warns, never blocks** — a deliberate multi-run sweep stays possible; the debt is just undeniable.
  - **Nothing from a run is ever committed.** `manifest.json`, `results.jsonl`, the per-case `<case_id>.md` transcripts, the per-sample `.db` files and the staged comment parts all stay local on the eval host; the durable record is the posted PR comment. Only the generator is committed.
    - **Every tweak + re-run PUSHES the commit and ADDS A NEW COMMENT with the new report — never rewrite the body, never overwrite a prior comment.** The PR **body stays a stable description** (what/why + the current summary table + a pointer to the comments). Each review round — a prompt/scorer/fixture tweak the reviewer asked for — is a commit **plus a new comment** that tells its story: *the feedback → the change (commit SHA) → the result (means) → the transcript*. That preserves the whole review trail (each iteration's before/after) instead of flattening it to the latest state. **When the reviewer's feedback comes over chat, it IS the PR review — mirror each round into a comment.** (Learned the hard way, twice: overwriting the body + PATCHing the same comment erased the iteration history the reviewer explicitly wanted to keep.)
- **penny-client (Swift) change?** → also run `make client-check` from your worktree: it builds the iOS app and runs `PennyClientTests` on a freshly booted simulator via `scripts/client-check.sh`. Requires Xcode — confirm with `xcodebuild -version` first. If Xcode is unavailable on your machine, push and let the `client-check` CI job be the gate, and **say so in the PR** ("Swift side verified by CI only") instead of claiming local verification. A simulator-infrastructure failure (`FBSOpenApplicationServiceErrorDomain` / "failed preflight checks") is a flake, not a code failure — the script's erase+boot hygiene prevents most of it; re-run before diagnosing your code.
- `EXIT_CODE=0` is a hard gate. Do not open a PR on red. For `penny-client/` diffs, a green `make client-check` (or, without Xcode, the green `client-check` CI check) is equally hard.

## 5. Quality review — BEFORE the gate, before you publish
- When implementation is complete, review your **full diff** against the project's canonical checklist *before* running the §4 gate. Invoke the **`/quality`** skill if it's available to you; otherwise read **`docs/pr-review-guide.md`** and self-review the diff against every applicable rule (error handling, forbidden patterns, async patterns, testing discipline, prompt engineering).
- Fix everything it surfaces, **then** run the §4 gate once over the finished diff — quality-before-gate is what makes the single gate run possible (the gate validates the final state, fixes included).
- Don't push a diff you haven't run the checklist over.

## 6. Privacy gate — the repo is PUBLIC
- Before **any** commit or push, run the pre-publish PII checklist: no real user names, topics, dates, collections, handles, channel IDs, or run IDs in code, tests, fixtures, commit messages, or PR text. Genericize to synthetic equivalents.
- This is a hard line — it has been violated before. When in doubt, scrub.

## 7. Commit + open the PR
- `TOK=$(make token)` and **assert it's non-empty** before any `gh`/push — an empty token silently falls back to the wrong identity and creates PRs under the wrong author (immutable; must be closed + recreated). The guard applies to **every** `gh` call, reads included, every time — and an empty token is a **stop**: diagnose it (re-run `make token` without stderr suppression and read the error), then retry until you hold a real one. Never fall through to ambient `gh` auth "just for a read" — the habit is the defect.
- **Worktree gotcha:** a fresh worktree has no `.env` (it's gitignored), and Docker Compose creates a *directory* placeholder in its place — so `make token` fails inside the worktree with `failed to read .env: is a directory`. Two ways out, and which you need depends on whose code has to run. For a plain `gh`/push, mint against the primary checkout: `TOK=$(make -C <path-to-main-checkout> token)` — token generation only reads config and never touches that checkout's tree. For anything whose **code must be your branch's** — `make eval-report` above all — that is the wrong fix, and you make the worktree's `.env` a **symlink** to the primary checkout's instead (§4). Doing the symlink first makes both work from your own tree.
- **Mint inline, immediately before the call it authorizes — never stash a token in a file.** Shell state does not survive between commands, so the mint and the assertion belong on the same line as the `gh`/push they serve (`GH_TOKEN=$(make -C <main-checkout> token) gh …`), one mint per call, re-minted every time. Writing a token to scratch to "reuse it later" fails three ways: installation tokens expire in ~1 hour, the scratch area is shared and not stable storage, and a stale or half-written token file reads as empty — which is precisely the silent ambient-identity fallback the guard exists to prevent.
- **Immediately before pushing: `git fetch origin main` and re-check whether `main` moved** since your branch point or last rebase. Another session can merge at any moment, and any earlier statement about `main`'s position — including your supervisor's — goes stale in minutes; the only valid check is your own, at push time. If it moved and the changes plausibly touch your files, rebase *before* pushing (CI verifies the rebased result — no local re-gate): a PR born CONFLICTING helps no one (this happened — a sibling PR merged in the two-minute window between "main hasn't moved" and the push).
- **Push the branch first** (`GH_TOKEN=$TOK git push -u origin <branch>`), *then* `GH_TOKEN=$TOK gh pr create`.
- **Right after `gh pr create`: read back the PR's real state** — `gh pr view <n> --json mergeable,autoMergeRequest`. If `mergeable` is `CONFLICTING`, fix it *now* (rebase in place, `git push --force-with-lease`, re-flag `--auto`; CI verifies) — never leave a conflicted PR sitting while you report success.
- **Green gate → flagged PR is ONE uninterrupted sequence.** Your deliverable is a PR that exists, is merge-when-ready flagged, and is being shepherded — not a commit. Do not end your turn anywhere between the green §4 gate and the flagged PR (two agents in one fleet stalled exactly in that window: work committed, nothing published, nothing left running to wake them).
- Commit message ends with the `Co-Authored-By:` trailer; PR body ends with the `🤖 Generated with Claude Code` trailer.
- **PR body format — REQUIRED, this exact shape:**

  ```markdown
  Because
  * <the problem, stated as a problem — what was wrong, what it cost, how it showed up>

  This commit
  * <what changed, in terms of behaviour>

  <further detail only if it is genuinely needed>
  ```

  **`Because` is the motivation, not a preamble.** It says what was broken and why anyone should care — the symptom, who or what it hurt, the evidence. A reader who knows nothing about the ticket should finish it understanding why this work exists.

  **`This commit` is what changed, in behaviour.** Not a tour of the diff. "A blank optional string is now refused with a message naming the field" — not "added a validator to `OptionalText` and rewrote two tests". The diff is already on the PR; restating it in prose adds nothing and buries the part only you can supply.

  Then, and only if the reader genuinely needs it: the test evidence (`EXIT_CODE=0`, counts), eval results or the "Model-facing changes" inventory under an epic-wide deferral, anything you judged and want on the record, open questions you resolved conservatively, and `Closes #<issue>`.

  **The failure mode this replaces** (observed across a whole fleet, every PR): bodies that narrate the changes file by file and never state the problem. They read as a changelog written by someone who already knows why — which is exactly the reader who does not need it. If your body could be reconstructed by reading the diff, you have written the wrong thing.

  Keep it short. A small PR deserves two bullets and nothing else; length is not diligence.

## 8. Shepherd the PR to merge (stay alive until MERGED)
You are **not done when the PR opens.** Do not exit — stay alive and shepherd the PR until it is **merged**, so a red CI or a moved `main` never sits unattended (that's exactly how a green PR silently rots).

**Every `gh` below is shorthand for the §7 token-guarded form** — `TOK=$(make -C <main-checkout> token)`, assert non-empty, `GH_TOKEN=$TOK gh …`. And **installation tokens expire (~1 hour)**: a shepherd loop outlives its token, so re-mint `TOK` at the top of each polling cycle rather than reusing the one from §7 — a stale token fails (or worse, falls back to ambient identity) exactly when you're mid-recovery. Loop:
- **Flag for the merge queue immediately after opening:** `gh pr merge <n> --auto` ("merge when ready") — do **not** pass a strategy flag: the merge queue sets the strategy and rejects `--squash` ("merge strategy is set by the merge queue"). The PR then enqueues itself the moment it is approved and green — no one has to click merge. If the queue later kicks it back out (its `merge_group` checks failed against latest `main`), treat that exactly like red CI: diagnose, fix, push. **A force-push clears the merge-when-ready flag** — re-run `gh pr merge <n> --auto` after every rebase push, and verify it took (`gh pr view <n> --json autoMergeRequest`).
- **CI:** poll `gh pr checks <n>`. If red, diagnose from the CI log (`gh run view <id> --log-failed`), fix, and push — **CI is the verifier once the PR exists**; run the local gate again only when the CI log alone can't diagnose the failure (targeted single-test runs are usually the better probe).
- **The merge queue owns serialization — do NOT proactively rebase every time `main` moves.** The queue tests every PR against latest `main` (plus anything queued ahead of it) via `merge_group` checks before merging, so "my branch is behind `main`" is not a problem you need to solve — and a push to an enqueued PR **dequeues it and restarts its checks**, so rebase-thrash actively delays your own merge. Rebase (`git fetch origin main && git rebase origin/main`, `git push --force-with-lease` — CI verifies) only when something is actually wrong: GitHub reports the PR has conflicts, the queue bounced your PR, or a change on `main` broke your branch semantically (e.g. a signature change in code you call).
- **Review:** address every review comment; push (CI verifies).
- **Never destructively escape a rebase;** resolve conflicts in place. Re-verify the PR is still open before each push — if it merged, stop and go to §9.
- When CI is green, the PR has no conflicts, there are no open review threads, and the merge-when-ready flag is set: report "green · queued for merge (awaiting approval)" and **pause** — you'll be resumed on new CI / review / `main` activity. Don't busy-spin; pause between cycles.
- **Pause only on a RESOLVED state — never while a check is pending.** Ending your turn "to wait for CI" on the strength of a background monitor is the classic dead-waiter: unless you have **verified** a live waiter process exists, nothing will ever wake you (four agents in one fleet parked this way on phantom waiters). While any check is pending, poll `gh pr checks` in-turn with short sleeps until it resolves; only the "green · queued for merge" state (or an explicit supervisor-acknowledged block) is a legitimate place to stop.

## 9. Terminal cleanup — the REQUIRED last step of every task
- The **user** approves (code-owner review — no self-approval); the **merge queue** merges. With the merge-when-ready flag set (§8), approval alone carries the PR through the queue to merged with no further action from anyone.
- **Cleanup is not optional and not someone else's job — it is the final step of YOUR task, and your task is not complete until it's done.** The trigger is your PR reaching a **terminal state, either way**:
  - **Merged** → clean up.
  - **Closed without merge** (superseded, deferred, rejected) → clean up all the same. A closed PR's worktree is exactly as dead as a merged one's; this is the case that orphans trees.
- Cleanup runs **in this exact order**, and every step is finished before the last one — because the last one ends your shell:
  1. **Docker images: verify, then skip.** Project-scoped build artifacts left unswept pile up until the disk fills (56 images once took it to 99%) — but `make clean-project-images` is `make kill`'s own recipe, and this repo's worktree builds reuse the shared `penny:latest` tag instead of minting a project-scoped image, so a task agent here normally has **nothing** to reclaim and running the target against a live shared-image deployment would tear down the user's compose project for no gain. So verify rather than assume, from inside your worktree: `docker images --filter reference='<your-compose-project>*'`, `docker ps -a --filter name='<your-compose-project>'`, `docker volume ls --filter name='<your-compose-project>'`. All three empty → **skip the target**, and say so in your report. Run it only when those checks actually show project-scoped artifacts, and **never while a shared-image deployment is live**.
  2. **Delete the local branch(es).**
  3. **Confirm the remote branch is gone** — `git ls-remote origin <branch>`. GitHub auto-deletes a **merged** PR's branch but **not** a **closed-unmerged** one's: on a closed PR the remote branch is still live, so delete it yourself (`GH_TOKEN=$(make -C <main-checkout> token) git push origin --delete <branch>`) and **re-verify with `ls-remote`** rather than assuming the delete took.
  4. **Delete your `worktree-agent-*` placeholder branch** if one exists — ancestor-check it against `origin/main` first, and never touch another agent's branches. This happens **here, before removal**: once the tree is gone you have no shell left to do it from.
  5. **Discard the task plan file and your scratch subdirectory.**
  6. **Remove your worktree — the genuinely last command of the task.** `git worktree remove <absolute-path>`, run from **inside** the tree: the isolation guard refuses `git -C <primary-checkout>` and every other form that reaches into the shared checkout, so the cwd-independent invocation is simply not available to you. Removing the tree your shell stands in **bricks the shell** — the harness refuses all further commands from a session whose isolation tree is gone — so nothing may still be pending when you run it, and anything that is costs a throwaway helper agent to finish (this happened three times in one night before the reorder).
- Keep everything in place until the terminal state; nothing in place after it.
- **The harness placeholder branch** (`worktree-agent-<id>`, created in the primary repo when your worktree was provisioned) is deleted at step 4, while you still have a shell — but the isolation guard may refuse it too, since it lives in the shared checkout. Try once; if blocked, **report it for the supervisor's sweep** and move on (it carries no unique commits, so it's a safe one-command delete from the primary). Don't retry-loop against the guard, and don't let it delay step 6.
- Each pause-cycle while shepherding (§8), re-check the PR's state first — if it went terminal while you slept, run cleanup **now**, report "merged → cleaned up" (or "closed → cleaned up"), and end. Never end your final turn with the worktree still in place.
- If the change warrants it, update `CLAUDE.md` / `README.md` (docs-maintenance rule) — as part of the PR, not after.

## Invariants (true at every step)
1. **One ticket per agent; hold the scope boundary.** Adjacent work → a new issue, not this PR.
2. **Isolated worktree, branched from `origin/main`.** Never main's tree, never another agent's.
3. **`make token` non-empty check** before every GitHub op — reads included; minted inline on the call's own line, never stashed in a file; empty = stop and diagnose, never ambient fallback.
4. **`make fix check` is the only test path; `EXIT_CODE=0` is the gate** — run it **ONCE, at the end** (after quality fixes, before the PR; the fix loop is the only repetition), *from your worktree* on a *freshly built* image, to your branch's own output file, re-run cleanly if interrupted. **Post-PR, CI is the verifier.**
5. **Quality-review the diff** against `docs/pr-review-guide.md` (or `/quality`) before publishing.
6. **PII pre-publish check** before anything leaves the machine.
7. **Model-facing change ⇒ committed `tests/eval/` contract, dry-run first.**
8. **Flag merge-when-ready (`gh pr merge <n> --auto` — no strategy flag; re-flag after every force-push); the merge queue owns serialization** — rebase only on conflicts or a queue bounce, and never destructively escape a rebase.
9. **Stay alive shepherding the PR** — CI green, reviews addressed, queued — until it reaches a **terminal state (merged OR closed)**; then **cleanup is the required last step** — branches (a closed PR's remote branch is still live), plan file, scratch, then the worktree. **`git worktree remove` from inside the tree is the genuinely last command you run**; images are verify-then-skip on a shared-image deployment.
10. **Green gate → flagged PR without stopping; never park on an unverified waiter.** The turn's deliverable is a flagged, shepherded PR — not a commit. Gates run foreground (§4); re-check `main` at push time and `mergeable` right after create (§7); end a turn only on a resolved state.
