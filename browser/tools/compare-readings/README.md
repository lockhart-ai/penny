# Reading comparison harness — evidence for #1942 / PR #1961

> **DO NOT MERGE.** Branch `compare-readings-harness-1961` is throwaway tooling
> built on top of PR #1961's head. It has no PR, it changes no production code,
> and nothing in `tools/compare-readings/` should ever ship in the extension.
> When the question it exists to answer is answered, delete the branch.

PR #1961 reads a page two ways — the article body Defuddle finds, or the page's
own link index — and keeps whichever carries more of the page's words. The
fixtures say that is right. Fixtures are synthetic. This harness asks the same
question of ~20 real, JS-rendered news front pages, in a real browser, and writes
down what happened.

It does not decide anything. It records both readings, the numbers the PR's
arbiter decides on, and enough of each reading's text to check the numbers by
eye.

## Run it

```bash
cd browser && npm install && npm run compare
```

That builds the harness and launches Firefox **on a fresh temporary profile** —
no `--firefox-profile`, so `web-ext` makes a throwaway one and your real profile
is never opened, never modified, and contributes no cookies, consent state or
extensions to the run. Firefox is disposable here; close it when it is done.

Then leave it alone for roughly ten minutes. It opens each site in turn, reads
it, waits ten seconds, reads it again, and moves on. Progress is in the toolbar
badge (`7/21`) and in the Browser Console, which `--browser-console` opens for
you.

At the end it saves **`~/Downloads/compare-results.json`** and also prints the
whole file to the Browser Console, so a missed download is not a lost run.

### Spot-checking one page

`dist/compare/compare-snippet.js` is the same comparator as one self-contained
paste. Open DevTools on any page, paste the whole file into the console, press
enter: the comparison is logged as an expandable object and copied to your
clipboard as JSON. (Firefox makes you type `allow pasting` in the console once
before it will accept pasted input.)

Useful for the case the site list cannot cover: a real article on a real news
site, to check the PR leaves it alone.

## Defuddle version — read this before comparing two result files

This branch pins **`defuddle` to exactly `0.19.3`** (the PR and `main` carry
`^0.14.0`, which a `0.x` caret caps at `0.14.x`). The bump is **harness-scoped
evidence, not a shipping decision** — it is here so the field question can be
asked: does a current Defuddle rescue real front pages on its own, or does the
PR's arbiter still earn its keep on top of it?

Both readings go through Defuddle, so **the version changes both sides** and two
result files on different versions are not comparable. Every run therefore
records `defuddleVersion` (what was installed) and `defuddleRange` (what
`package.json` asked for) in its header, and the paste-in snippet stamps
`defuddleVersion` on its record too.

### Calibration on the fixtures

Measured by `npm test`, on `test/fixtures/`, both versions:

| | 0.14.0 (main/PR) | 0.19.3 (this branch) |
| --- | --- | --- |
| homepage, `production` | 2,026 chars / **22 words** / 1 of 10 headlines | 204 chars / **22 words** / 1 of 10 headlines |
| homepage, `pr` | 3,924 chars / **249 words** / 10 of 10 | 3,924 chars / **249 words** / 10 of 10 |
| homepage, `arbiter.picked` | `index` | `index` |
| article, `production` | 1,485 chars / 265 words | 1,435 chars / 258 words |
| article, `pr` | identical to `production` | identical to `production` |
| article, `arbiter.picked` | `article` | `article` |

**0.19.3 does not rescue the homepage fixture — it fails the other way.** On
0.14 Defuddle returns the whole grid with every headline emptied (2,026 chars of
bare `[](url)`); on 0.19.3 it returns **the lead card alone**, 204 chars, four
characters over the floor. Same 22 words, same one headline of ten, and the
arbiter still picks the index reading by 249 words to 22. Both shapes are the
ones the PR's own module docstring already names.

This is a fixture, not the field — which is the whole reason to run the harness.

### The one expected test failure

`test/page_text.test.mjs > "the article-only reading kept the links and dropped
their text"` fails on this branch, at exactly one assertion:

```js
assert.ok(before.markdown.includes(`](${SITE}${strippedPath})`));
```

That test pins the *0.14* failure shape — links kept, their text stripped — so it
asserts the last headline's URL is still present. Under 0.19.3 Defuddle returns
the lead card alone and the other twenty-four cards are gone entirely, URLs and
all, so the assertion is false. The test's other three assertions still hold
(over the floor, under 30 words, at most one headline kept).

The PR's test file is **untouched on this branch** — editing it would be
falsifying the PR's own evidence to make a tooling branch green. The failure is
the honest report: *this assertion encodes Defuddle 0.14's behaviour.*

## How to read the results

Each record is one page at one moment. Two per page: `pass: 1` five seconds after
load, `pass: 2` ten seconds after that — front pages are not finished when they
say they are, and a consent wall that vanishes between the two passes shows up as
two very different rows.

**The page.** `visibleWords` is the page's own text with script, style and
declared-hidden elements removed. `linkSharePercent` is how much of that is the
text of links to somewhere else. This is the gate: a front page sits at 90%+, an
article page at 10–30%, and `arbiter.isLinkIndex` is just the majority test on
it. If a page is not a link index, the index reading is never built and the PR
cannot change what that page yields.

**The two readings.** `production` is what ships today: naive Defuddle → Turndown
→ 200-char floor. `pr` is what #1961 would ship. Each has `chars`, `words`,
`extracted` and a 500-char `excerpt`. **Compare `words`, not `chars`** — the
defect this PR is about produces *thousands of characters carrying twenty words*,
because what fills them is the URLs of links whose headline Defuddle deleted.

**Headline survival.** `headlineProbes` is up to ten visible link labels of four
words or more, in document order — a structural stand-in for "the page's own
headlines", not a curated list. `headlinesSurvived` is how many of them appear in
each reading. On a front page this is the sharpest single number in the file.

Two things it is not. On an **article** page the probes are whatever long links
the page carries — a "more from this section" rail, usually — and *both* readings
scoring 0 is the correct answer, not a failure: an article reading should not
contain the sidebar. And an index reading's `excerpt` will start with the site's
nav ("World", "Business", "Sport") before it reaches the headlines, because the
reading is every link in document order. That on its own is not nav spam;
`headlinesSurvived` is what tells you whether the headlines are in there too.

**The arbitration.** `arbiter.picked` is which reading won, with both readings'
word counts beside it. `arbiter.mirrorAgreesWithReadPage` must be `true`: it says
the accounting shown landed where the real `readPage` did. **If it is ever
`false`, discard that row's `arbiter` block and both `words` counts** — those
come from the harness's copy of the PR's arbitration, and a `false` here means
the copy has drifted. What survives on such a row is `chars`, `extracted`,
`excerpt` and `headlinesSurvived`, which are measured off text the real code
produced. It should never be `false`; if it is, that is a finding in itself.

**Honesty flags.** `consentWalled` marks a page that was probably showing a
consent wall instead of itself (a CMP iframe, or too few words to be a rendered
page); `consentSignals` says why, and the row is still measured either way — read
the flag, then decide for yourself. `loadTimedOut` means the tab never said
`complete` and was measured as it stood. A page that could not be measured at all
is a row with an `error`, never a missing row.

### What would count as evidence

**For the PR.** On index pages: `picked: "index"`, `pr.words` well above
`production.words`, and `pr.headlinesSurvived` well above
`production.headlinesSurvived` — the page's actual content arriving where it
previously did not. On the article control: every `pr.*` number identical to
`production.*`, `isLinkIndex: false`, `picked: "article"` — untouched.

**Against the PR.** The arbiter picking junk. Concretely: an index reading that
wins but whose `excerpt` is nav spam and section links rather than headlines
("Sport", "Sign in", "Weather" repeated) — `headlinesSurvived` should catch this,
but read the excerpts too. Or the index reading winning on a page that had a real
article — either the control, or any row where `isLinkIndex` is true on something
that plainly is not an index. Or `pr.extracted: false` where `production` read
the page fine. Any of those is a reason not to merge, and the file is the record
either way — a run that comes back against the PR is a successful run.
